## 한 줄로 말하면

API를 만들고 게시하고, 인증·트래픽 제어·모니터링까지 대신 맡아 주는 **완전관리형 API 관문**입니다.

## 핵심 개념

- **API의 정문 역할** — 클라이언트 요청을 받아 뒤쪽의 [[aws-lambda]], [[amazon-ec2]], 다른 AWS 서비스나 HTTP 엔드포인트로 넘깁니다. 백엔드가 무엇이든 클라이언트는 주소 하나만 알면 됩니다.
- **서버리스 애플리케이션의 입구** — API Gateway + Lambda + [[amazon-dynamodb]] 조합이 서버 없이 API를 만드는 대표 구성입니다.
- **인증과 권한 부여** — IAM, Amazon Cognito 사용자 풀, Lambda 오서라이저로 누가 이 API를 호출할 수 있는지 통제합니다.
- **스로틀링과 사용량 계획** — 초당 요청 수를 제한해 백엔드를 보호하고, API 키를 발급해 사용자별 할당량을 둘 수 있습니다.
- **캐싱과 스테이지** — 응답을 캐싱해 백엔드 호출을 줄이고, dev·prod 같은 스테이지로 버전을 나눠 배포할 수 있습니다.
- **완전관리형** — 트래픽이 늘어도 서버를 늘릴 필요가 없고, 호출 로그와 지표는 Amazon CloudWatch로 나갑니다.

## 요금 모델

- **API가 받은 요청 수**가 기본 축입니다. 호출이 없으면 요금도 없습니다.
- 밖으로 나간 **데이터 전송량**이 더해집니다.
- **캐싱을 켜면** 캐시 크기에 따라 **시간당 요금**이 별도로 붙습니다. 요청이 없어도 나가는 요금이니 유의하시기 바랍니다.
- WebSocket API는 주고받은 메시지 수와 연결을 유지한 시간을 기준으로 과금합니다.
- 프리 티어로 매월 일정 건수의 요청을 무료로 처리할 수 있습니다.

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| [[elastic-load-balancing]] | ELB는 트래픽을 여러 인스턴스에 **분산**하는 것이 목적이고, API Gateway는 API를 **정의·인증·제한·버전 관리**하는 것이 목적입니다 |
| [[aws-lambda]] | Lambda는 코드를 실행하는 쪽, API Gateway는 그 코드를 HTTP로 **불러올 수 있게 열어 주는** 쪽입니다 |
| [[amazon-cloudfront]] | CloudFront는 콘텐츠를 엣지에서 캐싱해 전달하고, API Gateway는 API 요청을 받아 백엔드로 라우팅합니다 |
