> VPC → 서비스에 퍼블릭 인터넷을 거치지 않고 프라이빗 연결

## 한 줄로 말하면

내 VPC에서 AWS 서비스나 다른 회사의 서비스에 **퍼블릭 인터넷을 한 번도 거치지 않고** 프라이빗하게 연결하는 기술입니다.

## 핵심 개념

- **푸는 문제** — 프라이빗 서브넷의 인스턴스가 [[amazon-s3]]나 사내 공용 서비스를 부르려고 인터넷 게이트웨이·NAT 게이트웨이를 세워야 하는 상황을 없애 줍니다. 트래픽이 AWS 네트워크 안에만 머무릅니다.
- **VPC 엔드포인트로 구현합니다** — 내 VPC 서브넷 안에 **프라이빗 IP를 가진 엔드포인트**가 생기고, 인스턴스는 그 주소로 서비스를 부릅니다. 서비스가 내 VPC 안에 있는 것처럼 보이게 됩니다.
- **연결 방향은 한쪽입니다** — 소비자(내 VPC)가 제공자(서비스)를 향해 연결합니다. 두 네트워크를 통째로 서로에게 여는 방식이 아니므로 노출 범위가 좁습니다.
- **연결 대상** — AWS의 여러 서비스, AWS Marketplace의 SaaS 파트너 서비스, 그리고 **다른 계정에 있는 내 조직의 서비스**를 붙일 수 있습니다.
- **IP 주소가 겹쳐도 됩니다** — 양쪽 네트워크의 IP 대역이 충돌해도 연결할 수 있다는 점이 VPC 피어링과 갈리는 실무상의 큰 차이입니다.
- **게이트웨이를 따로 세우지 않습니다** — 인터넷 게이트웨이, NAT 게이트웨이, VPN, Direct Connect 없이도 프라이빗 접근이 성립한다는 점을 기억하시기 바랍니다.

## 요금 모델

- **엔드포인트를 가용 영역별로 띄워 둔 시간당 요금**이 붙습니다. 엔드포인트 개수와 AZ 수만큼 곱해집니다.
- 여기에 **엔드포인트를 통과한 데이터 처리량(GB)** 이 더해집니다.
- 프리 티어는 없습니다. 다만 NAT 게이트웨이를 통해 인터넷으로 우회하던 트래픽을 줄여 전체 비용이 내려가는 경우가 많습니다.

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| [[amazon-vpc]] | VPC의 **인터넷 게이트웨이**는 퍼블릭 인터넷으로 나가는 문이고, PrivateLink는 정확히 그 문을 쓰지 않으려고 만드는 **프라이빗 통로**입니다. VPC 피어링은 두 네트워크를 통째로 잇지만, PrivateLink는 **특정 서비스 하나만** 노출합니다 |
| [[aws-site-to-site-vpn]] | VPN은 **네트워크 전체**를 잇는 하이브리드 연결이고, PrivateLink는 VPC 안에서 **서비스에 접근**하는 수단입니다. 서로 대체 관계가 아닙니다 |
| [[aws-direct-connect]] | Direct Connect는 온프레미스와 AWS 사이의 **물리 회선**입니다. PrivateLink는 회선이 아니라 AWS 네트워크 내부의 연결 방식입니다 |
| [[aws-transit-gateway]] | Transit Gateway는 여러 **네트워크**를 모으는 허브이고, PrivateLink는 **서비스 단위**로 프라이빗 접근을 여는 도구입니다 |

## 시험 포인트

- [ ] "**퍼블릭 인터넷을 거치지 않고**", "**비공개로 서비스에 연결**", "**게이트웨이를 설정하지 않고**" → PrivateLink
- [ ] "VPC 안에 있는 것처럼 서비스를 사용한다", "SaaS 파트너 서비스에 프라이빗하게 접근한다"도 같은 신호입니다
- [ ] 함정: PrivateLink는 **대역폭을 늘려 주지 않습니다.** 대역폭·전용 회선 조건은 [[aws-direct-connect]]입니다
- [ ] 함정: 사이트 간 VPN을 대체하지 않습니다. 지문이 "지사와 데이터 센터"를 말하면 [[aws-site-to-site-vpn]]입니다
- [ ] 함정: 인터넷에 서비스를 **공개**하는 도구가 아닙니다. 방향은 언제나 "숨긴다"입니다
