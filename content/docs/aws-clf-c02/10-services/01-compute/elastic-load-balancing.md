## 한 줄로 말하면

들어오는 트래픽을 **여러 대상에 고르게 나눠 주는** AWS 관리형 로드 밸런서입니다.

## 핵심 개념

- **단일 진입점** — 클라이언트는 인스턴스 목록을 알 필요 없이 **ELB 주소 하나만** 알면 됩니다. 인스턴스가 늘고 줄어도 앞단은 바뀌지 않습니다.
- **상태 확인(헬스 체크)** — 대상이 살아 있는지 주기적으로 확인하고, **응답하지 않는 대상에는 트래픽을 보내지 않습니다.** 고가용성이 여기에서 실제로 구현됩니다.
- **리전 서비스이고 여러 AZ에 걸칩니다** — 한 리전 안의 여러 가용 영역에 있는 대상으로 분산하므로, AZ 하나가 죽어도 서비스가 이어집니다.
- **스스로 확장합니다** — 이름의 Elastic이 뜻하는 그대로, 트래픽이 늘면 로드 밸런서 자체가 알아서 커집니다. 미리 용량을 잡아 둘 필요가 없습니다.
- **로드 밸런서 종류** — HTTP·HTTPS를 다루는 **Application Load Balancer**, TCP·UDP를 초고성능으로 다루는 **Network Load Balancer**, 서드 파티 네트워크 어플라이언스를 붙이는 **Gateway Load Balancer**가 있습니다. CLF-C02에서는 앞의 두 가지만 구분하시면 충분하고, ALB는 **경로·호스트 기반 라우팅**과 **WebSocket**을 지원하며 EC2뿐 아니라 [[aws-lambda]] 함수도 대상으로 지정할 수 있다는 점까지 기억해 두시기 바랍니다.
- **느슨한 결합을 만듭니다** — 앞단과 뒷단이 서로 직접 알지 않아도 되므로, 각 계층이 독립적으로 스케일링할 수 있습니다.

## 요금 모델

- **로드 밸런서를 띄워 둔 시간**과 **처리한 트래픽 양**을 기준으로 과금합니다. 트래픽 양은 LCU(로드 밸런서 용량 단위)라는 단위로 계산합니다.
- 트래픽이 늘어 로드 밸런서가 스스로 커지더라도 **추가로 로드 밸런서를 살 필요는 없습니다.** 사용한 만큼만 붙습니다.
- 프리 티어에 매월 일정 시간·일정 용량의 Application/Network Load Balancer 사용량이 포함되어 있습니다.

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| [[amazon-ec2-auto-scaling]] | ELB는 이미 떠 있는 인스턴스에 **트래픽을 나누고**, Auto Scaling은 인스턴스 **대수를 조절합니다.** ELB는 인스턴스를 만들지 않습니다. |
| [[amazon-route-53]] | Route 53은 **DNS 단계**에서 어느 리전·엔드포인트로 보낼지 정하고, ELB는 **한 리전 안에서** 대상들에게 나눕니다. |
| [[amazon-cloudfront]] | CloudFront는 **엣지 로케이션에서 콘텐츠를 캐싱**해 지연 시간을 줄이고, ELB는 캐싱하지 않고 요청을 그대로 분산합니다. |

## 시험 포인트

- [ ] 문제에 **"여러 인스턴스에 워크로드를 고르게 분산"**, **"단일 장애점을 없앤다"**, **"여러 AZ에 트래픽을 나눈다"** 가 나오면 ELB입니다
- [ ] **ELB는 인스턴스를 추가하거나 제거하지 않습니다.** 그렇게 쓴 선택지는 전부 Auto Scaling의 설명입니다
- [ ] Auto Scaling과 ELB를 서로 **바꿔 놓은 선택지**가 한 문제에 두 개씩 들어 있는 경우가 흔합니다
- [ ] **HTTP·HTTPS 기반 웹 트래픽·경로 라우팅** 은 ALB, **극단적으로 낮은 지연 시간과 TCP·UDP** 는 NLB입니다
- [ ] ELB는 **리전 서비스**이고, 고가용성을 얻으려면 **최소 2개 가용 영역**에 걸쳐 구성합니다. "가용 영역 하나에만 존재한다"고 쓴 선택지는 오답입니다
