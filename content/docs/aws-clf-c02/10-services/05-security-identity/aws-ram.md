## 한 줄로 말하면

한 계정에서 만든 리소스를 **복제하지 않고 다른 계정이 그대로 쓰게** 공유해 주는 서비스입니다.

## 핵심 개념

- **푸는 문제** — 계정마다 같은 리소스를 따로 만들면 돈도 관리 부담도 배로 듭니다. RAM은 **하나를 만들어 여럿이 쓰게** 합니다.
- **공유할 수 있는 것들** — [[aws-transit-gateway]], VPC 서브넷, Route 53 Resolver 규칙, License Manager 구성, 용량 예약 등입니다. 네트워크 자원을 공유하는 사례가 대표적입니다.
- **공유 대상** — [[aws-organizations]] 안의 조직 전체·OU·특정 계정에 줄 수도 있고, 조직 밖의 특정 AWS 계정 하나를 지정할 수도 있습니다.
- **리소스 공유(resource share)** — 무엇을, 누구에게 줄지 묶은 단위입니다. 이 묶음을 만들고 초대를 수락하면 공유가 성립합니다.
- **소유권은 바뀌지 않습니다** — 리소스는 계속 원래 계정 소유이고, 그 계정이 요금과 관리 책임을 집니다. 받은 쪽은 사용만 합니다.
- **권한은 여전히 IAM이 통제합니다** — 공유를 받았다고 무엇이든 되는 것이 아니라, 받은 계정 안에서의 접근 권한은 IAM으로 다시 제한합니다.

## 요금 모델

- **AWS RAM 자체에는 요금이 없습니다.** 공유를 만들고 관리하는 데 추가 비용이 붙지 않습니다.
- 공유된 **리소스 본체의 요금**(예: Transit Gateway 연결 시간, 데이터 처리량)은 그대로 발생하며, 원칙적으로 **소유 계정**이 부담합니다.
- 오히려 같은 리소스를 계정마다 중복 생성하지 않게 되어 전체 비용이 내려갑니다.

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| [[aws-organizations]] | Organizations는 계정을 **묶고 정책·청구를 통합**하는 틀이고, RAM은 그 안에서 **리소스 하나하나를 공유**하는 실행 도구입니다 |
| [[aws-iam]] | IAM은 **한 계정 안의 주체**에게 권한을 주고, RAM은 **계정과 계정 사이**에 리소스를 공유합니다 |
| [[aws-transit-gateway]] | Transit Gateway는 공유되는 **대상**의 대표 사례입니다. 여러 계정이 하나의 허브를 쓰게 만들 때 RAM을 씁니다 |
| [[aws-service-catalog]] | Service Catalog는 승인된 **제품(템플릿)을 배포하게** 해 주고, RAM은 이미 존재하는 **실제 리소스를 함께 쓰게** 합니다 |

## 시험 포인트

- [ ] "**계정 간에 리소스를 공유**", "**중복 생성 없이 여러 계정이 함께 사용**" → AWS RAM
- [ ] "여러 계정이 하나의 Transit Gateway나 서브넷을 공유한다"는 전형적인 RAM 지문입니다
- [ ] 함정: 계정을 **만들고 묶고 청구를 합치는** 쪽은 [[aws-organizations]]입니다
- [ ] 공유해도 **소유권과 요금 부담은 원래 계정**에 남는다는 점이 선택지로 나옵니다
