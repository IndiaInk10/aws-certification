## 한 줄로 말하면

서버를 하나도 관리하지 않으면서 어떤 규모에서도 **밀리초 단위 응답**을 내는 키-값 NoSQL 데이터베이스입니다.

## 핵심 개념

- **키-값 NoSQL** — 테이블 · 항목(item) · 속성(attribute)으로 이루어지고, 각 항목은 **기본 키**로 찾습니다. 관계형처럼 테이블끼리 조인하는 방식이 아닙니다.
- **스키마가 유연합니다** — 항목마다 속성 구성이 달라도 됩니다. 미리 열을 고정할 필요가 없어, 요구사항이 자주 바뀌는 애플리케이션에 잘 맞습니다.
- **서버리스** — 프로비저닝하거나 패치할 서버가 없습니다. 테이블만 만들면 되고, 트래픽에 맞춰 자동으로 확장·축소됩니다.
- **일관된 속도** — 데이터가 얼마나 커지든 **한 자릿수 밀리초** 응답을 유지합니다. DynamoDB Accelerator(DAX) 캐시를 붙이면 마이크로초 단위까지 내려갑니다.
- **가용성** — 데이터를 리전 안 여러 가용 영역에 자동으로 복제합니다. **글로벌 테이블**을 쓰면 여러 리전에 **active-active**로 복제되어 어느 리전에서나 읽고 쓸 수 있습니다.
- **못 하는 것** — 복잡한 조인이나 SQL 집계 쿼리는 지원하지 않습니다. 이 지점이 관계형 데이터베이스와 갈리는 곳입니다.

## 요금 모델

- **읽기·쓰기 요청 수**와 **저장 용량(GB-월)** 이 과금 기준입니다.
- 용량 모드가 두 가지입니다. **온디맨드**는 실제 요청한 만큼만 내고, **프로비저닝됨**은 초당 처리 용량을 미리 잡아 두고 그만큼 냅니다. 트래픽이 예측 가능하면 프로비저닝 쪽이 저렴합니다.
- 백업, 글로벌 테이블 복제, DAX 캐시 노드는 별도 요금입니다.
- **관리할 서버가 없으므로 인스턴스 시간 요금이 없습니다.** 안 쓰면 요청 요금도 붙지 않습니다.
- 프리 티어로 일정량의 저장 용량과 요청을 **매월 계속** 무료로 쓸 수 있습니다.

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| [[amazon-rds]] | RDS는 스키마·SQL·조인이 있는 관계형, DynamoDB는 키로 찾는 NoSQL입니다. "유연한 스키마"·"키-값"이 보이면 DynamoDB입니다 |
| [[amazon-documentdb]] | 둘 다 NoSQL이지만 DynamoDB는 키-값, DocumentDB는 **MongoDB 호환 문서** 데이터베이스입니다 |
| [[amazon-elasticache]] | ElastiCache는 앞단에 두는 **휘발성 캐시**이고, DynamoDB는 데이터를 영구 보관하는 데이터베이스입니다 |
| [[amazon-s3]] | S3는 파일·객체를 통째로 저장하고, DynamoDB는 항목과 속성 단위로 읽고 씁니다 |

## 시험 포인트

- [ ] "**키-값**", "**NoSQL**", "**유연한 스키마**", "**한 자릿수 밀리초 응답**", "**서버 관리 없이 무제한 확장**" → DynamoDB
- [ ] 지문이 **마이크로초**를 요구하면 DynamoDB 자체가 아니라 **DAX 캐시를 붙이는** 쪽이 답입니다. 반대로 **여러 리전으로 넓히라**는 요구는 **글로벌 테이블**이고, DAX는 성능용이라 리전 확장과는 무관합니다
- [ ] "**서버리스 데이터베이스**"라는 표현이 나오면 DynamoDB를 먼저 떠올리시면 됩니다
- [ ] 게임 리더보드, 장바구니, 세션 상태, IoT 센서 데이터 같은 사례가 나오면 DynamoDB인 경우가 많습니다
- [ ] 함정: 복잡한 **조인**이나 SQL 리포팅이 필요하면 DynamoDB가 아닙니다. RDS 또는 Redshift 쪽입니다
- [ ] 함정: "확장하려면 샤딩을 직접 구성해야 한다"류 선택지는 DynamoDB의 자동 확장과 정반대이므로 오답입니다
