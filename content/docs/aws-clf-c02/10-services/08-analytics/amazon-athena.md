# Amazon Athena

> S3의 데이터에 바로 SQL 질의. 서버 불필요

## 한 줄로 말하면

S3에 쌓아 둔 데이터를 옮기지도, 서버를 띄우지도 않고 **표준 SQL로 그 자리에서 조회**하는 서비스입니다.

## 핵심 개념

- **서버리스** — 클러스터도 인스턴스도 프로비저닝하지 않습니다. 콘솔에서 쿼리를 쓰면 바로 결과가 나옵니다. 관리할 인프라가 아예 없습니다.
- **조회 대상은 Amazon S3** — 데이터를 데이터베이스로 적재(load)하지 않습니다. **S3에 있는 파일을 그대로** 읽습니다. CSV, JSON, Parquet 같은 형식을 지원합니다.
- **표준 SQL** — 새 쿼리 언어를 익히실 필요가 없습니다. 평소 쓰던 SQL 문법을 그대로 사용하시면 됩니다.
- **스키마는 읽을 때 씌웁니다** — 테이블 정의(어떤 컬럼이 있는지)는 보통 [[aws-glue]] 데이터 카탈로그에 두고, Athena가 그것을 참조해 S3 파일을 해석합니다.
- **애드혹 분석에 맞습니다** — 서버 로그, CloudTrail 감사 로그, 청구 리포트처럼 **가끔 필요할 때 한 번씩 뒤져 보는** 용도에 적합합니다.
- **분석용이지 트랜잭션용이 아닙니다** — 조회를 위한 서비스이므로 애플리케이션의 운영 데이터베이스로 쓰지 않습니다.

## 요금 모델

- **쿼리가 스캔한 데이터량**을 기준으로 과금합니다. 실행 시간도, 서버 대수도 아닙니다.
- 쿼리를 실행하지 않으면 Athena 요금은 발생하지 않습니다. 다만 원본이 놓인 **S3 스토리지 요금은 별도로** 내셔야 합니다.
- 스캔량이 곧 비용이므로, 데이터를 **압축하고 열 기반 형식(Parquet 등)으로 바꾸고 파티션을 나누면** 스캔량이 줄어 비용도 함께 줄어듭니다. 이 절감 방법이 문제로 나옵니다.

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| [[amazon-redshift]] | Redshift는 데이터를 **미리 적재해 두는 데이터 웨어하우스**이고, Athena는 **S3에 그대로 둔 채** 조회합니다. "대규모 데이터를 상시 고성능으로 분석"이면 Redshift, "가끔 S3를 SQL로 훑어본다"면 Athena입니다 |
| [[aws-glue]] | Glue는 데이터를 **옮기고 변환하는 ETL**이고, Athena는 **질의**합니다. Glue가 만든 카탈로그를 Athena가 읽는 관계입니다 |
| [[amazon-emr]] | EMR은 Hadoop·Spark **클러스터를 띄워** 대규모 처리를 돌립니다. Athena는 클러스터가 없습니다 |
| [[amazon-quicksight]] | QuickSight는 결과를 **차트와 대시보드로 보여 줍니다.** Athena는 쿼리 결과를 표로 돌려줄 뿐입니다 |

## 시험 포인트

- [ ] 문제에 **"S3에 있는 데이터를 SQL로", "서버리스", "인프라 관리 없이 즉시 쿼리"** 가 나오면 Athena입니다
- [ ] **"데이터를 이동하지 않고"** 라는 표현이 Athena를 가리키는 강한 신호입니다
- [ ] 과금 기준은 **스캔한 데이터량**입니다. "실행 시간당", "인스턴스 시간당"이라고 쓴 선택지는 오답입니다
- [ ] Athena 비용을 줄이는 방법을 물으면 **압축·열 기반 형식·파티셔닝**으로 스캔량을 줄이는 쪽입니다
- [ ] 데이터 웨어하우스를 요구하는 문제(대량 데이터의 정기적인 복합 분석)에는 Athena가 아니라 Redshift를 고르셔야 합니다
