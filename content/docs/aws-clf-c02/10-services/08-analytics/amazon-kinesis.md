## 한 줄로 말하면

끊임없이 흘러 들어오는 데이터를 **쌓이기를 기다리지 않고 들어오는 즉시** 받아서 처리하는 서비스입니다.

## 핵심 개념

- **실시간 스트리밍이 핵심입니다** — IoT 센서 값, 클릭스트림, 애플리케이션 로그, 동영상처럼 **끝없이 이어지는 데이터**를 다룹니다. 배치 분석이 "쌓인 것을 나중에 본다"면, Kinesis는 "들어오는 것을 지금 본다"입니다.
- **몇 초 안에 반응합니다** — 이상 탐지, 실시간 대시보드, 실시간 추천처럼 **늦으면 의미가 없는** 작업에 씁니다.
- **Data Streams** — 스트림 데이터를 받아 두면 여러 소비자 애플리케이션이 각자 읽어 갑니다. 처리 로직을 직접 짜는 쪽입니다.
- **Data Firehose** — 받은 스트림을 S3, Redshift 같은 **목적지로 자동 전달**합니다. 코드를 거의 짜지 않고 적재만 하고 싶을 때 씁니다.
- **Video Streams** — 기기에서 들어오는 동영상 스트림을 받아 저장하고 분석에 넘깁니다.
- **확장 방식이 두 가지입니다** — **온디맨드 모드**는 유입량에 맞춰 알아서 늘고 줄지만, **프로비저닝 모드**는 샤드 수를 직접 정해 두어야 합니다. Data Firehose는 별도 설정 없이 자동으로 확장됩니다.

## 요금 모델

- **처리한 데이터량과 확보한 처리 용량**을 기준으로 과금합니다. 스트림에 들어온 데이터의 양, 그리고 얼마나 큰 처리 용량을 열어 두었는지가 기준입니다.
- 데이터를 일정 기간 보관하도록 늘리면 **보존 기간에 대한 요금**이 추가됩니다.
- 스트림을 만들어 두기만 하고 데이터를 흘리지 않아도 확보된 용량에는 요금이 발생하므로, 쓰지 않는 스트림은 정리하시는 편이 좋습니다.

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| [[amazon-sqs]] | SQS는 메시지를 **하나씩 꺼내 처리하고 지우는 대기열**이고, Kinesis는 **연속된 스트림**을 여러 소비자가 동시에 읽습니다. "실시간 스트리밍 분석"이면 Kinesis입니다 |
| [[aws-glue]] | Glue는 쌓인 데이터를 **배치로** 가공하고, Kinesis는 흘러 들어오는 데이터를 **실시간으로** 받습니다 |
| [[amazon-athena]] | Athena는 이미 S3에 저장된 데이터를 **나중에** 조회합니다. "지금 이 순간의 데이터"가 필요하면 Kinesis입니다 |

## 시험 포인트

- [ ] 문제에 **"실시간", "스트리밍", "즉시 분석", "IoT 센서 데이터", "클릭스트림"** 이 나오면 Kinesis입니다
- [ ] **"몇 초 이내에 처리해야 한다"** 는 조건도 Kinesis를 가리킵니다
- [ ] 반대로 **"나중에 분석", "배치", "쌓아 둔 데이터"** 는 Kinesis가 아닙니다
- [ ] 스트림을 그대로 S3나 Redshift에 넣기만 하면 되는 상황이면 Data Firehose 쪽입니다
