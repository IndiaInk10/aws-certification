> 도메인 2 · 복원력을 갖춘 아키텍처 설계 **26%** · 과제 명세 **2개**뿐 → 과제당 **≈13%**

## 1. 왜 필요한가

> 도메인 2 는 과제가 둘뿐이라 **한 노트가 시험의 13%** 를 감당합니다. 밀도가 가장 높은 구간입니다.

"느슨한 결합" 은 말이 추상적이지만 시험에서는 아주 구체적인 한 가지를 뜻합니다.
**A 가 B 를 직접 부르지 않게 만드는 것.** 사이에 큐나 주제를 넣으면
B 가 죽어도 A 는 계속 돌고, B 가 느려도 요청이 쌓일 뿐 사라지지 않습니다.

문항은 대개 이렇게 옵니다. *"주문이 몰릴 때 처리 서버가 감당을 못 하고 요청이 유실됩니다."*
답은 거의 항상 **사이에 SQS 를 넣는 것**입니다.

## 2. 이번에 새로 나오는 서비스

| 서비스 | 한 줄 | 이 과제에서 맡는 역할 |
|---|---|---|
| [[amazon-sqs\|Amazon SQS]] | 큐. 꺼내 갈 때까지 남는다 | 이 과제의 중심. 완충과 유실 방지 |

## 3. 이 과제가 묻는 것

> [!tip] 도메인 2 전체를 묶는 말 — 복원력
> AWS 는 이 도메인을 **복원력**으로 묶습니다. Well-Architected Framework 의 정의로는,
> 워크로드가 **부하·공격·구성 요소 장애로 스트레스를 받을 때 복구할 수 있는 능력**입니다.
> 고가용성 · 내결함성 · 재해 복구 · 탄력성 · 확장성이 전부 이 우산 아래에 있고,
> **서로 독립된 주제가 아니라는 점**을 AWS 가 먼저 못 박습니다. 한 문항이 두세 개를 동시에 묻습니다.

### L1. 확장한다는 것 — 크기를 바꿀 수 있는 능력

> **이번 강의에서 다룰 내용** — 확장성과 탄력성이 각각 무엇을 가리키는 말인지, 그리고 한 대를 키우는 쪽과 대수를 늘리는 쪽이 왜 다른 결과를 내는지 살펴보겠습니다.

#### 확장성은 "지금 빠른가"가 아니라 "바꿀 수 있는가"입니다

빠른 시스템과 확장 가능한 시스템은 다른 말입니다.
확장성은 지금의 속도가 아니라 **부하가 늘거나 줄었을 때 시스템의 크기를 따라 바꿀 수 있는가**를 가리킵니다.
하루 만 건을 처리하던 구조가 백만 건에서도 그대로 통한다면 확장 가능한 것이고,
지금은 충분히 빠르지만 부하가 늘었을 때 손댈 자리가 없다면 확장 가능하지 않은 것입니다.

그래서 시험의 확장성 문항은 대개 "지금 느립니다"가 아니라 **"앞으로 늘어납니다"** 라는 조건을 깔아 둡니다.
지문이 미래의 트래픽 · 사용자 수 · 데이터 증가량을 흘려 두었다면 그것이 답을 가르는 조건입니다.

| 용어 | 뜻 |
|---|---|
| **크기 조정(확장성)** | 시스템에 걸리는 부하가 늘거나 줄 때 시스템의 크기를 바꿀 수 있는 능력입니다 |
| **수직 크기 조정** | 한 대를 더 크게 만듭니다. 대개 **중단**이 필요하고 언젠가 천장에 닿습니다 |
| **수평 크기 조정** | 대수를 늘립니다. 천장이 없고 무상태가 전제입니다 |
| **탄력성** | **수평 크기 조정 + 자동화**입니다. 수요에 맞춰 자동으로 늘리고 줄입니다 |

#### 한 대를 키우는 쪽과 대수를 늘리는 쪽

**수직 크기 조정**은 서버 한 대에 CPU 와 메모리를 더 얹는 방식입니다.
애플리케이션을 고칠 것이 없어 손이 가장 적게 갑니다. 대신 두 가지가 따라옵니다.
크기를 바꾸려면 대개 **한 번 멈춰야 하고**, 물리 서버가 낼 수 있는 최대 크기라는 **천장**이 있습니다.
그리고 아무리 키워도 그 한 대가 죽으면 전부 멈춘다는 사실은 그대로 남습니다.

**수평 크기 조정**은 같은 일을 하는 서버를 여러 대 두는 방식입니다.
천장이 없고, 한 대가 죽어도 나머지가 남습니다. SAA 가 거의 항상 이쪽을 원하는 이유입니다.
대신 조건이 하나 붙습니다 — **요청이 어느 대로 가도 같은 결과가 나와야 합니다.**
그 조건을 만드는 일이 `L5` 에서 다룰 스테이트리스입니다.

#### 탄력성은 거기에 자동화를 더한 것입니다

수평 확장이 "늘릴 수 있다"라면, 탄력성은 **"알아서 늘고 줄어든다"** 입니다.
사람이 콘솔을 열어 대수를 바꾸는 것은 확장이긴 해도 탄력적이지는 않습니다.
자동으로 **줄어드는** 쪽까지 있어야 탄력성이고, 비용이 여기서 갈립니다.

수요는 선형인 경우가 드물고 오르내립니다. 그래서 AWS 는 시작 구성과 자동 크기 조정으로
**수요가 늘면 리소스를 더하고, 줄면 서버를 줄이거나 아예 없애는** 방식을 기본으로 둡니다.
클라우드의 이점을 한 줄로 하면 **용량을 추측하지 않아도 된다**는 것이고,
이것이 비용 최적화 · 성능 효율성 · 운영 우수성으로 한꺼번에 이어집니다.

> [!warning] AWS Auto Scaling 과 EC2 Auto Scaling 은 다릅니다
> **EC2 Auto Scaling** 은 EC2 인스턴스의 대수만 다룹니다.
> **AWS Auto Scaling** 은 그 위에서 여러 서비스(ECS 작업 · DynamoDB 처리량 · Aurora 복제본 등)를
> 한 계획으로 함께 조정합니다. 두 이름을 가르는 문항이 나옵니다.

#### Auto Scaling 정책 네 가지

늘리고 줄이는 **판단 기준**을 어디에 두느냐로 갈립니다.

| | 언제 |
|---|---|
| **대상 추적** | `CPU 를 50% 로 유지`. 가장 단순하고 가장 자주 정답 |
| **단순 · 단계 조정** | 경보 하나에 몇 대를 더할지 직접 정할 때 |
| **예약** | `매주 금요일 오후에 트래픽이 는다` 처럼 **시간을 아는** 경우 |
| **예측** | 과거 패턴으로 미리 늘려 둔다 |

`시간을 아는가 모르는가` 가 예약과 나머지를 가르고, `과거 패턴이 있는가` 가 예측을 가릅니다.
아무 단서가 없으면 대상 추적이 기본값입니다.

### L2. 느슨한 결합 — 서로를 모르게 만드는 일

> **이번 강의에서 다룰 내용** — 결합이 느슨하다는 말이 실제로 무엇을 줄이는 것인지, 그리고 동기 호출과 비동기 메시지가 장애 앞에서 어떻게 갈리는지 살펴보겠습니다.

#### 결합이란 한쪽이 다른 쪽에 대해 아는 양입니다

A 가 B 를 직접 부르려면 A 는 B 에 대해 여러 가지를 알아야 합니다.
B 의 주소, B 가 지금 살아 있다는 것, B 가 정해진 시간 안에 답한다는 것, B 가 자기 요청을 받아 줄 만큼 한가하다는 것입니다.
이 **아는 것이 많을수록 결합이 강합니다.** 그리고 아는 것이 많다는 말은 그중 하나만 어긋나도 A 가 함께 무너진다는 말입니다.

강하게 결합된 구조에서 장애는 한 곳에서 끝나지 않습니다.
B 가 죽으면 A 의 호출이 실패하고, B 가 **느려지기만 해도** A 는 응답을 기다리며 묶입니다.
묶인 요청이 쌓이면 A 도 새 요청을 받지 못합니다. 뒤쪽의 문제가 **앞쪽으로 번지는** 것입니다.

느슨하게 결합한다는 것은 이 아는 것을 줄이는 일입니다.
사이에 큐나 주제를 하나 두면 A 가 아는 것은 **"메시지를 어디에 두면 되는가"** 하나로 줄어듭니다.
B 가 몇 대인지 · 지금 살아 있는지 · 얼마나 빠른지는 더 이상 A 가 알 필요가 없습니다.

AWS 가 말하는 **분리**의 정의도 같은 이야기입니다 — "구성 요소가 더 큰 시스템의 일부로 일하면서도
자율적으로 남고, **서로를 인식하지 못하는** 상태"입니다.

#### 동기와 비동기 — 기다리느냐 아니냐

**동기 호출**은 부르는 쪽이 **답이 올 때까지 기다립니다.**
응답을 그 자리에서 써야 하는 일에는 이 방식이 맞습니다. 대신 상대의 실패와 지연이 그대로 내 실패와 지연이 됩니다.

**비동기 메시지**는 부르는 쪽이 **메시지를 맡기고 곧바로 자기 일로 돌아갑니다.**
결과는 나중에 다른 경로로 받습니다. 상대가 멈춰 있어도 **맡기는 일 자체는 성공합니다.**
사용자에게는 "접수되었습니다"가 즉시 돌아가고, 실제 처리는 뒤에서 이어집니다.

AWS 는 분리 기법을 **두 가지로 나누어** 구별하라고 요구합니다.

| | 뜻 | 예 | 한쪽이 죽으면 |
|---|---|---|---|
| **동기식 분리** | 두 구성 요소가 **동시에 살아 있어야** 동작합니다 | ELB 뒤에 여러 AZ 의 인스턴스 | 그 순간의 요청은 실패합니다 |
| **비동기식 분리** | 한쪽이 멈춰도 통신이 이어질 **장치**가 있습니다 | 인스턴스 사이에 SQS 큐 | 메시지가 남아 있다가 나중에 처리됩니다 |

동기식 예에서 인스턴스끼리는 서로를 모르고 의존하지도 않지만, **각 AZ 에 최소 한 대는 살아 있어야** 합니다.
그래서 ELB 로 나누는 것도 분리이긴 하되, 장애를 통째로 흡수하지는 못합니다.

웹 애플리케이션은 보통 백엔드를 **동기식 API** 로 부릅니다.
그런데 프런트엔드가 백엔드 처리보다 훨씬 빠르거나 **오래 도는 작업**이 섞이면 이 구조가 무너집니다.
이때 SQS 나 DynamoDB 같은 **내구성 있는 메시지 저장소**를 끼워 요청 접수와 실제 처리를 떼어 놓으면,
사용자 경험이 좋아지는 동시에 **두 계층을 서로 다른 속도로 확장**할 수 있게 됩니다.

#### 끊는 자리는 정해져 있습니다

```d2
direction: right

web: "웹 계층\nALB + ASG"
q: "SQS 큐"
worker: "처리 계층\nASG (큐 길이로 확장)"
db: "데이터베이스"

users: 사용자
users -> web
web -> q: "요청을 넣기만"
q -> worker: "꺼내서 처리"
worker -> db
```

웹 계층이 처리 계층을 **직접 부르지 않는** 것이 핵심입니다.
처리 서버가 전부 죽어도 요청은 큐에 남아 있고, 살아나면 이어서 처리합니다.

#### 서비스 지향 · 마이크로서비스 아키텍처를 전제로 묻습니다

- **서비스 지향 아키텍처(SOA)** — 소프트웨어 구성 요소를 **서비스 인터페이스**로 재사용 가능하게 만드는 방식입니다
- **마이크로서비스** — 거기서 더 나아가 구성 요소를 **더 작고 단순하게** 쪼갭니다. 통신은 잘 정의된 **API** 로 합니다
- 패턴은 **API 기반 · 이벤트 중심 · 데이터 스트리밍** 등 여러 가지이고, 요구사항에 따라 더 맞는 것이 있습니다

여기서 놓치면 안 되는 전제가 하나 있습니다. **분산 시스템은 네트워크 위에 있습니다.**
네트워크에서는 **데이터 유실과 시간 초과가 일어나며**, 워크로드는 그런 상황에서도 안정적으로 동작해야 합니다.
또 한 구성 요소가 **다른 구성 요소에 나쁜 영향을 주지 않는 방식**으로 동작해야 합니다.
재시도 · 시간 초과 · 큐가 정답이 되는 이유가 여기 있습니다.

### L3. 큐 — 속도의 차이를 흡수합니다

> **이번 강의에서 다룰 내용** — 큐가 실제로 무엇을 대신 들고 있는지, 그리고 큐를 붙인 다음에는 무엇을 보고 확장해야 하는지 살펴보겠습니다.

#### 큐가 흡수하는 것은 요청이 아니라 속도 차이입니다

큐를 "요청을 저장해 두는 곳"으로만 이해하면 절반만 잡은 것입니다.
큐가 실제로 흡수하는 것은 **만들어지는 속도와 처리되는 속도의 차이**입니다.

주문이 초당 1000건 들어오는데 처리 서버가 초당 600건밖에 소화하지 못한다고 해 보겠습니다.
직접 호출하는 구조에서는 남는 400건이 갈 곳이 없어 그대로 실패합니다.
사이에 큐가 있으면 그 400건은 큐에 쌓이고, 몰리는 시간이 지나 생산이 초당 200건으로 떨어지면
남는 처리 능력으로 밀린 것을 마저 처리합니다. **시간을 옮겨 담는 것**이 큐가 하는 일입니다.

여기서 두 가지가 따라 나옵니다.

- **큐가 처리량을 늘려 주지는 않습니다.** 생산 속도가 소비 속도를 **계속** 웃돌면 큐는 무한정 길어질 뿐입니다.
  큐가 사 주는 것은 **일시적인 급증을 견딜 시간**이지 평균 처리 능력이 아닙니다
- **큐의 길이가 곧 밀린 양입니다.** 그래서 큐 기반 워커를 확장할 때 보는 지표는 CPU 가 아니라
  **큐에 쌓인 메시지 수**입니다. CPU 는 워커가 놀고 있을 때도 낮게 나오지만,
  큐 길이는 지금 얼마나 뒤처져 있는지를 그대로 보여 줍니다

그리고 큐를 끼우면 양끝을 **서로 다른 속도로 확장**할 수 있게 됩니다.
접수하는 쪽은 얇게, 처리하는 쪽은 두껍게 두는 구성이 그때부터 가능해집니다.

#### SQS 를 쓸 때 같이 나오는 것

- **가시성 제한 시간** — 꺼낸 메시지를 다른 소비자가 못 보게 하는 시간. **처리 시간보다 길게**
- **DLQ** — 몇 번 실패하면 따로 빼 둔다. `실패한 메시지를 조사` 가 나오면 이것
- **FIFO 큐** — 순서 보장과 중복 제거. 대신 처리량 제한이 있다
- **롱 폴링** — 빈 응답을 줄여 비용과 지연을 낮춘다

SQS 자체는 아주 높은 처리량을 낼 수 있습니다. 다만 그 처리량을 실제로 쓰려면
**생산자와 소비자를 수평으로 늘려야** 합니다. 큐를 넣었는데도 느리다는 지문이면 큐가 아니라 양끝을 봅니다.

---

### L4. 주제와 이벤트 — 큐와는 다른 문제를 풉니다

> **이번 강의에서 다룰 내용** — SQS · SNS · EventBridge · Step Functions 가 각각 어떤 문제를 맡는지, 그리고 큐와 주제를 가르는 한 가지 차이를 살펴보겠습니다.

#### 하나가 가져가느냐, 전원이 받느냐

큐(SQS)와 주제(SNS)는 둘 다 "사이에 끼워 넣는 것"이라 비슷해 보이지만 푸는 문제가 정반대입니다.

**큐는 일감을 나누어 주는 곳**입니다. 메시지 하나는 소비자 **한 명**이 가져가고,
가져간 동안에는 다른 소비자에게 보이지 않습니다. 그래서 워커를 열 대로 늘리면 일이 열 갈래로 나뉩니다.
목적은 **작업 분배와 완충**입니다.

**주제는 소식을 알리는 곳**입니다. 메시지 하나가 구독자 **전원**에게 각각 복사되어 갑니다.
주문 하나에 결제 · 재고 · 알림 세 시스템이 각자 반응해야 한다면 이쪽입니다.
목적은 **같은 사건을 여러 곳에 퍼뜨리는 것**, 곧 팬아웃입니다.

방향도 반대입니다. 큐는 소비자가 **가지러 오고**, 주제는 **밀어 보냅니다.**

| | 메시지 하나를 | 방향 | 받을 쪽이 멈춰 있으면 |
|---|---|---|---|
| **SQS 큐** | 소비자 **하나**가 가져갑니다 | 소비자가 가지러 옵니다 | 꺼내 갈 때까지 **남아 있습니다** |
| **SNS 주제** | 구독자 **전원**에게 갑니다 | 주제가 밀어 보냅니다 | 재시도 후에는 그대로 **놓칩니다** |

이 마지막 칸이 두 서비스를 함께 쓰는 이유입니다.
나중에 처리해도 되는 구독자가 있다면 **주제 뒤에 큐를 붙입니다.**
`SNS → SQS 여러 개` 조합이 팬아웃 문항의 단골 정답인 까닭이 여기에 있습니다.

#### 규칙으로 나누는 이벤트 버스와, 순서를 맡는 상태 기계

**EventBridge** 는 이벤트를 받아 **규칙에 맞는 대상에게만** 보냅니다.
SNS 가 "이 주제를 구독한 전원"이라는 **명단**으로 나눈다면, EventBridge 는 **이벤트의 내용**으로 나눕니다.
AWS 서비스 자체가 내는 이벤트와 서드파티 SaaS 이벤트를 받는 자리이고, 일정에 맞춰 무언가를 실행하는 자리이기도 합니다.

**Step Functions** 는 성격이 다릅니다.
큐와 주제가 "누구에게 전달할 것인가"를 푼다면, Step Functions 는
**여러 단계를 어떤 순서로 밟고 실패하면 어떻게 할 것인가**를 풉니다.
재시도와 분기를 애플리케이션 코드 밖으로 빼내 **상태 기계**로 그려 두는 방식입니다.

| | 푸는 문제 | 지문의 신호 |
|---|---|---|
| [[amazon-sqs\|SQS]] | 속도 차이 흡수 · 작업 분배 | `요청이 유실` · `급증` · 워커를 늘린다 |
| [[amazon-sns\|SNS]] | 하나의 사건을 여러 곳에 | `여러 시스템이 같은 이벤트를 각자` |
| [[amazon-eventbridge\|EventBridge]] | 내용 · 일정에 따른 라우팅 | `서드파티 SaaS` · `일정에 맞춰` · `패턴에 맞으면` |
| [[aws-step-functions\|Step Functions]] | 순서 · 재시도 · 분기 | `여러 단계를 순서대로` · `실패하면 재시도` |

---

### L5. 상태를 어디에 두느냐가 확장을 가릅니다

> **이번 강의에서 다룰 내용** — 스테이트리스라는 말이 무엇을 걷어 내라는 뜻인지, 그리고 끝내 없앨 수 없는 상태를 어디로 옮기는지 살펴보겠습니다.

#### 대수를 늘려도 소용이 없는 구조

수평 확장은 **요청이 어느 대로 가도 같은 결과가 나온다**를 전제로 합니다.
그런데 서버가 **자기 안에만** 무언가를 들고 있으면 이 전제가 그 자리에서 깨집니다.

로그인 세션을 1번 서버의 메모리에 두었다고 해 보겠습니다.
같은 사용자의 다음 요청이 2번 서버로 가면 2번은 그 사용자를 모릅니다. 사용자는 다시 로그인해야 합니다.
업로드한 파일을 서버의 디스크에 두었다면, 그 파일을 내려받는 요청이 다른 대로 갈 때 파일이 없습니다.
대수를 늘려도 **늘린 만큼 쓰이지 않거나 아예 동작하지 않습니다.**

**스테이트리스**하게 만든다는 것은 서버에서 이 "자기만 아는 것"을 걷어 내는 일입니다.
서버를 언제 죽여도 되고 언제 새로 띄워도 되는 상태로 만드는 것이고,
그래야 Auto Scaling 이 마음대로 늘리고 줄일 수 있습니다.
**확장성과 복구 가능성이 같은 조건에서 나온다**는 점을 여기서 잡고 가시기 바랍니다.

| 인스턴스 안에 두면 안 되는 것 | 어디로 옮기나 |
|---|---|
| 로그인 세션 | [[amazon-elasticache\|ElastiCache]] · [[amazon-dynamodb\|DynamoDB]] |
| 업로드 파일 · 공유 작업 디렉터리 | [[amazon-s3\|S3]] · [[amazon-efs\|EFS]] · [[amazon-fsx\|FSx]] |
| 반복 조회 결과 | ElastiCache · **DAX** |
| 로그 | [[amazon-cloudwatch\|CloudWatch Logs]] 처럼 인스턴스 밖으로 |

> [!warning] "확장 가능" 의 반대말은 상태입니다
> 인스턴스 안에 세션·파일·캐시를 들고 있으면 대수를 늘려도 소용이 없습니다.
> `수평 확장이 안 된다` 는 지문이 보이면 **무상태로 만드는 답**을 찾으세요 —
> 세션은 ElastiCache 나 DynamoDB 로, 파일은 EFS 나 S3 로.
>
> 상태를 **끝내 없앨 수 없는** 경우도 있습니다. 디스크에 쓰는 레거시 애플리케이션이나
> 스테이트풀 컨테이너가 그렇습니다. 이때는 [[amazon-efs\|EFS]] · [[amazon-fsx\|FSx]] 처럼
> **공유 스토리지를 밖에 두고 여러 대가 함께 마운트**하는 쪽이 답이 됩니다.
> 컨테이너 수명 주기와 분리된 볼륨을 붙이는 방식이라, ECS 와 EFS 를 함께 쓰는 구성이 자주 나옵니다.
> **스티키 세션**은 최후의 수단입니다. ALB 는 기본적으로 요청마다 대상을 독립적으로 고르고,
> 스티키 세션을 켜야 사용자의 세션이 특정 대상에 묶입니다 — 그만큼 확장의 자유를 잃습니다.

### L6. 무엇 위에서 돌릴 것인가 — 서버리스로 가는 조건

> **이번 강의에서 다룰 내용** — `운영 오버헤드가 가장 적은` 이라는 조건이 무엇을 고르라는 뜻인지, 그리고 서버리스가 답이 되지 않는 자리를 살펴보겠습니다.

#### 운영 부담은 사라지지 않고 누가 지느냐만 바뀝니다

패치 · 용량 계획 · 장애 대응은 어느 구조에서도 누군가는 해야 하는 일입니다.
서버리스가 파는 것은 그 일이 없어진다는 약속이 아니라, **그 일을 AWS 쪽 경계 안으로 옮겨 준다**는 약속입니다.
그래서 지문이 `운영 오버헤드 최소` 를 조건으로 걸면, 그것은 **관리 경계를 더 위로 올린 서비스를 고르라**는 뜻이 됩니다.
대신 경계를 올릴수록 우리가 통제할 수 있는 폭은 좁아집니다. 이 맞바꿈이 아래 표의 세 줄입니다.

| | 한계 |
|---|---|
| **Lambda** | 최대 실행 15분. 오래 도는 작업은 안 된다 |
| **Fargate** | 컨테이너는 그대로 쓰되 서버만 없앤다. 장시간 작업 가능 |
| **EC2 + ASG** | 커널·에이전트까지 통제해야 할 때만 |

#### 서버리스의 정의 네 가지

AWS 는 **서버리스의 정의**를 네 가지로 못 박습니다. 보기를 지울 때 이 네 가지를 기준으로 쓰시기 바랍니다.

1. 프로비저닝하거나 **관리할 인프라가 없다**
2. **소비 단위**에 따라 자동으로 크기가 조정된다
3. **종량제** 요금이다
4. **가용성과 내결함성이 내장**되어 있다

그래서 `이미 고가용성이 내장된 서비스인데 다중 AZ 를 따로 구성한다`는 보기는 대개 오답입니다.
API Gateway 는 자동으로 크기가 조정되고 많은 사용 사례에서 관리가 필요 없으며,
Lambda 는 서버 없이 코드를 실행하되 **동시성** 단위로 확장합니다.
`Lambda 의 크기를 어떻게 조정하는가`는 대수가 아니라 **동시성과 트랜잭션**을 묻는 질문입니다.

반대 방향도 있습니다. **고성능 컴퓨팅(HPC)** 처럼 성능을 끝까지 짜내야 하면 EC2 로 돌아옵니다.
이때는 **인스턴스 유형 · 배치 그룹 · 고급 네트워킹 옵션**이 답을 가릅니다.

#### 파일 전송을 직접 호스팅하지 않는 답

`SFTP·FTPS 로 파일을 받아야 하는데 서버를 세우고 패치하고 가동 시간을 감시하고 싶지 않다`
— 이 지문의 답이 [[aws-transfer-family\|AWS Transfer Family]] 입니다.
사용자 프로비저닝과 활동 감사까지 관리형으로 가져갑니다.

시험이 붙잡는 숫자는 하나입니다. **최대 3개의 가용 영역**을 지원하고,
연결과 전송 요청에 대해 **자동으로 크기가 조정되는 중복 플릿**이 뒤를 받칩니다.

> [!tip] AWS 가 이 과제에서 "깊이 알라"고 이름을 댄 서비스
> **API Gateway · Transfer Family · SQS · Secrets Manager · Application Load Balancer ·
> Fargate · Lambda · ECS · EKS.**
> 이 목록에 컨테이너 서비스 둘([[amazon-ecs\|ECS]] · [[amazon-eks\|EKS]])과
> [[aws-secrets-manager\|Secrets Manager]] 가 들어 있다는 점이 눈에 띕니다.
> 확장성 문항에도 자격 증명을 코드 밖으로 빼는 보기가 섞여 나온다는 뜻입니다.

### L7. 데이터 계층과 엣지도 확장 대상입니다

> **이번 강의에서 다룰 내용** — 웹 계층을 아무리 늘려도 남는 병목이 어디인지, 그리고 읽기를 줄이는 수단들이 어떻게 갈리는지 살펴보겠습니다.

#### 늘린 서버가 전부 한 곳으로 모입니다

웹 서버를 열 대로 늘려도 그 열 대의 요청은 결국 **같은 데이터베이스 하나**로 모입니다.
확장 문항이 컴퓨팅에서 끝나지 않는 이유가 이것입니다. 병목은 늘린 계층이 아니라 **그 뒤**로 옮겨 갑니다.

그런데 데이터 계층은 컴퓨팅처럼 대수만 늘려서 해결되지 않습니다.
서버는 복제해도 서로 같은 값을 들고 있을 필요가 없지만, **데이터는 복제하는 순간 어느 쪽이 맞는지**가 문제가 되기 때문입니다.
그래서 손대는 순서가 정해져 있습니다.

1. **애초에 데이터베이스까지 가지 않게 합니다** — 엣지 캐시와 인메모리 캐시
2. **읽기를 나눕니다** — 읽기 전용 복제본
3. **그 규모를 전제로 만들어진 데이터베이스로 옮깁니다** — 목적별 데이터베이스

쓰기를 나누는 일은 이 셋 중 어느 것으로도 풀리지 않습니다.
`쓰기가 한계` 라는 지문이 DynamoDB 나 샤딩 쪽으로 흐르는 이유가 여기에 있습니다.

#### 데이터베이스를 고르는 것도 확장성 문제입니다

예전에는 거의 모든 데이터를 관계형 데이터베이스에 넣었습니다.
그런데 **극단적인 규모에서는 관계형이 벽에 부딪힙니다.** 그래서 AWS 는 **목적별 데이터베이스**를 고르라고 합니다.

| | 언제 |
|---|---|
| [[amazon-dynamodb\|DynamoDB]] | **극단적 규모 + 한 자릿수 밀리초** 지연이 필요한 NoSQL |
| [[amazon-rds\|RDS]] | 관리형 관계형 데이터베이스가 필요할 때 |
| [[amazon-aurora\|Aurora]] | **클라우드 네이티브** 관계형. 더 큰 처리량과 복제가 필요할 때 |
| [[amazon-redshift\|Redshift]] | **데이터 웨어하우스** — 분석·집계 질의 |

#### 읽기를 확장하는 순서 — 복제본과 캐시는 다른 도구입니다

`읽기가 느리다` 의 첫 답은 **읽기 전용 복제본**입니다. 성능과 가용성이라는 이점이 둘 다 있습니다.
반면 **RDS 다중 AZ 는 읽기를 확장하지 않습니다.** 대기 인스턴스에는 **직접 접근할 수 없고**,
추가 성능을 주지 않으며 오직 고가용성만 담당합니다.

여기서 한 걸음 더 들어간 지점을 AWS 가 강조합니다.
**읽기 전용 복제본은 캐시를 대신하지 못합니다.** 복제본에 던지는 쿼리에도
**연결 생성 · 인증 · SQL 구문 분석과 최적화 · 잠금** 같은 오버헤드가 그대로 붙기 때문입니다.
같은 결과를 반복해서 읽는 부하라면 복제본을 더 붙일 것이 아니라 **캐시로 걷어내야** 합니다.

| 캐싱 선택지 | 무엇을 덜어내나 |
|---|---|
| [[amazon-cloudfront\|CloudFront]] | 정적·동적 콘텐츠를 **엣지**에서 돌려준다. 원본에 아예 닿지 않게 한다 |
| [[amazon-elasticache\|ElastiCache]] | 애플리케이션과 DB 사이의 인메모리 캐시. **세션 저장소**로도 쓴다 |
| **DynamoDB Accelerator(DAX)** | DynamoDB 전용 인메모리 캐시. 밀리초를 **마이크로초**로 |

**RDS 프록시** 도 이 자리에 같이 나옵니다. 애플리케이션이 데이터베이스와 맺은 연결을
**풀링하고 공유**하게 만들어, 연결 수 때문에 확장이 막히는 상황을 풉니다.
서버리스처럼 연결을 빠르게 열고 닫는 워크로드에서 특히 답이 됩니다.

#### 엣지에서 끝내는 방법

AWS 는 **엣지 네트워킹**을 확장성과 복원력의 도구로 함께 묶습니다.

| | 하는 일 |
|---|---|
| [[amazon-cloudfront\|CloudFront]] | 콘텐츠를 사용자 가까이에서 캐시해 원본 부하와 지연을 함께 줄인다 |
| [[amazon-route-53\|Route 53]] | DNS 단계에서 어디로 보낼지 정한다 (지연 시간 기반 · 지리 위치 · 장애 조치) |
| [[aws-global-accelerator\|Global Accelerator]] | **고정 IP** 로 받아 AWS 백본으로 태운다. TCP/UDP 를 포함한 비 HTTP 트래픽도 |

세 서비스 모두 **데이터를 암호화하고, 네트워크 홉을 줄이며, 애플리케이션 접근을 통제**하는 쪽으로
설명됩니다. `전 세계 사용자` · `지연 시간` 이 지문에 있으면 이 셋 중 하나를 먼저 보시기 바랍니다.

## 4. 시험에서 갈리는 지점

| 지문에 이게 있으면 | 이쪽 |
|---|---|
| `트래픽이 몰리면 요청이 유실` | **SQS** 를 사이에 |
| `여러 시스템이 같은 이벤트를 각자 처리` | **SNS → SQS 여러 개** (팬아웃) |
| `순서대로 정확히 한 번` | **SQS FIFO** |
| `일정에 맞춰 실행` · `서드파티 SaaS 이벤트` | **EventBridge** |
| `여러 단계를 순서대로, 실패하면 재시도` | **Step Functions** |
| `실행 시간이 15분을 넘는다` | Lambda 가 **아니다** → Fargate·EC2 |
| `운영 오버헤드 최소` + 컨테이너 | **Fargate** |
| `금요일 오후마다 트래픽 급증` | **예약 조정** |
| `큐가 밀릴 때 처리 서버를 늘린다` | 큐 **길이** 기반 대상 추적 |
| `세션 때문에 같은 서버로 가야` | 스티키 세션보다 **세션을 밖으로**(ElastiCache·DynamoDB)가 정답인 경우가 많다 |
| `한 대를 더 크게 키웠는데 또 한계` | **수평 확장**으로 방향을 바꾼다. 수직은 천장이 있다 |
| `여러 서비스의 확장을 한 계획으로` | **AWS Auto Scaling** (EC2 Auto Scaling 이 아니다) |
| `같은 쿼리가 반복되어 DB 가 버겁다` | **캐시**. 복제본을 더 붙이는 보기는 오버헤드가 그대로 남는다 |
| `DynamoDB 읽기를 마이크로초 단위로` | **DAX** |
| `연결 수 때문에 DB 가 한계` · `Lambda 가 연결을 소진` | **RDS 프록시** |
| `SFTP 로 받되 서버는 관리하지 않는다` | **Transfer Family** |
| `비 HTTP(TCP/UDP) 를 고정 IP 로, 지연 시간 최소` | **Global Accelerator** (CloudFront 가 아니다) |
| `큐를 넣었는데도 처리가 밀린다` | 생산자·**소비자를 수평으로** 늘린다 |
| `분석·집계 질의가 느리다` | **Redshift**. 관계형 DB 를 키우는 보기는 방향이 다르다 |

## 6. 셀프 체크

- [ ] SQS 를 넣으면 무엇이 좋아지는지 두 가지를 댄다
- [ ] SQS 와 SNS 를 각각 언제 쓰는지 한 문장으로 가른다
- [ ] Lambda 를 못 쓰는 상황을 하나 든다
- [ ] 큐 기반 워커를 확장할 때 어떤 지표를 봐야 하는지 안다
- [ ] 무상태로 만든다는 말이 구체적으로 무엇을 옮기는 것인지 말한다
- [ ] 수평 크기 조정 · 수직 크기 조정 · 탄력성을 각각 한 문장으로 구분한다
- [ ] 읽기 전용 복제본이 캐시를 대신하지 못하는 이유를 오버헤드로 설명한다
- [ ] 동기식 분리와 비동기식 분리를 예를 들어 가른다
- [ ] 결합이 강하다는 말이 무엇이 많다는 뜻인지 설명한다
- [ ] 큐가 흡수하는 것이 "요청"이 아니라 무엇인지 한 문장으로 말한다
