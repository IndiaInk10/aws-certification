> 도메인 3 · 고성능 아키텍처 설계 **24%** · 과제 명세 5개 중 **세 번째**

## 1. 왜 필요한가

> 실제 시험에 `SQL/DB 시나리오` 가 나왔다는 보고가 있습니다. 그리고 대부분 **읽기가 느리다**로 시작합니다.

DB 문항은 두 갈래로 갈립니다. 하나는 **어떤 DB 를 고를 것인가**, 다른 하나는
**이미 있는 DB 가 느린데 무엇을 붙일 것인가** 입니다. 후자가 더 자주 나옵니다.

그리고 후자의 답은 몇 개 안 됩니다 — 읽기 전용 복제본, ElastiCache, DAX, RDS Proxy.
어느 것이냐는 **무엇이 느린지**에 달려 있습니다. 읽기인지, 반복되는 같은 쿼리인지, 커넥션인지.

## 2. 이번에 새로 나오는 서비스

| 서비스 | 한 줄 | 이 과제에서 맡는 역할 |
|---|---|---|
| [[amazon-rds\|Amazon RDS]] | 관리형 관계형 DB | 읽기 전용 복제본 = 읽기 성능 |
| [[amazon-aurora\|Amazon Aurora]] | AWS 판 MySQL·PostgreSQL | 성능과 복원력을 한 번에 |
| [[amazon-dynamodb\|Amazon DynamoDB]] | 관리형 NoSQL | 한 자릿수 밀리초, 무제한 확장 |
| [[amazon-elasticache\|Amazon ElastiCache]] | 인메모리 캐시 (Redis · Memcached) | DB 앞에서 부하를 걷어낸다 |
| [[amazon-redshift\|Amazon Redshift]] | 데이터 웨어하우스 | 분석 쿼리. 트랜잭션용이 아니다 |
| [[amazon-documentdb\|Amazon DocumentDB]] | 관리형 MongoDB 호환 | `MongoDB` 가 지문에 있을 때 |
| [[amazon-neptune\|Amazon Neptune]] | 그래프 DB | 추천·소셜 관계 |
| [[aws-dms\|AWS DMS]] | DB 마이그레이션 | 옮기는 이야기가 나올 때 |

## 3. 이 과제가 묻는 것

---

### L1. 데이터베이스를 고른다는 것 — 관계형과 그 밖의 것들

> **이번 강의에서 다룰 내용** — 관계형 데이터베이스와 그렇지 않은 데이터베이스가 어디에서 갈리는지, 그리고 AWS 가 왜 데이터베이스를 종류별로 따로 두는지 살펴보겠습니다.

#### 관계형 데이터베이스가 하는 약속

관계형 데이터베이스는 데이터를 **행과 열로 된 표**에 담습니다. 표마다 어떤 열이 있고 그 열에 어떤 값이 들어갈 수 있는지를 **스키마**로 미리 못 박아 둡니다.
그리고 표와 표를 **조인**으로 이어 붙여 한 번의 질의로 읽어 옵니다. 주문 표와 고객 표를 따로 두고도 "이 주문을 낸 고객의 주소"를 한 문장으로 물을 수 있는 것이 이 구조 덕입니다.

여기에 하나가 더 붙습니다. **제약 조건**입니다. 존재하지 않는 고객의 주문은 아예 들어가지 못하게 막고,
여러 표를 함께 건드리는 작업은 **트랜잭션**으로 묶어 전부 되거나 전부 안 되게 합니다.
"돈이 빠져나갔는데 입금은 안 된 상태"가 남지 않는다는 약속이 여기서 나옵니다.

이 약속에는 값이 붙습니다. 스키마가 고정되어 있으니 필드를 하나 늘리는 일이 표 전체를 건드리는 일이 되고,
표 사이의 관계를 지키려면 쓰기가 한곳으로 모여야 해서 **쓰기를 여러 서버로 나누기가 어렵습니다.**

#### 그래서 갈라져 나온 것들

관계형의 약속 중 일부를 내려놓는 대신 다른 것을 얻은 데이터베이스를 통틀어 **NoSQL** 이라고 부릅니다.
내려놓는 것은 대개 **고정된 스키마와 조인**이고, 얻는 것은 **유연함과 수평 확장**입니다.

| 갈래 | 데이터를 어떻게 담는가 | AWS 서비스 |
|---|---|---|
| **키-값** | 키 하나로 값을 통째로 꺼냅니다. 조인이 없는 대신 아주 빠릅니다 | [[amazon-dynamodb\|DynamoDB]] · [[amazon-elasticache\|ElastiCache]] |
| **문서** | JSON 같은 문서를 한 건 그대로 담습니다. 문서마다 필드가 달라도 됩니다 | [[amazon-documentdb\|DocumentDB]] |
| **그래프** | 사물을 **노드**로, 사물 사이의 연결을 **관계**로 담습니다. "친구의 친구" 같은 질문에 강합니다 | [[amazon-neptune\|Neptune]] |
| **와이드 컬럼** | 행마다 열 구성이 달라도 되는 표입니다. Apache Cassandra 계열입니다 | **Amazon Keyspaces** |
| **원장** | 기록을 덧붙이기만 하고 지우거나 고치지 않습니다. 변경 이력 자체가 자산일 때 씁니다 | **Amazon QLDB** |
| **데이터 웨어하우스** | 여러 곳의 데이터를 한 창고에 모아 놓고 대규모로 집계합니다 | [[amazon-redshift\|Redshift]] |

> [!tip] NoSQL 은 "SQL 이 없다"는 뜻이 아닙니다
> **관계형이 아니라는 뜻**일 뿐이고, 지금은 대부분 SQL 을 닮은 질의 언어를 갖고 있습니다.
> 시험에서 갈리는 지점은 문법이 아니라 **조인이 필요한가**, **스키마가 고정되어 있는가**, **쓰기를 나눠야 하는가** 세 가지입니다.

**DB 를 가르는 축은 일곱 개입니다**

AWS 는 최적의 데이터베이스를 가르는 요구 사항으로 늘 같은 목록을 듭니다 —
**가용성 · 일관성 · 파티션 내결함성 · 지연 시간 · 내구성 · 확장성 · 쿼리 기능**.
지문은 이 중 한둘을 콕 집어 말해 줍니다. `10밀리초 미만이 일관되게` 는 지연 시간이고,
`리전이 통째로 죽어도` 는 가용성이며, `조인이 복잡하다` 는 쿼리 기능입니다.

그리고 **한 시스템이 하위 시스템마다 다른 DB 를 쓰는 것이 정상**입니다.
AWS 는 데이터베이스 선택이 "데이터를 보고" 가 아니라 "조직이 늘 쓰던 것으로" 정해지는 일이 잦다고 지적합니다.
`전부 하나의 데이터베이스로 통일한다` 는 보기는 대개 답이 아니고,
때로는 **데이터베이스가 아닌 다른 방법**이 더 효율적이라는 것까지 염두에 두시기 바랍니다.

**관계형이 아닌 것들**

| 지문 | 답 |
|---|---|
| `MongoDB 를 그대로` | **DocumentDB** |
| `관계·추천·소셜 그래프` | **Neptune** |
| `시계열 데이터` | Timestream |
| `원장 · 변경 불가 기록` | QLDB |
| `페타바이트 분석 · BI 도구 연결` | **Redshift** |

### L2. RDS — 데이터베이스를 맡긴다는 것

> **이번 강의에서 다룰 내용** — RDS 가 우리 대신 무엇을 해 주고 무엇을 남겨 두는지, 그리고 백업과 복구가 어떻게 도는지 살펴보겠습니다.

#### 직접 세우면 해야 하는 일들

데이터베이스 한 대를 직접 세운다고 해 보겠습니다. 서버를 준비하고, 운영체제를 올리고, 데이터베이스 엔진을 설치하고, 설정을 잡습니다.
거기서 끝나지 않습니다. 엔진에 보안 패치가 나오면 서비스를 잠깐 세우고 적용해야 하고,
백업을 걸어 둔 다음 그 백업으로 실제 복구가 되는지도 확인해야 합니다.
서버가 죽으면 새 서버에서 이 과정을 처음부터 되풀이해 데이터를 되살려야 합니다.

**Amazon RDS** 는 이 목록을 대신 가져갑니다.

| RDS 몫 | 내 몫 |
|---|---|
| 하드웨어와 운영체제 | **스키마 설계** |
| 데이터베이스 엔진 설치와 **패치** | **쿼리와 인덱스** |
| **자동 백업**과 특정 시점 복구 | 어떤 데이터를 넣을 것인가 |
| 장애가 난 인스턴스의 교체 | 인스턴스 클래스와 스토리지를 얼마나 잡을 것인가 |

그래서 RDS 는 관리형이지만 **서버리스는 아닙니다.** 인스턴스 클래스를 골라야 하고, 그 인스턴스가 떠 있는 동안 요금이 붙습니다.
`운영체제에 들어가 무언가를 설치해야 한다` 는 조건이 지문에 있으면 RDS 가 아니라 [[amazon-ec2\|EC2]] 위의 데이터베이스로 갑니다.

#### 엔진은 고르는 것입니다

RDS 는 **엔진을 골라서 띄우는** 서비스입니다. MySQL · PostgreSQL · MariaDB · Oracle · SQL Server, 그리고 Aurora 가 있습니다.
그래서 `기존 PostgreSQL 데이터베이스를 그대로 옮긴다` 같은 지문에는 **애플리케이션을 고칠 필요가 없다**는 뜻이 함께 깔려 있습니다.
반대로 Oracle · SQL Server 같은 상용 엔진에는 **라이선스가 따라붙습니다.** 이 이야기는 [[13-cost-database\|4.3]] 에서 비용 쪽으로 다시 나옵니다.

#### 백업은 두 종류입니다

| | 어떻게 도나 |
|---|---|
| **자동 백업** | 정해진 시간대에 스냅샷을 뜨고 그 사이의 변경 로그를 함께 남깁니다. 그래서 보존 기간 안이라면 **특정 시점 복구**가 됩니다. 보존 기간은 **최대 35일**이고, 인스턴스를 지우면 함께 사라집니다 |
| **수동 스냅샷** | 내가 눌러서 뜨는 것입니다. 지울 때까지 남고, 다른 리전으로 복사해 둘 수도 있습니다 |

복구는 **덮어쓰기가 아니라 새 인스턴스를 세우는 방식**입니다. 스냅샷이나 시점을 지정하면 그 상태의 인스턴스가 새로 뜨고,
애플리케이션이 바라보는 엔드포인트를 그쪽으로 옮겨야 합니다.
`복구에 걸리는 시간` 이 조건으로 나오면 이 과정이 통째로 걸린다는 뜻입니다.

### L3. 다중 AZ 와 읽기 전용 복제본 — 서로 다른 문제를 풉니다

> **이번 강의에서 다룰 내용** — 그림이 비슷하게 생긴 두 기능이 왜 다른 문제를 푸는지 갈라 보겠습니다.

#### 다중 AZ 는 가용성입니다

다중 AZ 를 켜면 다른 가용 영역에 **대기(standby) 인스턴스**가 한 대 따라붙습니다.
기본(primary) 인스턴스에 쓰기가 들어오면 **동기적으로** 대기 인스턴스에도 함께 씁니다. 양쪽에 다 써진 뒤에야 쓰기가 끝난 것으로 처리됩니다.

여기서 중요한 것은 **대기 인스턴스가 아무 요청도 받지 않는다**는 점입니다. 읽기도 받지 않습니다.
놀고 있는 것처럼 보이지만 그것이 이 기능의 목적입니다. 기본 인스턴스가 있는 AZ 가 통째로 죽으면
**장애 조치(failover)** 가 일어나 대기 인스턴스가 기본이 됩니다.

애플리케이션은 IP 가 아니라 **엔드포인트(도메인 이름)** 로 접속합니다. 장애 조치는 그 이름이 가리키는 곳을 바꾸는 방식이라
애플리케이션의 접속 문자열을 고칠 일이 없습니다. 다중 AZ 로 얻는 것은 **속도가 아니라 중단 시간**입니다.

#### 읽기 전용 복제본은 성능입니다

읽기 전용 복제본은 **비동기적으로** 복제됩니다. 기본 인스턴스는 자기 쓰기를 끝낸 다음 변경 사항을 흘려보내므로,
복제본이 잠깐 뒤처질 수 있습니다. 이 뒤처짐을 **복제 지연**이라고 하고, 그래서 복제본에서 읽은 값이 방금 쓴 값이 아닐 수 있습니다.

대신 복제본은 **자기 엔드포인트를 가지고 읽기 요청을 직접 받습니다.**
애플리케이션이 읽기 쿼리를 그쪽으로 보내면 기본 인스턴스의 부하가 그만큼 줄어듭니다.
복제본은 다른 AZ 에도, **다른 리전에도** 둘 수 있습니다. 다른 리전에 두면 그 지역 사용자의 읽기가 가까워집니다.

| | 다중 AZ | 읽기 전용 복제본 |
|---|---|---|
| **푸는 문제** | 가용성 · 중단 시간 | **읽기 성능** |
| 복제 방식 | 동기 | 비동기 (지연이 생깁니다) |
| 대기 쪽이 요청을 받나 | **받지 않습니다** | 읽기만 받습니다 |
| 장애 조치 | **자동** | 직접 승격시켜야 합니다 |
| 리전을 넘나 | 리전 안입니다 | **넘을 수 있습니다** |

> [!warning] `읽기가 느립니다` 에 다중 AZ 는 답이 아닙니다
> 대기 인스턴스는 읽기를 받지 않으므로 다중 AZ 를 켜도 읽기는 조금도 빨라지지 않습니다.
> 반대로 `AZ 장애에도 서비스가 이어져야` 라는 지문에 읽기 전용 복제본을 고르면, 승격이 자동이 아니라서 요구를 채우지 못합니다.
> **실무에서는 둘을 함께 켜지만, 문항은 그중 하나만 물어봅니다.**

> [!info] 다중 AZ DB 클러스터
> 다중 AZ 에는 대기 한 대짜리 배포 말고 **대기 두 대짜리 클러스터** 배포가 따로 있습니다.
> 이쪽 대기 인스턴스는 **읽기를 받을 수 있고**, MySQL · PostgreSQL 에서만 고를 수 있습니다.
> "다중 AZ 면 무조건 읽기를 못 받는다"고만 외워 두면 이 배포가 보기에 나왔을 때 걸립니다.

### L4. Aurora — 스토리지를 인스턴스에서 떼어 놓았습니다

> **이번 강의에서 다룰 내용** — Aurora 가 RDS 와 같은 자리에 있으면서도 왜 구조가 다른지, 그 구조가 무엇을 가능하게 하는지 살펴보겠습니다.

#### 보통의 데이터베이스는 디스크를 끌어안고 있습니다

RDS 인스턴스는 자기에게 붙은 볼륨에 데이터를 씁니다. 데이터가 인스턴스에 매여 있으니
복제본을 하나 더 두려면 **데이터를 통째로 한 벌 더 복사**해야 합니다.
복제본을 늘릴수록 복사할 것이 늘고, 그 복제 트래픽을 기본 인스턴스가 감당해야 합니다.

Aurora 는 이 구조를 뒤집습니다. 데이터는 인스턴스가 아니라 **공유 클러스터 볼륨**에 있습니다.
이 볼륨은 **3개 가용 영역에 6벌**로 저장되고, 인스턴스는 그 위에 붙었다 떨어졌다 하는 **컴퓨팅**일 뿐입니다.

| 그래서 생기는 일 | |
|---|---|
| 복제본을 붙이는 데 **데이터 복사가 없습니다** | 같은 볼륨을 함께 보므로 복제본을 빠르게 늘립니다 |
| 스토리지가 **알아서 늘어납니다** | 얼마를 잡을지 미리 정하지 않습니다 |
| 복제본이 곧 **장애 조치 대상**입니다 | 기본 인스턴스가 죽으면 복제본 중 하나가 승격합니다 |

RDS 에서 다중 AZ 와 읽기 전용 복제본으로 갈라져 있던 두 가지가 Aurora 에서 한 덩어리가 되는 이유가 이것입니다.
복제본이 읽기도 나눠 받고, 기본 인스턴스가 죽었을 때 그 자리도 물려받습니다.

**Aurora 를 고르는 신호**

- `MySQL·PostgreSQL 호환인데 더 빨라야` · `읽기 복제본이 많이 필요` (최대 15개)
- **3개 AZ 에 6벌 복제**. 스토리지가 자동으로 늘어난다
- `읽기 부하가 예측 불가` → **Aurora Auto Scaling** 또는 Serverless

**Aurora 가 RDS 와 다른 세 가지**

Aurora 는 RDS 제품군 안에 있지만 구조가 다릅니다. 그리고 시험은 그 "다른 점"을 묻습니다.

| | 차이 |
|---|---|
| **구조** | 인스턴스가 아니라 **클러스터**입니다. 프라이머리 하나에 읽기 전용 복제본 0개 이상이 붙습니다 |
| **복제본의 쓰임** | Aurora 의 읽기 전용 복제본은 **읽기 분산과 가용성을 겸합니다.** RDS 에서 읽기 전용 복제본과 다중 AZ 로 갈렸던 것이 여기서는 하나로 합쳐집니다 |
| **스토리지** | 컴퓨팅에 붙은 로컬 디스크를 쓰지 않고 **공유 클러스터 볼륨**을 씁니다. 그래서 프로비저닝이 빠르고 가용성과 성능이 함께 올라갑니다 |

**리전 범위**도 다릅니다. RDS 는 **리전 복원력** — 가용 영역 하나가 죽는 것까지 감당합니다.
리전을 넘어야 하면 **Aurora 글로벌 데이터베이스**입니다.
`리전 단위 장애 조치가 필요한 관계형 데이터베이스` 는 RDS 가 아니라 이쪽으로 옵니다.

**Aurora Serverless 와 ACU**

Aurora Serverless 는 인스턴스를 프로비저닝하지도 관리하지도 않는 Aurora 입니다.
공유 클러스터 스토리지는 그대로라 **3개 AZ 에 6벌**은 똑같이 유지되고, 컴퓨팅을 세는 단위만 달라집니다.

- 단위는 **ACU(Aurora 용량 단위)** 입니다. 일정량의 컴퓨팅과 그에 상응하는 메모리가 한 묶음입니다
- **최소 ACU 와 최대 ACU** 를 정해 두면 부하에 따라 그 사이에서 오르내립니다
- 비활성 구간에는 **0 까지 내려가 일시 중지**될 수 있고, 그동안은 **사용 중인 스토리지 요금만** 남습니다

그래서 `사용 빈도가 낮다` · `간헐적이다` · `언제 몰릴지 예측할 수 없다` 세 낱말이 지문에 있으면 Aurora Serverless 입니다.

### L5. DynamoDB — 키로 찾고, 조인하지 않습니다

> **이번 강의에서 다룰 내용** — DynamoDB 의 키 구조가 왜 그렇게 생겼는지, 그리고 용량을 무엇으로 세는지 살펴보겠습니다.

#### 용어부터 맞춰 보겠습니다

| 관계형에서 | DynamoDB 에서 |
|---|---|
| 테이블 | **테이블** |
| 행 | **항목(item)** |
| 열 | **속성(attribute)** |
| 기본 키 | **파티션 키**, 또는 **파티션 키 + 정렬 키** |

다른 점이 하나 있습니다. 관계형에서는 표를 만들 때 열을 전부 선언하지만,
DynamoDB 에서는 **키를 뺀 나머지 속성을 미리 정하지 않습니다.** 항목마다 속성이 달라도 됩니다.

#### 파티션 키는 "어디에 둘지"를 정합니다

DynamoDB 는 데이터를 여러 대의 서버에 나눠 담습니다. 어느 자리에 담을지를 정하는 것이 **파티션 키**입니다.
키 값을 해시 함수에 넣어 나온 결과로 자리가 정해지므로, **키만 알면 곧바로 그 자리로 갑니다.** 표 전체를 뒤지지 않습니다.
데이터가 몇 건이든 찾아가는 비용이 그대로인 것이 여기서 나옵니다.

여기에는 조건이 하나 붙습니다. 파티션 키 값이 골고루 퍼져야 합니다.
`국가` 처럼 값의 가짓수가 적은 것을 파티션 키로 삼으면 한 자리에 몰려 **핫 파티션**이 되고, 그 파티션만 느려집니다.

**정렬 키**를 함께 쓰면 파티션 키가 같은 항목들이 정렬 키 순서로 줄을 섭니다.
`사용자 ID` 를 파티션 키로, `주문 시각` 을 정렬 키로 두면 "이 사용자의 최근 주문 열 건"을 범위로 한 번에 읽어 옵니다.
이때는 둘을 합친 것이 그 항목의 유일한 키가 됩니다.

> [!warning] 조인이 없다는 말의 뜻
> 관계형에서는 표를 먼저 정규화해 두고, 필요한 질의를 나중에 조인으로 만들어 냅니다.
> DynamoDB 는 순서가 반대입니다. **어떤 질의를 할지 먼저 정하고, 그 질의가 키 하나로 끝나도록 테이블을 설계합니다.**
> 그래서 `복잡한 조인` · `임의의 조건으로 검색` 이 지문에 있으면 DynamoDB 는 답이 아닙니다.

#### 용량은 읽기와 쓰기를 따로 셉니다

DynamoDB 는 인스턴스 크기가 아니라 **처리량**으로 용량을 셉니다.

- **읽기 용량 단위(RCU)** — 4KB 까지의 항목을 **초당 한 번** 강력한 일관성으로 읽습니다. 최종 일관성으로 읽으면 같은 단위로 두 번 읽습니다
- **쓰기 용량 단위(WCU)** — 1KB 까지의 항목을 **초당 한 번** 씁니다

여기서 **일관성** 이야기가 나옵니다. DynamoDB 는 데이터를 여러 곳에 복제해 두므로,
방금 쓴 값이 모든 복제본에 퍼지기 전에 읽으면 **옛 값이 나올 수 있습니다.**
그것을 감수하는 대신 용량을 덜 쓰는 것이 **최종 일관성 읽기**이고, 반드시 최신값을 받아야 하면 **강력한 일관성 읽기**를 요청합니다.

| 용량 모드 | 어떻게 |
|---|---|
| **프로비저닝** | 초당 몇 단위를 쓸지 미리 정해 둡니다. 넘어서면 요청이 **제한(스로틀링)** 됩니다. Auto Scaling 을 붙이면 그 범위를 자동으로 조절합니다 |
| **온디맨드** | 미리 정하지 않고 **실제로 처리한 요청만큼** 냅니다. 급증에 알아서 따라갑니다 |

**DynamoDB 를 고르는 신호**

- `한 자릿수 밀리초` · `초당 수백만 요청` · `스키마가 유연` · `키로만 조회`
- **글로벌 테이블** — 여러 리전에서 동시에 쓰기
- **인덱스** — 파티션 키를 바꿔 조회하려면 **GSI**, 정렬 키만 바꾸면 **LSI**(테이블 생성 시에만)
- **스트림** — 변경 사항을 Lambda 로 흘려보낸다

### L6. 앞에서 걷어냅니다 — 캐시와 커넥션

> **이번 강의에서 다룰 내용** — 데이터베이스를 키우는 대신 데이터베이스에 닿는 요청 자체를 줄이는 방법들을 살펴보겠습니다.

#### 같은 것을 두 번 묻지 않게 합니다

어떤 애플리케이션이든 읽기를 뜯어보면 **같은 질문이 반복**됩니다.
첫 화면의 인기 상품 목록, 로그인한 사용자의 프로필, 환율 같은 것들입니다.
그때마다 데이터베이스가 디스크를 읽고 같은 답을 다시 계산합니다.

**캐시**는 그 답을 메모리에 들고 있다가 다음 요청에 바로 내주는 층입니다. 애플리케이션과 데이터베이스 **사이**에 놓입니다.
디스크가 아니라 메모리에서 꺼내므로 응답이 빨라지고, 데이터베이스에는 애초에 요청이 도착하지 않으므로 부하가 줄어듭니다.
**한 번에 두 가지가 풀립니다.**

대신 메모리는 **휘발성**입니다. 노드가 죽으면 담아 둔 것이 사라집니다.
그래서 캐시는 원본을 두는 곳이 아니라 **사본을 두는 곳**이고, 잃어버려도 데이터베이스에서 다시 채울 수 있어야 합니다.
`세션을 캐시에 두는데 캐시가 죽어도 로그인이 풀리면 안 된다` 같은 지문이 바로 이 지점을 찌릅니다.

#### 커넥션도 자원입니다

데이터베이스는 접속 하나마다 메모리와 처리 자원을 잡아 둡니다. 그래서 **동시 접속 수에 상한**이 있습니다.
[[aws-lambda\|Lambda]] 처럼 요청이 올 때마다 새로 뜨는 컴퓨팅이 앞에 있으면, 함수 하나하나가 접속을 열어 이 상한을 금세 채웁니다.

**RDS Proxy** 는 그 앞에 서서 접속을 **모아 두고 돌려씁니다.** 함수는 프록시에 붙고, 프록시가 이미 열어 둔 접속을 빌려 씁니다.
장애 조치가 일어났을 때 새 인스턴스 쪽으로 연결을 옮겨 주는 일도 함께 합니다.

**무엇이 느린가 → 무엇을 붙이는가**

| 증상 | 답 |
|---|---|
| 읽기 쿼리가 많아 DB 가 버겁다 | **읽기 전용 복제본** |
| **같은 쿼리**가 반복된다 | **ElastiCache** (앞에서 걷어낸다) |
| DynamoDB 읽기를 마이크로초까지 | **DAX** |
| Lambda 가 커넥션을 다 써 버린다 | **RDS Proxy** |
| 쓰기 자체가 한계 | 샤딩 · Aurora · DynamoDB 로 전환 |
| 분석 쿼리가 운영 DB 를 잡아먹는다 | **Redshift** 로 분리 |

**ElastiCache — Redis 와 Memcached**

| | Redis | Memcached |
|---|---|---|
| 복제 · 장애 조치 | **있다** | 없다 |
| 지속성(스냅샷) | 있다 | 없다 |
| 자료 구조 | 정렬 집합 · 리스트 등 | 단순 키-값 |
| 언제 | **세션 저장** · 리더보드 · 고가용성 캐시 | 단순 캐시를 수평으로 넓힐 때 |

`캐시가 죽어도 세션이 남아야` → **Redis**. 지문에 `다중 AZ` 나 `장애 조치` 가 붙으면 Memcached 는 탈락입니다.

**캐싱은 전략까지 묻습니다**

| | 어떻게 도나 |
|---|---|
| **지연 로딩(lazy loading)** | 캐시에 없을 때만 DB 에서 읽어 채웁니다. 안 쓰는 데이터는 캐시를 차지하지 않지만, 첫 요청이 느리고 **오래된 값이 남을 수 있습니다** |
| **동시 기록(write-through)** | 쓸 때 캐시도 함께 씁니다. 캐시가 늘 최신이지만 **읽히지 않을 데이터까지** 캐시에 들어갑니다 |

**DAX** 안에는 캐시가 두 개 있습니다 — 키로 가져온 것을 담는 **항목 캐시**와 조회 결과를 담는 **쿼리 캐시**입니다.
마이크로초 단위 응답이 필요할 때 DynamoDB 앞에 그대로 끼웁니다.

**용량 계획에서 갈리는 두 가지**

| 상황 | 답 |
|---|---|
| RDS 워크로드를 예측할 수 없다 | **스토리지 자동 크기 조정**을 켭니다. 다만 **최대 스토리지 임곗값이 증가분 이하로 잡혀 있으면 조정이 일어나지 않습니다** — 켜 두었는데 안 늘어난다는 지문의 정체가 이것입니다 |
| DynamoDB 를 새로 띄우는데 액세스 패턴을 아직 모른다 | **온디맨드 용량**으로 시작합니다. 패턴이 보이고 나서 프로비저닝으로 옮기면 비용이 내려갑니다 |

## 4. 시험에서 갈리는 지점

| 지문에 이게 있으면 | 이쪽 |
|---|---|
| `읽기 성능` | **읽기 전용 복제본** (다중 AZ 가 아니다) |
| `같은 조회가 반복` · `DB 부하를 줄인다` | **ElastiCache** |
| `세션을 캐시에 저장` + `장애에도 유지` | **ElastiCache for Redis** |
| `DynamoDB 인데 더 빨라야` | **DAX** |
| `Lambda 가 DB 커넥션을 소진` | **RDS Proxy** |
| `한 자릿수 밀리초` · `무제한 확장` | **DynamoDB** |
| `여러 리전에서 쓰기` | **DynamoDB 글로벌 테이블** |
| `MySQL 호환인데 성능과 복제본이 더` | **Aurora** |
| `기존 DB 를 최소 다운타임으로 이관` | **DMS** (스키마가 다르면 SCT 도) |
| `BI 대시보드용 대규모 집계` | **Redshift** |
| `리전 단위 장애 조치가 필요한 관계형 DB` | **Aurora 글로벌 데이터베이스** (RDS 는 리전 안까지) |
| `사용이 간헐적` · `안 쓸 때는 요금이 거의 안 나갔으면` | **Aurora Serverless** (ACU 가 0 까지 내려갑니다) |
| `액세스 패턴을 아직 모르는 새 애플리케이션` | **DynamoDB 온디맨드 용량** |
| `스토리지 자동 조정을 켰는데 늘어나지 않는다` | **최대 스토리지 임곗값**을 확인 |
| `캐시에 오래된 값이 남는다` | **동시 기록** 전략으로 |
| `10밀리초 미만을 튜닝 없이 일관되게` | **DynamoDB** |

> [!tip] 캐시는 어디에 두느냐가 다릅니다
> ElastiCache 는 **애플리케이션과 DB 사이**, DAX 는 **DynamoDB 전용**, CloudFront 는 **사용자와 앱 사이**입니다.
> 지문이 무엇을 줄이라고 했는지 보세요 — DB 부하인지, 응답 지연인지, 네트워크 왕복인지.
