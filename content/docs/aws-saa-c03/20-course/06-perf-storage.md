> 도메인 3 · 고성능 아키텍처 설계 **24%** · 과제 명세 5개 중 **첫 번째** (과제당 ≈4.8%)

## 1. 왜 필요한가

> CLF 는 "블록·파일·객체 중 무엇인가"까지 물었습니다. SAA 는 **파일이면 그중 어느 것인가**를 묻습니다.

여기서 갈리는 폭이 SAA 에서 확 넓어집니다. CLF 에서 `Amazon FSx` 하나로 배웠던 것이
SAA 에서는 **Lustre · Windows File Server · ONTAP · OpenZFS** 네 갈래로 쪼개져 나옵니다.
실제 시험에서 **FSx for Lustre 와 FSx for ONTAP 가 각각 따로** 나왔다는 보고가 있습니다.

EBS 도 마찬가지입니다. CLF 는 "EC2 에 붙는 디스크"면 충분했지만
SAA 는 gp3 인지 io2 인지, IOPS 가 필요한지 처리량이 필요한지를 묻습니다.

## 2. 이번에 새로 나오는 서비스

| 서비스 | 한 줄 | 이 과제에서 맡는 역할 |
|---|---|---|
| [[amazon-s3\|Amazon S3]] | 객체 스토리지 | 기본값. 정적 자산·데이터 레이크 |
| [[amazon-ebs\|Amazon EBS]] | EC2 한 대에 붙는 블록 볼륨 | 볼륨 유형 선택이 곧 성능 선택 |
| [[amazon-efs\|Amazon EFS]] | 여러 Linux 인스턴스가 함께 쓰는 NFS | 리전 단위 공유 |
| [[amazon-fsx\|Amazon FSx]] | 관리형 파일 시스템 4종 | **여기가 SAA 의 새 영역** |
| [[aws-storage-gateway\|AWS Storage Gateway]] | 온프레미스를 AWS 스토리지에 잇는다 | 하이브리드 |
| [[aws-datasync\|AWS DataSync]] | 대량 파일 전송 자동화 | 온프레미스 → AWS 이관 |
| [[aws-snow-family\|AWS Snow Family]] | 물리 장비로 데이터를 실어 나른다 | 네트워크로는 몇 주 걸릴 때 |

## 3. 이 과제가 묻는 것

> [!tip] 도메인 3 전체를 관통하는 원칙
> AWS 는 이 도메인을 컴퓨팅 · 스토리지 · 데이터베이스 · 네트워킹 **네 계층에 데이터 수집·변환**을 더한 다섯 갈래로 나눕니다.
> 그리고 성능은 한 번 고르고 끝나는 것이 아니라 **벤치마킹과 로드 테스트로 얻은 수치를 근거로 계속 다듬는 것**이라고 말합니다.
> `가장 성능이 좋은` 을 고를 때 감이 아니라 **지문이 준 수치와 요구 사항**을 근거로 삼으시기 바랍니다.

### L1. 스토리지는 세 갈래입니다 — 블록 · 파일 · 객체

> **이번 강의에서 다룰 내용** — 저장 방식이 왜 세 갈래로 나뉘는지, 그리고 요구 사항 한 줄로 어느 갈래인지 가르는 법을 살펴보겠습니다.

#### 데이터를 무엇으로 잘라 두느냐가 다릅니다

같은 데이터를 저장하더라도 **무엇을 하나의 덩어리로 보고, 그 덩어리를 무엇으로 찾느냐**가 방식마다 다릅니다.
이 차이 하나가 성능과 쓰임새를 통째로 결정하므로, 서비스 이름을 외우기 전에 여기부터 잡고 가겠습니다.

**파일 스토리지**는 데이터를 파일 단위로 두고 **디렉터리 경로**로 찾습니다.
우리가 컴퓨터에서 폴더를 열고 파일을 꺼내는 그 방식 그대로입니다.
운영체제가 이미 파일 시스템을 다룰 줄 알기 때문에 **기존 애플리케이션을 고치지 않고 그대로 얹을 수 있습니다.**
대신 파일 시스템이라는 틀 안에서 움직이므로, 규모가 아주 커지면 그 틀 자체가 제약이 됩니다.

**블록 스토리지**는 데이터를 **고정된 크기의 블록**으로 잘라 두고, 블록마다 붙은 식별자로 읽고 씁니다.
여기에는 파일이라는 개념이 아예 없고, 파일 시스템은 그 위에 올라가는 손님입니다.
한 조각만 골라 고쳐 쓸 수 있어 **일부가 계속 바뀌는 데이터**에 강하고, 그래서 데이터베이스의 데이터 파일이 늘 여기에 놓입니다.

**객체 스토리지**는 데이터를 **객체 하나**로 통째로 두고, 거기에 **고유 식별자와 메타데이터**를 함께 붙입니다.
폴더 계층을 유지하지 않으므로 아무리 많이 넣어도 구조가 무거워지지 않아, 사실상 무한에 가깝게 늘어납니다.
대신 객체의 일부만 고쳐 쓰는 일에는 맞지 않습니다 — 바꾸려면 통째로 다시 올려야 합니다.

> [!warning] 객체 스토리지 위에 데이터베이스를 올리는 보기
> 관계형 데이터베이스는 레코드 하나를 고치려고 **작은 블록을 아주 자주** 읽고 씁니다.
> 객체 스토리지는 그 일을 하라고 만든 물건이 아니라서, 값이 싸 보여도 그런 보기는 그대로 오답입니다.

#### 먼저 세 갈래로 가릅니다

| | 언제 | 단위 |
|---|---|---|
| **블록 (EBS · 인스턴스 스토어)** | 인스턴스 **한 대**의 디스크. DB 데이터 파일 | 단일 AZ |
| **파일 (EFS · FSx)** | **여러 대가 동시에** 같은 폴더를 본다 | EFS 는 리전 |
| **객체 (S3)** | 통째로 넣고 통째로 꺼낸다. 웹에서 접근 | 리전 |

관계형 데이터베이스를 올릴 자리를 물으면 답은 **블록**입니다. 객체 스토리지 위에 DB 를 올리는 보기는 그대로 오답입니다.

#### 크기 조정에 손이 가는가 안 가는가

AWS 가 이 과제에서 특히 힘주어 말하는 축이 하나 더 있습니다. **용량이 모자랄 때 사람이 무엇을 해야 하는가** 입니다.
같은 "스토리지"라도 크기를 늘리는 방식이 서비스마다 완전히 달라서, 그 차이가 그대로 운영 부담이 됩니다.

| | 용량이 모자라면 |
|---|---|
| **EBS** | **사람이 바꿉니다.** 볼륨 유형 · 크기 · IOPS 를 수정합니다. 다만 인스턴스를 멈추지 않고 **가동 중에** 바꿀 수 있습니다 |
| **EFS** | **저절로 늘고 줄어듭니다.** 파일을 넣고 지우는 만큼 파일 시스템이 따라갑니다 |
| **S3** | 손댈 것이 없습니다. 용량 상한을 생각하지 않아도 됩니다 |

`최소한의 운영 지원으로 스토리지가 늘어나야 한다` 는 조건이 붙으면 EBS 볼륨을 키우는 보기는 그 자리에서 탈락합니다.

#### 지금 용량이 아니라 5년 뒤 용량으로 고릅니다

AWS 는 이 과제에서 **데이터가 쌓이는 속도**를 설계 조건으로 꼽습니다.
지금은 3TB 면 충분하지만 5년 뒤에 100TB 가 필요한 애플리케이션이라면, 지금 값이 아니라 그 끝값으로 골라야 합니다.
그래서 서비스마다 **용량의 일반적인 상한**을 알아 두시기 바랍니다.
지문이 미래 증가량을 슬쩍 흘려 두었다면 그것이 답을 가르는 조건입니다.

### L2. Amazon S3 — 객체 스토리지의 기본값

> **이번 강의에서 다룰 내용** — S3 가 데이터를 어떤 모양으로 담는지, 그리고 크고 먼 데이터를 빠르게 넣고 빼는 방법을 살펴보겠습니다.

#### 버킷 · 키 · 객체

S3 에 무엇을 하나 올리면 그것이 **객체**입니다. 객체를 담는 통이 **버킷**이고, 버킷 안에서 객체를 가리키는 이름이 **키**입니다.

경로는 `s3://버킷이름/prefix/파일이름` 모양이고, 여기서 `prefix/파일이름` 전체가 하나의 키입니다.
콘솔을 열면 폴더가 있는 것처럼 보이지만 **실제로 폴더라는 것은 없습니다.**
키 안의 슬래시를 구분자로 삼아 화면에서만 접어 보여 주는 것입니다.
그래서 "폴더 이름 하나만 바꾼다" 는 조작이 S3 에는 없고, 그 아래 객체들의 키를 전부 다시 쓰는 일이 됩니다.

용량 쪽으로 기억하실 것은 두 가지입니다.
**버킷 하나에 담는 객체의 수에는 상한이 없고**, 대신 **객체 하나에는 크기 상한이 있습니다.**
시험은 **5TB** 를 기준으로 물어 왔습니다. 다만 AWS 문서는 현재 **50TB** 로 올려 적고 있으니, 두 숫자를 다 알아 두시기 바랍니다.
그리고 객체는 리전 안의 **여러 가용 영역에 나뉘어 저장됩니다.** 높은 내구성이 여기서 나옵니다.

#### 버전 관리 — 덮어써도 이전 것이 남습니다

버킷에 **버전 관리**를 켜 두면 같은 키에 새로 올릴 때마다 이전 것이 지워지지 않고 버전으로 쌓입니다.
실수로 덮어쓰거나 지운 객체를 되돌릴 수 있습니다.

- 켜고 끄는 단위는 **버킷**입니다. 객체 하나만 골라 켜는 설정은 없습니다
- 버전 관리가 켜진 버킷에서 객체를 지우면 실제로 지워지지 않고 **삭제 마커**가 맨 위에 얹힙니다. 목록에서는 사라져 보이지만, 그 마커를 걷어 내면 이전 버전이 그대로 돌아옵니다
- 지워지지 않고 쌓인다는 말은 **저장 용량이 계속 는다**는 말이기도 합니다. 오래된 버전을 정리하는 이야기가 [[11-cost-storage\|4.1 비용 최적화 스토리지]] 로 이어집니다

#### 복제 — 같은 리전 안이든 다른 리전으로든

| | 어디로 | 왜 |
|---|---|---|
| **SRR** (Same-Region Replication) | 같은 리전의 다른 버킷 | 로그를 한곳에 모으거나, 운영용과 분석용 계정을 나눌 때 |
| **CRR** (Cross-Region Replication) | 다른 리전의 버킷 | 리전 하나가 통째로 문제가 되는 상황을 대비하거나, 먼 지역 사용자 가까이에 사본을 둘 때 |

**둘 다 원본 버킷과 대상 버킷 양쪽에 버전 관리가 켜져 있어야 동작합니다.**
복제를 켜라는 보기가 있는데 버전 관리 이야기가 빠져 있다면 그 지점을 확인하시기 바랍니다.

#### S3 성능

- **멀티파트 업로드** — 큰 파일을 쪼개서 병렬로. `100MB 이상`이면 권장, `5GB 이상`이면 필수
- **Transfer Acceleration** — 엣지로 받아 AWS 백본으로. `멀리 있는 사용자가 업로드` 신호
- **바이트 범위 가져오기** — 큰 객체의 일부만 병렬로 내려받기
- 프리픽스를 나누면 요청 처리량이 함께 올라갑니다

#### 올리는 쪽이 느린지 내려받는 쪽이 느린지 먼저 보십시오

같은 "S3 가 느리다" 라도 손대는 자리가 다릅니다.

| 무엇이 느린가 | 손대는 곳 |
|---|---|
| 올리는 쪽 | 멀티파트 업로드 · **Transfer Acceleration** · CLI 의 병렬 전송 옵션 |
| 내려받는 쪽 | [[amazon-cloudfront\|CloudFront]] 로 **엣지에 캐시** · 바이트 범위 가져오기 |

### L3. EBS 와 인스턴스 스토어 — EC2 에 붙는 디스크

> **이번 강의에서 다룰 내용** — EC2 에 붙는 두 가지 디스크가 어떻게 다른지, EBS 볼륨 유형을 무엇으로 고르는지, 그리고 스냅샷이 어떤 성격의 물건인지 살펴보겠습니다.

#### EBS 볼륨은 인스턴스 밖에 있습니다

**Amazon EBS** 는 EC2 인스턴스에 붙여 쓰는 블록 스토리지입니다.
인스턴스 입장에서는 하드디스크나 SSD 를 하나 꽂아 둔 것과 똑같이 보이고,
그 위에 파일 시스템을 만들어 운영체제 · 애플리케이션 · 로그 · 설정 파일을 올립니다.

여기서 중요한 것은 **볼륨이 인스턴스 안에 들어 있지 않다**는 점입니다.
EBS 볼륨은 따로 만들어져 네트워크로 붙습니다. 이 한 가지에서 아래 성질이 전부 따라 나옵니다.

| 성질 | 뜻 |
|---|---|
| **수명이 분리됩니다** | 인스턴스를 종료해도 볼륨을 남길 수 있고, 떼어서 다른 인스턴스에 붙일 수도 있습니다 |
| **같은 AZ 안에서만 붙습니다** | 볼륨과 인스턴스가 같은 가용 영역에 있어야 합니다 |
| **가동 중에 바꿉니다** | 크기 · 유형 · IOPS 를 인스턴스를 멈추지 않고 수정합니다 |
| **여러 개를 붙입니다** | 기본은 루트 볼륨 하나지만 필요한 만큼 더 붙일 수 있습니다 |

#### 볼륨 유형은 두 계열, 네 갈래입니다

이름의 앞 글자가 곧 계열이고, 계열은 **매체가 SSD 인지 HDD 인지**로 갈립니다.

| 계열 | 매체 | 잘하는 일 |
|---|---|---|
| **gp** (general purpose) | SSD | 여기저기 흩어진 데이터를 조금씩 자주 읽고 씁니다 |
| **io** (provisioned IOPS) | SSD | 같은 일을 훨씬 많이. **IOPS 를 숫자로 약속받습니다** |
| **st** (throughput optimized) | HDD | 앞에서 뒤로 **줄줄이 읽어 내립니다** |
| **sc** (cold) | HDD | 줄줄이 읽되 **거의 읽지 않습니다** |

SSD 쪽(`gp` · `io`)의 강점은 **IOPS**, 즉 초당 입출력 횟수입니다.
HDD 쪽(`st` · `sc`)의 강점은 **처리량**, 즉 초당 옮기는 데이터의 양입니다.
지문이 무엇을 요구하는지로 계열이 먼저 갈리고, 세대(`gp2` · `gp3`, `io1` · `io2`)는 그다음 문제입니다.

#### EBS 볼륨 유형

| | 성격 | 언제 |
|---|---|---|
| **gp3** | 범용 SSD. IOPS 와 처리량을 **용량과 따로** 올린다 | 기본값. 대부분 여기 |
| **io1 · io2** | 프로비저닝 IOPS SSD | `수만 IOPS` · 미션 크리티컬 DB |
| **st1** | 처리량 최적화 HDD | 빅데이터 · 로그 처리처럼 **순차** 읽기 |
| **sc1** | 콜드 HDD | 거의 안 건드리는 데이터 |

**IOPS 와 처리량은 다른 요구입니다.** `초당 트랜잭션 수` 면 IOPS(SSD), `초당 MB` 면 처리량(HDD 도 답이 될 수 있음).

#### 인스턴스 스토어는 EBS 가 아닙니다

EC2 에 붙는 스토리지는 두 종류입니다. **인스턴스 스토어**는 호스트에 물려 있는 **임시** 디스크라
인스턴스를 멈추면 사라지고, **EBS 볼륨**은 인스턴스와 수명이 분리된 **영구** 스토리지입니다.
지문에 `DAS`, `SAN`, `EC2 용 영구 스토리지` 같은 말이 보이면 블록 스토리지를 고르라는 신호입니다.

인스턴스 스토어가 빠른 이유는 **물리 호스트 안에 직접 물려 있어 네트워크를 타지 않기** 때문입니다.
그 대신 인스턴스가 그 호스트를 떠나는 순간 데이터도 함께 사라집니다.
재부팅은 넘기지만 **중지 · 종료 · 호스트 장애는 넘기지 못합니다.**
그래서 캐시 · 스크래치 공간 · 다시 만들 수 있는 중간 결과처럼 **없어져도 되는 데이터**의 자리입니다.

#### 스냅샷 — 볼륨의 시점 사본을 S3 에 둡니다

**스냅샷**은 EBS 볼륨을 **그 시점 모습 그대로 떠 둔 사본**입니다. 성격을 세 가지로 잡아 두시기 바랍니다.

- **증분입니다.** 첫 스냅샷만 볼륨 전체를 담고, 그다음부터는 **직전 스냅샷 이후 바뀐 블록만** 담습니다. 그래서 자주 떠도 부담이 적습니다
- **저장되는 자리는 S3 입니다.** 우리가 만든 버킷에 보이지는 않지만, AWS 가 S3 에 보관합니다. 볼륨은 AZ 하나에 묶여 있어도 스냅샷은 **리전 수준의 복원력**을 갖는 이유가 여기에 있습니다
- **복원의 출발점입니다.** 스냅샷에서 새 볼륨을 만들 수 있고, 이때 **다른 AZ 를 골라도 됩니다.** 다른 리전으로 복사해 두면 리전 장애까지 대비합니다

`다른 AZ 로 데이터를 옮겨야 한다` · `AZ 장애에서도 지켜야 한다` 는 지문의 답이 늘 스냅샷인 이유가 이것입니다.

#### 복원력 수준은 스토리지에도 그대로 묻습니다

도메인 1 에서 쓰던 `이 서비스는 어디까지 버티는가` 라는 질문이 여기서도 반복됩니다.

| | 어디까지 버티나 |
|---|---|
| **인스턴스 스토어** | 인스턴스 하나. 멈추면 그것으로 끝입니다 |
| **EBS 볼륨** | **가용 영역 안**에서 중복 저장됩니다. AZ 를 넘지 못합니다 |
| **S3** | **리전 안**에서 중복 저장되어 AZ 하나가 죽어도 영향을 받지 않습니다. 리전 간 복제도 걸 수 있습니다 |

그래서 **EBS 스냅샷이 백업·재해 복구의 답**이 됩니다. 스냅샷은 S3 에 저장되므로,
AZ 단위였던 볼륨의 데이터가 스냅샷을 뜨는 순간 **리전 복원력**을 갖게 됩니다.

> [!info] "S3 는 글로벌"이라는 말
> AWS 강의는 S3 가 모든 리전에서 돌아간다는 뜻으로 **글로벌**이라는 말을 씁니다.
> 다만 **데이터가 실제로 놓이는 자리는 리전**입니다. 문항이 복원력을 물으면 리전 쪽으로 보시기 바랍니다.

### L4. 여러 대가 같은 폴더를 볼 때 — EFS 와 FSx

> **이번 강의에서 다룰 내용** — 공유 파일 시스템이 왜 따로 필요한지, 그리고 FSx 네 갈래를 가르는 낱말을 살펴보겠습니다.

#### 마운트한다는 것

EBS 볼륨은 원칙적으로 **한 인스턴스의 디스크**입니다.
그런데 웹 서버 열 대가 같은 업로드 폴더를 보아야 하거나, 여러 사람이 같은 작업 디렉터리를 함께 써야 하는 상황이 있습니다.
이때 필요한 것이 **여러 대가 네트워크로 동시에 붙는 파일 시스템**입니다.

**마운트**한다는 것은 원격에 있는 파일 시스템을 내 컴퓨터의 한 디렉터리인 것처럼 붙여 놓는 일입니다.
붙이고 나면 애플리케이션 눈에는 그냥 평범한 경로를 읽고 쓰는 것으로 보이므로 **코드를 고칠 일이 없습니다.**
파일 스토리지를 고르는 가장 큰 이유가 여기에 있습니다.

붙이는 규약을 **프로토콜**이라고 하고, 운영체제 세계에 따라 둘로 갈립니다.

| 프로토콜 | 어느 쪽 세계 | AWS 서비스 |
|---|---|---|
| **NFS** | Linux · Unix | **EFS** · FSx for NetApp ONTAP · FSx for OpenZFS |
| **SMB** | Windows | **FSx for Windows File Server** · FSx for NetApp ONTAP |

문항이 운영체제를 굳이 밝히거나 프로토콜 이름을 적어 두었다면, 그것이 답을 가르라고 심어 둔 조건입니다.

#### Amazon EFS 는 리전 단위로 늘었다 줄었다 합니다

**EFS** 는 NFS 를 쓰는 관리형 파일 시스템입니다. 성격을 세 줄로 잡아 두시기 바랍니다.

- **용량을 미리 정하지 않습니다.** 파일을 넣으면 늘고 지우면 줄어듭니다. 페타바이트 규모까지 그대로 갑니다
- **여러 AZ 에 걸칩니다.** AZ 마다 마운트 대상을 두면 여러 AZ 의 인스턴스가 같은 파일 시스템을 봅니다. AZ 하나를 넘지 못하는 EBS 와 여기서 갈립니다
- **온프레미스에서도 붙습니다.** Direct Connect 나 VPN 으로 이어 두면 사내 서버가 같은 파일 시스템을 마운트합니다

#### FSx 네 갈래

FSx 는 AWS 가 만든 파일 시스템이 아니라, **업계에서 이미 쓰던 파일 시스템을 관리형으로 대신 돌려 주는** 서비스입니다.
그래서 갈래를 고르는 기준도 "성능"이 아니라 **원래 쓰던 것이 무엇인가**인 경우가 많습니다.
[[service-comparisons]] 에 신호 표가 있습니다.

| | 한 줄 |
|---|---|
| **Lustre** | HPC · 머신러닝. **S3 를 파일 시스템처럼** 붙여 쓴다 |
| **Windows File Server** | SMB + Active Directory. Windows 애플리케이션 |
| **NetApp ONTAP** | NFS·SMB·iSCSI 를 한 볼륨에서. 온프레미스 NetApp 이관 |
| **OpenZFS** | ZFS 스냅샷·클론이 필요할 때 |

#### 지문에 박히는 낱말

파일 스토리지는 프로토콜과 운영체제 이름으로 갈립니다.

| 낱말 | 가리키는 곳 |
|---|---|
| `NFS` · `네트워크 기반 파일 시스템` · `Linux` · `VPN 이나 Direct Connect 로 온프레미스에서 접근` | **EFS** |
| `SMB` · `NTFS` · `Windows` · `Active Directory 통합` | **FSx for Windows File Server** |
| `HPC` · `S3 를 파일 시스템처럼` | **FSx for Lustre** |

EFS 에는 성능 모드(**범용** · **최대 I/O**)와 **수명 주기 정책**이 함께 있습니다.
접근이 뜸해진 파일을 저렴한 클래스로 내려 비용을 줄이는 쪽이고, 지문이 `가끔만 읽는 파일` 을 언급하면 여기입니다.
공유 리포지토리 · 개발 환경 · 미디어 저장소 · 홈 디렉터리가 EFS 의 전형적인 자리입니다.

---

### L5. 온프레미스에서 넘어올 때

> **이번 강의에서 다룰 내용** — 사내에 있던 데이터를 AWS 쪽으로 잇는 세 가지 방법이 각각 어떤 문제를 푸는지 살펴보겠습니다.

#### 세 서비스는 푸는 문제가 다릅니다

이름이 셋 다 "옮긴다"처럼 들리지만, 실제로 푸는 문제는 서로 겹치지 않습니다.

**AWS Storage Gateway** 는 온프레미스 애플리케이션을 그대로 두고 **저장할 자리만 AWS 로 옮깁니다.**
사내에 게이트웨이를 하나 두면 애플리케이션은 평소 쓰던 프로토콜 그대로 그 게이트웨이에 씁니다.
게이트웨이는 자주 쓰는 데이터를 **사내에 캐시**해 두고 나머지는 뒤편의 AWS 스토리지로 넘깁니다.
그래서 응답은 사내 속도로 오면서 용량은 클라우드 것을 쓰게 됩니다. `온프레미스에서 계속 쓰면서 뒤만 클라우드` 가 이 서비스의 자리입니다.

**AWS DataSync** 는 **파일을 옮기는 일 자체**를 자동화합니다.
에이전트를 두면 양쪽 목록을 비교해 **바뀐 것만** 옮기고 무결성까지 확인합니다.
한 번 옮기고 끝나는 이관에도 쓰고, 일정에 걸어 두는 주기적 동기화에도 씁니다.

**AWS Snow Family** 는 네트워크를 아예 쓰지 않습니다.
AWS 가 보낸 **물리 장비**에 데이터를 담아 돌려보내면 AWS 가 받아서 넣습니다.
회선으로 밀면 몇 주가 걸리는 규모일 때의 답입니다.

> [!tip] 회선으로 될 일인지 먼저 계산합니다
> 지문이 **옮길 데이터의 양과 회선 속도**를 나란히 준다면, 그것은 "네트워크로 하면 며칠 걸리는지 세어 보라"는 뜻입니다.
> 주어진 마감이 그 시간보다 짧으면 그 자리에서 Snow Family 쪽으로 넘어갑니다.

#### 온프레미스가 나오면

| 지문 | 답 |
|---|---|
| `온프레미스 앱은 그대로 두고 저장만 클라우드로` | **Storage Gateway** |
| `한 번에 대량으로 옮긴다`, 네트워크로 몇 주 | **Snow Family** |
| `주기적으로 계속 동기화` | **DataSync** |

## 4. 시험에서 갈리는 지점

| 지문에 이게 있으면 | 이쪽 |
|---|---|
| `여러 EC2 가 같은 파일을 동시에` (Linux) | **EFS** |
| `Windows 애플리케이션` · `SMB` · `Active Directory` | **FSx for Windows File Server** |
| `HPC` · `머신러닝 학습 데이터` · `S3 데이터를 고속으로` | **FSx for Lustre** |
| `NFS 와 SMB 를 동시에` · `NetApp` | **FSx for NetApp ONTAP** |
| `수만 IOPS 가 필요한 데이터베이스` | **io2** |
| `대용량 순차 처리`, 비용도 고려 | **st1** |
| `용량은 그대로인데 IOPS 만 올리고 싶다` | **gp3** (gp2 는 용량에 묶여 있다) |
| `전 세계 사용자가 큰 파일을 업로드` | **S3 Transfer Acceleration** |
| `5GB 넘는 파일 업로드` | **멀티파트 업로드** |
| `페타바이트를 옮기는데 회선이 느리다` | **Snow Family** |
| `최소한의 운영 지원으로 용량이 늘어나야` | **EFS** (볼륨을 키우는 보기는 탈락) |
| `DAS` · `SAN` · `EC2 용 영구 스토리지` | **EBS** — 블록 스토리지를 고르라는 신호 |
| `인스턴스를 멈추면 지워져도 되는 임시 작업 공간` | **인스턴스 스토어** |
| `EBS 데이터를 AZ 장애에서도 지켜야` | **EBS 스냅샷** (S3 에 저장되어 리전 복원력을 얻습니다) |
| `가끔만 읽는 파일의 비용을 줄여라` (EFS) | **수명 주기 정책** |
| `내려받기가 느리다` · `전 세계가 같은 파일을 본다` | **CloudFront 캐싱** |
| `관계형 데이터베이스를 올릴 스토리지` | **블록**. 객체 스토리지를 고르는 보기는 오답 |

> [!tip] EBS 는 AZ 를 못 넘습니다
> `다른 AZ 의 인스턴스에 붙인다` 는 보기는 그대로 오답입니다. 스냅샷을 떠서 다른 AZ 에 만들어야 합니다.
> `여러 인스턴스가 동시에` 도 원칙적으로 EBS 가 아닙니다 — EFS 쪽입니다.

## 6. 셀프 체크

- [ ] 블록·파일·객체를 요구사항 한 줄로 가른다
- [ ] FSx 네 갈래를 각각의 선택 신호로 구분한다
- [ ] gp3 와 io2 를 나누는 기준을 말한다
- [ ] IOPS 가 필요한 상황과 처리량이 필요한 상황을 구분한다
- [ ] Storage Gateway · Snow Family · DataSync 를 각각 언제 쓰는지 안다
- [ ] 용량이 모자랄 때 EBS 와 EFS 가 각각 어떻게 늘어나는지 말한다
- [ ] EBS 볼륨 · 인스턴스 스토어 · S3 의 복원력 수준을 각각 댄다
