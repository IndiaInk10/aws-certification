> 도메인 3 · 고성능 아키텍처 설계 **24%** · 과제 명세 5개 중 **두 번째**

## 1. 왜 필요한가

> 컴퓨팅 문항의 절반은 "**무엇 위에서 돌릴 것인가**" 하나로 끝납니다.

EC2 · ECS · EKS · Fargate · Lambda · Batch. 여섯 개가 다 "코드를 돌리는 곳"입니다.
문항은 지문 안에 딱 하나의 조건을 심어 두고 그중 하나를 고르게 합니다 —
실행 시간, 운영 부담, 기존 컨테이너 유무, 상태 유무 같은 것들입니다.

실제 시험에서 **EC2 가 Linux 와 Windows 양쪽으로** 나왔다는 보고가 있습니다.
운영체제 라이선스가 조건에 끼어드는 문항이 있다는 뜻입니다.

## 2. 이번에 새로 나오는 서비스

| 서비스 | 한 줄 | 이 과제에서 맡는 역할 |
|---|---|---|
| [[amazon-ec2\|Amazon EC2]] | 가상 서버 | 인스턴스 패밀리 선택이 곧 성능 선택 |
| [[amazon-ec2-auto-scaling\|EC2 Auto Scaling]] | 대수 자동 조절 | 탄력성의 기본 |
| [[aws-lambda\|AWS Lambda]] | 서버 없이 함수 실행 | 최대 15분 |
| [[aws-fargate\|AWS Fargate]] | 컨테이너를 서버 관리 없이 | 컨테이너 + 운영 오버헤드 최소 |
| [[amazon-ecs\|Amazon ECS]] | AWS 방식 컨테이너 오케스트레이션 | 단순한 컨테이너 운영 |
| [[amazon-eks\|Amazon EKS]] | 관리형 Kubernetes | `Kubernetes` 가 지문에 있을 때 |
| [[aws-batch\|AWS Batch]] | 배치 작업 큐 | 대량 일괄 처리 |
| [[elastic-load-balancing\|Elastic Load Balancing]] | 트래픽 분산 | ALB · NLB 선택 |

## 3. 이 과제가 묻는 것

---

### L1. EC2 — 서버를 빌린다는 것

> **이번 강의에서 다룰 내용** — EC2 가 실제로 무엇을 빌려 주는지, 그리고 인스턴스를 하나 세울 때 무엇을 정하게 되는지 짚어 보겠습니다.

#### 어디까지가 AWS 몫인가

온프레미스에서 서버 한 대를 놓으려면 서버랙과 네트워크 인프라가 필요하고, 물리 서버를 잘라 쓰기 위한 **하이퍼바이저**도 필요합니다.
EC2 는 **그 아래를 전부 AWS 가 맡는 서비스**입니다. 우리가 받는 것은 하이퍼바이저 위에서 잘린 **가상 머신 한 대**입니다.

그 위는 우리 몫입니다. 게스트 운영체제를 올리고, 애플리케이션을 배포하고, 몇 대로 늘릴지 정합니다.
[[02-secure-workloads\|1.2]] 에서 본 공동 책임 모델이 컴퓨팅에서는 이렇게 갈립니다.

#### 인스턴스를 세울 때 정하는 다섯 가지

| 정하는 것 | 무엇인가 |
|---|---|
| **AMI** | 운영체제와 소프트웨어 구성을 굳혀 둔 **템플릿 파일**입니다. Amazon Linux · Windows 처럼 종류별로 있고, 직접 만들어 둘 수도 있습니다 |
| **인스턴스 타입** | 이 가상 머신의 성능 구성입니다. 아래에서 이름 읽는 법을 보겠습니다 |
| **VPC · 서브넷** | 어느 네트워크에 놓을지입니다 ([[09-perf-network\|3.4]]) |
| **스토리지 볼륨** | 붙일 디스크와 그 종류입니다 ([[06-perf-storage\|3.1]]) |
| **보안 그룹** | 누가 이 인스턴스에 닿을 수 있는지입니다 ([[02-secure-workloads\|1.2]]) |

AMI 를 **템플릿**으로 이해해 두시면 뒤가 편합니다. 같은 구성을 다른 AZ·리전에서 그대로 다시 띄우는 이야기가
[[05-high-availability\|2.2 고가용성]] 에서 그대로 이어집니다.

#### 인스턴스 타입 이름은 세 토막입니다

`m5.large` 를 예로 들면 이렇게 읽습니다.

| 토막 | 뜻 |
|---|---|
| **m** | **패밀리** — 무엇에 최적화했는가 |
| **5** | **세대** — 숫자가 클수록 최신입니다 |
| **large** | **크기** — 같은 패밀리 안에서의 규모 |

시험은 세대와 크기를 외우게 하지 않습니다. **패밀리 한 글자로 용도를 읽어 내는지**를 봅니다.
패밀리별 용도는 아래 `L4` 의 표에 정리해 두었습니다.

### L2. 요금제 — 같은 인스턴스를 사는 다섯 가지 방법

> **이번 강의에서 다룰 내용** — 성능이 같아도 **어떻게 사느냐**에 따라 값이 갈립니다. 지문이 요구하는 조건과 요금제를 짝지어 보겠습니다.

| 요금제 | 성격 | 지문에 나오는 조건 |
|---|---|---|
| **온디맨드** | 쓴 만큼 냅니다. 약정이 없습니다 | `얼마나 쓸지 모른다` · `짧게 시험 삼아` |
| **예약 인스턴스(RI)** | 1년 또는 3년을 약정합니다. **인스턴스 패밀리와 크기를 미리 못 박습니다** | `구성이 고정된 워크로드를 오래` |
| **Savings Plans** | 같은 1~3년 약정이지만 **금액을 약정**합니다. 패밀리·리전·서비스를 옮겨도 적용됩니다 | `오래 쓸 건데 구성이 바뀔 수 있다` |
| **스팟 인스턴스** | 남는 용량을 씁니다. **AWS 가 회수하면 중단**됩니다. 가장 크게 깎입니다 | `중단되어도 괜찮다` · `배치` · `내결함성` |
| **전용 호스트 · 전용 인스턴스** | 물리 서버를 **다른 고객과 나누지 않습니다** | `규정 준수` · `물리적 격리` · `기존 서버 라이선스` |

> [!tip] RI 와 Savings Plans 를 가르는 한 문장
> **예약 인스턴스는 "이 모양의 인스턴스"를 약정하고, Savings Plans 는 "이만큼의 사용액"을 약정합니다.**
> 그래서 워크로드 구성이 바뀔 여지가 있으면 Savings Plans 쪽이 안전합니다.
> 지문에 `여러 서비스에 걸쳐` · `인스턴스 유형을 바꿀 수도` 가 있으면 Savings Plans 입니다.

비용 쪽 판단은 [[12-cost-compute\|4.2 비용 최적화 컴퓨팅]] 에서 한 번 더 다룹니다.
여기서는 **요금제가 성능이 아니라 약속의 문제**라는 것만 잡고 가시면 됩니다.

### L3. Auto Scaling — 대수를 자동으로 맞춥니다

> **이번 강의에서 다룰 내용** — 늘리고 줄이는 일을 사람 손에서 떼어 놓는 방법을 살펴보겠습니다.

대수를 **늘리는 것이 스케일 아웃**, **줄이는 것이 스케일 인**입니다.
인스턴스 한 대를 더 크게 바꾸는 수직 확장과 달리, 대수를 바꾸는 쪽은 **가동 중단 없이** 됩니다.

동작은 두 조각으로 이루어집니다.

| 조각 | 하는 일 |
|---|---|
| **시작 템플릿** | 새로 띄울 인스턴스의 설계도입니다. AMI · 인스턴스 타입 · 보안 그룹이 여기 들어갑니다 |
| **조정 정책** | 언제 늘리고 줄일지입니다. **목표 사용률**(예: CPU 50%) · **단순 · 단계** · **일정** · **예측** 네 갈래가 있습니다 |

상태 확인에 실패한 인스턴스를 **버리고 새로 띄우는 것**도 같은 기능입니다.
그래서 Auto Scaling 은 성능 도구이면서 동시에 [[05-high-availability\|2.2]] 의 복구 수단이기도 합니다.

> [!important] Auto Scaling 자체에는 요금이 붙지 않습니다
> 늘어난 인스턴스와 그에 딸린 리소스 값만 냅니다.
> `자동 확장을 붙이면 비용이 는다`는 식의 보기는 이 사실 하나로 걸러집니다.

### L4. 어디서 돌릴 것인가

**판단 순서**

```d2
direction: right

q1: "기존 컨테이너가\n있는가?"
q2: "짧고 이벤트\n기반인가?"
q3: "Kubernetes 를\n써야 하는가?"

lambda: "Lambda"
eks: "EKS"
ecs: "ECS + Fargate"
ec2: "EC2 + Auto Scaling"

q1 -> q2: "아니오"
q2 -> lambda: "예 (15분 이내)"
q2 -> ec2: "아니오"
q1 -> q3: "예"
q3 -> eks: "예"
q3 -> ecs: "아니오"
```

**본질적으로 탄력적인 서비스와 그렇지 않은 서비스**

AWS 가 이 과제에서 못을 박는 말이 있습니다. **AWS 위에 올렸다고 해서 저절로 확장되는 것은 아닙니다.**
확장성과 탄력성은 서비스를 어떻게 고르고 엮었느냐에서 나옵니다.

| | 확장은 누구 몫인가 |
|---|---|
| **Lambda** | 서비스 몫입니다. 초당 한 번을 부르든 백 번을 부르든 따로 설계할 것이 없습니다 |
| **Fargate** | 태스크 수만 정하면 그 아래는 서비스 몫입니다 |
| **EC2** | **내 몫입니다.** 본질적으로 확장 가능한 서비스가 아니라, Auto Scaling 그룹과 로드 밸런서를 붙여 **확장 가능하게 만드는 것**입니다 |

`온종일 사용량이 크게 달라지는 백엔드를 EC2 로 운영한다` 는 지문의 답이 늘
**EC2 + Elastic Load Balancing + EC2 Auto Scaling** 세트인 이유가 여기에 있습니다.

**크기를 조정하려면 먼저 보여야 합니다**

Auto Scaling 은 [[amazon-cloudwatch\|CloudWatch]] 지표 위에 얹혀 있습니다.
경보는 **지표가 정해진 시간 동안 임곗값을 넘을 때** 울리고, 그 경보가 조정 이벤트와 알림을 당깁니다.
그래서 이 과제는 "확장하라"가 아니라 **"무엇을 보고 확장할 것인가"** 를 묻습니다.

| 지표 | 성격 |
|---|---|
| **CPU 사용률** | EC2 의 기본 지표. 가장 흔한 조정 기준입니다. 높다는 것은 지금 수요를 못 따라간다는 신호입니다 |
| **메모리 사용량** | **기본으로는 나오지 않습니다.** CloudWatch 에이전트를 넣어 **사용자 지정 지표**로 올려야 합니다 |
| **HealthyHostCount** · **SurgeQueueLength** | 로드 밸런서 쪽 지표. 인스턴스가 아니라 **대기열이 밀리는지**를 봅니다 |

> [!warning] 메모리로 확장하라는 지문
> `메모리 사용률이 올라가면 확장` 이라고 적혀 있는데 보기에 그냥 "CloudWatch 지표로 조정"만 있다면 부족합니다.
> **에이전트를 설치해 사용자 지정 지표를 게시**하는 단계가 들어 있는 보기를 고르시기 바랍니다.

**인스턴스 패밀리** — 이름의 첫 글자가 곧 용도입니다.

| | 무엇에 강한가 | 지문의 신호 |
|---|---|---|
| **T** | 버스트 가능 범용 | 평소 한가하고 가끔 튄다 |
| **M** | 균형 잡힌 범용 | 특별한 요구가 없다 |
| **C** | 컴퓨팅 최적화 | `CPU 집약적` · 배치 · 게임 서버 |
| **R · X** | 메모리 최적화 | `인메모리 DB` · 대용량 캐시 |
| **I · D** | 스토리지 최적화 | `높은 로컬 IOPS` |
| **P · G · Inf** | 가속 컴퓨팅 | `GPU` · 머신러닝 · 추론 |

**Graviton** — ARM 기반. 같은 성능에 **가격이 낮습니다.**
`비용 대비 성능` 이 나오면 Graviton 으로 옮기는 보기가 정답인 경우가 많습니다.

> [!tip] 인스턴스 유형을 전부 외울 필요는 없습니다
> AWS 가 요구하는 것은 목록 암기가 아니라 **패밀리 선택이 성능과 확장성에 어떻게 영향을 주는지**입니다.
> 문항은 애플리케이션의 컴퓨팅 · 스토리지 · 네트워킹 요구를 지문에 깔아 두고 그것으로 패밀리를 고르게 합니다.
> 인스턴스 유형마다 **네트워크 대역폭과 리소스 할당량이 정해져 있다**는 것도 함께 기억하시기 바랍니다.

### L5. 컨테이너와 서버리스 — 관리 경계가 어디까지인가

컨테이너는 **애플리케이션과 그것이 돌아갈 환경을 한 덩어리로 묶은 것**입니다.
덩어리가 몇 개 안 되면 손으로 띄워도 되지만, 수십 개가 되면 어디에 몇 개를 띄우고 죽으면 누가 살릴지가 문제가 됩니다.
그 일을 맡는 것이 **오케스트레이션**이고, AWS 에서는 ECS 와 EKS 가 그 자리에 있습니다.

**ECS 는 두 가지 방식으로 돌아갑니다**

ECS 는 "이 컨테이너를 어디서 어떻게 돌릴지"를 받아 실행합니다. 그 "어디"가 두 갈래입니다.

| | 언제 |
|---|---|
| **Fargate 시작 유형** | 컨테이너용 **서버리스**. 인스턴스를 보지 않습니다 |
| **EC2 시작 유형** | 실행 환경의 **설치 · 구성 · 관리를 직접 통제**해야 할 때 |

컨테이너를 ALB 뒤에 붙일 때 쓰는 **포트 매핑**처럼, 컨테이너가 다른 서비스와 어떻게 맞물리는지도 함께 물어봅니다.
그리고 EKS 는 **EC2 인스턴스 위에서 Kubernetes 를 돌리는** 쪽이라는 점을 함께 잡아 두시기 바랍니다.

**Lambda 의 경계 두 가지**

- **시간** — 실행 제한은 **15분**입니다. 넘어가면 Lambda 가 아니고, 여러 단계를 이어 붙여야 하는 긴 처리는 [[aws-step-functions\|Step Functions]] 로 조율합니다
- **자리** — CloudFront 엣지 로케이션에 함수를 배포하면 사용자 가까이에서 실행됩니다. 응답이 빨라지고 성능이 올라갑니다

**서버리스로 갈 때 같이 묻는 것들**

| | 무엇을 묻나 |
|---|---|
| [[amazon-api-gateway\|API Gateway]] | **제한(스로틀링)과 할당량**을 걸어 API 가 요청에 파묻히지 않게 합니다. 막힌 클라이언트는 속도를 낮춰 다시 보내고, 그 결과 전체 성능이 올라갑니다 |
| **AWS AppSync** | 여러 소스(DynamoDB · Lambda · HTTP API)를 하나의 **GraphQL** 인터페이스로 묶습니다. 응답 캐싱과 Cognito 사용자 풀 연동으로 **필드 단위 액세스 제어**까지 갑니다 |
| [[amazon-sqs\|SQS]] + [[aws-lambda\|Lambda]] | 대규모에서 **실패한 메시지를 어떻게 처리하는가**, 그리고 Lambda 에 걸리는 **할당량**이 함께 나옵니다 |

**빠르게 늘어나야 할 때**

- ASG 의 확장은 **인스턴스 부팅 시간만큼 늦습니다.** 미리 만든 AMI 로 부팅을 줄입니다
- 갑작스러운 급증이 문제면 **예열 풀(warm pool)** 이나 예약 조정
- 정말 즉시 필요하면 컴퓨팅 자체를 **Lambda·Fargate** 로 바꾸는 것이 답입니다

### L6. 트래픽을 나누고 자리를 정합니다

**ALB vs NLB**

| | 언제 |
|---|---|
| **ALB** | HTTP/HTTPS. 경로·호스트 기반 라우팅, WAF 를 붙일 수 있다 |
| **NLB** | TCP/UDP, **초저지연**, 고정 IP 가 필요할 때, 초당 수백만 요청 |
| **GWLB** | 서드파티 방화벽·IDS 어플라이언스를 경로에 끼워 넣을 때 |

**배치 그룹**

| | 무엇을 위해 |
|---|---|
| **클러스터** | 같은 랙에 몰아 넣어 **지연을 최소화**. HPC |
| **분산** | 서로 다른 하드웨어에 흩어 **동시 장애를 막는다** |
| **파티션** | 파티션 단위로 나눠 대규모 분산 시스템(HDFS·Kafka) |

## 4. 시험에서 갈리는 지점

| 지문에 이게 있으면 | 이쪽 |
|---|---|
| `운영 오버헤드 최소` + 짧은 처리 | **Lambda** |
| `실행이 15분을 넘는다` | Lambda **아님** → Fargate · EC2 |
| `이미 컨테이너로 되어 있다` + `서버 관리 싫다` | **ECS + Fargate** |
| `Kubernetes` · `기존 k8s 매니페스트` | **EKS** |
| `수천 개 배치 작업을 큐에 넣고` | **AWS Batch** |
| `CPU 집약적` | **C 계열** |
| `대용량 인메모리` | **R · X 계열** |
| `머신러닝 학습` · `GPU` | **P · G 계열** |
| `비용은 줄이고 성능은 유지` | **Graviton** |
| `노드 간 지연이 중요한 HPC` | **클러스터 배치 그룹** (+ Elastic Fabric Adapter) |
| `고정 IP 가 필요` · `TCP` | **NLB** |
| `URL 경로에 따라 다른 서비스로` | **ALB** |
| `메모리 사용률을 기준으로 확장` | **CloudWatch 에이전트 + 사용자 지정 지표** (기본 지표가 아니다) |
| `대기열이 밀리는지 보고 확장` | **로드 밸런서 지표** (SurgeQueueLength · HealthyHostCount) |
| `여러 단계를 15분 넘게 이어서 처리` | **Step Functions** |
| `사용자 가까이에서 코드를 실행` | **CloudFront 엣지 로케이션에 배포한 Lambda** |
| `컨테이너를 쓰지만 실행 환경을 직접 통제해야` | **ECS EC2 시작 유형** |
| `API 가 과도한 요청에 파묻힌다` | **API Gateway 제한 · 할당량** |
| `여러 데이터 소스를 하나의 API 로` · `GraphQL` | **AppSync** |

> [!warning] 수직 확장은 대개 오답입니다
> `인스턴스 크기를 키운다` 는 보기는 그럴듯하지만 SAA 는 거의 항상 **수평 확장**을 원합니다.
> 크기를 키우면 재시작이 필요하고, 단일 장애점이 그대로 남습니다.
> 예외는 `단일 스레드 애플리케이션` 처럼 나눌 수 없다고 지문이 못 박은 경우뿐입니다.

## 6. 셀프 체크

- [ ] Lambda 를 쓸 수 없는 조건을 두 가지 댄다
- [ ] ECS 와 EKS 를 가르는 지문의 낱말을 안다
- [ ] 인스턴스 패밀리 첫 글자로 용도를 세 개 이상 맞춘다
- [ ] ALB 와 NLB 중 어느 쪽에 WAF 를 붙이는지 안다
- [ ] 클러스터 배치 그룹과 분산 배치 그룹의 목적이 반대라는 것을 설명한다
- [ ] EC2 가 "본질적으로 확장 가능하지 않다" 는 말의 뜻을 한 문장으로 말한다
- [ ] 메모리를 기준으로 확장하려면 무엇이 더 필요한지 안다
