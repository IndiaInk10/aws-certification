> 도메인 4 · 비용에 최적화된 아키텍처 설계 **20%** · 과제 명세 4개 중 **두 번째**

## 1. 왜 필요한가

> [[07-perf-compute\|3.2]] 의 짝입니다. 같은 서비스를 요금 쪽에서 봅니다.

컴퓨팅 비용을 줄이는 방법은 네 가지뿐입니다.

1. **오래 쓸 것을 약정한다** (Savings Plans · 예약 인스턴스)
2. **끊겨도 되는 일에 남는 용량을 쓴다** (스팟)
3. **안 쓸 때 끈다** (Auto Scaling · 예약 조정)
4. **더 싼 하드웨어로 옮긴다** (Graviton)

문항은 워크로드의 성격을 설명하고 이 넷 중 하나를 고르게 합니다.
성격만 정확히 읽으면 답이 하나로 떨어집니다.

## 2. 이번에 새로 나오는 서비스

| 서비스 | 한 줄 | 이 과제에서 맡는 역할 |
|---|---|---|
| [[amazon-ec2\|Amazon EC2]] | 가상 서버 | 요금 모델 선택이 곧 비용 설계 |
| [[amazon-ec2-auto-scaling\|EC2 Auto Scaling]] | 대수 자동 조절 | 안 쓸 때 줄인다 |
| [[aws-lambda\|AWS Lambda]] | 서버 없이 실행 | 안 쓰면 **0원** |
| [[aws-fargate\|AWS Fargate]] | 컨테이너 서버리스 | 유휴 서버 비용을 없앤다 |
| [[aws-batch\|AWS Batch]] | 배치 작업 | 스팟과 궁합이 좋다 |
| [[aws-compute-optimizer\|AWS Compute Optimizer]] | 크기가 맞는지 알려 준다 | `과다 프로비저닝` 신호의 답 |
| [[aws-cost-explorer\|AWS Cost Explorer]] | 비용 분석과 권장 사항 | 어디에 쓰는지 먼저 본다 |

## 3. 이 과제가 묻는 것

> [!tip] 이 과제의 문항은 늘 같은 모양입니다
> "이 워크로드의 성격은 이러합니다. **가장 비용 효율적인** 방법은 무엇입니까."
> 그래서 보기를 고르기 전에, 지문이 말한 성격이 **비용의 어느 자리**를 건드리는지부터 보시기 바랍니다.
> 자리를 정하면 보기 네 개 중 둘은 그 자리를 아예 건드리지 않는다는 것이 보입니다.

### L1. 컴퓨팅 비용은 어디에 붙는가

> **이번 강의에서 다룰 내용** — 컴퓨팅 요금이 실제로 무엇에 매겨지는지, 그리고 "비용을 줄여라"가 결국 어느 손잡이를 돌리라는 말인지 살펴보겠습니다.

#### 요금이 붙는 자리는 네 군데입니다

AWS 는 컴퓨팅 서비스를 고를 때 비용을 평가하는 기준으로 **리소스의 크기 또는 수 · 요금 모델 · 데이터 전송**을 꼽습니다.
여기에 "얼마나 오래 켜 두었는가"를 더하면 네 자리가 됩니다.

| 자리 | 무엇에 붙는가 | 줄이는 방법 |
|---|---|---|
| **크기** | 인스턴스 한 대의 vCPU · 메모리 같은 규모 | 실제 사용률에 맞게 줄입니다 (`L2`) |
| **개수 × 시간** | 몇 대가 얼마 동안 켜져 있었는가 | 안 쓸 때 줄이거나 끕니다 (`L4`) |
| **요금 모델** | 같은 자원을 **어떤 약속으로** 샀는가 | 약정이나 스팟으로 단가를 낮춥니다 (`L3`) |
| **데이터 전송** | 밖으로 나간 트래픽 | 캐싱과 엣지로 나가는 양 자체를 줄입니다 (`L5`) |

문항이 요구하는 절감이 이 넷 중 어디인지 먼저 정하시면, 엉뚱한 자리를 건드리는 보기가 곧바로 떨어집니다.
`인스턴스가 논다` 는 크기와 시간의 문제이지 요금 모델의 문제가 아닙니다.

#### 과금의 기준은 "일한 만큼"이 아니라 "잡아 둔 만큼"입니다

EC2 인스턴스는 CPU 를 100% 쓰든 2% 쓰든, **켜져 있는 시간**에 요금이 붙습니다.
그 시간 동안 물리 자원이 나에게 배타적으로 배정되어 있기 때문입니다.

이 한 문장에서 비용 최적화의 거의 전부가 나옵니다.
크기를 줄이는 것도, 안 쓸 때 끄는 것도, 서버리스로 옮기는 것도, 결국
**잡아 둔 양과 실제로 쓴 양의 차이를 좁히는 일**입니다.

서비스마다 "잡아 둔 것"을 세는 단위가 다릅니다.

| | 무엇으로 셈하는가 | 잡아 두는 시간 |
|---|---|---|
| **EC2** | 인스턴스가 실행 중인 시간 | 내가 끄기 전까지 |
| **Fargate** | 태스크에 요청한 vCPU · 메모리 × 실행 시간 | 태스크가 도는 동안 |
| **Lambda** | 호출 수 + 할당한 메모리 × 실행 시간 | 함수가 도는 동안만 |

아래로 갈수록 **잡아 두는 구간이 짧아집니다.** 이것이 `L5` 에서 볼 "서버리스로 옮기는 것이 절감"의 근거입니다.

### L2. 적절한 크기 조정이 왜 가장 먼저인가

> **이번 강의에서 다룰 내용** — AWS 가 비용 최적화 다섯 축의 **첫 자리**에 크기 조정을 둔 이유를 짚어 보겠습니다.

#### 과다 프로비저닝은 습관에서 나옵니다

온프레미스에서는 서버를 한 번 사면 몇 년을 씁니다.
그래서 **피크에 맞추고 거기에 여유까지 얹어** 사는 것이 합리적인 선택이었습니다.
나중에 모자라면 다시 사서 설치하는 데 몇 주가 걸리니까요.

그 습관을 그대로 들고 클라우드에 올리면, 평소 사용률이 10% 인 인스턴스가 24시간 돌아가게 됩니다.
클라우드에서는 몇 분이면 크기를 바꿀 수 있으므로 **지금 필요한 만큼만 잡는 것**이 맞습니다.
`온프레미스에서 그대로 옮겨 왔다` 는 지문은 거의 항상 크기 조정 문항입니다.

#### 크기의 오차는 뒤의 모든 결정에 곱해집니다

요금제 할인이든 자동 조정이든, 실제로 하는 일은 **단가나 대수에 곱해지는 조정**입니다.
바탕이 되는 크기가 두 배 크면, 할인을 아무리 잘 받아도 **두 배 큰 것을 싸게 산 것**일 뿐입니다.
순서를 바꿀 수 없는 이유가 여기에 있습니다.

#### 크기를 맞추려면 먼저 보아야 합니다

"이만큼이면 된다"는 감으로 나오지 않습니다.
CPU · 메모리 · 스토리지 사용률을 일정 기간 관찰해야 줄일 수 있는 인스턴스와 오히려 키워야 할 인스턴스가 갈립니다.
그 관찰을 대신해 주는 것이 [[aws-compute-optimizer\|Compute Optimizer]] 이고,
`과다 프로비저닝` · `CPU 가 늘 낮다` 는 신호에는 이 서비스가 따라붙습니다.

#### AWS 가 꼽는 비용 최적화의 다섯 축

AWS 는 컴퓨팅 비용을 다섯 가지 순서로 설명합니다. 순서 자체가 시험 신호입니다.

| | 무엇을 하는가 |
|---|---|
| 1. **적절한 크기 조정** | 모든 것의 **첫 단계**입니다. 요금 모델을 고르기 전에 크기부터 맞춥니다 |
| 2. **탄력성 높이기** | 필요할 때만 쓰고 필요 없을 때는 안 쓰는, 쓴 만큼만 내는 모델로 옮깁니다 |
| 3. **올바른 요금 모델 선택** | `L3` 에서 봅니다 |
| 4. **사용량에 맞춰 스토리지 조정** | 컴퓨팅에 붙은 볼륨도 같이 봅니다 ([[11-cost-storage\|4.1]] 과 겹치는 자리입니다) |
| 5. **측정·모니터링으로 지속 개선** | 아키텍처는 계속 바뀌므로 한 번 맞춰 놓고 끝나지 않습니다 |

크기가 틀린 인스턴스를 3년 약정하면 **틀린 크기를 3년 동안 사는 셈**입니다.
보기 두 개가 다 그럴듯할 때는 크기 조정이 먼저인지 확인하시기 바랍니다.

#### 패밀리를 잘못 고르면 요금제로 못 메웁니다

같은 크기라도 성능 요구를 채우는 **가장 저렴한 인스턴스 유형**을 고르는 것이 절감입니다.
배치 처리처럼 CPU 를 쓰는 일이면 컴퓨팅 최적화 쪽이고, 대용량 데이터 집합을 메모리에 올려 다루면 메모리 최적화 쪽입니다.
패밀리별 대표 사용 패턴을 알고 있어야 지문에서 바로 고를 수 있습니다.

#### 수평이냐 수직이냐

- **수직**(인스턴스를 키운다)은 일반적으로 **가동 중단**을 동반합니다
- **수평**(대수를 늘린다)은 중단이 없고, 큰 인스턴스 몇 대보다 **작은 인스턴스를 여러 대** 두는 편이 싸게 끝나는 경우가 많습니다
- 크기 조정 전략에는 **최대 절전 모드**(hibernation)도 들어갑니다. 상태를 남긴 채 멈춰 두는 선택지입니다

### L3. 요금제는 약속의 길이와 폭으로 갈립니다

> **이번 강의에서 다룰 내용** — [[07-perf-compute\|3.2]] 에서는 요금제를 **어떤 워크로드에 맞는가**로 보았습니다. 여기서는 **왜 할인이 생기는가**, 그리고 그 할인의 대가로 무엇을 내주는가로 보겠습니다.

#### 할인은 선물이 아니라 교환입니다

AWS 쪽에서 가장 어려운 일은 **수요를 예측하는 것**입니다.
우리가 "1년 동안 이만큼은 반드시 쓰겠다"고 약속하면 그만큼 예측이 쉬워지고, 그 대가로 단가를 깎아 줍니다.
반대로 "언제 회수당해도 좋다"고 하면 AWS 는 놀고 있는 용량을 팔 수 있게 되고, 역시 깎아 줍니다.

**우리가 내주는 것은 유연성이고, 받는 것은 단가입니다.** 다섯 요금제는 이 교환의 크기 순서로 늘어섭니다.

| 무엇을 내주는가 | 무엇을 받는가 | 해당 요금제 |
|---|---|---|
| 아무것도 내주지 않습니다 | 정가. 대신 언제든 그만둘 수 있습니다 | **온디맨드** |
| **기간**을 내줍니다 (1년 · 3년) | 큰 폭의 할인. 쓰는 모양은 자유롭습니다 | **Savings Plans** |
| 기간에 더해 **구성까지** 못 박습니다 | 같은 폭의 할인 + 용량 확보 | **예약 인스턴스** |
| **중단당하지 않을 권리**를 내줍니다 | 가장 큰 폭의 할인 | **스팟** |
| 남과 서버를 나눌 권리를 내줍니다 (독점을 삽니다) | 할인이 아니라 **웃돈** | **전용 호스트 · 전용 인스턴스** |

맨 아랫줄을 눈여겨보시기 바랍니다.
전용 호스트는 인스턴스가 아니라 **호스트 한 대 단위로** 시간당 요금을 내고, 전용 인스턴스는 인스턴스 요금에 더해 **리전 단위 요금**까지 붙습니다.
**절감 수단이 아니라, 규정 준수와 기존 서버 라이선스를 지키기 위해 더 내는 선택지**입니다.
`비용을 최소화하라` 는 조건에 전용 호스트가 답이 되는 경우는 거의 없습니다.

#### 약정은 "안 써도 낸다"는 위험을 지는 것입니다

약정에는 반대쪽 면이 있습니다. 약정한 만큼을 쓰지 못해도 **그 몫은 그대로 청구됩니다.**
그래서 약정은 없어질 리 없는 **바닥 부하에만** 겁니다.

- 바닥에서 늘 도는 부분 → **약정**
- 그 위로 출렁이는 부분 → **온디맨드**
- 끊겨도 되는 부분 → **스팟**

`비용을 최소화하면서 안정적으로` 라는 조건에 혼합이 정답이 되는 이유가 이것입니다.
전부 약정하면 안 쓴 몫을 물게 되고, 전부 온디맨드면 바닥 부하에서 손해를 봅니다.

선지급 방식도 함께 알아 두시기 바랍니다. **전체 선결제 · 부분 선결제 · 선결제 없음** 세 가지가 있고,
먼저 낼수록 할인 폭이 커집니다. `초기 비용을 쓸 수 없다` 는 조건이면 선결제 없음 쪽입니다.

#### EC2 요금 모델

| | 언제 | 할인 |
|---|---|---|
| **온디맨드** | 예측 불가 · 단기 · 테스트 | — |
| **Savings Plans** | 1~3년 **금액**을 약정. 인스턴스 종류를 바꿔도 적용 | 최대 72% |
| **예약 인스턴스(RI)** | 1~3년 **특정 인스턴스**를 약정 | 최대 72% |
| **스팟** | **중단돼도 되는** 작업 | 최대 90% |
| **전용 호스트** | 물리 서버 독점. **서버 바인딩 라이선스** | — |

> **Savings Plans 와 RI 중 하나를 고르라면 대개 Savings Plans 입니다.**
> 인스턴스 종류·리전·심지어 Lambda·Fargate 까지 유연하게 적용되기 때문입니다.
> RI 가 정답인 경우는 `용량을 예약해 두어야 한다`(용량 예약)처럼 조건이 붙을 때입니다.

#### 스팟을 고르는 신호

- `중단되어도 된다` · `언제 끝나도 상관없다` · `체크포인트가 있다`
- 배치 처리 · 렌더링 · 빅데이터 · CI 빌드 · 무상태 웹 계층
- **반대 신호:** `장기 실행되는 상태 저장 DB` · `중단되면 안 되는` → 스팟은 오답

#### 혼합이 정답인 경우가 많습니다

```d2
direction: right

base: "기본 부하\nSavings Plans / RI"
peak: "예측 가능한 피크\n온디맨드"
burst: "여유·배치\n스팟"

asg: "Auto Scaling 그룹"

base -> asg
peak -> asg
burst -> asg
```

`비용을 최소화하면서 안정적으로` 같은 조건에는 **기본은 약정, 여유분은 스팟**이 정답입니다.

### L4. 유휴 자원은 그 자체가 비용입니다

> **이번 강의에서 다룰 내용** — 켜져 있지만 일하지 않는 자원이 왜 곧바로 요금이 되는지, 그리고 그것을 없애는 일이 왜 "탄력성"이라 불리는지 살펴보겠습니다.

#### 유휴는 "잡아 둔 양 빼기 실제로 쓴 양"입니다

`L1` 에서 요금은 잡아 둔 시간에 붙는다고 했습니다.
그러니 켜 두고 쓰지 않은 시간은 **아무 결과물 없이 요금만 남습니다.**
비용 문항에서 `놀고 있다` · `사용률이 낮다` · `밤에도 켜져 있다` 가 나오면 전부 이 이야기입니다.

유휴가 생기는 자리는 대체로 셋입니다.

| 어디에서 | 왜 생기는가 | 손대는 곳 |
|---|---|---|
| **피크에 맞춘 상시 대수** | 하루 중 몇 시간을 위해 온종일 그 대수를 유지합니다 | 수요를 따라가도록 [[amazon-ec2-auto-scaling\|Auto Scaling]] 을 붙입니다 |
| **업무 외 시간의 개발·테스트 환경** | 아무도 안 쓰는 밤과 주말에도 켜져 있습니다 | 일정 기반 조정 · 인스턴스 스케줄러 |
| **죽었지만 살아 있는 인스턴스** | 상태 확인에 실패했는데 교체되지 않아 요금만 나갑니다 | 그룹에 상태 확인을 추가해 교체합니다 |

프로덕션은 대체로 24시간 돌아야 하지만, **테스트와 개발 환경은 그럴 이유가 없습니다.**
이 구분이 지문에 깔려 있으면 답은 거의 항상 "안 쓰는 시간에 줄인다" 쪽입니다.

#### 탄력성을 높인다는 말은 유휴를 없앤다는 말입니다

AWS 가 비용 최적화 두 번째 축으로 꼽는 "탄력성 높이기"가 정확히 이것입니다 —
필요할 때만 쓰고 필요 없을 때는 놓아, **쓴 만큼만 내는 모델로 옮기는 것**입니다.

큰 인스턴스 몇 대보다 작은 인스턴스를 여러 대 두는 편이 싼 이유도 여기 있습니다.
조각이 작을수록 수요선에 더 촘촘히 맞출 수 있고, **남는 조각이 그만큼 작아집니다.**

> [!tip] Auto Scaling 기능 자체에는 요금이 붙지 않습니다
> 늘어난 인스턴스와 그에 딸린 리소스 값만 냅니다.
> `자동 조정을 붙이면 비용이 는다` 는 보기는 이 사실 하나로 걸러집니다.

#### 끄는 것도 답입니다

| 지문 | 답 |
|---|---|
| `개발·테스트 환경이 밤에도 켜져 있다` | **예약 조정** 또는 인스턴스 스케줄러 |
| `트래픽이 없는 시간에도 최소 대수가 돈다` | ASG 최소 용량 재검토 · **Lambda·Fargate 로 전환** |
| `인스턴스가 CPU 10% 로 논다` | **Compute Optimizer** 권장에 따라 축소 |

끄고 켜는 일정은 태그로 대상을 고르는 방식이 일반적입니다. 태깅 전략이 여기서도 쓰입니다.

#### 로드 밸런서를 붙이면 크기 조정이 정확해집니다

적절한 크기 조정은 [[elastic-load-balancing\|Elastic Load Balancing]] 과 짝일 때 수요에 맞게 수평으로 따라갑니다.

- Auto Scaling 그룹의 조정 기준으로 **ALB 요청 수 같은 ELB 지표**를 쓸 수 있습니다. CPU 만 보는 것보다 실제 수요에 가깝습니다
- 그룹에 **ELB 상태 확인**을 추가하면 비정상 인스턴스를 찾아 교체합니다. 요금만 먹고 일하지 않는 인스턴스가 줄어듭니다
- 대상 그룹의 정상 호스트 수가 기준 아래로 내려가면 [[amazon-cloudwatch\|CloudWatch]] 경보로 알리게 해 둡니다
- ALB · NLB · **Gateway Load Balancer** 중 무엇을 쓸지도 사용 사례와 비용으로 갈립니다

### L5. 관리형·서버리스로 옮기는 것 자체가 절감입니다

> **이번 강의에서 다룰 내용** — 왜 "서버를 직접 굴리지 않는 것"이 비용 항목이 되는지, 그리고 그렇다고 늘 싼 것은 아닌 이유까지 짚어 보겠습니다.

#### 비용은 청구서에만 있지 않습니다

직접 굴리는 서버에는 인스턴스 요금 말고도 붙는 것이 있습니다.
운영체제 패치, 백업이 제대로 도는지 확인하는 일, 모니터링 구성, 장애가 났을 때 대응하는 당번,
그리고 상용 엔진이라면 **라이선스**입니다.

관리형 서비스로 옮기면 그 일들이 서비스 요금 안으로 들어갑니다.
AWS 가 "서버를 유지 관리하는 대신 관리형 서비스를 쓰면 비용을 절감할 수 있다"고 반복하는 것은 이 뜻입니다.
바꿔 말하면 **사람이 하던 일을 요금으로 치환하는 것**이고, 대개 그쪽이 쌉니다.

#### 관리형 서비스로 옮기는 것 자체가 절감입니다

서버를 유지 관리하는 대신 관리형 서비스를 쓰면 그만큼 비용이 줄어든다는 것이 AWS 가 반복하는 문장입니다.
데이터베이스라면 값비싼 엔진 라이선스가 따로 붙지 않는 Aurora 로 라이선스 비용을 없애는 것이 예시로 나옵니다.

#### 서버리스에는 유휴가 구조적으로 없습니다

`L1` 의 표를 다시 떠올려 보시기 바랍니다.
서버리스는 **프로비저닝된 시간이 아니라 실행된 시간**에 요금이 붙습니다.
요청이 없으면 실행이 없고, 실행이 없으면 청구가 없습니다.
`L4` 에서 본 세 종류의 유휴가 **애초에 생기지 않는 구조**입니다.

> [!warning] 그렇다고 서버리스가 늘 싼 것은 아닙니다
> 같은 시간을 놓고 보면 단가는 오히려 더 비쌀 수 있습니다.
> 하루 종일 꽉 차게 도는 워크로드라면 EC2 를 약정으로 사는 편이 쌉니다.
> **가동률이 낮고 들쭉날쭉할수록 서버리스가 유리하고, 높고 고를수록 약정한 EC2 가 유리합니다.**
> 컨테이너에서도 같은 판단이 나옵니다 — 운영 부담을 줄이려면 [[aws-fargate\|Fargate]],
> 단가를 최대한 눌러야 하고 클러스터를 직접 관리할 수 있으면 EC2 시작 유형입니다.

#### 서버리스는 코드가 곧 요금입니다

Lambda 는 함수가 **소비한 리소스와 실행된 시간**에 요금이 붙습니다.
그래서 메모리를 덜 잡고 실행 시간을 줄이도록 함수를 고치는 것이 그대로 절감입니다.
컨테이너도 같습니다. 이미지를 작고 가볍게 만들고, 클러스터를 EC2 위에 둘지 Fargate 로 둘지 성격에 맞게 고르면 비용이 갈립니다.

#### 하이브리드와 엣지도 이 과제에 들어옵니다

**AWS Outposts** · **AWS Snowball Edge** 같은 하이브리드 컴퓨팅은 계층과 구성 요소가 여러 개라
**무엇이 요금에 포함되는지**를 알아야 비용을 맞출 수 있습니다.
예를 들어 Outposts 위에서 AWS 관리형 서비스를 쓰면, 밑에 깔린 EC2 인스턴스와 EBS 스토리지 요금을 제외하고
그 서비스의 **인스턴스 시간 사용량 기준**으로만 청구됩니다.

엣지 컴퓨팅은 지리와 네트워킹을 묶어 최종 사용자 가까이에서 처리하는 방식입니다.
[[amazon-cloudfront\|CloudFront]] 로 엣지에서 캐싱하는 배포, 원격지에서 지연 시간이 짧은 로직을 돌리는 IoT 가 예시이고,
여기서의 절감 요소는 **데이터 센터를 운영하지 않고 관리할 서버가 없다는 것** 자체입니다.

엣지 캐싱은 `L1` 의 네 번째 자리인 **데이터 전송**에도 그대로 듣습니다.
같은 파일을 매번 원본에서 내보내는 대신 엣지에서 돌려주면 밖으로 나가는 양이 줄어듭니다.

---

### L6. 측정하지 않으면 최적화도 없습니다

> **이번 강의에서 다룰 내용** — 비용 최적화가 왜 한 번 하고 끝나는 일이 아닌지, 그리고 무엇을 계속 보아야 하는지 살펴보겠습니다.

#### 지금 맞는 크기는 곧 틀린 크기가 됩니다

트래픽이 두 배가 되거나 기능이 하나 붙으면, 어제까지 딱 맞던 구성이 오늘부터 어긋납니다.
AWS 가 다섯 번째 축을 **측정과 모니터링을 통한 지속적 개선**으로 둔 이유가 이것입니다.
비용 최적화는 한 번 맞춰 놓고 끝나는 설정이 아니라 **계속 도는 절차**입니다.

| 무엇을 보나 | 무엇으로 |
|---|---|
| 어디에 얼마가 나가는가 | [[aws-cost-explorer\|Cost Explorer]] 로 서비스별 · 태그별로 갈라 봅니다 |
| 이 자원이 큰가 작은가 | [[amazon-cloudwatch\|CloudWatch]] 의 CPU · 메모리 · 스토리지 사용률, 그리고 [[aws-compute-optimizer\|Compute Optimizer]] 권장 |
| 선을 넘으면 알려 다오 | CloudWatch 경보와 예산 알림 |

`어디에 돈이 나가는지 모르겠다` 는 지문에 서비스를 바꾸는 보기가 답이 되지 않는 이유가 여기 있습니다.
**보이지 않는 것은 줄일 수 없으므로, 보는 일이 먼저입니다.**

#### 태그가 없으면 비용을 나눌 수 없습니다

청구서는 계정 단위로 옵니다.
어느 팀 · 어느 환경 · 어느 프로젝트의 몫인지는 **비용 할당 태그**를 붙여 두어야 갈라집니다.
같은 태그가 `L4` 에서 본 "끄고 켜는 일정의 대상 고르기"에도 그대로 쓰입니다.
태깅 전략이 비용 과제마다 반복해서 나오는 이유입니다.

#### Graviton

**Graviton** — 같은 성능에 더 싸고 전력도 적습니다.
`애플리케이션 코드 변경 없이 비용 절감` 이 나오면 후보로 올려야 합니다
(다만 아키텍처가 바뀌므로 컴파일이 필요한 경우가 있습니다).

## 4. 시험에서 갈리는 지점

| 지문에 이게 있으면 | 이쪽 |
|---|---|
| `3년간 꾸준히 돌아간다` | **Savings Plans** |
| `특정 인스턴스 용량을 확보해야` | **예약 인스턴스** (용량 예약) |
| `중단돼도 되는 배치 작업` | **스팟** |
| `밤과 주말에는 안 쓴다` | **예약 조정** |
| `요청이 있을 때만 돈다` | **Lambda** |
| `유휴 서버 비용이 아깝다` + 컨테이너 | **Fargate** |
| `인스턴스가 너무 크다` | **Compute Optimizer** → 축소 |
| `Windows 서버 라이선스를 그대로 가져온다` | **전용 호스트** |
| `가격 대비 성능을 올려라` | **Graviton** |
| `어디에 돈이 나가는지 모르겠다` | **Cost Explorer** 먼저 |
| `크기도 안 맞는데 약정부터 하려 한다` | 순서가 틀렸습니다 — **크기 조정이 먼저** |
| `CPU 지표로는 수요를 못 따라간다` | **ALB 요청 수 지표**로 Auto Scaling 조정 |
| `비정상 인스턴스가 요금만 먹는다` | 그룹에 **ELB 상태 확인** 추가 |
| `메모리에 대용량 데이터를 올려 처리` | **메모리 최적화 패밀리** |
| `키우려면 잠깐 멈춰야 한다` | 수직 대신 **수평 크기 조정** |
| `Lambda 요금을 더 줄여라` | 메모리·실행 시간을 줄이도록 **함수를 고칩니다** |
| `Outposts 위 관리형 서비스 요금` | 인스턴스 시간 기준. EC2·EBS 는 **별도** |

> [!warning] 예약은 유연성을 잃는 것입니다
> `워크로드가 자주 바뀐다` · `아직 규모를 모른다` 인데 RI 를 고르면 오답입니다.
> 그 경우는 온디맨드로 시작하거나 Savings Plans 처럼 유연한 쪽입니다.

## 6. 셀프 체크

- [ ] Savings Plans 와 예약 인스턴스를 가르는 조건을 말한다
- [ ] 스팟을 써도 되는 워크로드와 안 되는 워크로드를 각각 든다
- [ ] `비용 최소화 + 안정성` 조건에서 왜 혼합이 답인지 설명한다
- [ ] 개발 환경 비용을 줄이는 방법을 두 가지 댄다
