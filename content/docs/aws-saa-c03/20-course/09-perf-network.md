> 도메인 3 · 고성능 아키텍처 설계 **24%** · 과제 명세 5개 중 **네 번째**

## 1. 왜 필요한가

> `가장 낮은 지연 시간` 이 나오면 답은 셋 중 하나입니다 — **캐시하거나, 경로를 바꾸거나, 전용선을 깔거나.**

지연 시간을 줄이는 방법은 물리적으로 세 가지뿐입니다.
사용자 **가까이에 복사본을 두거나**(CloudFront), 같은 거리라도 **더 좋은 길로 보내거나**(Global Accelerator),
아예 **인터넷을 안 타거나**(Direct Connect · 엔드포인트).

문항은 이 셋 중 하나를 고르게 합니다. 그리고 CloudFront 와 Global Accelerator 를 헷갈리게 만드는 것이
가장 흔한 함정입니다. 둘은 **캐시하느냐 아니냐**로 갈립니다.

## 2. 이번에 새로 나오는 서비스

| 서비스 | 한 줄 | 이 과제에서 맡는 역할 |
|---|---|---|
| [[amazon-cloudfront\|Amazon CloudFront]] | 엣지에 **복사본을 둔다** | 정적·동적 콘텐츠 캐싱 |
| [[aws-global-accelerator\|AWS Global Accelerator]] | 엣지에서 **AWS 백본으로 태운다** | 캐시가 아니라 경로 |
| [[amazon-route-53\|Amazon Route 53]] | DNS + 라우팅 정책 | 어느 엔드포인트로 보낼지 |
| [[aws-direct-connect\|AWS Direct Connect]] | 온프레미스 전용선 | 안정적 대역폭 |
| [[aws-site-to-site-vpn\|Site-to-Site VPN]] | 인터넷 위 암호화 터널 | 싸고 빠르게 깔린다 |

## 3. 이 과제가 묻는 것

---

### L1. 네트워크를 읽는 기본기 — 주소 · 범위 · 경로

> **이번 강의에서 다룰 내용** — IP 주소와 CIDR, DNS, 라우팅 테이블이 각각 무엇을 하는지 살펴보겠습니다. 뒤에 나오는 이야기가 전부 이 네 낱말 위에 얹힙니다.

#### IP 주소 — 장치마다 붙는 고유한 번호

네트워크에 붙은 장치는 저마다 번호를 하나씩 갖습니다. 그 번호가 **IP 주소**이고, 이 번호가 있어야 인터넷에서 서로를 찾아 통신할 수 있습니다.

지금 가장 널리 쓰이는 체계는 **IPv4** 입니다. `192.168.1.10` 처럼 마침표로 끊은 네 개의 숫자로 적고, 숫자 하나가 0부터 255까지의 값을 가집니다.
숫자 한 칸이 **8비트**이므로 주소 전체는 32비트이고, 그래서 만들 수 있는 주소가 약 43억 개입니다.
이것으로도 모자라 나온 것이 **IPv6** 이고, VPC 는 IPv4 와 IPv6 를 둘 다 받습니다.

#### CIDR — 주소 범위를 잘라 내는 표기법

주소를 하나씩 나눠 주는 방식으로는 네트워크를 관리할 수 없습니다. 그래서 **범위**로 잘라 나눠 주고, 그 범위를 적는 방법이 **CIDR 표기법**입니다.

`10.0.0.0/16` 처럼 주소 뒤에 슬래시와 숫자를 붙입니다. 이 숫자는 **앞에서부터 몇 비트를 고정할 것인가**를 뜻합니다.

| 표기 | 고정되는 앞부분 | 남는 비트 | 만들 수 있는 주소 |
|---|---|---|---|
| `/16` | 앞 16비트 | 16비트 | 2의 16승 = 65,536개 |
| `/24` | 앞 24비트 | 8비트 | 2의 8승 = 256개 |
| `/28` | 앞 28비트 | 4비트 | 2의 4승 = 16개 |

**숫자가 클수록 고정되는 앞부분이 길어지고, 그만큼 범위는 좁아집니다.** `/16` 이 `/24` 보다 넓다는 것만 잡아 두시면 지문을 읽을 때 헷갈리지 않습니다.

그리고 이 범위를 전부 쓰지는 못합니다. 비트가 **전부 0인 주소는 네트워크 자신**을 가리키는 데 쓰고,
**전부 1인 주소는 브로드캐스트**용으로 예약되어 있어 둘은 빠집니다.

#### DNS — 이름을 주소로 바꿔 주는 전화번호부

사람은 숫자로 된 주소를 외우지 못합니다. **DNS** 는 `example.com` 같은 도메인 이름을 받아 그에 해당하는 IP 주소로 바꿔 줍니다.
인터넷의 전화번호부라고 생각하시면 됩니다. 이 자리를 맡는 AWS 서비스가 `L6` 에서 다룰 [[amazon-route-53\|Route 53]] 입니다.

#### 라우터와 라우팅 테이블 — 다음 한 칸을 정합니다

**라우터**는 네트워크와 네트워크 사이에서 데이터 패킷을 넘겨 주는 장치입니다.
패킷에는 출발지 주소와 목적지 주소가 적혀 있고, 라우터는 그 목적지를 들고 **라우팅 테이블**을 조회합니다.

라우팅 테이블에는 `이 목적지 범위로 갈 것은 이쪽으로 내보내라` 는 줄이 나열되어 있습니다.
라우터는 여기서 다음 한 칸을 정해 패킷을 넘기고, 이 과정이 최종 목적지에 닿을 때까지 반복됩니다.

> [!tip] 이 강의에서 가장 중요한 한 줄
> **라우팅 테이블이 곧 "어디로 나갈 수 있는가"입니다.**
> 뒤에 나오는 퍼블릭 서브넷과 프라이빗 서브넷의 차이도, 엔드포인트가 인터넷을 우회하는 원리도
> 전부 **라우팅 테이블에 어떤 줄이 들어 있느냐**로 결정됩니다.

#### 방화벽과 로드 밸런서

**방화벽**은 오가는 트래픽을 규칙에 비추어 허용하거나 막는 장치입니다.
`이 주소에서 오는 것은 막는다` · `이 포트로 오는 것만 받는다` 같은 규칙을 씁니다.
AWS 에서 이 자리에 앉는 것이 보안 그룹과 네트워크 ACL 이고, `L4` 에서 다루겠습니다.

**로드 밸런서**는 들어온 트래픽을 여러 서버에 나누어 보내는 장치입니다.
한 대에 몰려서 죽는 것을 막고, 한 대가 죽으면 나머지로 우회시켜 서비스를 이어 갑니다. `L7` 에서 계층별로 다시 보겠습니다.

### L2. VPC 와 서브넷 — 리전과 AZ 위에 그리는 내 네트워크

> **이번 강의에서 다룰 내용** — VPC 가 어디에 놓이고 서브넷이 어디에 놓이는지, 그리고 그 둘을 CIDR 로 어떻게 잘라 쓰는지 살펴보겠습니다.

#### VPC 는 리전에, 서브넷은 AZ 에 놓입니다

AWS 의 물리 구조는 **리전 → 가용 영역(AZ) → 데이터 센터** 순으로 좁아집니다. 네트워크는 이 구조 위에 그대로 얹힙니다.

```layers VPC 는 리전 하나에 걸치고, 서브넷은 AZ 하나 안에 들어갑니다
AWS 리전 | VPC 는 여기에 만들어집니다
  VPC — 10.0.0.0/16 | 리전 안의 여러 AZ 에 걸칩니다
    가용 영역 A
      퍼블릭 서브넷 10.0.0.0/24 | 라우팅 테이블에 인터넷 게이트웨이 경로가 있습니다
      프라이빗 서브넷 10.0.1.0/24 | 그 경로가 없습니다
    가용 영역 B
      퍼블릭 서브넷 10.0.2.0/24
      프라이빗 서브넷 10.0.3.0/24
```

**VPC 는 리전 하나에 만들어지고, 그 리전의 여러 AZ 에 걸칩니다.** 그래서 VPC 자체는 AZ 하나가 죽어도 남습니다 — 아래에서 말하는 **리전 복원력**이 이 뜻입니다.

**서브넷은 AZ 하나 안에서만 삽니다.** 그래서 서브넷을 여러 AZ 에 나누어 만드는 것이 곧 고가용성 설계의 출발점이 됩니다.
`여러 AZ 에 걸쳐 배포한다` 는 지문은 실제로는 **AZ 마다 서브넷을 두고 그 위에 리소스를 나누어 놓는다**는 뜻입니다.

#### CIDR 를 두 번 자릅니다

VPC 를 만들 때 먼저 **VPC 전체의 CIDR 범위**를 정합니다. 그다음 그 범위 **안에서** 서브넷의 범위를 다시 잘라 냅니다. 규칙은 둘입니다.

- 서브넷의 범위는 VPC 의 CIDR 블록 **안에** 있어야 합니다
- 같은 VPC 안의 서브넷끼리 **범위가 겹치면 안 됩니다**

그리고 서브넷을 만들면 그 안의 **IP 주소 다섯 개가 예약되어** 우리가 쓰지 못합니다.
네트워크 주소, 라우터용 주소, DNS 용 주소, 앞으로 쓰려고 남겨 둔 주소, 브로드캐스트 주소입니다.
`/28` 짜리 서브넷이라면 16개 중 다섯 개가 빠져 11개만 남는다는 뜻이라, **서브넷을 너무 잘게 자르면 주소가 모자랍니다.**

> [!warning] 주소 범위는 나중에 바꾸기 어렵습니다
> 아래에서 볼 **VPC 피어링**은 양쪽의 CIDR 블록이 **겹치면 아예 연결되지 않습니다.**
> 지금은 혼자 쓰는 VPC 라도 나중에 다른 VPC 나 온프레미스와 이을 것을 생각해 범위를 정해야 한다는 뜻입니다.
> `피어링이 연결되지 않는다` 는 지문의 첫 번째 용의자가 **CIDR 중복**입니다.

#### 퍼블릭 서브넷과 프라이빗 서브넷을 가르는 것

서브넷을 만들 때 "퍼블릭"이라는 항목을 고르는 것이 아닙니다.
**라우팅 테이블에 인터넷 게이트웨이로 나가는 경로가 있으면 퍼블릭, 없으면 프라이빗**입니다. 이름이 아니라 경로가 성격을 정합니다.

#### VPC 는 정해진 순서로 세웁니다

네트워크 아키텍처 문항은 VPC 를 처음부터 그릴 수 있다는 것을 전제로 깔고 들어옵니다.
만드는 방법은 여러 가지지만 부품과 순서는 늘 같습니다.

1. **VPC** — **리전 복원력**을 갖습니다. 사용자 지정 VPC 는 **명시적으로 열기 전까지 프라이빗**입니다
2. **서브넷** — 가용 영역 하나에 놓입니다
3. **라우팅 테이블** — 어디로 내보낼지 정합니다
4. **인터넷 게이트웨이** — 인터넷으로 나가는 문
5. **네트워크 ACL** — 서브넷 경계
6. **보안 그룹** — 인스턴스 경계

여기까지가 뼈대이고, 그다음이 사용자 지정입니다 — 리소스를 넣고, 보안 규칙을 손보고,
필요하면 **NAT 게이트웨이**를 붙이고, 다른 VPC 와 **피어링**하고, **엔드포인트**를 만듭니다.
그리고 이 전체를 **코드형 인프라**로 정의해 두면 네트워크를 빠르게 다시 세우거나 고칠 수 있습니다.

### L3. 인터넷으로 나가는 두 개의 문 — 인터넷 게이트웨이와 NAT 게이트웨이

> **이번 강의에서 다룰 내용** — 퍼블릭 서브넷이 어떻게 인터넷과 통하고, 프라이빗 서브넷은 어떤 우회로로 바깥에 나가는지 살펴보겠습니다.

#### 인터넷 게이트웨이 — VPC 에 붙이는 대문

**인터넷 게이트웨이**는 **VPC 에 붙는** 부품입니다. 이것이 붙어 있어야 VPC 안의 리소스가 인터넷과 통할 수 있습니다.

다만 **붙이는 것만으로는 아무 일도 일어나지 않습니다.**
앞에서 본 대로 서브넷의 **라우팅 테이블에 인터넷 게이트웨이로 향하는 경로가 들어가야** 그 서브넷이 비로소 퍼블릭이 됩니다.
웹 서버를 퍼블릭 서브넷에 두는 이유가 여기에 있습니다 — 그 경로가 있어야 바깥의 요청을 받고 필요한 것을 내려받을 수 있습니다.

#### NAT 게이트웨이 — 나가기만 하는 쪽문

프라이빗 서브넷의 인스턴스는 인터넷과 직접 통하지 못합니다. 그런데 업데이트를 내려받거나 외부 API 를 부를 일은 생깁니다.
이때 쓰는 것이 **NAT 게이트웨이**입니다. 두 게이트웨이는 **붙는 자리부터 다릅니다.**

| | 어디에 두나 | 무엇을 하나 |
|---|---|---|
| **인터넷 게이트웨이** | **VPC 에 붙입니다** | 안팎 양방향 통신을 가능하게 합니다 |
| **NAT 게이트웨이** | **퍼블릭 서브넷 안에 만듭니다** | 프라이빗 서브넷이 **나가기만** 하게 해 줍니다 |

프라이빗 서브넷의 라우팅 테이블은 바깥으로 나가는 트래픽을 NAT 게이트웨이로 보내고,
NAT 게이트웨이가 출발지 주소를 자기 것으로 갈아 끼워 인터넷 게이트웨이 쪽으로 내보냅니다.
그래서 **인스턴스의 프라이빗 주소는 바깥에 드러나지 않고**, 바깥에서 먼저 말을 걸어 올 수도 없습니다.

> [!warning] NAT 게이트웨이는 퍼블릭 서브넷에 있어야 합니다
> `프라이빗 서브넷에 NAT 게이트웨이를 만든다` 는 보기는 그 자체로 틀린 구성입니다.
> NAT 게이트웨이 자신이 인터넷 게이트웨이로 나갈 수 있어야 하기 때문입니다.
> 그리고 NAT 게이트웨이는 **시간과 처리한 데이터량 양쪽에 요금이 붙습니다** — 비용 쪽 이야기는 [[14-cost-network\|4.4]] 에서 이어집니다.

#### 탄력적 IP 주소

EC2 인스턴스에 그냥 붙는 퍼블릭 주소는 **동적**이라 인스턴스를 멈췄다 켜면 바뀔 수 있습니다. 프라이빗 주소는 그대로 남습니다.

주소가 고정되어야 하면 **탄력적 IP 주소**를 씁니다. 계정에 할당해 두고 인스턴스에 붙이는 방식이라,
인스턴스에서 **떼어 다른 인스턴스에 다시 붙일 수 있습니다.** 죽은 인스턴스의 주소를 대체 인스턴스로 옮기는 식으로 쓸 수 있다는 뜻입니다.

### L4. 경계마다 다른 방화벽 — 보안 그룹과 네트워크 ACL

> **이번 강의에서 다룰 내용** — 두 방화벽이 각각 어디에 붙고, 왜 규칙을 쓰는 방식이 서로 다른지 살펴보겠습니다. 시험에서 가장 자주 짝으로 나오는 대비입니다.

#### 붙는 자리가 다릅니다

| | 붙는 자리 | 성격 |
|---|---|---|
| **보안 그룹** | **인스턴스 · ENI** — 리소스 하나하나에 붙습니다 | 상태를 기억하는 **스테이트풀** |
| **네트워크 ACL** | **서브넷** — 서브넷 경계에 걸립니다 | 상태를 기억하지 않는 **스테이트리스** |

같은 서브넷 안의 두 인스턴스가 서로 통신할 때는 **네트워크 ACL 을 지나지 않습니다.** 서브넷 경계를 넘지 않기 때문입니다.
보안 그룹은 그 경우에도 적용됩니다. **어디에 붙느냐가 곧 어디에 걸리느냐**입니다.

#### 스테이트풀과 스테이트리스

**스테이트풀**은 들어온 트래픽을 기억해 두었다가 **그 응답을 자동으로 내보내 주는** 방식입니다.
보안 그룹은 인바운드를 허용하면 그에 대한 응답이 규칙 없이도 나갑니다.

**스테이트리스**는 기억하지 않습니다. 그래서 네트워크 ACL 은 **들어오는 규칙과 나가는 규칙을 양쪽 다 명시적으로 써야** 합니다.
인바운드만 열어 두면 응답이 나가지 못해 통신이 되지 않습니다.
`인바운드는 열었는데 응답이 돌아오지 않는다` 는 지문은 거의 언제나 네트워크 ACL 의 아웃바운드 규칙 이야기입니다.

#### 규칙을 쓰는 방식도 다릅니다

| | 보안 그룹 | 네트워크 ACL |
|---|---|---|
| 허용 · 거부 | **허용만 있습니다.** 규칙에 없으면 막힙니다 | **허용과 거부를 둘 다** 씁니다 |
| 평가 순서 | 모든 규칙을 함께 봅니다 | **번호가 낮은 것부터** 순서대로 보고 **처음 일치한 규칙**을 적용합니다 |
| 기본값 | 인바운드는 전부 막히고, 아웃바운드는 전부 열려 있습니다 | 기본 네트워크 ACL 은 양방향 모두 허용입니다 |
| 대상 지정 | CIDR 뿐 아니라 **다른 보안 그룹 자체**를 지정할 수 있습니다 | CIDR 로만 지정합니다 |

**특정 주소를 막아야 한다면 네트워크 ACL 입니다.** 보안 그룹에는 거부 규칙이 아예 없기 때문입니다.

반대로 **웹 계층만 DB 계층에 닿게 하라** 는 요구는 보안 그룹 쪽이 깔끔합니다.
DB 보안 그룹의 인바운드 소스에 **웹 서버의 보안 그룹을 그대로 적어 두면** 인스턴스가 늘거나 주소가 바뀌어도 규칙을 고칠 일이 없습니다.

#### ENI — 인스턴스에 꽂는 네트워크 카드

**ENI** 는 가상의 네트워크 인터페이스 카드입니다. 보안 그룹이 실제로 붙는 자리가 바로 이 ENI 이고, 인스턴스 하나에 여러 개를 꽂을 수도 있습니다.
`L5` 에서 볼 **인터페이스 엔드포인트**가 VPC 안에 프라이빗 주소를 갖는 것도 이 ENI 를 쓰기 때문입니다.

보안 관점에서 두 방화벽을 정리한 내용은 [[02-secure-workloads\|1.2 안전한 워크로드 및 애플리케이션 설계]] 에 있습니다.
여기서는 **성능·구조 문항을 읽을 때 어느 경계에 걸리는지**만 잡고 가시면 됩니다.

### L5. VPC 를 바깥과 잇는 방법들

> **이번 강의에서 다룰 내용** — 인터넷을 타지 않고 다른 VPC · AWS 서비스 · 온프레미스에 닿는 길들을 살펴보겠습니다.

#### VPC 피어링 — 둘씩 잇습니다

VPC 두 개를 **일대일**로 잇습니다. 붙고 나면 양쪽이 서로의 프라이빗 주소로 통신합니다. 두 가지를 기억하시기 바랍니다.

- **CIDR 블록이 겹치면 연결되지 않습니다**
- **전이되지 않습니다.** A–B 를 잇고 B–C 를 이어도 **A 와 C 는 통하지 않습니다.** A–C 를 따로 이어야 합니다

그래서 VPC 가 늘어날수록 이어야 할 짝의 수가 급격히 불어납니다. 이 문제를 푸는 것이 다음의 Transit Gateway 입니다.

#### Transit Gateway — 허브 하나에 전부 물립니다

VPC 마다 서로 이어 그물을 만드는 대신, **허브를 하나 두고 각자 거기에 한 번씩만 붙입니다.**
VPC 뿐 아니라 VPN 연결과 Direct Connect 도 같은 허브에 물릴 수 있어 연결 관리가 한 자리로 모이고, 수천 개 규모의 VPC 까지 붙습니다.
`VPC 가 계속 늘어난다` · `피어링 연결이 너무 많아졌다` 는 지문의 답은 언제나 이쪽입니다.

#### VPC 엔드포인트 — 인터넷을 아예 타지 않습니다

프라이빗 서브넷의 인스턴스가 S3 를 읽으려면 원래는 NAT 게이트웨이를 거쳐 인터넷으로 나갔다가 다시 들어와야 합니다.
같은 AWS 안에 있는 서비스를 부르는데 바깥으로 한 바퀴 도는 셈입니다.

**VPC 엔드포인트**는 이 경로를 없앱니다. 두 종류가 있고, **붙는 방식이 다릅니다.**

| | 어떻게 붙나 | 어디에 쓰나 |
|---|---|---|
| **게이트웨이 엔드포인트** | **라우팅 테이블에 경로를 한 줄 추가**하는 방식입니다 | **S3 와 DynamoDB** 입니다 |
| **인터페이스 엔드포인트** | 서브넷 안에 **ENI 를 만들고 프라이빗 IP 를 붙입니다** | 그 밖의 많은 AWS 서비스, 그리고 **남의 VPC 에 있는 서비스** |

인터페이스 엔드포인트를 뒤에서 가능하게 하는 것이 [[aws-privatelink\|PrivateLink]] 입니다.
네트워크 전체를 잇는 것이 아니라 **서비스 하나만** 여는 방식이라, 인터넷 게이트웨이도 NAT 게이트웨이도 피어링도 없이 여러 VPC 에 같은 서비스를 열어 줄 수 있습니다.

**게이트웨이 엔드포인트는 AWS 퍼블릭 영역용**입니다. S3 와 DynamoDB 처럼 퍼블릭 영역에 사는 서비스에,
인터넷도 NAT 게이트웨이도 없는 프라이빗 서브넷에서 닿게 해 줍니다.

#### 온프레미스와 잇기 — 인터넷 위인가 전용선인가

**Site-to-Site VPN** 은 **기존 인터넷 위에 암호화된 터널**을 뚫는 방식입니다.
회선을 새로 깔지 않으므로 빠르게 붙지만, 속도가 그날의 인터넷 사정에 좌우됩니다.
사용자 기기를 하나씩 임시로 붙이는 **Client VPN** 은 성격이 다른 별개 서비스라는 것도 함께 구분해 두시기 바랍니다.

**Direct Connect** 는 통신 사업자나 AWS 파트너를 통해 **물리적인 전용 회선**을 까는 방식입니다.
대역폭과 지연이 일정하지만 준비에 시간이 걸립니다.
회선을 깐 뒤 실제로 트래픽을 태우려면 **가상 인터페이스(VIF)** 를 만들어야 하고, 붙일 대상에 따라 퍼블릭 · 프라이빗 · 전송 VIF 로 갈립니다.

| | 성격 |
|---|---|
| **Site-to-Site VPN** | 인터넷 위. 몇 시간이면 깔린다. 대역폭이 인터넷에 좌우된다 |
| **Direct Connect** | 전용 회선. **일관된 대역폭과 지연**. 준비에 몇 주~몇 달 |
| **Direct Connect + VPN 백업** | DX 가 끊겼을 때를 대비. `복원력` 이 붙으면 이 조합 |

> `안정적이고 일관된 성능` · `대용량을 매일 전송` → **Direct Connect**
> `빠르게 연결해야` · `비용이 우선` → **VPN**

#### 연결을 잇는 다섯 갈래와 각각의 자리

| | 무엇을 잇나 |
|---|---|
| **VPC 피어링** | VPC 둘을 일대일로. 개수가 늘수록 관리할 연결이 급격히 늘어납니다 |
| [[aws-transit-gateway\|Transit Gateway]] | 허브 하나에 VPC · VPN · Direct Connect 를 모두 물립니다. **피어링 그물을 없애는 답** |
| **Direct Connect 게이트웨이** | 전용선 하나로 여러 리전의 여러 VPC 에 닿습니다 |
| [[aws-privatelink\|PrivateLink]] · VPC 엔드포인트 | 네트워크 전체가 아니라 **서비스 하나**만. 인터넷 게이트웨이도 NAT 도 피어링도 없이 수십·수백 개 VPC 에 엽니다 |
| **AWS CloudHub** | VPN 여러 개를 허브 앤 스포크로 묶어 지점끼리도 통하게 합니다. 개략적으로만 알아 두시면 됩니다 |

### L6. 사용자 가까이로 — Route 53 · CloudFront · Global Accelerator

> **이번 강의에서 다룰 내용** — 지연 시간을 줄이는 세 가지 길이 각각 어디서 무슨 일을 하는지 살펴보겠습니다. 이 과제에서 가장 많이 갈리는 자리입니다.

#### Route 53 — 이름을 물었을 때 무엇을 돌려줄 것인가

Route 53 은 DNS 서비스입니다. 그런데 시험이 묻는 것은 "이름을 주소로 바꿔 준다"가 아니라 **여러 후보 중 무엇을 돌려줄 것인가**입니다.
그 판단 기준이 **라우팅 정책**이고, 여기에 **상태 확인**이 붙으면 죽은 엔드포인트를 답에서 빼 줍니다.
DNS 이면서 동시에 리전 수준의 고가용성 장치이기도 하다는 뜻입니다.

**Route 53 라우팅 정책**

| | 언제 |
|---|---|
| **단순** | 하나뿐 |
| **가중치** | `트래픽의 10%만 새 버전으로` — 카나리 배포 |
| **지연 시간** | `가장 빠른 리전으로` |
| **장애 조치** | `주 사이트가 죽으면 대기 사이트로` |
| **지리 위치** | `국가별로 다른 콘텐츠` · 규정 준수 |
| **지리 근접** | 리소스 위치 기준 + 편향치 조정 |
| **IP 기반** | 사용자 IP 대역을 알고 있을 때 대역별로 |
| **다중값 응답** | 여러 IP 를 돌려주고 상태 확인까지 |

`가장 낮은 지연 시간` 은 **지연 시간 기반**, `한국 사용자는 한국 법을 따라야` 는 **지리 위치**입니다. 헷갈리기 쉽습니다.

**장애 조치**는 평소에 주 엔드포인트로 보내다가 상태 확인이 실패하면 대기 엔드포인트로 넘기는 구조이고,
**다중값 응답**은 정상인 주소 여러 개를 한꺼번에 돌려주는 구조입니다. 로드 밸런서를 두지 않고도 트래픽이 갈라진다는 점이 다릅니다.

#### CloudFront — 엣지에 복사본을 둡니다

전 세계에 흩어진 **엣지 로케이션**에 콘텐츠의 사본을 두고, 사용자 요청을 **가장 가까운 엣지**로 보냅니다. 동작은 두 갈래입니다.

| | 무슨 일이 일어나나 |
|---|---|
| **캐시 히트** | 그 엣지에 이미 사본이 있습니다. **오리진까지 가지 않고** 바로 응답합니다 |
| **캐시 미스** | 사본이 없습니다. 오리진에서 받아 사용자에게 주고, **그 엣지에 저장해 둡니다** |

원본을 들고 있는 쪽을 **오리진**이라고 부릅니다. S3 버킷 · EC2 인스턴스 · 로드 밸런서는 물론 AWS 밖의 서버도 오리진이 될 수 있습니다.
캐시가 먹히는 만큼 오리진에 닿는 요청이 줄어, **응답이 빨라지는 동시에 오리진 부하와 전송량이 함께 내려갑니다.**

바꾼 파일이 엣지의 낡은 사본 때문에 안 보이는 문제를 푸는 것이 **객체 무효화**입니다. 방법은 넷입니다.

| 방법 | 어떻게 |
|---|---|
| **TTL 만료** | 캐시 보관 시간을 짧게 두어 저절로 만료되게 합니다 |
| **헤더 사용** | 헤더로 바뀐 파일만 다시 가져오게 합니다 |
| **객체 이름 변경** | 아예 다른 이름으로 올려 새 객체로 만듭니다 |
| **명시적 무효화** | 특정 객체를 지금 지우라고 요청합니다 |

CloudFront 에는 [[aws-shield\|Shield]] 와 [[aws-waf\|WAF]] 를 붙일 수 있고, **지리적 제한**으로 특정 국가에만 콘텐츠를 열어 줄 수도 있습니다.

#### Global Accelerator — 캐시하지 않고 길만 바꿉니다

먼 곳의 서버로 갈수록 거쳐야 할 네트워크 장비가 많아지고, 그만큼 느려지고 흔들립니다.
**Global Accelerator** 는 사용자를 가까운 엣지에서 받아 그때부터 **AWS 백본**으로 태워 보냅니다.
콘텐츠를 저장하지 않으므로 **캐시 서비스가 아닙니다.**

그리고 **고정 애니캐스트 IP 두 개**를 받습니다. 클라이언트는 늘 같은 주소만 보고,
그 뒤에서 어느 리전으로 보낼지는 서비스가 정합니다. 그래서 리전을 넘기는 전환이 DNS 를 기다리지 않고 이루어집니다.

**CloudFront vs Global Accelerator — 여기서 가장 많이 갈립니다**

| | CloudFront | Global Accelerator |
|---|---|---|
| 하는 일 | 엣지에 **캐시**한다 | 엣지에서 **AWS 백본**으로 태워 보낸다 |
| 프로토콜 | HTTP/HTTPS | **TCP · UDP 전부** |
| IP | 도메인 이름 | **고정 애니캐스트 IP 2개** |
| 언제 | 정적 자산 · 동영상 · 웹 | 게임 · VoIP · IoT · **캐시할 수 없는** 트래픽 |
| 장애 조치 | 오리진 장애 조치 | **초 단위 리전 전환** |

`고정 IP 가 필요` 나 `UDP` 가 보이면 CloudFront 는 탈락입니다.
`이미지와 동영상` 이 보이면 Global Accelerator 가 아닙니다.

**AWS 가 예로 든 글로벌 서버리스 구성**

`전 세계 사용자 · 매우 큰 볼륨 · 비용은 최소` 라는 조건에 AWS 가 내놓은 답을 그대로 옮기면 이렇습니다.

- 정적 콘텐츠는 **S3 정적 웹사이트 호스팅**으로 내보냅니다
- Route 53 의 **지연 시간 기반 + 장애 조치** 라우팅으로 가까운 리전에 붙이고, 죽으면 넘깁니다
- 데이터는 **DynamoDB 글로벌 테이블**로 리전 간에 복제합니다

여기서 더 개선하라고 하면 답은 둘입니다. 앞에 **CloudFront** 를 두어 캐시 · 성능 · 보안을 한꺼번에 올리거나,
**Global Accelerator 의 S3 다중 리전 액세스 포인트**로 여러 리전의 버킷을 하나의 엔드포인트로 묶는 것입니다.

---

### L7. 흐름을 나누고 VPC 안의 성능을 올립니다

> **이번 강의에서 다룰 내용** — 로드 밸런서를 계층으로 고르는 법과, VPC 안쪽에서 성능을 끌어올리는 수단들을 살펴보겠습니다.

#### 로드 밸런서는 OSI 계층으로 외웁니다

AWS 가 이 과제에서 시험 요령으로 직접 짚어 준 항목입니다.
각 로드 밸런서가 **몇 계층에서 판단하는지**를 알면 지문의 표현이 그대로 답으로 이어집니다.

| | 계층 | 무엇을 보고 나누나 |
|---|---|---|
| **ALB** | 7 (애플리케이션) | URL 경로 · 호스트 · 헤더 |
| **NLB** | 4 (전송) | TCP · UDP 포트. 내용은 보지 않습니다 |
| **GWLB** | 3 (네트워크) | IP 패킷을 통째로 어플라이언스에 넘깁니다 |

**계층이 높을수록 내용을 깊이 들여다보고, 낮을수록 빠릅니다.** ALB 가 경로와 헤더로 나눌 수 있는 것은 7계층까지 열어 보기 때문이고,
NLB 가 초저지연을 낼 수 있는 것은 주소와 포트만 보고 넘기기 때문입니다.

Auto Scaling 과 묶을 때는 **최소 · 최대 · 원하는 용량**과 조정 정책을 정하고,
로드 밸런서의 상태 확인을 함께 걸어 **죽은 인스턴스를 트래픽에서 빼는 것**까지가 한 세트입니다.
[[amazon-route-53\|Route 53]] 의 DNS 상태 확인은 **퍼블릭으로 라우팅되는 엔드포인트에만** 직접 걸 수 있고,
프라이빗 주소는 **CloudWatch 경보를 감시하는 상태 확인**으로 대신합니다.
어느 쪽이든 정상인 엔드포인트로만 트래픽을 보내게 합니다.

#### VPC 안의 성능

- **향상된 네트워킹(ENA)** · **Elastic Fabric Adapter(EFA)** — HPC 노드 간 통신
- **클러스터 배치 그룹** — 같은 랙에 몰아 지연 최소화
- **VPC 엔드포인트** — 인터넷을 안 타면 지연도 줄고 비용도 준다

> [!info] 도메인 3 의 추가 자료가 가리키는 곳
> AWS 는 이 과제의 추가 자료로 **Route 53 Resolver DNS 방화벽**,
> [[aws-network-firewall\|AWS Network Firewall]] 로 네트워크 트래픽을 거르는 방법, 그리고 VPC 시나리오 모음을 함께 걸어 두었습니다.
> 성능 문항의 정답이 되는 일은 드물지만, `VPC 를 나가는 DNS 질의를 걸러야` 는 **DNS 방화벽**,
> `VPC 경계에서 트래픽을 검사하고 필터링` 은 **Network Firewall** 이라는 것만 짚고 넘어가시기 바랍니다.

## 4. 시험에서 갈리는 지점

| 지문에 이게 있으면 | 이쪽 |
|---|---|
| `전 세계 사용자에게 이미지·동영상` | **CloudFront** |
| `고정 IP` · `UDP` · `게임 서버` | **Global Accelerator** |
| `가장 빠른 리전으로 보낸다` | Route 53 **지연 시간 기반** |
| `국가별로 다르게` | Route 53 **지리 위치** |
| `새 버전에 10%만` | Route 53 **가중치** |
| `주 사이트 장애 시 자동 전환` | Route 53 **장애 조치** + 상태 확인 |
| `일관된 대역폭` · `매일 대용량 전송` | **Direct Connect** |
| `며칠 안에 연결해야` | **Site-to-Site VPN** |
| `VPC 가 계속 늘어난다` | **Transit Gateway** |
| `HPC 노드 간 통신` | **EFA + 클러스터 배치 그룹** |
| `S3 접근이 NAT 게이트웨이를 거쳐 느리고 비싸다` | **Gateway 엔드포인트** |
| `HTTP 헤더·경로를 보고 나눈다` / `TCP 포트만 본다` | **ALB(7계층)** / **NLB(4계층)** — GWLB 는 3계층 |
| `전용선 하나로 여러 리전의 VPC 에` | **Direct Connect 게이트웨이** |
| `여러 리전의 S3 버킷을 하나의 엔드포인트로` | **Global Accelerator + S3 다중 리전 액세스 포인트** |
| `VPC 경계에서 트래픽을 검사·필터링` | **AWS Network Firewall** |
| `여러 지점의 VPN 을 서로 통하게` | **AWS CloudHub** |

> [!tip] "지연 시간" 과 "처리량" 은 다른 요구입니다
> 지연 시간 → 가까이 두거나 경로를 좋게. 처리량 → 대역폭을 늘리거나 병렬로.
> 지문이 `응답이 느리다` 인지 `전송이 오래 걸린다` 인지 구분하면 답이 갈립니다.

## 6. 셀프 체크

- [ ] CloudFront 와 Global Accelerator 를 가르는 신호를 두 개 댄다
- [ ] Route 53 라우팅 정책 여덟 개 중 다섯 개의 용도를 말한다
- [ ] Direct Connect 를 못 쓰는 상황(시간이 없을 때)의 대안을 안다
- [ ] `복원력 있는 온프레미스 연결` 의 정답 조합을 말한다
- [ ] 지연 시간을 줄이는 세 가지 접근을 구분한다
- [ ] ALB · NLB · GWLB 가 각각 OSI 몇 계층에서 판단하는지 말한다
- [ ] VPC 를 서로 잇는 방법을 세 가지 대고 언제 어느 것인지 구분한다
