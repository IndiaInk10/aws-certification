> 도메인 3 · 고성능 아키텍처 설계 **24%** · 과제 명세 5개 중 **다섯 번째**

## 1. 왜 필요한가

> 실제 시험에 **EMR 과 EMR 클러스터**가 나왔다는 보고가 있습니다. 분석 서비스는 이름만 알아서는 안 됩니다.

이 과제는 데이터가 **들어와서 · 쌓이고 · 바뀌고 · 조회되는** 한 줄기를 묻습니다.
서비스 이름은 많지만 판단은 두 축으로 정리됩니다.

- **실시간인가 배치인가**
- **코드를 쓸 것인가, 그냥 흘려보낼 것인가**

이 두 축만 잡으면 Kinesis Data Streams / Data Firehose / Glue / EMR / Athena 가 제자리를 찾습니다.

## 2. 이번에 새로 나오는 서비스

| 서비스 | 한 줄 | 이 과제에서 맡는 역할 |
|---|---|---|
| [[amazon-kinesis\|Amazon Kinesis]] | 실시간 스트림 수집 | Data Streams · Data Firehose 로 갈린다 |
| [[amazon-emr\|Amazon EMR]] | 관리형 Hadoop · Spark | **클러스터 구성까지 물어본다** |
| [[aws-glue\|AWS Glue]] | 서버리스 ETL + 데이터 카탈로그 | 코드 없이 변환 |
| [[amazon-athena\|Amazon Athena]] | S3 에 SQL 을 그대로 | 서버 없는 조회 |
| [[amazon-redshift\|Amazon Redshift]] | 데이터 웨어하우스 | 대규모 집계·BI |
| [[amazon-opensearch-service\|Amazon OpenSearch]] | 검색·로그 분석 | 로그를 찾아 봐야 할 때 |
| [[amazon-quick-sight\|Amazon Quick Sight]] | 대시보드 | 마지막 시각화 |
| [[aws-datasync\|AWS DataSync]] | 대량 파일 전송 자동화 | 온프레미스 데이터 유입 |
| [[aws-lambda\|AWS Lambda]] | 서버 없이 코드 실행 | 가벼운 변환 |

## 3. 이 과제가 묻는 것

> [!tip] 이 과제를 관통하는 한 줄
> 서비스 이름이 아홉 개나 나오지만 이들은 **자리를 다투는 후보가 아니라 서로 다른 층**입니다.
> 데이터가 **들어오고 · 쌓이고 · 바뀌고 · 조회되는** 네 층 가운데 지문이 어느 층을 말하는지부터 잡으시면
> 후보가 두세 개로 줄어듭니다.

**한 줄기로 보면 이렇습니다**

```d2
direction: right

src: "데이터 원천\n(앱 · IoT · 로그 · 온프레미스)"
ingest: "수집\nKinesis · DataSync"
lake: "S3 데이터 레이크"
etl: "변환\nGlue · EMR · Lambda"
query: "조회\nAthena · Redshift · OpenSearch"
viz: "Quick Sight"

src -> ingest -> lake -> etl -> lake
lake -> query -> viz
```

### L1. 데이터 수집이란 무엇인가 — 배치와 스트리밍이 갈리는 지점

> **이번 강의에서 다룰 내용** — AWS 가 말하는 "수집"이 어디까지를 가리키는지, 그리고 같은 데이터를 두고 배치와 스트리밍이 어디에서 갈리는지 살펴보겠습니다.

#### 수집은 "가져오는 일"이 아니라 "쓸 수 있게 만드는 일"입니다

AWS 는 데이터 수집을 단순히 "가져오는 일"이 아니라
**소스에서 모아 · 다듬어 · 쓸 수 있게 준비하는 과정 전체**로 봅니다.
그래서 이 과제의 문항은 "무엇으로 옮길까요" 로 끝나지 않고, 옮긴 뒤에 그 데이터가
**분석이나 머신러닝에 바로 쓸 수 있는 모양인지**까지 함께 묻습니다.

무엇으로 옮길지를 고를 때 근거가 되는 요구 사항은 다섯 가지입니다 —
**성능 · 지연 시간 · 규모 · 보안 · 거버넌스**.
지문은 이 중 하나를 반드시 못 박아 두고, 그것이 답을 가르는 조건이 됩니다.

#### 배치와 스트리밍은 "값이 언제 생기는가"에서 갈립니다

두 방식의 차이를 "빠르냐 느리냐"로만 외우시면 지문을 놓칩니다.
실제로 갈리는 지점은 **그 데이터가 언제 가장 값어치가 있는가** 입니다.

**배치 수집**은 일정 기간 모아 두었다가 묶음 단위로 한 번에 처리합니다.
처리 단위가 묶음이므로 결과도 묶음이 끝나야 나옵니다.
어제 하루치 매출을 오늘 아침에 집계하는 일에서는 이 지연이 아무 문제가 되지 않습니다.

**스트리밍 수집**은 레코드 하나가 도착하는 즉시 흘려보내며 처리합니다.
결제 이상 탐지나 기기 고장 감지처럼 **1분 뒤에 알면 이미 늦는** 데이터가 여기에 해당합니다.

| 무엇을 보나 | 배치 | 스트리밍 |
|---|---|---|
| **데이터가 도착하는 모양** | 파일·테이블처럼 뭉쳐서 | 레코드 하나씩 끊임없이 |
| **값이 가장 큰 시점** | 모아서 볼 때 (일·시간 단위 집계) | 도착한 직후 (탐지 · 알림 · 실시간 대시보드) |
| **허용되는 지연** | 분 · 시간 · 일 | 초 이하 |
| **실패했을 때** | 그 묶음을 통째로 다시 돌립니다 | 스트림에 남아 있어야 다시 읽습니다 |
| **지문의 신호** | `매일 밤` · `한 번에 옮긴다` · `주기적으로` | `실시간` · `초당 수십만 이벤트` · `즉시 감지` |

> [!info] 둘은 배타적이지 않습니다
> 실시간으로 받아 두고 나중에 배치로 다시 집계하는 구성이 오히려 일반적입니다.
> 문항이 물어보는 것은 "둘 중 하나만 고르라"가 아니라 **지금 이 요구 사항이 어느 쪽 지연을 견디는가** 입니다.

#### 형식을 그대로 옮기는가, 바꿔서 넣는가

같은 "수집"이라도 목적지에 넣을 때 형식을 손대느냐 마느냐로 패턴이 둘로 갈립니다.

| | 무엇이 다른가 | 초점 |
|---|---|---|
| **동종(homogeneous)** | 소스와 **같은 형식 · 같은 스토리지 엔진**으로 그대로 옮깁니다 | 옮기는 일을 **자동화**해서 계속 돌게 하는 것 |
| **이기종(heterogeneous)** | 대상에 맞게 **데이터 유형과 형식을 바꿔서** 넣습니다 | 변환. 또는 머신러닝으로 **새 속성을 뽑아내는 것** |

`빈도` 도 함께 봅니다 — **일회성**인가 **계속**인가.
한 번에 대량이면 [[aws-snow-family\|Snow Family]] 쪽이고, 계속 흘러 들어오면 스트리밍이나
[[aws-datasync\|DataSync]] 의 예약 동기화 쪽입니다.

### L2. 스트리밍 수집 — 샤드와 보존이 정하는 것

> **이번 강의에서 다룰 내용** — 스트림이 데이터를 어떤 모양으로 들고 있는지, 그리고 샤드와 보존 기간이 각각 무엇을 결정하는지 살펴보겠습니다.

#### 스트림은 "읽어도 사라지지 않는 대기열"입니다

스트림에는 **생산자**와 **소비자**가 있습니다.
생산자가 **레코드**라는 단위로 데이터를 밀어 넣고, 소비자가 그것을 읽어 갑니다.
여기까지는 [[amazon-sqs\|SQS]] 같은 큐와 같아 보이지만 결정적인 차이가 하나 있습니다.

**큐는 읽으면 사라지고, 스트림은 읽어도 남습니다.**
큐의 메시지는 처리한 소비자 하나로 끝나지만, 스트림의 레코드는 정해진 기간 동안 그 자리에 남아 있고
소비자들은 각자 "내가 어디까지 읽었는지"를 따로 들고 읽어 갑니다.
그래서 `여러 애플리케이션이 같은 데이터를 각자 다르게 처리한다` 는 지문이 스트림 신호가 됩니다.

#### 샤드가 정하는 것은 세 가지입니다

**샤드**는 스트림을 세로로 쪼갠 한 줄기입니다. 서버가 아니라 **용량이자 병렬 처리의 단위**입니다.

| 샤드가 정하는 것 | 뜻 |
|---|---|
| **처리량** | 스트림 전체 용량은 `샤드 하나의 용량 × 샤드 수` 입니다. 밀리면 샤드를 늘립니다 |
| **병렬성** | 한 샤드는 한 소비자가 순서대로 읽습니다. 읽는 속도를 올리려면 샤드를 늘려 나눠 읽습니다 |
| **순서** | 순서는 **샤드 안에서만** 보장됩니다. 스트림 전체의 순서는 보장되지 않습니다 |

레코드가 어느 샤드로 갈지는 레코드마다 붙이는 **파티션 키**가 정합니다.
같은 키는 항상 같은 샤드로 가므로, 기기별로 순서를 지켜야 한다면 기기 식별자를 파티션 키로 씁니다.
반대로 키가 한쪽으로 몰리면 그 샤드만 한계에 부딪히는 **핫 샤드**가 됩니다.
`특정 키에 트래픽이 몰려 제한에 걸린다` 는 지문은 파티션 키를 다시 고르라는 뜻입니다.

> [!warning] "샤드를 늘린다" 와 "소비자를 늘린다" 는 다른 처방입니다
> 스트림 쪽에서 요청이 제한되고 있다면 답은 **샤드를 늘리는 것**입니다.
> 소비자 코드가 느려서 처리가 밀리는 것이라면 샤드를 늘려도 그대로입니다.
> 어느 쪽이 막혔는지를 지문에서 먼저 확인하시기 바랍니다.

#### 보존이 있고 없고가 재처리 가능 여부를 가릅니다

**보존 기간**은 읽힌 뒤에도 레코드를 스트림에 남겨 두는 기간입니다. 이 한 가지가 아래를 전부 결정합니다.

| 보존이 있으면 | 보존이 없으면 |
|---|---|
| 소비자가 멈췄다 살아나 **멈춘 지점부터** 다시 읽습니다 | 멈춰 있는 동안 흘러간 것은 스트림에서 찾을 수 없습니다 |
| 처리 로직의 버그를 고친 뒤 **처음부터 되감아** 다시 돌립니다 | 목적지에 이미 적재된 결과물을 손보는 수밖에 없습니다 |
| 나중에 붙인 두 번째 소비자가 **과거분부터** 읽습니다 | 새 소비자는 붙은 시점 이후만 봅니다 |

`재처리` · `되감기` · `나중에 소비자를 하나 더 붙인다` 가 지문에 있으면 **보존이 있는 쪽**입니다.
반대로 `받아서 그냥 S3 에 넣어 두면 된다` 면 보존이 필요 없는 적재 전용 경로입니다.

#### 두 갈래 — 가장 자주 갈리는 곳

| | Kinesis Data Streams | Amazon Data Firehose |
|---|---|---|
| 성격 | 스트림을 **보관**하고 여러 소비자가 각자 읽는다 | 받은 것을 목적지로 **흘려보낸다** |
| 코드 | 소비자 코드를 내가 쓴다 | 없다 (완전관리형) |
| 지연 | 실시간(200ms 내외) | 거의 실시간(버퍼링, 0~900초 사이로 잡습니다) |
| 보관 | 최대 365일 재생 가능 | 보관하지 않는다 |
| 확장 | 샤드를 내가 관리 | 자동 |
| 신호 | `여러 애플리케이션이 같은 스트림을` · `재처리` | `S3·Redshift 로 그냥 넣어라` · `운영 오버헤드 최소` |

#### 스트리밍 제품군은 둘이 아니라 넷입니다

| | 하는 일 |
|---|---|
| **Kinesis Data Streams** | 생산자가 **레코드**를 스트림에 직접 밀어 넣고, 소비자들이 각자 읽어 갑니다 |
| **Amazon Data Firehose** | 받은 것을 AWS 데이터 스토어로 **적재**합니다. 가장 손이 덜 가는 길입니다 |
| **Managed Service for Apache Flink** | 흐르는 스트림 위에서 **기본 변환과 집계**를 겁니다. `기본 데이터 변환 옵션이 있는 Kinesis 솔루션` 은 이것입니다 |
| **Kinesis Video Streams** | 스트리밍 **동영상**을 수집합니다 |

> [!info] 이름이 바뀐 두 서비스
> **Amazon Data Firehose** 는 예전 이름이 Kinesis Data Firehose 이고,
> **Managed Service for Apache Flink** 는 예전 이름이 Kinesis Data Analytics 입니다.
> 기출과 강의 자료에는 옛 이름으로 남아 있는 경우가 많으니 **같은 것**으로 알아보시기 바랍니다.

**Amazon MSK(Managed Streaming for Apache Kafka)** 도 같은 자리에 섭니다.
`이미 Kafka 로 되어 있다` · `Kafka API 를 그대로 써야 한다` 가 지문에 있으면 Kinesis 가 아니라 MSK 입니다.

### L3. 적재 · 처리 · 조회는 서로 다른 층입니다

> **이번 강의에서 다룰 내용** — 이름이 비슷해 헷갈리는 세 서비스가 왜 서로 대체재가 아닌지 짚어 보겠습니다.

#### 세 층은 하는 일이 겹치지 않습니다

| 층 | 하는 일 | 대표 | 이 층이 빠지면 |
|---|---|---|---|
| **적재** | 받은 것을 목적지에 **써 넣습니다** | Amazon Data Firehose | 데이터가 쌓이지 않습니다 |
| **처리** | 흐르는 중에 **계산합니다** | Managed Service for Apache Flink | 값이 나오지 않습니다 |
| **조회** | 이미 쌓인 것을 **읽습니다** | [[amazon-athena\|Athena]] | 볼 수가 없습니다 |

**적재 층은 버퍼로 움직입니다.**
도착한 레코드를 정해진 크기나 정해진 시간만큼 모았다가 한 번에 씁니다.
그래서 "실시간"이 아니라 "거의 실시간"이고, 지연에 하한이 생깁니다.
버퍼를 짧게 잡으면 지연은 줄지만 작은 객체가 잔뜩 생겨 뒤쪽 처리가 무거워집니다 — 그 부담은 `L5` 에서 다시 보겠습니다.

**처리 층에는 "구간"이 필요합니다.**
흐르는 데이터에는 끝이 없으므로, 합계나 평균을 내려면 **어디부터 어디까지를 셀 것인지**를 사람이 정해 줘야 합니다.
그 구간이 **윈도**입니다. `최근 5분` · `1분마다 지난 10분` 같은 식으로 잡습니다.
끝이 있는 테이블에 SQL 을 던지는 일과 결정적으로 다른 점이 이것입니다.

**조회 층은 지나간 것만 봅니다.**
이미 저장된 데이터를 읽는 자리라서, 지금 이 순간 흐르고 있는 데이터에 대해서는 답을 낼 수 없습니다.

> [!warning] 층을 바꿔 놓은 보기가 자주 나옵니다
> `실시간 이상 탐지` 가 요구인데 조회 도구로 답하거나, `S3 에 적재만 하면 된다` 인데 스트림 처리 애플리케이션을 세우는 보기입니다.
> 지문이 요구하는 층과 보기의 층이 다르면 나머지가 아무리 그럴듯해도 오답입니다.

### L4. ETL 과 데이터 카탈로그

> **이번 강의에서 다룰 내용** — 변환이 왜 필요한지, 그리고 변환해 둔 결과를 조회 도구가 어떻게 찾아내는지 살펴보겠습니다.

#### ETL 세 글자

**추출(Extract) · 변환(Transform) · 적재(Load)** 의 앞 글자입니다.
소스에서 꺼내고, 쓸 수 있는 모양으로 바꾸고, 목적지에 넣는 세 단계를 거칩니다.

가운데 **변환**에서 실제로 하는 일은 이런 것들입니다.

- 소스마다 제각각인 **형식을 하나로** 맞춥니다
- 컬럼 이름과 데이터 타입을 정리하고, 날짜 표기처럼 어긋난 것을 통일합니다
- 비어 있거나 깨진 레코드를 걸러 냅니다
- 여러 소스에서 온 것을 **하나의 표로 합칩니다**
- 조회에 유리한 **열 기반 포맷**으로 다시 씁니다

순서를 바꿔 **먼저 적재하고 목적지 안에서 변환**하는 방식은 **ELT** 라고 부릅니다.
목적지의 계산 능력이 충분할 때 쓰는 방식이고, 데이터 레이크와 궁합이 좋습니다.

#### 데이터 카탈로그 — 어디에 무엇이 어떤 모양으로 있는지 적어 둔 장부

여기가 이 과제에서 가장 자주 빠뜨리는 개념입니다.

[[amazon-s3\|S3]] 는 **파일을 담을 뿐, 그 안에 어떤 컬럼이 어떤 타입으로 들어 있는지 모릅니다.**
그것을 따로 적어 두는 곳이 **데이터 카탈로그**입니다. 적히는 내용은 이렇습니다.

| 카탈로그가 들고 있는 것 | 예 |
|---|---|
| 논리적인 데이터베이스와 **테이블** 이름 | `sales.orders` |
| **컬럼과 타입** | `order_id: string` · `amount: double` |
| **저장 위치** | `s3://버킷/orders/` |
| **포맷** | Parquet · CSV · JSON |
| **파티션** | `year=2026/month=03/` |

이 표를 사람이 손으로 채울 수도 있지만, **크롤러**를 돌리면 S3 를 훑어 스키마를 추론해 대신 채워 줍니다.

카탈로그가 있어야 [[amazon-athena\|Athena]] 가 S3 의 파일에 `SELECT` 를 던질 수 있고,
[[amazon-emr\|EMR]] 이나 [[amazon-redshift\|Redshift]] 도 **같은 정의를 공유**해 같은 데이터를 같은 이름으로 봅니다.

> [!tip] ETL 과 카탈로그의 관계를 한 문장으로
> **ETL 은 데이터를 바꾸는 일이고, 카탈로그는 바뀐 결과가 어디에 어떤 모양으로 놓였는지 적어 두는 일입니다.**
> [[aws-glue\|Glue]] 가 이 과제에서 자주 정답이 되는 이유는 **둘을 한 서비스 안에 함께** 가지고 있기 때문입니다.
> 변환만 물어보는 것 같아도 "그다음 조회까지 이어져야 한다"는 조건이 붙어 있으면 Glue 쪽입니다.

#### EMR vs Glue vs Athena

| | 언제 |
|---|---|
| **EMR** | `Hadoop` · `Spark` · `HBase` 를 **그대로** 써야 할 때. 클러스터를 내가 통제한다 |
| **Glue** | 서버리스 ETL. `운영 오버헤드 최소` + 변환 |
| **Athena** | 변환 없이 **S3 를 바로 조회**. 가끔 쓰는 임시 쿼리에 가장 싸다 |

`기존 Spark 작업을 옮긴다` → EMR. `ETL 인프라를 관리하고 싶지 않다` → Glue.
`데이터를 옮기지 않고 그냥 SQL 로 보고 싶다` → Athena.

### L5. 데이터 레이크가 푸는 문제

> **이번 강의에서 다룰 내용** — 데이터를 한곳에 모아 두는 것이 왜 설계 문제가 되는지, 그리고 그 위에서 성능과 비용이 어디서 갈리는지 살펴보겠습니다.

#### 데이터가 시스템마다 흩어져 있으면 생기는 일

레이크가 무엇인지보다 **레이크가 없을 때 무엇이 문제인지**를 먼저 보시는 편이 오래 남습니다.

- **사본이 늘어납니다.** 팀마다 필요한 데이터를 자기 쪽으로 복사해 가고, 시간이 지나면 어느 것이 맞는 값인지 아무도 모르게 됩니다
- **권한이 흩어집니다.** 누가 무엇을 볼 수 있는지가 시스템마다 따로 관리되어, 전체를 한눈에 확인할 수 없습니다
- **질문 하나마다 옮기는 일부터 다시 시작합니다.** 새 분석을 하려 할 때마다 데이터를 모으는 데 시간이 다 갑니다

#### 넣을 때 모양을 정하는가, 읽을 때 정하는가

데이터 웨어하우스와 데이터 레이크를 가르는 핵심이 여기 있습니다.

| | 데이터 레이크 | 데이터 웨어하우스 |
|---|---|---|
| **스키마를 정하는 시점** | **읽을 때** 정합니다 | **넣기 전에** 정해야 합니다 |
| **받는 데이터** | 정형 · 반정형 · 비정형 무엇이든 네이티브 형식 그대로 | 정해진 스키마에 맞는 정형 데이터 |
| **강점** | 일단 다 모아 두고 나중에 질문을 만듭니다 | 정해진 질문에 빠르게 답합니다 |
| **바닥** | [[amazon-s3\|S3]] | [[amazon-redshift\|Redshift]] 같은 웨어하우스 엔진 |

웨어하우스는 스키마를 먼저 정해야 하므로, 형식이 정해지지 않은 이미지나 로그는 **아예 들어가지 못합니다.**
레이크는 그대로 받아 두고 읽는 쪽이 그때 해석하므로 무엇이든 들어갑니다.
그래서 둘은 대체재가 아니라 **앞뒤**입니다 — 원본은 레이크에 두고, 정제해서 정형이 된 것만 웨어하우스로 올리는 구성이 흔합니다.

#### 데이터 레이크가 해결하는 것

데이터 레이크는 **네이티브 형식 그대로** 조직의 모든 데이터를 받아 두는 한 곳입니다.
정형(메인프레임 · 데이터 웨어하우스에서 온 것), 반정형, 비정형(이미지 · 텍스트 · 오디오 · 비디오 · 그래프)을 가리지 않습니다.
그래서 얻는 것이 **빠른 수집**, **사본이 여기저기 늘어나는 것을 막는 일**, **중앙집중식 거버넌스**입니다.

바닥은 거의 항상 [[amazon-s3\|S3]] 이고, 그 위에 권한과 카탈로그를 얹는 것이 [[aws-lake-formation\|Lake Formation]] 입니다.
수집은 여러 갈래에서 들어옵니다 — 스트리밍은 Amazon Data Firehose,
온프레미스 대량은 [[aws-snow-family\|Snow Family]] 와 [[aws-storage-gateway\|Storage Gateway]],
파일은 [[aws-datasync\|DataSync]] 와 [[aws-transfer-family\|Transfer Family]],
회선은 [[aws-direct-connect\|Direct Connect]], 데이터베이스는 [[aws-dms\|DMS]] 입니다.

#### Athena vs Redshift

| | Athena | Redshift |
|---|---|---|
| 데이터 위치 | S3 그대로 | 클러스터에 적재 |
| 요금 | **스캔한 데이터량** | 클러스터 시간 |
| 언제 | 가끔 · 임시 조회 | 항상 도는 BI · 복잡한 집계 |

`한 달에 몇 번 조회` → Athena. `매일 대시보드가 돈다` → Redshift.

> Athena 비용은 **스캔량**에 붙습니다. 파티셔닝하고 **Parquet 같은 열 기반 포맷**으로 바꾸면
> 스캔량이 줄어 성능과 비용이 함께 좋아집니다. 이 답이 정답인 문항이 자주 나옵니다.

#### 왜 파티셔닝과 열 기반 포맷이 스캔량을 줄이는가

위 문장을 외우기 전에 **왜 그런지**를 잡아 두시면 응용 문항에서도 흔들리지 않습니다.

**행 기반 포맷**(CSV · JSON)은 한 줄을 통째로 이어 붙여 저장합니다.
컬럼 두 개만 필요해도 줄 전체를 읽어야 하므로 안 쓰는 컬럼까지 전부 스캔에 잡힙니다.
**열 기반 포맷**(Parquet · ORC)은 같은 컬럼끼리 모아 저장합니다. 그래서 **필요한 컬럼만 골라 읽습니다.**
같은 값이 붙어 있으니 압축도 훨씬 잘 됩니다.

**파티셔닝**은 데이터를 `year=2026/month=03/` 처럼 폴더로 갈라 두는 것입니다.
조회 조건이 3월이면 나머지 폴더는 **열어 보지도 않습니다.**
스캔량이 줄면 요금이 줄고, 읽을 것이 줄었으니 속도도 함께 올라갑니다.

#### S3 위에서 대규모로 처리할 때 손대는 것들

S3 는 수평으로 늘어나고 EMR · Glue 는 고도로 분산되어 도는데, 그 둘이 만나는 자리에서 병목이 생깁니다.
설계에 따라 이런 것들을 조정하게 됩니다.

- **동시 S3 요청 수** — 너무 많으면 요청이 제한되고, 너무 적으면 클러스터를 놀립니다
- **재시도 전략** — 실패한 S3 요청을 어떻게 다시 보낼지
- **한 번에 처리하는 객체 수** — 작은 객체 수백만 개는 그 자체가 부담입니다
- **포맷** — 데이터 레이크 자산을 **Parquet** 같은 열 기반 포맷으로 바꿉니다. 가벼운 변환이면 [[aws-lambda\|Lambda]] 로도 충분합니다

### L6. 수집 경로의 보안과 거버넌스

> **이번 강의에서 다룰 내용** — 데이터를 한곳에 모으는 설계에 왜 권한 이야기가 항상 따라붙는지 짚어 보겠습니다.

#### 한곳에 모았다는 말은 위험도 한곳에 모였다는 말입니다

데이터가 시스템마다 흩어져 있을 때는 각 시스템이 자기 몫만 들고 있었습니다.
레이크는 조직의 데이터를 전부 한 버킷 아래로 끌어모읍니다.
편의가 커진 만큼, **권한 하나가 넓게 잘못 열리면 그 순간 전부가 노출됩니다.**
그래서 이 과제는 "어떻게 가져오는가" 뿐 아니라 **"가져온 다음 누가 볼 수 있는가"** 를 함께 묻습니다.

막는 자리는 세 겹으로 나누어 보시면 정리가 됩니다.

| 겹 | 무엇을 막나 |
|---|---|
| **들어오는 길** | 밖에서 데이터를 밀어 넣는 쪽이 정말 그 권한을 가진 상대인지 |
| **놓인 자리** | 저장된 데이터를 누가 읽을 수 있는지, 그리고 가져가더라도 읽지 못하게 되어 있는지 |
| **꺼내 가는 길** | 분석 도구와 그 도구가 쓰는 역할이 필요한 만큼만 볼 수 있는지 |

**거버넌스**란 이 셋을 사람의 기억이 아니라 **규칙으로 정해 두고 기록을 남기는 것**입니다.
여러 계정 · 여러 팀이 같은 레이크를 쓰는 자리에서는 규칙이 없으면 곧바로 통제가 무너집니다.

#### 수집 경로에서 실제로 쓰는 것들

데이터 레이크는 여러 계정 · 여러 팀이 같이 쓰는 자리라, "누가 무엇을 읽을 수 있는가" 가 설계의 일부입니다.

| 무엇을 | 어떻게 |
|---|---|
| 접근 통제 | **버킷 정책**으로 계정 · 사용자별 접근을, **사용자 정책**으로 분석 도구가 쓰는 역할의 권한을 정합니다 |
| 암호화 | S3 의 암호화 옵션 + [[aws-kms\|KMS]] 로 키 관리를 한곳에 모읍니다 |
| 지워지지 않게 | **버전 관리 · 객체 잠금 · 교차 리전 복제** |
| 수집 앞단 | 밖에서 들어오는 수집 API 는 [[amazon-api-gateway\|API Gateway]] + [[amazon-cognito\|Cognito]] 로 막습니다 |
| PII 규정 준수 | 훨씬 강한 보호가 요구되면 [[aws-cloudhsm\|CloudHSM]] 까지 갑니다 |

**태깅**도 함께 언급됩니다. 데이터 자산에 태그를 붙여 두면 권한과 비용을 분류 단위로 다룰 수 있습니다.

## 4. 시험에서 갈리는 지점

| 지문에 이게 있으면 | 이쪽 |
|---|---|
| `여러 애플리케이션이 같은 스트림을 각자 처리` | **Kinesis Data Streams** |
| `S3 로 그냥 적재` · `코드 없이` | **Data Firehose** |
| `기존 Spark·Hadoop 작업` | **EMR** |
| `ETL 서버를 관리하고 싶지 않다` | **Glue** |
| `S3 데이터를 SQL 로 즉시` | **Athena** |
| `Athena 비용을 줄여라` | 파티셔닝 + **Parquet** |
| `대시보드가 항상 돈다` · `복잡한 조인` | **Redshift** |
| `로그를 검색하고 시각화` | **OpenSearch** |
| `온프레미스 NAS 를 매일 동기화` | **DataSync** |
| `IoT 기기 수백만 대의 실시간 데이터` | **Kinesis Data Streams** |
| `소스와 같은 형식 그대로 계속 옮긴다` | **동종 수집** — 답은 서비스보다 **자동화** 쪽에 있습니다 |
| `스트림 위에서 바로 집계·변환` | **Managed Service for Apache Flink** |
| `동영상 스트림을 수집` | **Kinesis Video Streams** |
| `이미 Kafka 를 쓰고 있다` | **Amazon MSK** |
| `데이터 레이크의 권한과 카탈로그를 한곳에서` | **Lake Formation** |
| `온프레미스에서 SFTP 로 파일을 받는다` | **Transfer Family** |
| `작은 객체가 너무 많아 처리가 느리다` | 동시 요청 수 · 처리 객체 수 조정 + **Parquet 변환** |
| `수집한 데이터에 PII 가 있고 규정 준수가 엄격` | **KMS**, 더 강하면 **CloudHSM** |

> [!tip] `운영 오버헤드가 가장 적은` 이 붙으면 한 칸씩 옮겨 가세요
> Data Streams → **Firehose**, EMR → **Glue**, Redshift → **Athena** 쪽으로.
> 이 수식 어구는 거의 항상 "관리할 것이 없는 쪽"을 가리킵니다.

## 6. 셀프 체크

- [ ] Kinesis Data Streams 와 Data Firehose 를 가르는 신호를 두 개 댄다
- [ ] EMR 을 골라야만 하는 상황을 하나 든다
- [ ] Athena 와 Redshift 를 조회 빈도로 가른다
- [ ] Athena 비용을 줄이는 두 가지 방법을 안다
- [ ] 수집 → 저장 → 변환 → 조회 각 단계에 서비스를 하나씩 배치한다
- [ ] 동종 수집과 이기종 수집이 각각 무엇에 초점을 두는지 말한다
- [ ] Kinesis 네 갈래를 용도로 구분하고, Kafka 가 나온 지문에서 MSK 를 고른다
