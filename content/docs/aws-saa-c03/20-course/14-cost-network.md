> 도메인 4 · 비용에 최적화된 아키텍처 설계 **20%** · 과제 명세 4개 중 **네 번째** (마지막)

## 1. 왜 필요한가

> 네트워크 비용은 **어디로 나가느냐**에 붙습니다. 이 규칙 하나가 이 과제의 절반입니다.

스토리지와 컴퓨팅 비용은 눈에 보입니다. 네트워크 비용은 안 보입니다.
그래서 시험은 **"이 트래픽이 어느 경계를 넘는가"** 를 읽을 수 있는지 묻습니다.

기억할 것은 짧습니다.

- **AWS 로 들어오는 것(인바운드)은 대체로 무료**
- **AWS 밖으로 나가는 것(아웃바운드)에 돈이 붙는다**
- **AZ 를 넘어도, 리전을 넘어도 돈이 붙는다**
- **같은 AZ 안, 프라이빗 IP 통신은 무료**

## 2. 이번에 새로 나오는 서비스

| 서비스 | 한 줄 | 이 과제에서 맡는 역할 |
|---|---|---|
| [[amazon-cloudfront\|Amazon CloudFront]] | 엣지 캐시 | 오리진으로 나가는 전송을 줄인다 |
| [[amazon-vpc\|Amazon VPC]] | 가상 네트워크 | NAT 게이트웨이 · 엔드포인트가 여기 |
| [[aws-direct-connect\|AWS Direct Connect]] | 전용선 | 대량이면 인터넷보다 단가가 낮다 |
| [[aws-transit-gateway\|AWS Transit Gateway]] | 연결 허브 | 편하지만 데이터 처리 요금이 붙는다 |
| [[aws-privatelink\|AWS PrivateLink]] | 서비스 하나만 노출 | 경로를 짧게 |
| [[aws-global-accelerator\|AWS Global Accelerator]] | 백본 경로 | 성능 쪽이지 비용 절감은 아니다 |
| [[aws-cost-explorer\|AWS Cost Explorer]] | 비용 분석 | 어느 전송이 비싼지 먼저 본다 |

## 3. 이 과제가 묻는 것

---

### L1. 데이터 전송 요금 — 경계를 넘을 때마다 값이 붙습니다

> **이번 강의에서 다룰 내용** — 네트워크 요금이 무엇에 붙는지, 그리고 "경계"라는 것이 정확히 어디를 말하는지 살펴보겠습니다. 이 과제의 나머지는 전부 이 한 가지의 응용입니다.

#### 리소스 값과 이동 값은 다릅니다

인스턴스를 켜 두면 시간만큼 값이 붙고, 버킷에 넣어 두면 용량만큼 값이 붙습니다. 여기까지는 **가만히 있는 것에 붙는 값**입니다.

네트워크 요금은 성격이 다릅니다. **데이터가 한 곳에서 다른 곳으로 옮겨 갈 때** 붙습니다.
그래서 아키텍처를 바꾸지 않고 리소스만 줄여서는 사라지지 않고, **경로를 바꿔야** 사라집니다.
이 과제가 유독 "무엇을 쓰느냐"가 아니라 **"어디를 거치게 하느냐"** 를 묻는 이유가 여기에 있습니다.

#### "경계"는 이 네 가지입니다

옮겨 간다고 다 값이 붙는 것은 아닙니다. **정해진 경계를 넘을 때** 붙습니다.

| 경계 | 값이 붙나 |
|---|---|
| 인터넷 → AWS (**인바운드**) | 대체로 **무료**입니다 |
| AWS → 인터넷 (**아웃바운드**) | **유료**입니다 |
| AZ → 다른 AZ | **유료**입니다 |
| 리전 → 다른 리전 | **유료**입니다 |
| 같은 AZ 안, 프라이빗 IP 로 주고받기 | **무료**입니다 |

인바운드가 무료인 것은 클라우드 사업자 쪽에서 보면 자연스러운 일입니다.
**데이터를 들여오는 데는 문턱을 없애고, 내보내는 데 값을 매기는** 구조이기 때문입니다.
그래서 `인바운드 전송 비용을 줄여라` 라는 지문은 그 자체가 함정입니다. 줄일 것이 거의 없습니다.

> [!tip] 이 과제를 푸는 순서
> 지문을 읽을 때 서비스 이름부터 찾지 마시고 **트래픽이 어느 경계를 몇 번 넘는지** 먼저 세어 보시기 바랍니다.
> 경계를 한 번 덜 넘게 만드는 보기가 대개 정답입니다.

#### 데이터 전송 요금이 붙는 자리

```d2
direction: right

vpc: "VPC" {
  az_a: "AZ-a" {
    ec2_a: "EC2"
    nat: "NAT 게이트웨이"
  }
  az_b: "AZ-b" {
    ec2_b: "EC2"
  }
  ep: "S3 Gateway 엔드포인트"
}

s3: "Amazon S3"
net: "인터넷"

vpc.az_a.ec2_a -> vpc.az_b.ec2_b: "AZ 간 — 유료"
vpc.az_a.ec2_a -> vpc.az_a.nat: "NAT 처리 — 유료"
vpc.az_a.nat -> net: "아웃바운드 — 유료"
vpc.az_a.ec2_a -> vpc.ep: "무료"
vpc.ep -> s3: "무료"
net -> vpc: "인바운드 — 무료"
```

#### 가장 자주 나오는 절감 세 가지

| 문제 | 답 |
|---|---|
| S3·DynamoDB 트래픽이 **NAT 게이트웨이**를 거친다 | **Gateway 엔드포인트** — NAT 처리 요금과 아웃바운드가 둘 다 사라진다 |
| 같은 콘텐츠를 계속 오리진에서 내보낸다 | **CloudFront** — 엣지에서 나가는 단가가 더 낮고 오리진 전송이 준다 |
| 온프레미스로 매일 대량 전송 | **Direct Connect** — 전송 단가가 인터넷보다 낮다 |

---

### L2. NAT 게이트웨이와 엔드포인트 — 경로를 바꿔 요금을 없앱니다

> **이번 강의에서 다룰 내용** — 비용 문항의 단골 정답인 엔드포인트가 무엇을 없애는지, 그리고 두 종류의 엔드포인트가 어떻게 다른지 살펴보겠습니다.

#### 프라이빗 서브넷이 S3 를 읽는 두 가지 길

프라이빗 서브넷의 인스턴스는 인터넷과 직접 통하지 못하므로, 기본 구성에서는 **NAT 게이트웨이**를 거쳐 인터넷으로 나갔다가 S3 로 들어갑니다.
같은 AWS 안에 있는 서비스를 부르는데 **바깥으로 한 바퀴 돌고 오는** 셈이고, 그 한 바퀴가 그대로 요금이 됩니다.

**VPC 엔드포인트**는 이 바깥 구간을 통째로 없앱니다. 두 종류가 있고 **붙는 방식과 요금 성격이 다릅니다.**

| | 어떻게 붙나 | 무엇에 값이 붙나 |
|---|---|---|
| **게이트웨이 엔드포인트** | **라우팅 테이블에 경로를 한 줄** 넣습니다. 대상은 **S3 와 DynamoDB** 입니다 | 엔드포인트 자체에는 값이 붙지 않습니다 |
| **인터페이스 엔드포인트** | 서브넷 안에 **ENI 를 만들고 프라이빗 IP** 를 붙입니다. 그 밖의 여러 AWS 서비스에 쓰입니다 | **엔드포인트가 떠 있는 시간과 처리한 데이터량** |

**두 엔드포인트가 같은 값이 아니라는 점이 시험 포인트입니다.**
`S3 를 읽는데 NAT 요금이 크다` 는 지문이면 게이트웨이 엔드포인트가 값을 거의 그대로 없애 주지만,
인터페이스 엔드포인트는 NAT 를 없애는 대신 **자기 몫의 시간·처리 요금을 새로 만듭니다.**
그래도 대개 이득이지만, "무조건 공짜"로 외우시면 안 됩니다.

#### NAT 게이트웨이는 이중으로 돈이 듭니다

시간당 요금 + **처리한 데이터량**입니다.
프라이빗 서브넷의 인스턴스가 S3 를 많이 읽는데 NAT 를 거치고 있다면
Gateway 엔드포인트 하나로 그 두 가지가 함께 사라집니다. **비용 문항의 단골 정답**입니다.

개수도 환경에 따라 갈립니다. 운영 환경이라면 **AZ 마다 퍼블릭 서브넷에 하나씩** 두어 AZ 장애와 교차 AZ 요금을 피하지만,
개발 환경이라면 **하나를 공유**해서 시간 요금을 줄이는 것이 AWS 가 드는 절감 예시입니다.
지문이 어느 환경을 말하는지가 그대로 정답을 가릅니다.

### L3. AZ 를 넘는 트래픽 — 가용성과 맞바꾸는 자리

> **이번 강의에서 다룰 내용** — 왜 같은 리전 안인데도 AZ 를 넘으면 값이 붙는지, 그리고 그것을 줄이려 할 때 무엇을 내놓게 되는지 살펴보겠습니다.

#### AZ 는 물리적으로 떨어져 있습니다

가용 영역은 서로 **다른 건물, 다른 전력, 다른 네트워크**로 지어 놓은 별개의 시설입니다.
AZ 하나가 통째로 죽어도 다른 AZ 가 살아남게 하려면 그래야 합니다.
그러니 AZ 사이의 통신은 **실제로 시설과 시설 사이를 지나는 통신**이고, 그 구간에 값이 붙습니다.

여기서 이 과제의 가장 중요한 긴장이 나옵니다. **여러 AZ 에 흩어 놓는 것이 가용성이고, 한 AZ 에 모으는 것이 절감입니다.**
둘은 같은 방향으로 갈 수 없습니다. 그래서 지문이 **비용을 우선하라고 못 박았는지**를 반드시 확인하셔야 합니다.

#### AZ 를 넘는 트래픽

- ALB 는 여러 AZ 에 걸쳐 있어 교차 AZ 트래픽이 생기지만, **그 전송에는 요금이 붙지 않습니다.** NLB 는 교차 영역 로드 밸런싱을 켜면 붙습니다
- 대량 통신을 하는 두 인스턴스라면 **같은 AZ 에 두는 것**이 답이 되는 경우가 있습니다
- 다만 그러면 가용성이 떨어집니다 — 지문이 비용을 우선하라고 했는지 확인하세요

### L4. VPC 를 잇는 방법마다 값의 성격이 다릅니다

> **이번 강의에서 다룰 내용** — 피어링 · Transit Gateway · PrivateLink 가 각각 무엇에 요금을 매기는지, 그래서 VPC 개수에 따라 어떻게 답이 뒤집히는지 살펴보겠습니다.

#### 무엇에 값을 매기느냐가 다릅니다

**VPC 피어링**은 연결을 만들어 두는 것 자체에는 값이 붙지 않습니다. 오간 데이터에만 값이 붙습니다.
대신 [[09-perf-network\|3.4]] 에서 본 대로 **전이되지 않아서** VPC 가 늘면 이어야 할 짝이 급격히 불어납니다.

**Transit Gateway** 는 반대입니다. 연결 관리를 대신 해 주는 대가로 **붙여 둔 연결마다 시간 요금**을 받고,
그 위로 지나간 **데이터 처리량**에도 값을 매깁니다. 편해지는 만큼 고정적으로 나가는 값이 생긴다는 뜻입니다.

**PrivateLink** 도 엔드포인트가 떠 있는 시간과 처리량에 값이 붙습니다. 네트워크를 통째로 잇지 않고 서비스 하나만 연다는 성격의 값입니다.

그래서 **개수가 답을 뒤집습니다.** VPC 가 두어 개라면 짝이 몇 개 되지 않으니 피어링이 가장 쌉니다.
수십 개가 되면 짝의 수가 폭발해서, 관리 부담까지 합쳐 보면 Transit Gateway 쪽이 실질적으로 낫습니다.

#### 연결 방식의 비용 성격

| | 성격 |
|---|---|
| **VPC 피어링** | 연결 자체는 무료. 데이터 전송료만. **VPC 두어 개면 가장 싸다** |
| **Transit Gateway** | 연결당 시간 요금 + 데이터 처리 요금. VPC 가 많아질수록 관리 이득이 커진다 |
| **PrivateLink** | 엔드포인트 시간 요금 + 데이터 처리 |

`VPC 두 개를 잇는 가장 저렴한 방법` → **피어링**.
`VPC 수십 개` 라면 피어링 연결이 폭발하므로 Transit Gateway 가 실질적으로 낫습니다.

### L5. 온프레미스와 잇는 값 — 성능 과제와 답이 뒤집힙니다

> **이번 강의에서 다룰 내용** — 같은 두 서비스를 비용 쪽에서 보면 왜 순서가 바뀌는지 살펴보겠습니다.

#### 회선을 까는 값과 인터넷을 빌려 쓰는 값

**Direct Connect** 는 물리적인 전용 회선입니다. 회선 자체를 두는 값이 있고, 포트를 잡아 두는 값이 있습니다.
데이터 전송 단가는 인터넷보다 낮지만, **깔아 두기만 해도 나가는 값**이 있다는 것이 비용 관점의 핵심입니다.

**Site-to-Site VPN** 은 이미 있는 인터넷 위에 터널을 얹는 방식이라, 새로 까는 값이 없습니다.
대신 데이터는 인터넷 아웃바운드로 나가고, 속도는 그날의 인터넷 사정에 좌우됩니다.

그래서 **매일 대량으로 옮기는 경우**라면 낮은 전송 단가가 회선 값을 덮어 Direct Connect 가 유리해지고,
**가끔 조금씩 오가는 경우**라면 회선 값을 그대로 손해 보게 됩니다. 지문의 **전송량**이 답을 가릅니다.

#### 온프레미스와 잇는 값 — 비용 쪽 기본값은 VPN 입니다

성능 과제([[09-perf-network\|3.4]])에서는 Direct Connect 가 답인 자리가 많았지만, **비용 과제에서는 순서가 뒤집힙니다.**
AWS 는 **연결이 한시적이거나 비용이 관건이면 Site-to-Site VPN 을**,
**높은 대역폭과 낮은 지연이 일관되게 필요하고 연결이 상시로 있어야 하면 Direct Connect 를** 쓰라고 안내합니다.

| 질문 | 답 |
|---|---|
| Direct Connect 연결 하나면 기본적으로 고가용성입니까 | **아닙니다.** 회선 하나는 단일 장애 지점입니다 |
| 이미 있는 Direct Connect 에 장애 조치를 **가장 싸게** 붙이려면 | **Site-to-Site VPN**. 회선을 하나 더 놓는 쪽은 비용도 구성 시간도 더 듭니다 |
| Direct Connect 를 Transit Gateway 에 직접 꽂습니까 | **Direct Connect 게이트웨이를 거쳐** 연결합니다 |

### L6. 엣지로 밀어내기 — CloudFront 가 값을 줄이는 구조

> **이번 강의에서 다룰 내용** — 캐시가 왜 성능 도구이면서 동시에 비용 도구인지, 그리고 S3 요금에서 네트워크가 차지하는 몫을 살펴보겠습니다.

#### 오리진에 닿는 요청 자체를 줄입니다

CloudFront 는 전 세계 **엣지 로케이션**에 콘텐츠 사본을 두고, 사용자를 가장 가까운 엣지에 붙입니다.
그 엣지에 사본이 있으면(**캐시 히트**) 오리진까지 가지 않고 바로 응답합니다.

성능 이야기로 읽으면 "빨라진다"이지만, 비용 이야기로 읽으면 **오리진이 같은 파일을 몇 번 내보내느냐가 줄어든다**입니다.
같은 파일을 백만 명에게 보낼 때 오리진에서 백만 번 내보내는 것과, 엣지에 한 번 올려 두고 거기서 나가는 것은 전혀 다른 값이 됩니다.

#### CloudFront 가 비용을 줄이는 두 지점

- 오리진이 S3·EC2·ELB 같은 **AWS 오리진이면, 오리진에서 CloudFront 엣지 로케이션으로 가는 전송에는 요금이 붙지 않습니다**
- **리전 엣지 캐시**를 추가 비용 없이 한 겹 더 두므로 오리진에 도달하는 요청 자체가 줄고,
  컴퓨팅을 많이 쓰는 오리진이라면 그 운영 비용까지 함께 내려갑니다

`S3 버킷 앞에 붙이기` 는 CloudFront 의 여러 사용 사례 중 하나일 뿐이라는 점도 함께 짚어 두시기 바랍니다.

#### S3 요금은 세 갈래이고, 그중 둘이 네트워크입니다

버킷에 **저장한 용량** · S3 에 대한 **API 호출** · **버킷 밖으로 나가는 전송**입니다.
그래서 S3 비용을 줄이는 길은 스토리지 클래스를 바꾸는 것([[11-cost-storage\|4.1]])만이 아니라
**호출 수와 전송량 자체를 줄이는 것**이 있습니다. 앞에 CloudFront 를 두면 이 둘이 함께 내려갑니다.

여기서 Global Accelerator 와 갈리는 지점도 분명해집니다. Global Accelerator 는 **캐시를 하지 않습니다.**
길을 좋게 해 줄 뿐이라 오리진에 닿는 요청 수는 그대로이고, 그래서 절감 효과가 없습니다. 이 대비는 `4. 시험에서 갈리는 지점` 아래에서 한 번 더 짚겠습니다.

---

### L7. 새는 곳을 찾고, 관리 경로에 붙는 값을 없앱니다

> **이번 강의에서 다룰 내용** — 요금이 트래픽뿐 아니라 **띄워 둔 부속**에도 붙는다는 것, 그리고 어디가 새는지 먼저 보는 순서를 살펴보겠습니다.

#### 서버에 들어가는 길에도 값이 붙습니다

관리자가 인스턴스에 들어가려고 **배스천 호스트**를 하나 띄워 두는 구성이 흔합니다.
그런데 그 배스천은 **인스턴스 값과 퍼블릭 주소 값**을 하루 종일 냅니다. 실제로 접속하는 시간은 하루 몇 분인데도 그렇습니다.

이런 **"기능을 위해 띄워 둔 부속"** 을 없애는 것이 이 과제의 또 한 갈래입니다. 트래픽을 줄이는 것과는 다른 종류의 절감입니다.

#### 인스턴스에 붙는 방법도 비용입니다

로그를 보러 EC2 에 들어가는 길은 SSH·RDP 같은 기존 방식, **Session Manager**, **EC2 Instance Connect** 로 나뉘고
각각 비용에 미치는 영향이 다릅니다. SSH 를 쓰겠다고 배스천 호스트를 따로 띄우면
그 인스턴스와 퍼블릭 주소가 그대로 요금이 되므로, [[aws-systems-manager\|Systems Manager]] 의 Session Manager 로 바꾸면
그 몫이 통째로 사라집니다.

#### API Gateway 는 쓰는 양을 제한할 수 있습니다

고객마다 초당·주간 호출 수를 통제하려면, API 를 만들고 테스트해 배포한 뒤 **사용량 계획과 API 키**를 구성합니다.
그러면 고객은 키로 선택된 API 에만 접근하고, 정의된 한도와 할당량 안에서만 호출하게 됩니다.
**API 수준에서도, 메서드 수준에서도** 걸 수 있습니다.
`특정 고객이 호출을 몰아쳐 요금이 튄다`는 지문의 답이 여기입니다.

#### 어디가 새는지 보는 도구

네트워크 쪽에는 [[amazon-cloudwatch\|CloudWatch]] 말고도 **AWS Health Dashboard**, **VPC Reachability Analyzer**,
**Transit Gateway Network Manager**, [[aws-config\|AWS Config]], **Route Analyzer** 가 있습니다.
먼저 과거 비용 패턴을 보고, 데이터를 **같은 AZ·같은 리전 안에 묶을 수 있는 자리**를 찾는 순서로 검토하시기 바랍니다.

## 4. 시험에서 갈리는 지점

| 지문에 이게 있으면 | 이쪽 |
|---|---|
| `NAT 게이트웨이 비용이 높다` + S3 접근 | **Gateway 엔드포인트** |
| `같은 파일을 전 세계에 반복 전송` | **CloudFront** |
| `온프레미스로 매일 테라바이트 전송` | **Direct Connect** |
| `VPC 두 개만 잇는다, 가장 저렴하게` | **VPC 피어링** |
| `VPC 가 수십 개로 늘어난다` | **Transit Gateway** |
| `AZ 간 트래픽 요금이 크다` | 같은 AZ 로 모으기 (가용성과 맞바꾼다) |
| `인바운드 전송 비용을 줄여라` | 함정 — **인바운드는 대체로 무료** |
| `어느 전송이 비싼지 모르겠다` | **Cost Explorer** 로 먼저 확인 |
| `온프레미스와 프라이빗 연결, 비용 최소화` | **Site-to-Site VPN**. Direct Connect 는 일관된 대역폭·지연이 상시로 필요할 때 |
| `Direct Connect 에 장애 조치를 싸게 붙여라` | **Site-to-Site VPN** 백업 연결 |
| `배스천 호스트 요금이 아깝다` | **Session Manager** |
| `개발 VPC 의 NAT 게이트웨이 비용` | AZ 마다 두지 말고 **하나를 공유** |
| `고객별 호출량을 제한해야 한다` | **API Gateway 사용량 계획 + API 키** |
| `S3 비용의 대부분이 API 호출과 전송이다` | 앞에 **CloudFront** 를 둡니다 |

> [!warning] Global Accelerator 는 비용 절감이 아닙니다
> 성능(지연 시간·장애 조치) 을 위한 서비스이고 요금이 **추가**됩니다.
> 비용 최적화 문항에서 답으로 나오면 대개 오답입니다. CloudFront 와 헷갈리기 쉬운 자리입니다.

## 6. 셀프 체크

- [ ] 인바운드와 아웃바운드 중 어느 쪽에 요금이 붙는지 안다
- [ ] NAT 게이트웨이 요금이 두 갈래라는 것과, 그것을 없애는 답을 말한다
- [ ] CloudFront 가 비용을 줄이는 원리를 한 문장으로 설명한다
- [ ] 피어링과 Transit Gateway 중 어느 쪽이 언제 싼지 판단한다
- [ ] AZ 를 모으는 것이 무엇과 맞바꾸는 선택인지 안다
- [ ] 비용 관점에서 VPN 과 Direct Connect 중 어느 쪽이 기본값인지 말한다
- [ ] S3 요금 세 갈래를 대고, 그중 네트워크에 해당하는 둘을 짚는다
