> 도메인 4 · 비용에 최적화된 아키텍처 설계 **20%** · 과제 명세 4개 중 **세 번째**

## 1. 왜 필요한가

> [[08-perf-database\|3.3]] 의 짝입니다. 성능을 올리려고 붙인 것들이 그대로 비용이 됩니다.

읽기 전용 복제본을 늘리면 읽기가 빨라지지만 인스턴스가 늘어난 만큼 돈이 나갑니다.
DynamoDB 를 프로비저닝 모드로 넉넉하게 잡으면 안 쓰는 용량도 그대로 청구됩니다.

그래서 이 과제의 판단은 하나로 모입니다 — **트래픽이 예측 가능한가.**
예측 가능하면 약정해서 깎고, 예측 불가하면 쓴 만큼 내는 쪽으로 갑니다.

## 2. 이번에 새로 나오는 서비스

| 서비스 | 한 줄 | 이 과제에서 맡는 역할 |
|---|---|---|
| [[amazon-rds\|Amazon RDS]] | 관리형 관계형 DB | 예약 인스턴스와 크기 조정 |
| [[amazon-aurora\|Amazon Aurora]] | AWS 판 MySQL·PostgreSQL | **Serverless** 로 유휴 비용을 없앤다 |
| [[amazon-dynamodb\|Amazon DynamoDB]] | 관리형 NoSQL | 온디맨드 vs 프로비저닝 |
| [[amazon-elasticache\|Amazon ElastiCache]] | 인메모리 캐시 | DB 인스턴스를 키우는 대신 |
| [[amazon-redshift\|Amazon Redshift]] | 데이터 웨어하우스 | 일시 중지 · 동시성 확장 |
| [[amazon-athena\|Amazon Athena]] | S3 에 SQL | 가끔 쓰는 분석이면 클러스터보다 싸다 |
| [[aws-backup\|AWS Backup]] | 백업 정책 | 보존 기간이 곧 비용 |

## 3. 이 과제가 묻는 것

---

### L1. 데이터베이스 요금은 어디에 붙는가

> **이번 강의에서 다룰 내용** — 데이터베이스에서 실제로 돈이 붙는 항목이 무엇인지, 그리고 왜 "일단 관계형에 다 넣기"가 비싼 선택이 되는지 살펴보겠습니다.

#### 붙는 자리는 네 군데입니다

관리형 데이터베이스라고 해서 요금이 한 덩어리로 나오지는 않습니다. 항목을 나눠 보면 어디를 건드려야 하는지가 보입니다.

| 항목 | 무엇에 붙나 | 줄이는 방향 |
|---|---|---|
| **인스턴스 시간** | 데이터베이스 인스턴스가 **떠 있는 시간**. 요청이 없어도 붙습니다 | 크기를 줄이거나, 약정하거나, 안 쓸 때 내립니다 |
| **스토리지** | 확보한 용량과 실제로 담긴 데이터 | 안 보는 데이터를 싼 곳으로 내립니다 |
| **백업 스토리지** | 스냅샷이 차지하는 용량 | 보존 기간과 스냅샷 개수 |
| **데이터 전송** | 밖으로 나가는 데이터, 특히 AZ·리전을 넘는 복제 | 복제본을 어디에 둘 것인가 |

여기서 첫 줄이 중요합니다. **인스턴스 시간은 요청이 0건이어도 붙습니다.**
개발용 데이터베이스가 주말 내내 떠 있어도, 분석용 클러스터가 밤새 놀고 있어도 요금은 똑같이 흐릅니다.
비용 문항이 `유휴` · `가끔만` · `밤에는` 같은 낱말을 심어 두는 이유가 이것입니다.

DynamoDB 나 Aurora Serverless 처럼 **인스턴스를 세지 않는 서비스**에는 이 첫 줄이 없습니다. 요청과 처리량이 곧 요금입니다.
그래서 같은 워크로드라도 **모양이 들쭉날쭉할수록** 이런 쪽이 유리해집니다.

**전부 관계형 데이터베이스에 넣지 않는 것이 첫 절감입니다**

AWS 가 이 과제에서 가장 먼저 짚는 것은 요금제가 아니라 **데이터를 어디에 둘 것인가** 입니다.
관계형 데이터베이스 관리 시스템은 트랜잭션 처리 시스템의 중심이지만, 모든 데이터를 거기에 넣으면
성능 문제가 생기고 총 소유 비용이 올라갑니다.
데이터 스토어는 **액세스 패턴 · 예상 규모와 성장 · 액세스 빈도** 세 가지를 보고 고릅니다.

데이터를 AWS 로 옮길 때 AWS 가 드는 비용 최적화는 세 갈래입니다.

| 옮기는 것 | 어디로 |
|---|---|
| 관계형 데이터베이스의 **일부** | [[amazon-ec2\|EC2]] 위의 DB 또는 [[amazon-rds\|RDS]] |
| 관계형 데이터베이스 안의 **대용량 객체** | [[amazon-s3\|S3]] — 행 안에 파일을 담아 두는 구조가 비쌉니다 |
| 관계형 데이터베이스의 **일부 데이터** | [[amazon-dynamodb\|DynamoDB]] 같은 NoSQL |

**관계형에 남길 것과 NoSQL 로 보낼 것을 가르는 질문**

지문이 데이터의 성격을 길게 설명한다면 이 표를 떠올리시기 바랍니다.

| 이쪽이면 관계형에 남깁니다 | 이쪽이면 NoSQL 로 보낼 수 있습니다 |
|---|---|
| 여러 테이블을 조인하는 복잡한 SQL 을 돌립니다 | 자주, 그리고 빠르게 기록됩니다 |
| 테이블과 엔터티 정의가 고정된 채로 갑니다 | 레코드마다 필드·속성 개수가 다릅니다 |
| 테이블 사이의 제약 조건을 적용해야 합니다 | 다른 테이블과 독립적으로 기록됩니다 |
| 이 데이터에 맞춰 절차 코드·화면 코드가 이미 쓰여 있습니다 | **최종 일관성**으로 읽어도 됩니다 |

예전에는 하나의 데이터베이스로 전부 감당했지만, 지금은 **목적별 데이터 스토어**를 씁니다.
대규모에서 10밀리초 미만 지연이면 DynamoDB, 데이터 웨어하우스면 Redshift, 관계형 요구면 RDS 라는 식입니다.

### L2. 예측이 서는가 — 약정과 사용량 요금

> **이번 강의에서 다룰 내용** — 같은 데이터베이스를 싸게 사는 방법이 왜 트래픽의 모양에 달려 있는지 살펴보겠습니다.

#### 약정은 "오래 쓰겠다"를 담보로 깎는 것입니다

AWS 는 미리 알 수 있으면 깎아 줍니다. **예약 인스턴스**는 1년 또는 3년 동안 이 데이터베이스를 계속 쓰겠다고 약속하고
그 대가로 단가를 낮추는 방식입니다. [[07-perf-compute\|3.2]] 에서 본 EC2 예약 인스턴스와 발상이 같습니다.

문제는 약속을 지키지 못했을 때입니다. 워크로드가 절반으로 줄어도 약정한 몫은 그대로 나갑니다.
그래서 약정은 **예측이 서는 워크로드에만** 겁니다. "3년 뒤에도 이 데이터베이스가 이 크기로 있을 것인가"가 판단 기준입니다.

#### 예측이 안 서면 반대로 갑니다

예측이 안 서는 워크로드에는 **쓴 만큼 내는 쪽**이 맞습니다. 단가는 비싸지만 **안 쓸 때 거의 0 이 된다**는 것이 그 값을 합니다.

| | 약정하는 쪽 | 쓴 만큼 내는 쪽 |
|---|---|---|
| 단가 | 낮습니다 | 높습니다 |
| 유휴 시간의 요금 | **그대로 나갑니다** | 거의 없습니다 |
| 맞는 지문 | `수년간 꾸준한 부하` | `언제 몰릴지 모른다` · `가끔만 쓴다` |

Aurora Serverless 가 유휴에 강한 이유도 여기에 있습니다. 컴퓨팅을 **ACU** 라는 단위로 세면서 부하에 따라 오르내리고,
아무도 쓰지 않는 구간에는 0 까지 내려가 **저장해 둔 데이터 요금만** 남깁니다.
인스턴스 시간이라는 항목 자체가 사라지는 셈입니다.

**예측 가능한가 — 이 한 축입니다**

| | 예측 가능 | 예측 불가 |
|---|---|---|
| **RDS · Aurora** | 예약 인스턴스 | Aurora **Serverless** |
| **DynamoDB** | **프로비저닝** 모드 (+ Auto Scaling) | **온디맨드** 모드 |
| **Redshift** | 예약 노드 | 필요할 때만 · Athena 로 대체 |

**DynamoDB 두 모드**

| | 프로비저닝 | 온디맨드 |
|---|---|---|
| 요금 | 확보한 용량 단위 | **실제 요청 수** |
| 언제 | 트래픽이 일정하고 예측된다 | 급증이 심하거나 신규 서비스라 모른다 |
| 단가 | 낮다 | 높다 (대신 유휴 비용 0) |

`트래픽이 예측 가능하고 꾸준하다` → 프로비저닝 + Auto Scaling.
`언제 얼마나 올지 모른다` · `가끔만 쓴다` → 온디맨드.

### L3. 키우기 전에 덜어냅니다

> **이번 강의에서 다룰 내용** — 느린 데이터베이스에 더 큰 인스턴스를 붙이는 것이 왜 비용 문항에서 대개 오답인지 살펴보겠습니다.

#### 크기를 올리면 요금은 계단으로 오릅니다

데이터베이스 인스턴스 크기는 대개 **두 배씩** 올라갑니다. CPU 가 조금 모자란다고 한 단계 올리면 요금도 그만큼 뜁니다.
게다가 그 크기는 **가장 바쁜 순간에 맞춰** 잡히므로, 한가한 시간에도 그 값을 계속 내게 됩니다.

요청을 덜어내는 쪽은 반대로 움직입니다. 캐시가 읽기의 상당 부분을 받아 내면 원본 데이터베이스는 원래 크기로 버팁니다.
**캐시 노드를 하나 두는 편이 데이터베이스 인스턴스를 한 단계 올리는 것보다 싸게 먹히는 구간**이 넓어서,
비용 문항이 이쪽을 정답으로 두는 경우가 많습니다.

#### 읽기와 쓰기를 나눠서 봅니다

| 무엇이 모자란가 | 비용상 먼저 볼 것 |
|---|---|
| 같은 조회가 반복된다 | **캐시** — 인스턴스를 그대로 두고 요청만 걷어냅니다 |
| 읽는 내용이 매번 다르다 | **읽기 전용 복제본** — 대신 인스턴스가 늘어난 만큼 요금이 붙습니다 |
| 분석 쿼리가 섞여 있다 | 운영 데이터베이스에서 **떼어 냅니다** |
| 쓰기가 한계다 | 여기서야 인스턴스 크기나 데이터베이스 종류를 다시 봅니다 |

읽기 전용 복제본이 공짜가 아니라는 점을 함께 잡아 두시기 바랍니다.
복제본 한 대는 **인스턴스 한 대 값**이고, 리전을 넘기면 **데이터 전송 요금**이 더 붙습니다.
그래서 `같은 쿼리가 반복된다` 는 신호가 있으면 복제본보다 캐시가 먼저입니다.

**인스턴스를 키우기 전에**

`DB 가 느려서 더 큰 인스턴스로 올린다` 는 보기는 비용 문항에서 대개 오답입니다. 먼저 볼 것은

1. **캐시** — 같은 쿼리가 반복되면 ElastiCache 가 훨씬 싸다
2. **읽기 전용 복제본** — 읽기만 몰린다면
3. **쿼리·인덱스** — 문항에는 잘 안 나오지만 순서상 먼저

AWS 는 여기서 **수평적 크기 조정이 일반적으로 더 비용 효율적**이라고 못 박습니다.
읽기 요청이 몰려 CPU 가 높다는 지문에서 인스턴스를 키우는 보기는 비용이 함께 올라가고,
요청을 덜어내는 보기는 성능 요구를 채우면서 비용을 눌러 줍니다.
스토리지 쪽은 처음부터 크게 잡지 말고 **RDS 스토리지 자동 크기 조정**으로 따라가게 두는 편이 맞습니다.

### L4. 남겨 둔 만큼 냅니다 — 수명과 백업

> **이번 강의에서 다룰 내용** — 데이터를 언제까지 어디에 둘 것인가가 왜 그 자체로 비용 설계인지 살펴보겠습니다.

#### 데이터는 시간이 지나면 성격이 바뀝니다

오늘 들어온 주문 기록은 하루에도 여러 번 조회됩니다. 3년 전 주문 기록은 감사 때나 한 번 꺼내 봅니다.
같은 표에 들어 있다는 이유로 이 둘을 같은 자리에 두면, **거의 안 보는 데이터를 가장 비싼 스토리지에 얹어 두는 셈**이 됩니다.

그래서 비용 설계는 데이터마다 **언제까지 여기 있어야 하는가**를 정하는 일에서 시작합니다.

| 이 데이터는 | 이렇게 |
|---|---|
| 애초에 수명이 정해져 있다 (세션 · 임시 토큰 · 로그) | **만료되면 스스로 지워지게** 합니다 |
| 지금은 안 보지만 나중에 필요할 수 있다 | 데이터베이스 밖 **객체 스토리지로 내리고** 필요할 때 조회합니다 |
| 법이나 계약이 보관을 요구한다 | 보관 기간을 정하고 **그 이상은 남기지 않습니다** |

#### 백업은 빈도와 보존 기간이 곱해집니다

백업은 안전을 사는 일이지만, 스냅샷 하나하나가 스토리지를 차지합니다. 자주 잡을수록, 오래 남길수록 늘어납니다.
그래서 백업 계획은 **얼마나 잃어도 되는가** 에서 거꾸로 내려옵니다. 그 허용치를 **RPO(복구 시점 목표)** 라고 부릅니다.

RPO 가 한 시간이면 한 시간마다 잡으면 됩니다. 5분마다 잡을 이유가 없고, 그렇게 잡으면 요구 이상으로 스토리지를 씁니다.
**보존 기간**은 이와 다른 질문입니다. "언제까지의 상태로 돌아갈 수 있어야 하는가"이고,
빈도와 보존 기간은 요금에 곱해져서 나타납니다.

**오래된 데이터를 버리는 것도 비용 설계입니다**

- **DynamoDB TTL** — 만료 시각을 넣어 두면 알아서 지워집니다. `세션·로그를 30일만 보관` 의 답
- **RDS 스냅샷 보존 기간** — 길수록 돈이 됩니다
- **오래된 데이터를 S3 로 내리고** Athena 로 조회하는 것이 정답인 문항이 있습니다

**백업은 RPO 에 맞추되, 그 이상 남기지 않습니다**

백업 계획은 **RPO 요구를 충족하는 빈도**로 설계합니다. 더 자주 잡는 만큼 스토리지가 늘기 때문입니다.
어떤 관리형 데이터베이스 서비스가 **특정 시점 복구**를 지원하는지도 함께 알아 두시기 바랍니다.
그리고 불필요한 스토리지 비용을 없애려면 **유용한 수명을 넘긴 스냅샷을 남기지 않도록 보존 정책을 설계**해야 합니다.
글로벌 서비스라 리전 간 백업까지 있다면 [[aws-backup\|AWS Backup]] 으로 정책을 한곳에 모읍니다.

또 하나, RDS 엔진이 여러 가지라는 사실 자체가 문항이 됩니다.
**어떤 엔진을 왜 고르는지**를 정리해 두면 라이선스와 요금이 걸린 지문에서 갈립니다.

---

### L5. 분석은 따로 셉니다 — 웨어하우스와 쿼리 서비스

> **이번 강의에서 다룰 내용** — 분석 워크로드의 요금이 왜 운영 데이터베이스와 다른 모양인지, 그리고 어느 쪽으로 가야 하는지 살펴보겠습니다.

#### 창고를 지을 것인가, 있는 자리에서 물어볼 것인가

데이터 웨어하우스는 여러 곳의 데이터를 한곳에 모아 두고 대규모 집계를 빠르게 돌리는 곳입니다.
[[amazon-redshift\|Redshift]] 는 이 일을 **클러스터**로 합니다. 노드를 띄워 두고 그 위에 데이터를 얹어 둡니다.
질의는 빨라지지만, **클러스터가 떠 있는 시간에 요금이 붙습니다.**

[[amazon-athena\|Athena]] 는 반대쪽입니다. 클러스터가 없습니다.
[[amazon-s3\|S3]] 에 있는 파일을 **그 자리에서** SQL 로 물어보고, **읽어 들인 데이터 양**에 요금이 붙습니다.
아무도 질의하지 않는 날에는 저장 요금 말고 붙는 것이 없습니다.

| | Redshift | Athena |
|---|---|---|
| 요금이 붙는 기준 | 클러스터가 **떠 있는 시간** | 질의가 **읽어 들인 양** |
| 유리한 쪽 | 종일 반복되는 대시보드 · 복잡한 조인 | **가끔** 하는 조회 |
| 안 쓸 때 | 일시 중지하지 않으면 계속 붙습니다 | 붙지 않습니다 |

Athena 쪽에서는 읽어 들인 양이 곧 요금이므로, 파일을 **열 단위로 저장하는 형식**으로 바꾸고 날짜별로 나눠 두면
질의가 훑는 양이 줄어 요금도 함께 내려갑니다. 같은 질문에 같은 답을 주면서 값만 깎는 방법입니다.

**Redshift**

- `클러스터가 밤에는 논다` → **일시 중지 / 재개**
- `가끔 몰리는 동시 쿼리` → **동시성 확장** (평소 용량을 그것 때문에 키우지 않는다)
- `한 달에 몇 번 조회` → 애초에 Redshift 가 아니라 **Athena**

---

### L6. 마지막은 늘 관리형입니다

> **이번 강의에서 다룰 내용** — 직접 운영하는 쪽이 왜 거의 항상 더 비싼 선택이 되는지 짚어 보겠습니다.

[[amazon-ec2\|EC2]] 위에 데이터베이스를 직접 올리면 인스턴스 요금만 볼 때는 싸 보입니다. 하지만 값은 거기서 끝나지 않습니다.
패치를 적용할 사람, 백업이 실제로 복구되는지 확인할 사람, 장애가 났을 때 새벽에 일어날 사람이 필요합니다.
**총 소유 비용**은 청구서에 찍히는 숫자와 이 몫을 합한 것입니다.

여기에 **라이선스**가 한 겹 더 얹힙니다. 상용 엔진을 EC2 위에 직접 올리면 라이선스를 따로 사서 관리해야 하고,
그 값은 인스턴스 요금과 별개로 붙습니다.

직접 운영하는 쪽이 답이 되는 경우는 지문이 **관리형에서 지원하지 않는 것**을 요구할 때뿐입니다 —
특정 엔진 버전이나 운영체제 수준의 설정 같은 것들입니다. 그 조건이 지문에 없다면 관리형 쪽을 고르시기 바랍니다.

> [!tip] 마지막 팁은 언제나 관리형입니다
> 관리형 서비스는 서버를 유지하는 운영 부담을 없애고, 클라우드 규모로 운영되므로
> **트랜잭션당·서비스당 단가를 더 낮게** 제공합니다.
> 그래서 직접 EC2 에 DB 를 올려 운영하는 보기와 관리형 서비스 보기가 함께 나오면 대개 관리형 쪽입니다.
> 상용 엔진 라이선스 비용이 지문에 나오면, 라이선스가 따로 붙지 않는 **Aurora** 가 답이 되는 자리입니다.

## 4. 시험에서 갈리는 지점

| 지문에 이게 있으면 | 이쪽 |
|---|---|
| `3년간 꾸준한 DB 부하` | **RDS 예약 인스턴스** |
| `사용량이 불규칙하고 유휴 시간이 길다` | **Aurora Serverless** |
| `트래픽 예측 불가` + DynamoDB | **온디맨드 모드** |
| `트래픽이 일정하고 비용을 낮춰야` + DynamoDB | **프로비저닝 + Auto Scaling** |
| `세션 데이터를 30일 뒤 삭제` | **DynamoDB TTL** |
| `같은 조회가 반복돼 DB 가 비싸다` | **ElastiCache** |
| `분석 클러스터가 밤에는 논다` | **Redshift 일시 중지** |
| `가끔 하는 분석 때문에 웨어하우스를 유지한다` | **Athena** 로 전환 |
| `오래된 기록은 거의 안 본다` | S3 로 내리고 Athena 로 조회 |
| `개발용 DB 가 다중 AZ 로 떠 있다` | 개발 환경은 **단일 AZ** 로 |
| `상용 엔진 라이선스 비용이 부담이다` | **Aurora** — 라이선스가 따로 붙지 않습니다 |
| `이미지·첨부 파일이 DB 안에 들어 있다` | 대용량 객체는 **S3** 로 빼냅니다 |
| `레코드마다 필드가 다르고 조인이 없다` | **DynamoDB** 로 옮길 후보 |
| `복잡한 조인과 테이블 간 제약 조건이 필요하다` | 관계형에 **남깁니다** — NoSQL 로 옮기는 보기는 오답 |
| `스토리지를 얼마나 잡을지 모르겠다` + RDS | **스토리지 자동 크기 조정** |
| `몇 년치 스냅샷이 그대로 쌓여 있다` | **보존 정책**을 다시 설계 |
| `DB 를 EC2 에 직접 올려 운영한다` | 가능하면 **관리형 서비스**로 |

> [!tip] 비용 문항에서 다중 AZ 는 조건을 봅니다
> 운영 환경이면 다중 AZ 가 정답이지만, **개발·테스트 환경**에서 다중 AZ 를 쓰고 있다면
> 그것이 줄일 비용입니다. 지문이 어떤 환경을 말하는지 먼저 확인하세요.

## 6. 셀프 체크

- [ ] DynamoDB 온디맨드와 프로비저닝을 가르는 조건을 말한다
- [ ] Aurora Serverless 가 유리한 트래픽 모양을 설명한다
- [ ] DB 인스턴스를 키우기 전에 검토할 것을 두 가지 댄다
- [ ] TTL 이 비용에 어떻게 작용하는지 안다
- [ ] Redshift 를 유지할지 Athena 로 갈지 판단하는 기준을 말한다
- [ ] 관계형에 남길 데이터와 NoSQL 로 보낼 데이터를 가르는 질문을 두 개 댄다
- [ ] 백업 빈도와 보존 정책이 왜 비용 항목인지 설명한다
