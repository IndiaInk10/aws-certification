> 도메인 1 · 보안 아키텍처 설계 **30%** · 과제 명세 3개 중 **첫 번째**

## 1. 왜 필요한가

> 보안 문항의 절반은 "권한을 어떻게 주느냐"이고, 정답은 거의 항상 **역할**입니다.

SAA 에서 도메인 1 이 30% 로 가장 큽니다. 그런데 이 과제가 묻는 것은 암호화가 아니라
**"이 주체가 저 리소스에 어떻게 닿는가"** 한 가지입니다.

그리고 이 질문의 답은 놀랄 만큼 자주 같습니다. **IAM 역할.**
EC2 가 S3 를 읽어야 하면 역할, Lambda 가 DynamoDB 를 써야 하면 역할,
다른 계정이 내 버킷을 봐야 하면 역할, 사내 계정으로 로그인하고 싶어도 역할입니다.

그래서 이 과제는 외울 것이 적은 대신 **오답을 알아보는 눈**이 중요합니다.
보기에 액세스 키가 등장하면 대개 그것이 틀린 답입니다.

## 2. 이번에 새로 나오는 서비스

| 서비스 | 한 줄 | 이 과제에서 맡는 역할 |
|---|---|---|
| [[aws-iam\|AWS IAM]] | 누가 무엇을 할 수 있는지 정한다 | 이 과제의 중심. 사용자·그룹·**역할**·정책 |
| [[aws-iam-identity-center\|IAM Identity Center]] | 여러 계정에 한 번에 로그인 | 계정이 여러 개일 때의 사람 로그인 |
| [[aws-organizations\|AWS Organizations]] | 계정을 묶고 정책을 위에서 건다 | SCP 로 **최대 권한의 천장**을 씌운다 |
| [[aws-directory-service\|AWS Directory Service]] | Microsoft AD 를 AWS 와 잇는다 | 온프레미스 AD 통합 시나리오 |
| [[amazon-cognito\|Amazon Cognito]] | 앱 사용자의 가입·로그인 | 손님용 인증. IAM 은 직원용 |
| [[aws-ram\|AWS RAM]] | 리소스를 다른 계정과 공유 | 서브넷·Transit Gateway 를 계정끼리 나눠 쓸 때 |
| [[aws-secrets-manager\|AWS Secrets Manager]] | 비밀번호·키 보관과 **자동 교체** | 자격 증명을 코드 밖으로 |
| [[aws-control-tower\|AWS Control Tower]] | 다계정 환경을 정해진 모양으로 세운다 | 새 계정을 규칙에 맞게 찍어낼 때 |

### L1. AWS 계정과 루트 사용자 — 권한 이야기의 출발점

> **이번 강의에서 다룰 내용** — AWS 계정이 무엇을 가르는 단위인지, 그리고 그 안에 처음부터 있는 사용자 하나가 왜 특별한지 살펴보겠습니다.

#### 계정은 담장입니다

AWS 계정은 로그인 아이디가 아니라 **리소스가 갇히는 담장**입니다.
어떤 계정에서 만든 버킷·인스턴스·키는 기본적으로 그 계정 안에서만 보이고,
요금도 계정 단위로 묶여 청구됩니다.

이 담장이 있기 때문에 "**교차 계정**" 이라는 말이 따로 존재합니다.
다른 계정의 리소스에 닿는 일은 같은 계정 안에서 권한을 주는 일과 **성질이 다른 작업**이고,
그 차이가 이 과제 문항의 절반을 만듭니다.

AWS 는 이 과제에서 "흔히 간과하는 영역"으로 **AWS 계정 자체**를 꼽습니다.
너무 기초라 건너뛰기 쉬운데, 문항은 여기서부터 갈립니다.

| 질문 | 답 |
|---|---|
| IAM 은 가용 영역·리전·글로벌 중 어느 수준입니까 | **글로벌**입니다. 모든 리전에 걸쳐 같은 자격 증명이 통합니다 |
| 계정은 무엇으로 시작합니까 | **전체 권한을 가진 루트 사용자 하나**입니다 |
| 루트 권한을 줄일 수 있습니까 | **IAM 정책으로는 못 합니다.** 그래서 루트가 손상되면 환경 전체가 손상됩니다 |
| 새로 만든 IAM 자격 증명은 무엇을 할 수 있습니까 | **아무것도 못 합니다.** 권한 없이 시작해서 부여받습니다 |

#### 루트 사용자는 권한을 깎을 수 없습니다

계정을 처음 열면 그 안에 사용자가 딱 하나 있습니다. **계정 루트 사용자**입니다.
이 사용자는 계정 안의 모든 일을 할 수 있고, **자격 증명 기반 정책도 권한 경계도 붙일 수 없습니다.**
IAM 사용자라면 정책을 걸어 "이것만 하라"고 묶을 수 있지만 루트에는 그 손잡이가 없습니다.
계정 안에서 루트를 묶을 방법이 없다는 뜻이고, 조직에 속한 멤버 계정이라면 **위에서 SCP 로** 씌우는 길만 남습니다.

그래서 루트가 털리면 계정 하나가 통째로 털립니다.
루트를 지키는 첫 수단은 **MFA** 이고, 그다음이 **권한을 제한한 별도 사용자를 만들어 루트를 쓰지 않는 것**입니다.
`복원력이 어느 수준인가`(가용 영역 / 리전 / 글로벌)를 묻는 방식은 이 시험 전체에서 반복되므로,
서비스를 볼 때마다 한 번씩 스스로 물어보시기 바랍니다.

> [!warning] 루트 권한을 제한하는 보기
> `루트 사용자의 권한을 최소한으로 줄인다` 는 보기는 문장만 보면 최소 권한 원칙에 맞아 보입니다.
> 하지만 **IAM 정책으로는 불가능한 조작**이라 그대로 오답입니다. 루트에 할 수 있는 일은 **쓰지 않는 것**과 **MFA 를 거는 것**,
> 그리고 조직의 멤버 계정이라면 **SCP 로 위에서 천장을 씌우는 것**입니다.

### L2. IAM 의 구성 요소 — 사용자 · 그룹 · 역할 · 정책

> **이번 강의에서 다룰 내용** — IAM 이 왜 네 조각으로 나뉘어 있는지, 그리고 그 넷이 서로 어떤 관계인지 살펴보겠습니다.

#### 신원을 담는 그릇 셋과, 권한을 적는 종이 한 장

IAM 을 처음 보면 이름이 넷이라 복잡해 보이지만, 실제로는 **두 종류**밖에 없습니다.
**누구인가**를 담는 그릇이 셋이고, **무엇을 할 수 있는가**를 적어 두는 종이가 하나입니다.

| | 무엇인가 | 붙는 성질 |
|---|---|---|
| **사용자(User)** | 사람 한 명 또는 애플리케이션 하나에 대응하는 **영구 신원**입니다. 콘솔 비밀번호와 액세스 키를 가질 수 있습니다 | 주인이 정해져 있고, 자격 증명이 **만료되지 않습니다** |
| **그룹(Group)** | 사용자를 묶어 두는 **바구니**입니다. `개발자` · `감사자` 처럼 직무 단위로 만듭니다 | **로그인할 수 없습니다.** 그룹 자체는 신원이 아니라 권한을 한꺼번에 나눠 주는 편의 장치입니다 |
| **역할(Role)** | **주인이 없는 신원**입니다. 필요한 쪽이 잠깐 빌려 씁니다 | 비밀번호도 액세스 키도 없습니다. 빌릴 때마다 **임시 자격 증명**이 새로 나옵니다 |
| **정책(Policy)** | 무엇을 허용하고 무엇을 거부하는지 적어 둔 **JSON 문서**입니다 | 혼자서는 아무 힘이 없습니다. 위 셋 중 하나 또는 리소스에 **붙어야** 효력이 생깁니다 |

여기서 놓치기 쉬운 것이 **그룹은 신원이 아니라는 점**입니다.
그룹에는 로그인할 수 없고, 그룹을 역할로 지정할 수도 없습니다.
그룹이 하는 일은 오직 하나 — 같은 정책을 여러 사용자에게 한 번에 붙여 주는 것입니다.

#### 역할이 사용자와 다른 진짜 이유

사용자와 역할은 둘 다 "신원" 이지만 **자격 증명의 수명**이 다릅니다.

- **사용자**는 자격 증명을 **들고 있습니다.** 액세스 키를 한 번 만들면 지울 때까지 살아 있습니다. 그 키가 코드나 이미지 안에 남으면 그대로 사고가 됩니다
- **역할**은 자격 증명을 **들고 있지 않습니다.** 쓸 때마다 발급받고, 몇 시간 뒤에 저절로 만료됩니다

`언제 자격 증명을 애플리케이션에 하드코딩해야 합니까` 라는 질문에 AWS 가 내놓는 답은 **"절대 하지 않습니다"** 입니다.
이 과제의 정답이 거의 항상 역할인 이유가 여기에 있습니다.

#### 최소 권한은 설계 원칙입니다

**최소 권한의 원칙**은 "필요한 권한만 주고 그 이상은 주지 않는다" 입니다.
이 원칙이 중요한 이유는 도덕이 아니라 **피해 범위** 때문입니다.
자격 증명 하나가 새어 나갔을 때 그 자격 증명이 할 수 있는 일의 크기가 곧 사고의 크기가 됩니다.

그래서 문항에서 두 보기가 다 동작한다면 **덜 주는 쪽**이 정답입니다.
이 판단은 뒤의 `4. 시험에서 갈리는 지점` 에서 다시 한번 확인하겠습니다.

### L3. 역할을 "맡는다"는 것 — STS 임시 자격 증명

> **이번 강의에서 다룰 내용** — 역할을 맡는다는 말이 시스템 안에서 실제로 무슨 일인지, 그리고 그 일이 어떤 자리에서 벌어지는지 살펴보겠습니다.

#### 역할에는 정책이 두 장 붙습니다

역할이 다른 신원과 결정적으로 다른 점은 **정책이 두 장**이라는 것입니다.

| 붙는 정책 | 답하는 질문 |
|---|---|
| **신뢰 정책** (Trust policy) | **누가 이 역할을 맡을 수 있는가.** EC2 서비스인지, 특정 계정인지, 특정 IdP 인지 여기에 적습니다 |
| **권한 정책** (Permissions policy) | **이 역할을 맡으면 무엇을 할 수 있는가.** 보통의 자격 증명 기반 정책과 같은 모양입니다 |

교차 계정 문항이 어려워지는 지점이 여기입니다.
**빌려주는 쪽**은 신뢰 정책에 상대 계정을 적어야 하고, **빌리는 쪽**은 자기 사용자에게 `sts:AssumeRole` 권한을 줘야 합니다.
**양쪽이 다 있어야 통합니다.** 한쪽만 있는 보기는 그대로 오답입니다.

#### 맡는 순간 벌어지는 일

역할을 맡는 절차는 이렇게 흘러갑니다.

```d2
who: "주체\n(EC2 · 사용자 · 페더레이션 사용자)"
sts: "AWS STS"
role: "IAM 역할\n신뢰 정책 + 권한 정책"
cred: "임시 자격 증명\n액세스 키 · 시크릿 키 · 세션 토큰"
api: "AWS API 호출"

who -> sts: "이 역할을 맡겠습니다"
sts -> role: "신뢰 정책을 확인합니다"
role -> sts: "허용"
sts -> cred: "발급 (수명이 정해져 있습니다)"
cred -> api
```

받는 것은 **세 조각**입니다. 액세스 키 ID, 시크릿 액세스 키, 그리고 **세션 토큰**입니다.
영구 자격 증명에는 없는 세 번째 조각이 붙는다는 것이 임시 자격 증명의 표식이고,
정해진 수명이 지나면 **저절로 못 쓰게 됩니다.**

여기서 두 가지가 따라 나옵니다.

- **회수할 것이 없습니다.** 만료가 곧 회수라서, 키를 지우러 다닐 일이 생기지 않습니다
- **저장할 자리가 필요 없습니다.** EC2 인스턴스 프로파일이나 Lambda 실행 역할은 이 발급을 인스턴스·함수 대신 알아서 해 주고, 유효 기간이 끝나기 전에 갱신까지 해 줍니다

#### 역할을 쓰는 네 가지 자리

1. **EC2·Lambda 같은 서비스가** AWS API 를 부를 때 → 인스턴스 프로파일 / 실행 역할
2. **다른 계정이** 내 리소스를 쓸 때 → 역할 수임(AssumeRole) + 신뢰 정책
3. **사내 계정으로** AWS 에 로그인할 때 → 페더레이션 (SAML · IAM Identity Center)
4. **앱 사용자가** AWS 리소스에 닿을 때 → Cognito 자격 증명 풀

네 가지 모두 바탕에는 **AWS STS** 가 있습니다. 역할을 맡는다는 것은 STS 가 **수명이 짧은 임시 자격 증명**을
발급해 준다는 뜻입니다. 계정 안에서든 교차 계정에서든 같은 방식으로 작동하고,
`키를 만들어 전달한다`는 보기가 오답이 되는 이유도 여기에 있습니다.

### L4. 정책 문서를 읽는 법

> **이번 강의에서 다룰 내용** — 정책 문서에서 무엇을 보아야 하는지, 그리고 정책이 여러 장 겹쳤을 때 결과가 어떻게 정해지는지 살펴보겠습니다.

#### 쓰는 것이 아니라 읽는 것입니다

고급 정책을 작성하는 능력은 요구하지 않습니다. 대신 **주어진 정책 문서를 읽고 해석**할 수 있어야 합니다.
정책이 여러 개 붙었을 때 결과가 어떻게 결정되는지, 즉 **IAM 결정 로직**을 따라갈 수 있으면 됩니다.

#### 한 문장은 네 칸으로 되어 있습니다

정책 문서는 `Statement` 라는 문장의 목록이고, 문장 하나는 아래 칸들로 이루어집니다.
칸 이름만 알면 그림처럼 읽힙니다.

| 칸 | 묻는 것 | 예 |
|---|---|---|
| **Effect** | 허용인가 거부인가 | `Allow` · `Deny` |
| **Action** | **무슨 작업**인가 | `s3:GetObject` — 앞이 서비스, 뒤가 그 서비스의 API 이름입니다 |
| **Resource** | **무엇에 대해서**인가 | `arn:aws:s3:::my-bucket/*` — AWS 리소스의 주소인 **ARN** 입니다 |
| **Principal** | **누구에게**인가 | 다른 계정 · 서비스 · IAM 주체 |
| **Condition** | 어떤 조건에서만인가 | 출발지 IP · MFA 사용 여부 · 태그 값 |

여기서 **`Principal` 이 있느냐 없느냐**가 정책의 종류를 가릅니다.
사용자·역할에 붙는 정책은 이미 "누구에게" 가 정해져 있으니 그 칸이 없고,
버킷이나 키에 붙는 정책은 아무나 오므로 그 칸이 반드시 필요합니다.

`*` 는 "전부" 입니다. `"Action": "*"` 와 `"Resource": "*"` 가 함께 있는 보기는
**모든 리소스에 대한 전체 권한**이라는 뜻이고, 최소 권한과 정반대이므로 대개 오답입니다.

#### 자격 증명 기반과 리소스 기반 — 어느 쪽에서 문을 여는가

같은 허용이라도 **문고리를 어느 쪽에 다느냐**가 다릅니다.
자격 증명 기반 정책은 **들어가는 사람 쪽**에서 "너는 저기에 갈 수 있다" 고 적고,
리소스 기반 정책은 **문 쪽**에서 "너는 들어와도 된다" 고 적습니다.

계정 하나 안에서는 어느 쪽이든 한 장이면 통합니다.
그런데 **계정이 다르면 두 장이 다 있어야 합니다.** 남의 계정 관리자가 적어 준 허용만으로는 부족하고,
내 계정에서도 내 사용자에게 그 일을 허용해 주어야 합니다.
`교차 계정` 이라는 낱말이 지문에 있으면 이 두 겹을 확인하시기 바랍니다.

| 정책 종류 | 어디에 붙나 | 언제 쓰나 |
|---|---|---|
| 자격 증명 기반 | 사용자·그룹·역할 | 기본. "이 주체가 무엇을 할 수 있는가" |
| 리소스 기반 | S3 버킷 · KMS 키 · SQS 큐 … | 리소스 쪽에서 "누구를 들일지" 정한다. **교차 계정에 필수** |
| 서비스 제어 정책(SCP) | Organizations 의 OU·계정 | 허용이 아니라 **천장**. 여기서 막으면 관리자도 못 한다 |
| 권한 경계 | 사용자·역할 | 그 주체가 가질 수 있는 최대치 |

#### 평가 순서 — 거부가 언제나 이깁니다

정책이 여러 장 겹쳤을 때 IAM 은 아래 순서로 판정합니다.

1. **명시적 거부(Deny)가 하나라도 있으면 거부입니다.** 여기서 끝나고 더 볼 것이 없습니다
2. 거부가 없고 **명시적 허용(Allow)이 있으면 허용**입니다
3. 둘 다 없으면 **거부**입니다. 이것이 **암묵적 거부** 이고, 새 IAM 자격 증명이 아무것도 못 하는 이유입니다

그래서 SCP · 권한 경계 · 리소스 정책 중 **어느 한 군데서만 막아도** 그 작업은 실패합니다.
반대로 어느 한 군데서 허용했다고 되는 것은 아닙니다.
문항이 정책 두 장을 나란히 보여 준다면, 먼저 **`Deny` 부터 찾으시기 바랍니다.**

### L5. 여러 계정과 페더레이션 — 사람을 어떻게 들이는가

> **이번 강의에서 다룰 내용** — 계정이 여러 개일 때 권한을 어디에서 잠그는지, 그리고 AWS 밖에 이미 있는 신원을 어떻게 들이는지 살펴보겠습니다.

#### 계정이 늘어나면 잠그는 자리가 위로 올라갑니다

계정 하나에서는 IAM 정책으로 충분합니다.
그런데 계정이 수십 개가 되면, 각 계정 관리자가 자기 계정 안에서 무엇이든 허용할 수 있다는 것이 문제가 됩니다.

[[aws-organizations\|Organizations]] 는 계정을 **OU** 라는 묶음으로 정리하고,
그 위에 **서비스 제어 정책(SCP)** 을 걸어 **아무리 허용해도 넘을 수 없는 천장**을 씌웁니다.
SCP 는 권한을 주지 않습니다. **줄이기만 합니다.**
그래서 `조직 전체에서 이 리전만 쓰게 하라` 처럼 **아래에서 뚫을 수 없어야 하는 요구**의 답이 됩니다.

[[aws-control-tower\|Control Tower]] 는 그 위에서, 새 계정을 만들 때마다 정해진 구성과 가드레일이
자동으로 붙도록 **틀 자체를 찍어 내는** 쪽입니다.

#### 페더레이션이 필요한 이유

사내 직원이 이미 회사 디렉터리에 계정을 갖고 있다고 해 보겠습니다.
이 사람들에게 AWS 를 쓰게 하는 방법은 둘입니다.

- 사람 수만큼 **IAM 사용자를 새로 만드는 것**
- 이미 있는 신원을 **그대로 인정하고** 역할만 빌려 주는 것

앞쪽은 신원이 두 벌이 된다는 뜻입니다. 입사하면 두 곳에 만들고, 퇴사하면 두 곳에서 지워야 하고,
한쪽을 잊으면 그것이 그대로 **살아 있는 뒷문**이 됩니다.
**페더레이션**은 뒤쪽입니다. 신원은 회사 디렉터리에 한 벌만 두고,
AWS 는 그 디렉터리의 인증 결과를 믿고 **역할을 빌려 줍니다.**

여기서도 결국 나오는 것은 **임시 자격 증명**입니다.
페더레이션한 사용자에게 IAM 사용자나 액세스 키가 생기지 않는다는 점을 기억하시기 바랍니다.

| 들이려는 사람 | 쓰는 것 |
|---|---|
| **사내 직원** — 여러 AWS 계정에 로그인해야 합니다 | [[aws-iam-identity-center\|IAM Identity Center]] 또는 SAML 페더레이션 |
| **사내 직원** — 온프레미스 AD 를 그대로 쓰고 싶습니다 | [[aws-directory-service\|Directory Service]] (아래 표) |
| **앱의 손님** — 가입·로그인하는 일반 사용자 수백만 명입니다 | [[amazon-cognito\|Cognito]]. 사용자 풀이 인증을, 자격 증명 풀이 AWS 리소스 접근을 맡습니다 |

**IAM 은 직원용, Cognito 는 손님용**이라는 구분을 잡아 두시면 이 갈래에서 헤매지 않습니다.

#### AD 통합 세 갈래

실제 시험에서 온프레미스 MS AD 통합 시나리오가 나왔다는 보고가 있습니다.

| | 언제 |
|---|---|
| **AWS Managed Microsoft AD** | AWS 안에 진짜 AD 를 세운다. 온프레미스와 신뢰 관계도 맺을 수 있다 |
| **AD Connector** | 인증을 온프레미스 AD 로 **넘기기만** 한다. AWS 에 사용자를 두지 않는다 |
| **Simple AD** | 작고 싼 AD 호환. 신뢰 관계나 고급 기능이 필요 없을 때 |

### L6. 누가 무엇을 했는지 남기는 것까지가 이 과제입니다

> **이번 강의에서 다룰 내용** — 권한을 설계하는 일과 액세스를 추적하는 일이 왜 한 짝인지 살펴보겠습니다.

권한을 설계하는 일은 액세스를 **추적**하는 일과 짝입니다.
계정 리소스와 데이터에 누가 닿을 수 있는지에 대한 가시성이 없으면 최소 권한을 지켰는지 확인할 방법이 없습니다.
API 호출 기록은 [[aws-cloudtrail\|CloudTrail]], 지표와 경보는 [[amazon-cloudwatch\|CloudWatch]] 가 맡습니다.
여러 계정을 함께 볼 때는 [[aws-organizations\|Organizations]] 아래에서 기록을 한곳으로 모으는 구성이 답이 됩니다.

기록을 **한곳으로 모으는 것**이 왜 따로 언급되는지도 짚고 가겠습니다.
계정마다 기록이 흩어져 있으면, 사고가 난 계정의 기록을 그 계정 관리자가 지울 수 있습니다.
그래서 감사 로그는 **별도 계정의 버킷**에 모아 두고, 그 계정에는 아무나 들어가지 못하게 합니다.
`여러 계정의 감사 기록을 한 곳에서` 가 지문에 있으면 이 구성을 떠올리시기 바랍니다.

## 4. 시험에서 갈리는 지점

| 지문에 이게 있으면 | 이쪽 |
|---|---|
| `EC2 에서 S3 에 접근` | **IAM 역할**. 인스턴스에 키를 넣는 보기는 오답 |
| `액세스 키를 코드에`, `키를 환경 변수에` | 거의 항상 **오답 보기**. 역할이나 Secrets Manager 로 간다 |
| `다른 AWS 계정이 접근` | **역할 수임** + 리소스 기반 정책 |
| `조직 전체에서 이 리전만 허용` · `루트 사용자도 못 하게` | **SCP** |
| `사내 계정으로 로그인` · `SSO` | **IAM Identity Center** 또는 SAML 페더레이션 |
| `앱 사용자 수백만 명의 가입·로그인` | **Cognito**. IAM 사용자를 만들어 주는 보기는 오답 |
| `온프레미스 AD 를 그대로` | **Directory Service** — 셋 중 어느 것인지는 위 표로 |
| `데이터베이스 비밀번호를 주기적으로 교체` | **Secrets Manager** (자동 교체가 결정적) |
| `설정값을 저장, 교체는 필요 없고 저렴하게` | **Parameter Store** |
| `서브넷을 다른 계정과 공유` | **RAM** |
| `루트 사용자를 보호하려면` | **MFA**. IAM 정책으로 루트 권한 자체를 줄이는 보기는 오답입니다 |
| `누가 이 API 를 불렀는지 확인` · `감사 기록` | **CloudTrail** |

> [!tip] 최소 권한은 답이 아니라 채점 기준입니다
> 두 보기가 다 동작한다면 **권한을 덜 주는 쪽**이 정답입니다.
> `모든 리소스에 대한 전체 액세스` 같은 표현이 보이면 그 보기는 지우세요.

## 6. 셀프 체크

- [ ] EC2 가 S3 를 읽게 하는 방법을 두 가지 대고, 왜 하나가 오답인지 말할 수 있다
- [ ] 리소스 기반 정책이 **꼭 필요한** 상황을 하나 든다
- [ ] SCP 가 허용 정책이 아니라 천장이라는 말의 뜻을 설명한다
- [ ] Managed Microsoft AD 와 AD Connector 를 가르는 한 문장을 안다
- [ ] IAM 과 Cognito 를 각각 누구를 위한 것인지로 구분한다
- [ ] IAM 이 글로벌 서비스라는 것과, IAM 정책으로는 루트 사용자의 권한을 줄일 수 없다는 것을 말할 수 있다
- [ ] 역할을 맡을 때 실제로 무엇이 발급되는지 한 문장으로 설명한다
