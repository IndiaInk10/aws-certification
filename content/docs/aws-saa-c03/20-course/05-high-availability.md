> 도메인 2 · 복원력을 갖춘 아키텍처 설계 **26%** · 과제당 **≈13%** — 14개 노트 중 **밀도 1위**

## 1. 왜 필요한가

> 이 노트 하나가 시험의 약 13% 입니다. **DR 전략 4종과 RPO/RTO 가 통째로** 여기 들어 있습니다.

비중을 과제 수로 나눠 보면 순위가 뒤집힙니다. 도메인 2 는 26% 인데 과제가 **둘뿐**이라
개당 밀도가 도메인 3(≈4.8%)의 **거의 세 배**입니다. 학습 순서에서 이 노트를 앞으로 당기는 이유입니다.

내용도 그럴 만합니다. 고가용성은 SAA 의 정체성에 가깝습니다.
실제 시험에서 `고가용성 아키텍처` 시나리오가 나왔다는 보고가 있고,
대부분의 문항이 은근히 "단일 AZ 짜리 보기를 지울 수 있는가"를 함께 묻습니다.

## 2. 이번에 새로 나오는 서비스

| 서비스 | 한 줄 | 이 과제에서 맡는 역할 |
|---|---|---|
| [[amazon-route-53\|Amazon Route 53]] | DNS + 상태 확인 | **장애 조치 라우팅**. 리전 단위 전환 |
| [[elastic-load-balancing\|Elastic Load Balancing]] | 트래픽 분산 + 상태 확인 | AZ 단위 장애 흡수 |
| [[amazon-ec2-auto-scaling\|EC2 Auto Scaling]] | 대수 자동 조절 | 죽은 인스턴스를 **자동으로 갈아 끼운다** |
| [[amazon-rds\|Amazon RDS]] | 관리형 관계형 DB | **다중 AZ** = 가용성 (읽기 성능이 아니다) |
| [[amazon-aurora\|Amazon Aurora]] | AWS 판 MySQL·PostgreSQL | 3개 AZ 에 6벌 복제 |
| [[amazon-dynamodb\|Amazon DynamoDB]] | 관리형 NoSQL | **글로벌 테이블** = 다중 리전 쓰기 |
| [[amazon-s3\|Amazon S3]] | 객체 스토리지 | 교차 리전 복제 |
| [[aws-backup\|AWS Backup]] | 백업 정책 한 곳에서 | 백업 & 복원 전략의 도구 |
| [[aws-elastic-disaster-recovery\|Elastic Disaster Recovery]] | 서버를 통째로 실시간 복제 | 파일럿 라이트·예열 대기의 도구 |

## 3. 이 과제가 묻는 것

> [!tip] 이 과제는 세 낱말을 갈라 놓는 데서 시작합니다
> **고가용성 · 내결함성 · 재해 복구.** 셋은 겹치는 부분이 있지만 정의가 다르고,
> AWS 는 이 시험을 위해 **셋이 각각 무엇인지 알아야 한다**고 못 박습니다.
> 앞의 둘은 시스템을 어떻게 **설계**할 것인가의 문제이고, 마지막 하나는 미리 세워 두는 **계획**의 문제입니다.

### L1. 가용성과 내결함성은 다른 말입니다

> **이번 강의에서 다룰 내용** — 두 낱말이 각각 무엇을 약속하는 말인지, 그리고 활성-대기와 활성-활성이 그 차이를 어떻게 만들어 내는지 살펴보겠습니다.

#### 가용성은 "쓸 수 있는 시간의 비율"입니다

**가용성**은 시스템이 요청을 받아 줄 수 있는 상태로 **얼마나 오래 있었는가**를 재는 값입니다.
`99.9%` 처럼 비율로 말하는 이유가 그것입니다 — 한 해에 얼마만큼 못 쓰는 시간을 허용할 것인가를 정하는 숫자입니다.
**고가용성**은 그 비율을 최대한 끌어올리도록 설계한다는 뜻이고,
방법은 **장애가 나면 최대한 빨리 원래대로 되돌리는 것**입니다.

여기서 흔한 오해가 하나 있습니다. **고가용성은 장애를 멈추게 한다는 뜻이 아닙니다.**
가동 중단이 없다는 약속도 아닙니다. 장애가 나면 아주 짧게라도 끊기고, 그 끊긴 시간을 줄이는 것이 목표입니다.

**내결함성**은 재는 값이 아니라 **성질**입니다.
구성 요소 하나가 고장 난 **그 상태 그대로 시스템이 계속 동작하는가**를 묻습니다.
고장을 빨리 고치는 것이 아니라, 고장이 난 채로도 서비스가 이어지는 것입니다.

| | 뜻 | 예 |
|---|---|---|
| **고가용성** | 죽어도 **빨리 복구**된다 | ASG 가 죽은 인스턴스를 새로 띄운다 (그동안 잠깐 끊긴다) |
| **내결함성** | 죽어도 **안 끊긴다** | 다중 AZ 로 이미 두 대가 돌고 있다 |

지문이 `무중단` · `사용자가 알아채지 못하게` 라고 하면 내결함성 쪽 답을 골라야 합니다.

#### 활성-대기와 활성-활성 — 같은 두 대를 다르게 쓰는 것

두 개념의 차이는 결국 **여분으로 둔 두 번째 대를 평소에 어떻게 쓰느냐**로 갈립니다.
AWS 는 같은 시나리오를 두 번 굴려서 이 차이를 보여 줍니다.
서버 한 대로 돌던 사내 애플리케이션을 두고,

- **고가용성으로 설계하면** — 한 대는 활성, 한 대는 **대기**로 둡니다. 활성이 죽으면 대기로 넘깁니다.
  이때 직원은 **다시 로그인해야 할 수 있고**, 짧은 가동 중단이 생깁니다. 그 정도는 감수합니다
- **내결함성으로 설계하면** — 두 대가 **모두 활성**입니다. 한 대가 죽어도 나머지가 이미 서비스 중이라
  실제로 중단이 없습니다

**활성-대기(액티브/패시브)** 는 대기 쪽이 평소에 일을 하지 않습니다.
넘기는 순간이 필요하고, 그 순간이 곧 가동 중단입니다. 대신 대기 쪽을 작게 유지하면 값이 쌉니다.
**활성-활성** 은 양쪽이 평소에도 실제 트래픽을 받습니다. 넘길 것이 없으니 중단도 없습니다.
대신 평상시에도 두 배를 돌리고 있는 셈이라 값이 비쌉니다.

그래서 두 설계는 **목표 자체가 다릅니다.** 고가용성은 중단을 짧게 만드는 쪽이고, 내결함성은 중단을 없애는 쪽입니다.
그리고 **내결함성 설계는 일반적으로 고가용성 설계보다 비쌉니다.**
`비용도 고려하라`는 단서가 붙으면 무조건 활성-활성으로 가는 보기가 오답이 되는 이유입니다.

### L2. 단일 장애점을 찾는 법

> **이번 강의에서 다룰 내용** — 단일 장애점이 무엇을 가리키는 말인지, AWS 가 권하는 찾는 절차, 그리고 계층마다 죽는 단위가 어떻게 다른지 살펴보겠습니다.

#### 그것 하나가 죽으면 전체가 멈추는 자리

**단일 장애점**은 **대체할 것이 없는 구성 요소**입니다.
그것 하나가 멈추면 나머지가 아무리 멀쩡해도 서비스 전체가 멈춥니다.
가용성 설계는 결국 이 자리를 하나씩 찾아 **여분을 붙이는 일**입니다.

주의할 점은 **여분을 붙이는 것만으로는 끝나지 않는다**는 것입니다. 세 가지가 함께 있어야 합니다.

1. **이중화** — 같은 역할을 하는 것이 둘 이상 있는가
2. **감지** — 하나가 죽은 것을 누가 알아채는가
3. **전환** — 알아챈 다음 트래픽을 살아 있는 쪽으로 어떻게 넘기는가

둘째와 셋째가 빠지면 서버가 두 대여도 사람이 새벽에 일어나 손으로 넘겨야 합니다.
`상태 확인` · `자동 교체` · `장애 조치` 라는 낱말이 정답 보기에 그렇게 자주 들어 있는 이유가 이것입니다.

#### 계층마다 죽는 단위가 다릅니다

| 계층 | 단일 장애점 | 답 |
|---|---|---|
| 인스턴스 | 한 대 | ASG (최소 2대) |
| 가용 영역 | AZ 하나 | **여러 AZ 에 걸친 ASG + ELB** |
| 리전 | 리전 하나 | 다중 리전 + Route 53 장애 조치 |
| 데이터베이스 | DB 한 대 | RDS 다중 AZ |
| 상태·세션 | 인스턴스 안의 세션 | 밖으로 (ElastiCache · DynamoDB) |

> **NAT 게이트웨이도 AZ 단위입니다.** AZ 마다 하나씩 두지 않으면 그게 단일 장애점이 됩니다.

여분을 어느 단위로 두느냐가 곧 **어디까지 버티는가**입니다.
한 AZ 안에 두 대를 두면 인스턴스 장애까지 버티고, 두 AZ 에 나누어 두면 AZ 장애까지 버팁니다.
`한 AZ 가 통째로 사라져도` 라는 지문에서 같은 AZ 안의 이중화 보기가 전부 탈락하는 근거가 여기에 있습니다.

#### 단일 장애점은 거꾸로 찾습니다

AWS 가 알려 주는 방법은 단순합니다. **장애에서 거꾸로 거슬러 생각하는 것**입니다.
아키텍처를 훑으면서 구성 요소를 하나씩 짚고, **그것이 죽으면 무슨 일이 일어나는지**를 묻습니다.

> 웹 서버 한 대가 죽으면? · 애플리케이션 서버 한 대가 죽으면? · 데이터베이스가 죽으면?
> · AZ 하나가 통째로 사라지면? · 이 NAT 게이트웨이가 죽으면?

이렇게 평가한 다음 각각을 어떻게 완화할지 정합니다. 시험에서 아키텍처 그림이 주어지는 문항은
사실상 이 절차를 머릿속으로 한 번 돌리라는 요구입니다.
설계에 필요한 리소스의 **양**을 정하는 일 — 서버와 데이터베이스의 **이중화**를 보장하는 것 — 만이 아니라,
**데이터 복제 · 트래픽 관리 · 장애 감지**를 맡을 구성 요소까지 함께 세는 것이 이 과제입니다.

많은 AWS 관리형 서비스는 **처음부터 고가용성이 내장된 채로** 만들어졌다는 점도 같이 기억하시기 바랍니다.
SQS · Lambda · Fargate 가 그렇습니다. 이런 서비스 앞에 이중화를 덧붙이는 보기는 대개 불필요한 답입니다.

### L3. 감지하고 넘기는 장치 — 상태 확인과 장애 조치

> **이번 강의에서 다룰 내용** — 죽은 것을 알아채는 장치가 계층마다 어떻게 다른지, 그리고 그 알아챔이 무엇을 당기는지 살펴보겠습니다.

#### 같은 상태 확인이라도 결과가 다릅니다

이중화를 해 두어도 **누가 언제 알아채느냐**에 따라 실제 복구 시간이 달라집니다.
AWS 에서 이 감지를 맡는 장치는 계층마다 따로 있고, 알아챈 뒤에 하는 일도 다릅니다.

| 감지하는 쪽 | 무엇을 보나 | 알아채면 |
|---|---|---|
| **ELB 상태 확인** | 등록된 대상이 응답하는가 | 그 대상에게 **트래픽을 보내지 않습니다**. 대상 자체는 그대로 둡니다 |
| **EC2 Auto Scaling 상태 확인** | 인스턴스가 정상인가 | 그 인스턴스를 **종료하고 새로 띄웁니다** |
| **Route 53 상태 확인** | 엔드포인트가 살아 있는가 | **DNS 응답을 바꿔** 다른 리전·엔드포인트로 보냅니다 |

세 줄의 차이가 문항을 가릅니다.
ELB 만으로는 죽은 인스턴스가 **계속 죽은 채로 남아** 대수가 줄어듭니다.
그래서 ASG 에 **ELB 상태 확인을 연결해** 두어야 비로소 "죽으면 자동으로 갈아 끼운다"가 완성됩니다.
`상태 확인 후 자동 교체` 라는 지문이 이 조합을 가리킵니다.

#### 넘길 수 있는 범위가 곧 버틸 수 있는 범위입니다

ELB 는 **AZ 안팎의 인스턴스 사이**로만 넘길 수 있습니다. 리전이 통째로 사라지면 ELB 도 함께 사라집니다.
리전을 넘는 전환은 그 위 계층, 곧 **DNS** 에서 일어납니다.
[[amazon-route-53\|Route 53]] 이 상태 확인 결과에 따라 응답할 주소를 바꾸는 방식입니다.

| 라우팅 정책 | 언제 |
|---|---|
| **장애 조치** | 기본 엔드포인트가 죽으면 대기 엔드포인트로. 리전 단위 전환의 기본 |
| **지연 시간 기반** | 사용자에게 가장 빠른 리전으로 |
| **지리 위치** | 접속 지역에 따라 정해진 리전으로 |

DNS 로 넘기는 방식에는 **응답이 캐시된 만큼 늦어진다**는 성질이 따라옵니다.
정말 빠른 전환이 필요하면 [[aws-global-accelerator\|Global Accelerator]] 처럼
**고정 IP** 로 받아 AWS 백본 안에서 경로를 바꾸는 쪽을 봅니다.

### L4. 데이터베이스를 살려 두는 방법

> **이번 강의에서 다룰 내용** — 다중 AZ 와 읽기 전용 복제본이 왜 다른 물건인지, 그리고 복제가 동기냐 비동기냐가 무엇을 바꾸는지 살펴보겠습니다.

#### 동기 복제와 비동기 복제

데이터베이스를 이중화한다는 것은 **같은 데이터를 두 벌 들고 있는다**는 뜻이고,
여기서 갈리는 지점은 **두 벌을 언제 맞추느냐**입니다.

**동기 복제**는 쓰기를 받았을 때 **사본 쪽에도 기록된 것을 확인한 뒤에** 성공을 돌려줍니다.
그래서 넘어가도 잃는 데이터가 없습니다. 대신 매 쓰기가 사본을 기다리므로 그만큼 느려지고,
멀리 떨어진 곳에는 쓰기 어렵습니다.

**비동기 복제**는 먼저 성공을 돌려주고 사본은 **뒤따라 갑니다.**
빠르고 먼 거리에도 쓸 수 있지만, 넘어가는 순간 **아직 따라오지 못한 만큼을 잃습니다.**
이 잃는 양이 `L6` 에서 볼 RPO 의 정체입니다.

RDS 의 두 기능이 정확히 이 두 갈래 위에 있습니다.

| | 다중 AZ | 읽기 전용 복제본 |
|---|---|---|
| 목적 | **가용성** | **읽기 성능** |
| 복제 | 동기 | 비동기 |
| 평소에 쓰나 | 대기 인스턴스는 **안 쓴다** | 읽기 트래픽을 받는다 |
| 장애 시 | **자동** 전환 (엔드포인트 그대로) | 수동 승격 |

`읽기가 느리다` → 복제본. `장애 시에도 계속` → 다중 AZ. **둘은 같이 쓸 수 있습니다.**

다중 AZ 를 외울 때는 동작만이 아니라 **얼마나 오래 끊기는지**까지 같이 보시기 바랍니다.
자동 장애 조치는 즉시가 아니라 **데이터베이스 접근이 중단되는 구간**을 남깁니다.
`무중단` 을 요구하는 지문에서 다중 AZ 하나만으로 답이 되지 않는 경우가 여기서 생깁니다.

#### 데이터베이스의 장애 조치를 리전 밖으로

| | 무엇을 하나 |
|---|---|
| [[amazon-rds\|RDS]] 다중 AZ | **AZ 단위**. 기본이 죽으면 자동 장애 조치 |
| [[amazon-aurora\|Aurora]] 글로벌 데이터베이스 | **리전 단위**. 교차 리전 장애에 대비. 승격까지 걸리는 시간을 알아 둘 것 |
| [[amazon-dynamodb\|DynamoDB]] 글로벌 테이블 | 여러 리전에서 **동시에 쓰기**. 활성-활성 |

마지막 줄이 앞의 둘과 성격이 다릅니다.
앞의 둘은 대기 쪽이 평소에 쓰기를 받지 않는 **활성-대기**이고,
글로벌 테이블은 양쪽이 모두 쓰기를 받는 **활성-활성**입니다.
`여러 리전에서 동시에 쓰기` 라는 지문이 곧바로 DynamoDB 로 가는 이유입니다.

**RDS 프록시** 는 이 과제에서도 다시 나옵니다. RDS 를 위한 **완전관리형 고가용성 데이터베이스 프록시**로,
연결을 풀링해 확장성을 올리는 동시에 **데이터베이스 장애에 대한 복원력**을 높입니다.

- 서버리스 애플리케이션은 연결을 **아주 많이, 아주 빠르게 열고 닫아** 데이터베이스의 메모리와 컴퓨팅을 소진시킵니다
- 프록시를 끼우면 연결을 **풀링하고 공유**해 그 소진을 막습니다
- Aurora·RDS 의 **장애 조치 시간이 최대 66% 까지 짧아집니다**
- [[aws-secrets-manager\|Secrets Manager]] · [[aws-iam\|IAM]] 과 통합해 자격 증명과 접근까지 함께 관리합니다

### L5. 백업과 복제는 다른 물건입니다

> **이번 강의에서 다룰 내용** — 사본을 두는 두 가지 방식이 각각 어떤 사고를 막아 주는지, 그리고 백업을 어디에 두어야 하는지 살펴보겠습니다.

#### 하나는 과거의 사본, 하나는 현재의 사본

둘 다 "데이터를 한 벌 더 두는 일"이지만 막아 주는 사고가 다릅니다.

**복제**는 **지금 이 순간의 사본**을 유지합니다. 원본이 바뀌면 사본도 곧바로 따라 바뀝니다.
그래서 원본이 있는 자리가 통째로 사라지는 사고 — 인스턴스 · AZ · 리전 장애 — 를 넘길 때 씁니다.
넘어가면 거의 최신 데이터로 계속할 수 있습니다.

**백업**은 **특정 시점의 사본**을 따로 떼어 보관합니다. 원본이 바뀌어도 백업은 그대로 남습니다.
그래서 사람이 실수로 지웠거나, 잘못된 배포가 데이터를 망가뜨렸거나, 랜섬웨어가 파일을 덮어썼을 때
**그 시점으로 되돌아가는** 수단이 됩니다.

여기서 시험이 노리는 지점이 나옵니다. **복제는 실수까지 복제합니다.**
테이블을 잘못 지우면 사본에서도 그 삭제가 그대로 반영됩니다.
그래서 `실수로 삭제한 데이터를 되살려야` 라는 지문에서는 다중 AZ 나 교차 리전 복제가 답이 되지 않고,
**백업 · 스냅샷 · 버전 관리 · 특정 시점 복구** 쪽이 답이 됩니다.

| | 무엇을 막나 | 시험의 신호 |
|---|---|---|
| **복제** | 인프라가 사라지는 사고 | `AZ 장애` · `리전 장애` · `장애 조치` |
| **백업** | 데이터가 잘못되는 사고 | `실수로 삭제` · `특정 시점으로 복원` · `보존 기간` |

둘은 서로를 대신하지 못하므로 실제 설계에서는 **둘 다** 둡니다.

#### 백업을 어디에 두는가

RTO·RPO 를 정했으면 그것을 실제로 충족하는 **백업 계획**이 따라와야 합니다.
AWS 가 이 자리에서 이름을 대는 스토리지는 셋입니다.

| | 언제 |
|---|---|
| [[amazon-s3\|S3]] | 저렴하고 내구성이 매우 높은 **객체** 스토리지. 백업의 기본 자리 |
| [[amazon-efs\|EFS]] | 리눅스 계열 **파일** 스토리지가 필요할 때 |
| [[amazon-fsx\|FSx]] | Windows 파일 서버·Lustre 등 특정 파일 시스템이 필요할 때 |

셋 다 **가용성 · 암호화 옵션 · 제한 사항**을 함께 알고 있어야 한다고 못 박습니다.
그리고 [[aws-backup\|AWS Backup]] 은 이 백업들을 **한 곳에서 정책으로 묶어** 관리하는 자리입니다.

### L6. 재해 복구 — RPO·RTO 와 전략 네 가지

> **이번 강의에서 다룰 내용** — RPO 와 RTO 가 각각 무엇을 재는 시간인지, 그리고 DR 전략 네 가지가 왜 하나의 축 위에 놓이는지 살펴보겠습니다.

#### 재해 복구는 "계획"입니다

고가용성과 내결함성이 **설계**라면, 재해 복구는 **미리 세워 두는 계획과 절차**입니다.
AWS 가 한 문장으로 정리합니다. **재해에서 복구를 시작하기 가장 나쁜 시점은 그 재해가 한창일 때입니다.**

- 재해가 나기 **전에** 복구 계획이 이미 서 있어야 합니다
- 백업은 **시스템과 같은 건물에 두지 않습니다.** 그 건물이 당하면 백업도 함께 당합니다.
  다른 사이트나 클라우드로 뺍니다
- **재해 복구 훈련을 실제로 돌려 봅니다.** 그래야 진짜 상황에서 절차가 매끄럽게 굴러갑니다
- 복구 수단은 데이터만이 아닙니다. 환경을 다시 세울 **CloudFormation 템플릿**을 준비해 두는 것도 계획의 일부입니다

#### RPO 와 RTO 는 서로 다른 시간을 잽니다

계획을 세우려면 먼저 **무엇을 얼마나 허용할 것인지**를 숫자로 정해야 합니다.
그 숫자가 둘이고, 둘은 재는 대상이 다릅니다.

**RPO 는 데이터의 시간입니다.** 재해가 난 순간에서 **거꾸로 얼마나 되돌아가도 되는가**를 잽니다.
6시간마다 백업한다면 최악의 경우 6시간 치 데이터가 사라지므로 RPO 는 6시간입니다.
줄이려면 **더 자주 찍거나 계속 복제해야** 하고, 그것이 곧 비용입니다.

**RTO 는 서비스의 시간입니다.** 멈춘 순간부터 **다시 쓸 수 있게 되기까지 얼마나 걸려도 되는가**를 잽니다.
줄이려면 복구할 것을 **미리 켜 두어야** 하고, 그것도 곧 비용입니다.

| | 뜻 |
|---|---|
| **RPO** (복구 지점 목표) | **데이터를 얼마나 잃어도 되는가** — 마지막 백업 시점까지 되돌아간다 |
| **RTO** (복구 시간 목표) | **얼마나 빨리 복구되어야 하는가** |

요구사항에서 이 둘을 끄집어낼 때는 **질문으로 바꿔** 보시기 바랍니다.
RPO 는 `데이터를 얼마나 자주 백업해야 하는가`, RTO 는 `애플리케이션을 못 쓰는 최대 시간은 얼마인가` 입니다.

두 값은 **따로 움직입니다.** 데이터는 1초도 잃으면 안 되지만 복구에 한나절이 걸려도 되는 시스템이 있고,
반대로 몇 시간 치 데이터는 버려도 되지만 5분 안에 다시 떠야 하는 시스템도 있습니다.
지문이 둘 중 하나만 주었다면 **주지 않은 쪽은 답을 가르는 조건이 아니라는 뜻**입니다.

#### DR 전략 4종 — 미리 무엇을 켜 두느냐의 차이

네 전략의 차이는 결국 **재해가 나기 전에 대상 리전에 무엇을 얼마나 켜 두는가** 하나입니다.
아무것도 안 켜 두면 싸고 느리고, 전부 켜 두면 비싸고 빠릅니다.

```d2
direction: right

br: "백업 & 복원\nRTO 시간~일\n비용 최저" {
  a: "백업만 보관\n복구 시 전부 새로 만든다"
}
pl: "파일럿 라이트\nRTO 수십 분" {
  a: "DB 는 복제 중\n서버는 꺼져 있다"
}
ws: "예열 대기\nRTO 수 분" {
  a: "전체가 작게 돌고 있다\n장애 시 키운다"
}
ms: "다중 사이트 활성\nRTO 거의 0\n비용 최고" {
  a: "양쪽이 실제 트래픽을\n동시에 받는다"
}

br -> pl -> ws -> ms: "비용과 복구 속도가 함께 오른다"
```

핵심은 **네 전략이 같은 축 위에 있다**는 것입니다.
왼쪽으로 갈수록 싸고 느리고, 오른쪽으로 갈수록 비싸고 빠릅니다.
문항은 항상 `RTO 는 N분` 같은 조건을 주고 그 축의 한 지점을 고르게 합니다.

| 지문의 조건 | 전략 |
|---|---|
| `비용이 가장 중요` · `며칠 걸려도 된다` | **백업 & 복원** |
| `데이터는 최신이어야 하지만 서버는 꺼 둬도 된다` | **파일럿 라이트** |
| `몇 분 안에` · `축소된 규모로 이미 돌고 있다` | **예열 대기** |
| `무중단` · `양쪽에서 동시에 서비스` | **다중 사이트 활성** |

파일럿 라이트와 예열 대기를 가르는 지점은 **애플리케이션 계층이 돌고 있는가**입니다.
파일럿 라이트는 데이터만 계속 따라가고 서버는 꺼져 있어 **켜는 시간**이 RTO 에 들어갑니다.
예열 대기는 작게라도 이미 돌고 있어 **키우기만** 하면 됩니다.

AWS 는 이 네 가지를 다시 **두 덩이**로 묶습니다. 보기를 반으로 줄일 때 쓰기 좋습니다.

| | 들어가는 전략 | 뜻 |
|---|---|---|
| **액티브/패시브** | 백업 & 복원 · 파일럿 라이트 · 웜 스탠바이 | 평소에는 **한쪽만** 서비스합니다 |
| **액티브/액티브** | 다중 사이트 활성 | **양쪽이 동시에** 실제 트래픽을 받습니다 |

그리고 이 스타일들을 **하나만 골라 쓸 필요는 없습니다.** 시스템마다 등급을 달리 매겨,
핵심 워크로드는 웜 스탠바이로 두고 나머지는 백업 & 복원으로 가는 조합이 실제 설계에 가깝습니다.

### L7. 복구를 자동화하고, 계속 지켜봅니다

> **이번 강의에서 다룰 내용** — 복구를 사람 손에서 떼어 놓는 도구들과, 설계를 계속 손보기 위해 무엇을 보아야 하는지 살펴보겠습니다.

#### 복구를 사람 손에서 떼어 놓는 도구들

| | 무엇을 맡나 |
|---|---|
| **AMI · EC2 Image Builder** | EC2 에서 도는 애플리케이션을 **이미지로 굳혀** 다른 리전·AZ 에서 바로 띄운다 |
| **CloudFormation · Elastic Beanstalk** | 배포 자체를 자동화한다. 재해 후 환경을 **다시 찍어내는** 수단 |
| [[amazon-ecs\|ECS]] · [[amazon-eks\|EKS]] | 컨테이너 배포를 여러 AZ 에 걸쳐 유지한다 |
| [[aws-elastic-disaster-recovery\|Elastic Disaster Recovery]] | 클라우드 네이티브가 아닌 **레거시**의 복구. **온프레미스와 클라우드 기반 양쪽**에 쓴다 |

AWS 가 특히 강조하는 지점은 **레거시**입니다. 구성 요소를 옮길 수 없거나
데이터 복제 같은 기능이 사용 사례에 맞지 않는 경우에도 신뢰성 요구를 충족하는 방법을 알아야 합니다.

#### 설계를 계속 손보려면 먼저 보여야 합니다

Well-Architected Framework 는 설계를 **최신 상태로 유지하고 계속 개선하는 것**까지 요구합니다.
그러려면 주요 지표를 추적하고 그 지표에 반응할 수 있어야 합니다.

| | 무엇을 보나 |
|---|---|
| [[amazon-cloudwatch\|CloudWatch]] | **지표와 로그**. 경보로 자동화된 작업을 트리거한다 |
| **AWS X-Ray** | 요청이 서비스들을 지나가는 **경로를 추적**한다. 어느 구간이 느린지 |
| [[amazon-eventbridge\|EventBridge]] | 환경의 **변화**에 거의 실시간으로 반응한다 |

`무엇이 느린지 구간별로` 는 X-Ray, `임곗값을 넘으면 조치` 는 CloudWatch 경보입니다.

#### 네트워킹을 모르면 여기서 막힙니다

AWS 는 고가용성·내결함성의 **기초가 네트워킹**이라고 말합니다.
라우팅 테이블의 동작, **VPC 피어링**, [[aws-transit-gateway\|Transit Gateway]],
[[aws-site-to-site-vpn\|Site-to-Site VPN]], [[aws-direct-connect\|Direct Connect]] 로케이션과 게이트웨이,
**Route 53 Resolver** 까지가 이름이 오른 목록입니다.
연결 경로 자체가 단일 장애점이 되는 문항이 여기서 나옵니다.

> [!info] AWS 가 직접 경고한 의외의 조합
> 강의는 **Amazon Polly** 가 이 버전의 시험에 다시 등장한다는 이야기를 많이 들었다고 밝힙니다.
> 시나리오는 이렇습니다 — IT 서비스 요청이 대량으로 들어오는데 분류를 요청자가 직접 해서
> 오분류가 잦고, 그 탓에 해결이 늦어집니다. **Amazon Comprehend** 로 요청을 자동 분류하고,
> **Polly** 로 음성 출력을 붙입니다. Polly 는 **Amazon Connect** 안에서 셀프 서비스를 만들 때도 쓰입니다.
> 고가용성 문항에 AI 서비스 이름이 섞여 나와도 당황하지 마시기 바랍니다.

## 4. 시험에서 갈리는 지점

| 지문에 이게 있으면 | 이쪽 |
|---|---|
| `한 AZ 가 죽어도` | **여러 AZ 에 걸친 ASG + ELB**. 단일 AZ 보기는 전부 지운다 |
| `읽기 쿼리가 느리다` | **읽기 전용 복제본** (다중 AZ 가 아니다) |
| `DB 장애 시에도 계속` | **RDS 다중 AZ** |
| `리전 전체 장애` | 다중 리전 + **Route 53 장애 조치 라우팅** |
| `여러 리전에서 동시에 쓰기` | **DynamoDB 글로벌 테이블** |
| `RPO 가 거의 0` | 동기 복제 또는 지속 복제 (백업만으로는 안 된다) |
| `RTO 수 분` + `비용도 중요` | **예열 대기** |
| `서버를 통째로 다른 리전에 복제해 두었다가` | **Elastic Disaster Recovery** |
| `상태 확인 후 자동 교체` | ASG 의 **ELB 상태 확인**을 켜는 것 |
| `리전 간 장애 조치` + `관계형 데이터베이스` | **Aurora 글로벌 데이터베이스** |
| `지연 시간이 가장 낮은 리전으로` | Route 53 **지연 시간 기반 라우팅** |
| `고정 IP` · `비 HTTP 트래픽을 리전 간에` | **Global Accelerator** |
| `서버리스가 DB 연결을 소진` · `장애 조치를 더 빨리` | **RDS 프록시** |
| `어느 구간에서 느려지는지 추적` | **X-Ray** (CloudWatch 는 지표·경보) |
| `백업을 같은 데이터 센터에 보관 중` | 그 자체가 오답 조건. 다른 사이트·리전으로 뺀다 |
| `비용도 중요` + `무중단까지는 아니어도` | 활성-활성 보기를 지운다. 더 비싼 쪽이다 |
| `SQS·Lambda·Fargate 를 이중화해야` | 이미 **복원력이 내장**되어 있다. 대개 불필요한 보기 |

> [!warning] 가장 흔한 함정
> **다중 AZ 를 읽기 성능 해결책으로 고르는 것.** 대기 인스턴스는 트래픽을 받지 않습니다.
> 반대로 **읽기 전용 복제본을 가용성 해결책으로 고르는 것**도 오답입니다. 자동 전환이 안 됩니다.

## 6. 셀프 체크

- [ ] 고가용성과 내결함성을 예를 들어 구분한다
- [ ] RDS 다중 AZ 와 읽기 전용 복제본을 각각 무엇을 위해 쓰는지 말한다
- [ ] RPO 와 RTO 를 각각 한 문장으로 정의한다
- [ ] DR 4종을 비용·복구 속도 순으로 늘어놓는다
- [ ] `RTO 는 10분, 비용은 최소` 라는 조건에서 어느 전략인지 고른다
- [ ] 아키텍처 그림에서 단일 장애점을 세 군데 찾아낸다
- [ ] DR 4종을 액티브/패시브와 액티브/액티브로 나눠 담는다
- [ ] CloudWatch 와 X-Ray 를 무엇으로 가르는지 한 문장으로 말한다
- [ ] 재해 복구가 설계가 아니라 계획이라는 말의 뜻을 예를 들어 설명한다
- [ ] 백업과 복제가 각각 어떤 사고를 막아 주는지 구분한다
- [ ] ELB · Auto Scaling · Route 53 의 상태 확인이 알아챈 뒤 각각 무엇을 하는지 말한다
