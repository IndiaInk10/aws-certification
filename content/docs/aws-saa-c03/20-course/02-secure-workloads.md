> 도메인 1 · 보안 아키텍처 설계 **30%** · 과제 명세 3개 중 **두 번째**

## 1. 왜 필요한가

> 앞 과제가 "누가 들어오는가"였다면 여기는 **"어디로 들어오는가"** 입니다.

권한을 아무리 잘 짜도 인스턴스가 인터넷에 그대로 노출돼 있으면 소용이 없습니다.
이 과제는 **네트워크 경계**를 묻습니다. 그리고 SAA 에서 그림이 필요한 자리는 대부분 여기입니다 —
VPC 안에 가용 영역이 있고, 그 안에 퍼블릭·프라이빗 서브넷이 있고, 그 안에 인스턴스가 있는 **3중 중첩** 구조.

시험 문항은 거의 항상 같은 모양입니다.
*"인터넷에서 접근할 수 없어야 하는데 이 리소스가 저 리소스에 닿아야 한다."*
답은 **프라이빗 서브넷 + 필요한 통로 하나**입니다. 그 통로가 무엇이냐가 문제입니다.

## 3. 이 과제가 묻는 것

---

### L1. VPC 와 서브넷 — 내 네트워크를 잘라 두는 일

> **이번 강의에서 다룰 내용** — VPC 가 무엇을 빌려 주는 것인지, 그리고 그 안을 서브넷으로 나누는 이유를 살펴보겠습니다.

#### VPC 는 내 계정 몫으로 잘라 낸 네트워크입니다

**Amazon VPC** 는 AWS 클라우드 안에 **내 계정만 쓰는 가상 네트워크**를 만들어 주는 서비스입니다.
물리적으로는 다른 고객의 트래픽과 같은 설비 위를 지나가지만, **논리적으로 완전히 격리되어** 서로 보이지 않습니다.
온프레미스에서 스위치와 라우터를 사서 사무실 네트워크를 꾸미던 일을, 설정 화면에서 하는 것이라고 보시면 됩니다.

VPC 를 만들 때 반드시 정해야 하는 것이 하나 있습니다. **이 네트워크가 쓸 IP 주소 범위**입니다.
이 범위를 적는 방법이 다음 강의에서 볼 CIDR 입니다.

#### 서브넷은 VPC 를 가용 영역 단위로 자른 조각입니다

VPC 하나를 그대로 쓰지 않고 **서브넷**으로 나눕니다. 서브넷은 두 가지 일을 동시에 합니다.

- **자리를 정합니다.** 서브넷은 **가용 영역 하나 안에** 들어갑니다. 인스턴스를 어느 서브넷에 두느냐가 곧 어느 AZ 에 두느냐입니다
- **경계를 만듭니다.** 서브넷마다 라우팅과 네트워크 ACL 을 따로 붙일 수 있어, 여기서 퍼블릭과 프라이빗이 갈립니다

서브넷은 서비스가 실제로 상주하고 실행되는 자리입니다.
EC2 인스턴스도, RDS 인스턴스도, 로드 밸런서의 노드도 전부 어느 서브넷 안에 놓입니다.

```layers VPC 안에 AZ 가 있고, AZ 안에 서브넷이 있습니다
VPC — 10.0.0.0/16 | 리전 하나 · 계정 하나
  가용 영역 A
    퍼블릭 서브넷 — 10.0.0.0/24 | IGW 로 가는 경로가 있습니다
    프라이빗 서브넷 — 10.0.1.0/24 | 그 경로가 없습니다
  가용 영역 B
    퍼블릭 서브넷 — 10.0.2.0/24
    프라이빗 서브넷 — 10.0.3.0/24
```

#### VPC 두 종류와 복원력 수준

VPC 에는 계정을 만들 때 리전마다 딸려 오는 **기본 VPC** 와, 직접 만드는 **사용자 지정 VPC** 가 있습니다.
둘은 **처음 상태의 보안 구성이 다릅니다.** 기본 VPC 는 퍼블릭 서브넷과 인터넷 게이트웨이가 이미 붙어 있어
바로 인터넷에 닿고, 사용자 지정 VPC 는 아무것도 없는 상태에서 시작합니다.
`기본 설정 그대로 두었더니 노출되었다`는 지문은 여기를 묻는 것입니다.

| 대상 | 복원력 수준 |
|---|---|
| **VPC** | **리전** — 하나의 리전, 하나의 계정 안에 있습니다 |
| **서브넷** | **가용 영역** — 서비스가 실제로 상주하는 자리입니다 |

그래서 `AZ 하나가 죽어도 살아 있어야 한다`는 요구는 **서브넷을 AZ 마다 두는 것**으로 풀립니다.
VPC 를 여러 개 만드는 보기는 과한 구성입니다.

### L2. CIDR — 주소 범위를 자르는 표기법

> **이번 강의에서 다룰 내용** — `10.0.0.0/16` 같은 표기가 무엇을 뜻하는지, 그리고 그 숫자가 서브넷을 어떻게 나누는지 살펴보겠습니다.

#### 슬래시 뒤의 숫자는 "고정된 앞부분의 길이" 입니다

IPv4 주소는 `10.0.1.25` 처럼 숫자 네 토막이고, **토막마다 8비트**라서 전부 32비트입니다.
CIDR 표기는 그 주소 뒤에 슬래시와 숫자를 붙여 씁니다.
이 숫자는 **앞에서부터 몇 비트가 고정인지**를 뜻합니다.

`10.0.0.0/16` 이라면 앞 16비트, 즉 `10.0` 까지가 고정이고 **뒤 16비트가 자유롭게 쓸 수 있는 자리**입니다.
자유로운 자리가 16비트면 주소는 2의 16승, 곧 65,536 개입니다.

| 표기 | 고정 | 쓸 수 있는 주소 수 | 감각 |
|---|---|---|---|
| `/16` | 앞 두 토막 | 약 65,000 | VPC 전체에 흔히 쓰는 크기 |
| `/24` | 앞 세 토막 | 256 | 서브넷 하나에 흔히 쓰는 크기 |
| `/28` | | 16 | 아주 작은 조각 |

**숫자가 작을수록 범위가 넓습니다.** 고정된 부분이 짧아지니 남는 자리가 늘어나기 때문입니다.
`/16` 이 `/24` 보다 크다는 것만 잡아 두시면 시험에서 헤맬 일은 없습니다.

#### 서브넷은 VPC 범위를 겹치지 않게 잘라 씁니다

VPC 에 `10.0.0.0/16` 을 주었다면, 그 안의 서브넷들은 **이 범위 안에서** 자기 몫을 떼어 갑니다.
그리고 **서브넷끼리 범위가 겹칠 수 없습니다.** 겹치면 어느 서브넷으로 보내야 할지 정할 수 없기 때문입니다.

주소 수를 셀 때 한 가지 함정이 있습니다.
**서브넷마다 AWS 가 IP 주소 5개를 먼저 가져갑니다.**
네트워크 주소, 라우터용, DNS 용, 예비, 브로드캐스트 몫입니다.
그래서 `/24` 서브넷에 실제로 쓸 수 있는 주소는 256개가 아니라 **251개**입니다.

> [!warning] 범위가 겹치면 나중에 못 잇습니다
> VPC 두 개를 피어링으로 이으려면 두 VPC 의 CIDR 이 **겹치지 않아야 합니다.**
> 온프레미스와 VPN 으로 이을 때도 마찬가지입니다.
> 그래서 주소 범위는 지금 필요한 크기가 아니라 **나중에 무엇과 이을지**를 보고 정합니다.
> 지문에 `기존 네트워크와 주소가 겹친다` 가 나오면 그것이 답을 가르는 조건입니다.

### L3. 라우팅 테이블 — 퍼블릭과 프라이빗을 가르는 한 줄

> **이번 강의에서 다룰 내용** — 라우팅 테이블이 정확히 무엇을 정하는지, 그리고 왜 서브넷의 성격이 이 표 한 줄로 결정되는지 살펴보겠습니다.

#### 목적지 대역을 보고 어디로 넘길지 정합니다

라우팅 테이블은 **"이 주소로 가는 트래픽은 저리로 넘겨라"** 를 적어 둔 목록입니다.
줄마다 **목적지 대역(CIDR)** 과 **대상**이 짝지어 있고, 패킷이 나갈 때마다 이 표를 조회합니다.
서브넷마다 라우팅 테이블을 하나씩 연결하며, 아무것도 붙이지 않으면 VPC 의 기본 라우팅 테이블을 씁니다.

| 목적지 | 대상 | 뜻 |
|---|---|---|
| `10.0.0.0/16` | `local` | **지울 수 없는 줄입니다.** VPC 안끼리는 언제나 통합니다 |
| `0.0.0.0/0` | 인터넷 게이트웨이 | 위에서 못 찾은 나머지는 전부 인터넷으로 — **이 줄이 있으면 퍼블릭 서브넷입니다** |
| `0.0.0.0/0` | NAT 게이트웨이 | 나머지를 NAT 로 — 나갈 수만 있는 프라이빗 서브넷 |

`0.0.0.0/0` 은 "고정된 비트가 0개", 즉 **모든 주소**입니다.
그래서 다른 줄에서 걸리지 않은 트래픽이 마지막으로 떨어지는 자리가 됩니다.

#### 서브넷 설정에 "퍼블릭" 스위치는 없습니다

서브넷 설정 어디에도 퍼블릭·프라이빗을 고르는 항목이 없습니다.
**인터넷 게이트웨이로 가는 경로가 라우팅 테이블에 있으면** 퍼블릭, 없으면 프라이빗입니다.
`서브넷을 프라이빗으로 바꾼다` 는 조작은 곧 **그 줄을 지우는 일**입니다.

```d2
vpc: "VPC 10.0.0.0/16" {
  az_a: "가용 영역 A" {
    pub_a: "퍼블릭 서브넷" {
      nat: "NAT 게이트웨이"
      alb_a: "ALB"
    }
    pri_a: "프라이빗 서브넷" {
      ec2_a: "EC2"
    }
  }
  az_b: "가용 영역 B" {
    pub_b: "퍼블릭 서브넷" {
      alb_b: "ALB"
    }
    pri_b: "프라이빗 서브넷" {
      ec2_b: "EC2"
    }
  }
  ep: "S3 Gateway 엔드포인트"
}

igw: "인터넷 게이트웨이"
users: "사용자"
s3: "Amazon S3"

users -> igw
igw -> vpc.az_a.pub_a.alb_a
igw -> vpc.az_b.pub_b.alb_b
vpc.az_a.pub_a.alb_a -> vpc.az_a.pri_a.ec2_a
vpc.az_b.pub_b.alb_b -> vpc.az_b.pri_b.ec2_b
vpc.az_a.pri_a.ec2_a -> vpc.az_a.pub_a.nat: "밖으로만"
vpc.az_a.pub_a.nat -> igw
vpc.az_a.pri_a.ec2_a -> vpc.ep
vpc.ep -> s3: "인터넷을 안 탄다"
```

### L4. 문을 여는 세 가지 장치 — IGW · NAT · 엔드포인트

> **이번 강의에서 다룰 내용** — 세 장치가 각각 어느 방향으로 무엇을 여는지 살펴보겠습니다. 이름이 비슷해 보이지만 여는 문이 전혀 다릅니다.

#### 인터넷 게이트웨이 — 양방향으로 인터넷을 엽니다

**인터넷 게이트웨이(IGW)** 는 **VPC 에 붙습니다.** 서브넷이 아닙니다. VPC 하나에 하나면 됩니다.
붙였다고 바로 통하는 것은 아니고, **라우팅 테이블에 경로를 적어야** 그 서브넷이 인터넷에 닿습니다.

IGW 를 지나려면 리소스에 **퍼블릭 IP 주소**가 있어야 합니다.
그래서 "퍼블릭 서브넷에 있는데 인터넷에서 안 보인다" 는 상황의 원인은 대개 경로가 아니라 주소 쪽입니다.

#### NAT 게이트웨이 — 나가는 방향만 엽니다

프라이빗 서브넷의 인스턴스도 밖에서 패치를 받아야 할 때가 있습니다.
그렇다고 IGW 경로를 주면 **밖에서도 들어올 수 있게** 되어 프라이빗이 아니게 됩니다.

**NAT 게이트웨이**는 이 요구를 반쪽만 들어주는 장치입니다.
프라이빗 인스턴스가 보낸 패킷의 출발지 주소를 **NAT 자신의 퍼블릭 주소로 바꿔서** 대신 내보내고,
돌아온 응답을 원래 인스턴스에게 되돌려 줍니다.
그래서 나갈 수는 있어도 **밖에서 먼저 말을 걸 수는 없습니다.** 인스턴스의 프라이빗 IP 는 밖에 드러나지 않습니다.

여기서 자주 걸리는 함정이 두 가지입니다.

- NAT 게이트웨이는 **퍼블릭 서브넷에 놓입니다.** 자기가 인터넷에 닿아야 남을 내보낼 수 있기 때문입니다
- NAT 게이트웨이는 **AZ 하나에 사는 물건입니다.** 그 AZ 가 죽으면 그 NAT 를 쓰던 서브넷도 같이 끊깁니다

#### VPC 엔드포인트 — 인터넷을 아예 타지 않고 AWS 서비스로 갑니다

S3 나 DynamoDB 는 VPC 밖에 있는 **AWS 퍼블릭 서비스**입니다.
프라이빗 서브넷에서 S3 를 부르려면 원래는 NAT 를 거쳐 인터넷으로 나갔다 들어와야 합니다.

**VPC 엔드포인트**는 그 왕복을 없앱니다. VPC 안에 만드는 통로이고,
게이트웨이도 NAT 도 없이 **AWS 내부 네트워크만 타고** 서비스에 닿습니다.
데이터가 인터넷에 나가지 않으므로 더 안전하고, NAT 처리량 요금도 들지 않습니다.

| | 어떻게 붙나 | 대상 |
|---|---|---|
| **게이트웨이 엔드포인트** | 라우팅 테이블에 경로가 추가됩니다 | **S3 · DynamoDB 뿐입니다.** 추가 요금이 없습니다 |
| **인터페이스 엔드포인트** | 서브넷 안에 **ENI** 가 생기고 프라이빗 IP 를 받습니다 | 그 밖의 대부분의 AWS 서비스. PrivateLink 기술을 씁니다 |

#### 밖으로 나가는 통로 세 가지

| | 무엇을 위해 |
|---|---|
| **NAT 게이트웨이** | 프라이빗 서브넷이 **인터넷으로** 나갈 때 (패치·업데이트). 밖에서는 못 들어온다 |
| **VPC 엔드포인트** | **AWS 서비스**에 갈 때. 인터넷을 아예 안 탄다 — 더 안전하고 대개 더 싸다 |
| **PrivateLink** | 남의 VPC 에 있는 **서비스 하나**에 갈 때 |

> [!tip] 피어링이 아니라 PrivateLink 인 이유
> 애플리케이션 하나를 여러 VPC 에 열어 줘야 할 때 피어링으로도 됩니다.
> 다만 **VPC 가 늘어날수록 연결을 관리하는 부담이 같이 늘고**, 피어링은 그 VPC 의 **다른 애플리케이션까지 노출**합니다.
> PrivateLink 는 게이트웨이도 피어링도 없이 **서비스 하나만** 수십·수백 개 VPC 에 여는 방법입니다.
> 지문에 `수십 개 VPC`, `다른 것은 보이면 안 된다`가 함께 있으면 이쪽입니다.

### L5. 보안 그룹과 네트워크 ACL — 붙는 자리와 상태 저장

> **이번 강의에서 다룰 내용** — 이름이 닮은 두 방화벽이 어디에 붙는지, 그리고 "상태를 저장한다" 는 말이 실제로 무슨 뜻인지 살펴보겠습니다.

#### 붙는 자리가 다릅니다

라우팅이 "어디로 갈 수 있는가" 라면, 이 둘은 "**들어와도 되는가**" 를 봅니다.
그런데 서 있는 자리가 다릅니다.

- **보안 그룹**은 **인스턴스의 네트워크 카드(ENI)** 에 붙습니다. 인스턴스 바로 앞을 지키는 문지기입니다
- **네트워크 ACL** 은 **서브넷의 경계**에 붙습니다. 서브넷을 드나드는 모든 트래픽이 여기를 지납니다

그래서 같은 서브넷 안의 두 인스턴스끼리 주고받는 트래픽은 **네트워크 ACL 을 지나지 않습니다.**
그 사이를 막고 싶다면 보안 그룹으로 막아야 합니다.

#### 상태 저장이란 나간 것을 기억한다는 뜻입니다

**보안 그룹은 상태 저장(stateful)** 입니다.
인바운드로 들어온 요청을 기억해 두었다가, 그에 대한 **응답은 아웃바운드 규칙과 무관하게 자동으로 내보냅니다.**
반대 방향도 같습니다. 나갔던 요청의 응답은 인바운드 규칙에 없어도 들어옵니다.

**네트워크 ACL 은 상태 비저장(stateless)** 입니다. 기억하지 않습니다.
들어오는 것과 나가는 것을 **각각 규칙으로 허용**해야 합니다.
웹 응답이 돌아가는 포트는 요청 포트가 아니라 **임시 포트**라서, 여기가 자주 사고 원인이 됩니다.
`인바운드는 열었는데 응답이 안 나간다` 는 증상은 대개 네트워크 ACL 의 아웃바운드입니다.

#### 보안 그룹 vs 네트워크 ACL

이름이 비슷해서 매 시험 나옵니다.

| | 보안 그룹 | 네트워크 ACL |
|---|---|---|
| 적용 대상 | **인스턴스**(ENI) | **서브넷** |
| 상태 | 상태 저장 — 나간 것의 응답은 자동 허용 | 상태 **비**저장 — 응답도 규칙에 있어야 한다 |
| 규칙 | **허용만** | 허용 + **거부** |
| 평가 | 전체 규칙을 합쳐서 | **번호 순서대로**, 먼저 맞는 규칙이 이긴다 |
| 기본값 | **새로 만들면** 인바운드 전부 차단 | **기본 NACL 은** 전부 허용 · **직접 만들면 전부 거부** |

> **특정 IP 하나를 막아야 한다** → 보안 그룹은 거부 규칙이 없으므로 **NACL** 입니다.

> [!tip] 보안 그룹은 다른 보안 그룹을 가리킬 수 있습니다
> 규칙의 출발지에 IP 대역 대신 **다른 보안 그룹**을 적을 수 있습니다.
> `웹 계층 보안 그룹에서 오는 3306 포트만 허용` 처럼 적어 두면,
> 인스턴스가 늘고 줄어 IP 가 바뀌어도 규칙을 손댈 일이 없습니다.
> 다중 티어 구성의 정석이 이것입니다.

### L6. 다중 티어 구조 — 왜 퍼블릭과 프라이빗으로 갈리는가

> **이번 강의에서 다룰 내용** — 애플리케이션을 여러 층으로 쪼개고, 그중 일부만 인터넷에 내놓는 이유를 살펴보겠습니다.

#### 인터넷에 내놓는 것은 최소한으로 줄입니다

많은 애플리케이션 아키텍처가 **멀티 티어**입니다.
사용자를 받는 **웹 계층**, 로직을 처리하는 **애플리케이션 계층**, 데이터를 쥔 **데이터베이스 계층**으로 나뉩니다.

이 계층을 서브넷에 나누어 놓는 이유는 하나입니다. **공격받을 수 있는 면을 줄이는 것**입니다.
인터넷에서 직접 닿을 수 있는 자리에는 **로드 밸런서만** 두고,
실제로 코드가 도는 인스턴스와 데이터베이스는 프라이빗 서브넷으로 내립니다.
그러면 밖에서 EC2 나 RDS 로 가는 길 자체가 없어집니다.

트래픽은 이렇게 흐릅니다. **사용자 → IGW → 퍼블릭 서브넷의 ALB → 프라이빗 서브넷의 EC2 → 더 안쪽의 DB.**
한 겹씩 지날 때마다 보안 그룹이 "앞 계층에서 온 것만" 허용하도록 좁혀 둡니다.
`EC2 를 인터넷에 노출하지 않고 웹 서비스를 제공하라` 는 지문의 답이 늘 같은 모양인 이유가 여기에 있습니다.

#### 밖에서 안으로 들어오는 다른 길들

인터넷 말고도 VPC 로 들어오는 길이 있습니다. 지문이 온프레미스를 들고 나오면 이 갈래입니다.

| 요구 | 쓰는 것 |
|---|---|
| 빨리 깔아야 하고, 인터넷 위를 암호화해서 지나가도 된다 | [[aws-site-to-site-vpn\|Site-to-Site VPN]] |
| 대역폭이 일정해야 하고 지연이 예측 가능해야 한다 | [[aws-direct-connect\|Direct Connect]] — 전용선을 실제로 깝니다. 준비에 시간이 걸립니다 |
| 개인 단말이 하나씩 접속한다 | **AWS Client VPN** |
| VPC 와 온프레미스가 수십 개라 연결이 얽힌다 | [[aws-transit-gateway\|Transit Gateway]] — 가운데 허브를 두고 전부 여기에 붙입니다 |

VPN 을 타고 들어온 요청이라도 **VPC · 서브넷 · 인스턴스 세 자리 모두에서 허용되어야** 애플리케이션에 닿습니다.
라우팅 테이블에 그 대역으로 가는 경로가 있는지, 네트워크 ACL 이 막고 있지 않은지,
보안 그룹이 그 출발지를 받아 주는지 — 이 세 겹을 순서대로 확인하시기 바랍니다.

#### SSH 를 열지 않고 인스턴스에 붙는 법

프라이빗 인스턴스에 접속하려고 **배스천 호스트**를 퍼블릭 서브넷에 두는 구성이 오래 쓰였습니다.
다만 이 호스트 자체가 인터넷에 열린 서버라 관리 대상이자 공격 대상이 됩니다.

[[aws-systems-manager\|Systems Manager]] 의 **Session Manager** 는 인스턴스 안의 에이전트가
**밖으로** 연결을 맺어 두는 방식이라, 인바운드 포트를 하나도 열지 않고 셸을 얻습니다.
접속 기록도 남습니다. `배스천을 없애고 싶다` 는 지문의 답은 항상 이쪽입니다.

### L7. 애플리케이션 계층 보호와 민감 데이터

> **이번 강의에서 다룰 내용** — 네트워크 경계를 지난 다음, 요청 자체를 보고 막는 도구들을 살펴보겠습니다.

**민감 데이터가 지문에 나오면**

개인 식별 정보(PII)는 이름·주소·이메일·주민 등록 번호·여권 번호·생년월일·은행 계좌·신용카드처럼
**개인의 신원을 확인할 수 있는 데이터**입니다. 지문이 이런 데이터를 들고 나오면 묻는 것은 대개 세 가지 중 하나입니다.

| 요구 | 서비스 |
|---|---|
| S3 에 민감 데이터가 있는지 **찾아내라** | [[amazon-macie\|Macie]] — 기계 학습으로 검색·분류합니다 |
| 앱 사용자의 **가입·로그인**을 맡겨라 | [[amazon-cognito\|Cognito]] — 사용자 풀(인증)과 자격 증명 풀(AWS 리소스 접근)을 구분해 두시기 바랍니다 |
| 계정에서 **수상한 활동을 탐지**하라 | [[amazon-guardduty\|GuardDuty]] — 로그를 읽어 위협을 알립니다 |

**애플리케이션 계층 보호**

보안 그룹과 네트워크 ACL 은 **주소와 포트**까지만 봅니다. 요청의 내용은 읽지 않습니다.
그래서 `80 포트로 들어온 정상적인 HTTP 요청`처럼 보이는 공격은 이 두 겹을 그대로 통과합니다.
그 안쪽을 보는 것이 아래 두 서비스입니다.

- **WAF** — 요청 **내용**이 나쁠 때 (SQL 인젝션 · XSS · 봇 · 속도 제한 · 국가 차단)
- **Shield** — 트래픽을 **들이부을** 때. **Standard 는 모든 계정에 이미 켜져 있고 무료**입니다.
  **Advanced** 는 유료이고, 대응 팀 지원과 요금 급증 보호가 붙습니다. `추가 비용 없이`가 보이면 Standard 쪽입니다
- 붙는 자리는 겹치지만 같지는 않습니다. WAF 는 CloudFront · ALB · API Gateway 앞에,
  Shield Advanced 는 CloudFront · ALB · Route 53 · Global Accelerator · Elastic IP 에 붙습니다

`SQL 인젝션`은 공격자가 악의적인 SQL 구문을 입력값에 섞어 데이터베이스를 조작하는 공격이고,
`크로스 사이트 스크립팅(XSS)`은 악성 스크립트를 심어 다른 사용자의 브라우저에서 실행시키는 공격입니다.
둘 다 **요청 본문을 읽어야 알 수 있는 것**이라 WAF 의 자리입니다.

계정이 여러 개라 규칙을 일일이 붙이기 어렵다면 [[aws-firewall-manager\|Firewall Manager]] 가
조직 단위로 같은 규칙을 **강제**합니다. 새로 만들어진 계정에도 자동으로 적용된다는 점이 결정적입니다.

## 4. 시험에서 갈리는 지점

| 지문에 이게 있으면 | 이쪽 |
|---|---|
| `인터넷에서 접근 불가` + `패치는 받아야` | 프라이빗 서브넷 + **NAT 게이트웨이** |
| `S3 에 접근하되 인터넷을 타지 않게` | **Gateway 엔드포인트** (무료) |
| `S3·DynamoDB 이외의 AWS 서비스에 프라이빗하게` | **Interface 엔드포인트** |
| `특정 IP 주소를 차단` | **네트워크 ACL** (보안 그룹은 거부를 못 한다) |
| `SSH 로 접속해야 하는데 배스천을 두기 싫다` | **Systems Manager Session Manager** |
| `SQL 인젝션` · `크로스 사이트 스크립팅` | **WAF** |
| `DDoS` | **Shield** (기본은 이미 켜져 있다) |
| `여러 계정에 같은 방화벽 규칙을 강제` | **Firewall Manager** |
| `EC2 를 인터넷에 노출하지 않고 웹 서비스` | ALB 는 퍼블릭, **EC2 는 프라이빗** |
| `S3 에 개인정보가 섞여 있는지 찾아야` | **Macie** |
| `온프레미스에서 VPC 로 안전하게 연결` | 대역폭·요금이면 **Direct Connect**, 빨리 깔아야 하면 **Site-to-Site VPN**, 개인 단말이면 **Client VPN** |

> [!warning] 자주 나오는 오답
> **NAT 게이트웨이를 프라이빗 서브넷에 두는 보기.** NAT 는 **퍼블릭 서브넷**에 있어야 동작합니다.
> 그리고 NAT 게이트웨이는 **AZ 단위**입니다. AZ 마다 하나씩 두지 않으면 그 AZ 가 죽을 때 같이 끊깁니다.
