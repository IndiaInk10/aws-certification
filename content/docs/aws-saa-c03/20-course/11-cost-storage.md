> 도메인 4 · 비용에 최적화된 아키텍처 설계 **20%** · 과제 명세 4개 중 **첫 번째**

## 1. 왜 필요한가

> [[06-perf-storage\|3.1]] 과 **같은 서비스를 반대편에서** 봅니다. 짝으로 보면 한 번에 끝납니다.

3.1 은 "얼마나 빨라야 하는가"를 물었고, 4.1 은 "얼마나 싸게 할 수 있는가"를 묻습니다.
그런데 등장 서비스가 거의 같습니다. 따로 공부하면 두 번 외우게 됩니다.

스토리지 비용 문항은 답이 몇 개 안 됩니다.
**수명 주기 정책 · Intelligent-Tiering · 적절한 볼륨 유형 · 안 쓰는 것 지우기.**

## 2. 이번에 새로 나오는 서비스

| 서비스 | 한 줄 | 이 과제에서 맡는 역할 |
|---|---|---|
| [[amazon-s3\|Amazon S3]] | 객체 스토리지 | 스토리지 클래스가 곧 비용 설계 |
| [[amazon-s3-glacier\|S3 Glacier]] | 아카이브 클래스 묶음 | 장기 보관 |
| [[amazon-ebs\|Amazon EBS]] | 블록 볼륨 | 유형 전환과 스냅샷 관리 |
| [[amazon-efs\|Amazon EFS]] | 공유 파일 시스템 | IA 계층으로 자동 이동 |
| [[aws-backup\|AWS Backup]] | 백업 정책 | 보존 기간이 곧 비용 |
| [[aws-storage-gateway\|AWS Storage Gateway]] | 온프레미스 연결 | 온프레미스 스토리지 증설을 대신한다 |

## 3. 이 과제가 묻는 것

---

### L1. 비용 최적화란 무엇인가 — 요구를 먼저, 값은 그다음

> **이번 강의에서 다룰 내용** — 비용 문항을 푸는 순서를 정하고, 스토리지 요금이 실제로 무엇에 붙는지 갈라 보겠습니다.

#### 비용 최적화가 무엇인지부터 맞추고 가겠습니다

AWS 는 비용 최적화를 **가장 낮은 가격으로 비즈니스 가치를 제공하는 능력**이라고 정의합니다.
싸게 만드는 일이 아니라, **요구 사항을 충족하는 설계를 먼저 찾고 그중에서 가장 싼 것을 고르는** 순서입니다.
그래서 보기 중 제일 저렴해 보이는 것을 바로 집으면 안 되고, 요구 사항을 못 지키는 보기를 지운 다음에 가격을 봅니다.

그리고 이 일은 한 번으로 끝나지 않습니다. 클라우드는 매달 쓴 만큼 내는 구조라서,
이번 달에는 놀고 있는 인스턴스를 줄이고 다음 달에는 S3 클래스를 손보는 식으로 **반복해서 깎아 나가는 것**을
AWS 는 도메인 4 전체의 태도로 설명합니다. 리전마다 단가가 다르다는 점, 많은 서비스에 프리 티어가 있다는 점도
설계 단계에서 함께 보시기 바랍니다.

> [!warning] 값보다 종류를 먼저 틀립니다
> 시나리오가 **파일 시스템**을 요구하는데 S3 를 고르면, 아무리 싸도 답이 아닙니다.
> S3 는 파일 스토리지가 아니라 **객체 스토리지**이기 때문입니다.
> 비용 문항이라도 첫 판정은 언제나 "이 요구에 맞는 스토리지 종류가 무엇인가" 입니다.

#### 스토리지 요금은 한 줄이 아닙니다

"스토리지 값"이라고 하면 담아 둔 용량만 떠올리기 쉽지만, 청구서에 올라오는 줄은 하나가 아닙니다.
**어느 줄이 큰지에 따라 손댈 곳이 달라지므로**, 먼저 무엇에 돈이 붙는지 갈라 두겠습니다.

| 무엇에 붙나 | 어떤 성격인가 | 어디서 커지나 |
|---|---|---|
| **저장한 양** | 담아 둔 데이터의 크기에 보관한 시간을 곱해 냅니다 | 안 쓰는 데이터가 그대로 쌓여 있을 때 |
| **요청 수** | 넣고 꺼내고 목록을 부르는 **횟수**마다 붙습니다 | 아주 작은 객체를 아주 많이 다룰 때 |
| **꺼내는 값** | 저장 단가가 싼 클래스는 **꺼낼 때 따로** 받습니다 | 아카이브에 넣어 두고 자주 꺼낼 때 |
| **밖으로 나가는 데이터** | AWS 밖으로 내보내는 전송에 붙습니다 | 인터넷으로 대량 배포할 때 |
| **미리 잡아 둔 성능** | 프로비저닝한 IOPS 처럼 **약속받은 성능**에 붙습니다 | 그 성능을 실제로 안 쓰면서 높게 잡아 둘 때 |

시험이 노리는 지점이 여기서 나옵니다. **저장 단가만 보고 고르면 틀립니다.**
자주 꺼내는 데이터를 싼 클래스로 내리면 꺼내는 값과 요청 값이 저장에서 아낀 것을 넘어섭니다.

### L2. S3 스토리지 클래스 — 접근 빈도 하나로 고릅니다

> **이번 강의에서 다룰 내용** — 클래스를 바꾸면 무엇이 함께 움직이는지, 그리고 지문의 어떤 낱말이 어느 클래스를 가리키는지 살펴보겠습니다.

#### 클래스마다 달라지는 것은 네 가지입니다

S3 는 데이터를 담는 방식이 아니라 **어떻게 보관할지**를 클래스로 고르게 합니다.
같은 버킷 안에서 객체마다 다른 클래스를 둘 수도 있습니다. 클래스를 아래로 내리면 네 가지가 함께 움직입니다.

| 축 | 아래 클래스로 갈수록 |
|---|---|
| **저장 단가** | 싸집니다 |
| **꺼내는 값** | 붙기 시작하고 점점 커집니다 |
| **꺼내는 데 걸리는 시간** | 즉시에서 분 · 시간 단위로 늘어납니다 |
| **최소 보관 기간** | 생깁니다. 그전에 지워도 그 기간만큼은 냅니다 |

**내구성은 어느 클래스나 같은 수준을 목표로 설계되어 있습니다.**
달라지는 것은 데이터를 **몇 개의 가용 영역에 나누어 두느냐**이고, 이름에 `One Zone` 이 붙은 것만 AZ 하나에 둡니다.
그래서 One Zone 은 AZ 하나가 통째로 문제가 되면 데이터를 잃을 수 있고, **다시 만들 수 있는 데이터**에만 씁니다.

#### S3 스토리지 클래스 — 접근 빈도 축 하나입니다

| 클래스 | 언제 | 꺼내는 비용 |
|---|---|---|
| **Standard** | 자주 | 없다 |
| **Intelligent-Tiering** | **모를 때** | 없다 (모니터링 수수료) |
| **Standard-IA** | 가끔, 즉시 필요 | 있다 |
| **One Zone-IA** | 가끔, **다시 만들 수 있는** 데이터 | 있다 (AZ 하나뿐) |
| **Glacier Instant Retrieval** | 분기 1회, 즉시 | 있다 |
| **Glacier Flexible Retrieval** | 연 1~2회, 분~시간 | 있다 |
| **Glacier Deep Archive** | 연 1회 미만, **12시간** | 가장 싸다 |

#### Glacier 세 갈래는 "얼마나 기다릴 수 있는가"로 갈립니다

이름에 `Glacier` 가 붙은 셋은 전부 **아카이브**, 즉 거의 꺼내지 않는 데이터를 위한 자리입니다.
셋을 가르는 조건은 하나뿐입니다. **꺼내 달라고 한 뒤 실제로 손에 들어올 때까지 얼마나 기다릴 수 있는가.**

| 클래스 | 꺼내면 | 어떤 데이터인가 |
|---|---|---|
| **Instant Retrieval** | 곧바로 옵니다 | 볼까 말까 하지만 **볼 때는 즉시** 필요한 것 |
| **Flexible Retrieval** | 분에서 시간 단위로 기다립니다 | 1년에 한두 번, 기다려도 되는 것 |
| **Deep Archive** | 시간 단위로 기다립니다 | 규정 때문에 몇 년을 두지만 사실상 안 볼 것 |

그러므로 지문이 `즉시 조회가 필요한지` 를 굳이 밝혀 두었다면, 그 한 줄이 세 갈래를 가르라고 심어 둔 조건입니다.

#### Intelligent-Tiering 은 무엇을 대신해 주나

접근 패턴을 아직 모를 때 사람이 매달 들여다보며 클래스를 옮기는 대신,
**객체마다 읽히는지를 지켜보다가 뜸해지면 아래 계층으로, 다시 읽히면 위로 자동으로 옮겨 주는** 클래스입니다.
계층을 옮기는 동작 자체에는 꺼내는 값이 붙지 않고, 대신 **객체 수에 비례하는 모니터링 수수료**가 붙습니다.
그래서 아주 작은 객체가 엄청나게 많은 경우가 아니라면 대체로 이득입니다.

#### 핵심 판정 두 가지

- `접근 패턴을 모른다` · `예측할 수 없다` → **Intelligent-Tiering**. 이 신호는 거의 예외가 없습니다
- `30일 뒤 IA, 90일 뒤 Glacier` 처럼 **패턴을 안다** → **수명 주기 정책**

둘을 헷갈리면 안 됩니다. **아는 패턴이면 수명 주기, 모르는 패턴이면 Intelligent-Tiering** 입니다.

### L3. 수명 주기 — 시간이 지나면 저절로 내려갑니다

> **이번 강의에서 다룰 내용** — 수명 주기 규칙이 무엇을 어떻게 옮기고 지우는지, 그리고 조용히 쌓이는 것들을 자동으로 치우는 방법을 살펴보겠습니다.

#### 규칙은 "무엇을 · 며칠 뒤에 · 어떻게" 세 조각입니다

수명 주기 규칙은 사람이 매달 들여다보는 대신 **날짜를 기준으로 저절로 움직이게** 적어 둔 것입니다.
규칙 하나는 세 조각으로 되어 있습니다.

| 조각 | 무엇을 정하나 |
|---|---|
| **대상** | 버킷 전체인지, 특정 **프리픽스**나 **태그**가 붙은 객체만인지 |
| **시점** | 객체가 만들어지고 **며칠 뒤**인지 |
| **동작** | 다른 클래스로 **전환**할지, 아예 **만료**시켜 지울지 |

`30일 뒤 Standard-IA, 90일 뒤 Glacier, 7년 뒤 삭제` 같은 시나리오는 이 세 조각을 그대로 옮겨 적은 것입니다.
지문이 **기간을 숫자로 밝혀 두었다면** 그것이 수명 주기를 고르라는 신호입니다.

#### 내려가기는 쉽고 올라오기는 번거롭습니다

수명 주기의 전환은 **값이 싼 쪽으로 내려가는 방향**을 전제로 합니다.
아카이브로 내려간 객체를 다시 읽으려면 **복원을 요청하고 기다려야 합니다.**
규칙을 되돌린다고 객체가 알아서 위로 올라오는 것이 아니라는 뜻입니다.

그래서 접근 패턴이 정말 불확실하면 규칙을 촘촘히 짜기보다 **Intelligent-Tiering** 쪽이 안전하고,
반대로 보존 기간이 계약이나 규정으로 못 박혀 있으면 수명 주기 쪽이 더 싸게 끝납니다.

#### 수명 주기 정책이 하는 일

- 클래스 간 **전환**
- 오래된 버전 **만료**
- **불완전한 멀티파트 업로드 삭제** ← 조용히 쌓이는 비용. 문항으로 나옵니다

#### 쌓이는 것은 자동으로 지웁니다

수명 주기 규칙으로 더 이상 필요 없는 데이터를 자동 삭제하는 방법을 알아야 합니다.
EBS 스냅샷은 **Amazon Data Lifecycle Manager**(스냅샷 생성·보존·삭제를 일정으로 돌리는 서비스)가 맡고,
여러 서비스의 백업은 [[aws-backup\|AWS Backup]] 쪽 보존 정책이 맡습니다.

#### EFS 와 FSx

- EFS **수명 주기 관리** — 30일 안 쓰면 IA 로 자동 이동
- `한 AZ 안에서만 쓰면 된다` → **EFS One Zone**

### L4. 블록 스토리지 비용 — 채운 만큼이 아니라 만들어 둔 만큼

> **이번 강의에서 다룰 내용** — EBS 요금이 왜 "쓴 만큼"이 아닌지, 그리고 조용히 청구되는 볼륨과 스냅샷을 어떻게 찾아내는지 살펴보겠습니다.

#### 비어 있어도 값은 그대로 나옵니다

S3 는 넣은 만큼 내지만, **EBS 볼륨은 만들어 둔 크기만큼 냅니다.**
500GB 볼륨을 만들어 20GB 만 쓰고 있어도 청구는 500GB 기준입니다.
프로비저닝된 IOPS 볼륨이라면 **약속받은 IOPS 에도 따로** 붙고, 그 성능을 실제로 쓰든 안 쓰든 마찬가지입니다.

여기서 두 가지가 따라 나옵니다.

- **처음부터 크게 잡을 이유가 없습니다.** EBS 볼륨은 가동 중에 키울 수 있으므로, 모자라질 때 키우는 편이 낫습니다
- **인스턴스를 지워도 볼륨은 남습니다.** 종료할 때 함께 삭제되도록 해 두지 않았다면 볼륨이 그대로 남아 계속 청구됩니다. 어디에도 붙어 있지 않은 볼륨은 아무 일도 하지 않으면서 값만 냅니다

#### 스냅샷은 증분이지만 개수로 쌓입니다

EBS 스냅샷은 볼륨 전체를 매번 복사하지 않습니다.
첫 스냅샷만 전체를 담고, 그다음부터는 **직전 스냅샷 이후 바뀐 블록만** 담습니다.
그래서 하나하나는 작지만, 매일 뜨는 스냅샷을 지우지 않으면 **개수로 쌓여 결국 눈에 띄는 금액이 됩니다.**

지우는 일을 사람이 기억할 필요는 없습니다.
**Amazon Data Lifecycle Manager** 에 "며칠마다 뜨고 몇 개까지 보관한다"를 적어 두면 생성과 삭제를 함께 맡습니다.

#### EC2 에 붙는 스토리지는 두 가지이고, 비용 성격이 다릅니다

| | 성격 | 요금 | 무엇에 |
|---|---|---|---|
| **인스턴스 스토어** (임시·비영구) | 인스턴스가 사라지면 같이 사라집니다 | **EC2 시간당 요금에 포함** — 컴퓨팅 기준으로 가장 싼 선택입니다 | 로그 · 캐시 · 없어져도 되는 데이터 |
| **Amazon EBS** | 인스턴스와 분리되어 남고 다른 인스턴스에 옮겨 붙일 수 있습니다 | **따로 붙습니다** | 지속성이 필요한 애플리케이션·워크로드 |

`중요하지 않은 임시 데이터인데 EBS 를 붙여 두었다`는 지문이면 인스턴스 스토어로 내리는 쪽이 절감입니다.

#### 크기 조정은 배포할 때 한 번, 돌려 본 뒤에 또 한 번입니다

AWS 가 스토리지 절감의 첫 단계로 꼽는 것은 **과도하게 프로비저닝하지 않는 것**입니다.
그리고 초기 산정으로 끝내지 말고, 워크로드가 한동안 돌아간 뒤에 실제 사용량을 보고 다시 조정하라고 말합니다.

- **지불 중인 IOPS 와 실제로 쓰는 IOPS 를 비교**합니다. 성능 좋은 볼륨 유형 값을 내면서 그 성능을 안 쓰고 있다면,
  볼륨 유형을 내려도 성능 저하 없이 비용만 줄어듭니다
- 버스팅 수준이면 충분한 워크로드에 프로비저닝된 IOPS 볼륨을 쓰고 있는지 확인합니다
- **Trusted Advisor** 가 연결되지 않은 EBS 볼륨과 활용도가 낮은 볼륨을 짚어 줍니다.
  아카이브 전략을 정해 두고 그 목록을 정리하는 것이 그대로 절감입니다

#### EBS 비용

| | |
|---|---|
| gp2 → **gp3** | 대체로 더 싸고 IOPS 를 따로 올릴 수 있다. `비용 절감` 의 단골 답 |
| 안 붙은 볼륨 | 인스턴스를 지워도 볼륨은 남아 계속 과금된다 |
| 스냅샷 | 증분이지만 쌓인다. **Data Lifecycle Manager** 로 자동 정리 |
| 프로비저닝 IOPS | 실제로 필요 없으면 gp3 로 내린다 |

---

### L5. 데이터를 옮기는 값과, 그 값을 누가 낼 것인가

> **이번 강의에서 다룰 내용** — 데이터 전송에 어느 방향으로 값이 붙는지, 그리고 그 값을 받아 가는 쪽에 물리는 방법을 살펴보겠습니다.

#### 들어오는 것과 나가는 것은 값이 다릅니다

데이터 전송은 **방향**으로 값이 갈립니다.
대체로 **AWS 안으로 들어오는 것**에는 값이 붙지 않고, **AWS 밖으로 나가는 것**에 붙습니다.
그래서 클라우드로 옮겨 오는 이관은 생각보다 싸고, 매일 대량으로 내보내는 서비스는 생각보다 비쌉니다.

같은 AWS 안이라도 **가용 영역을 넘거나 리전을 넘는 전송**에는 값이 붙습니다.
아키텍처를 그릴 때 데이터가 경계를 몇 번 넘는지 세어 보시기 바랍니다.
인터넷으로 같은 파일을 여러 번 내보내는 상황이라면 [[amazon-cloudfront\|CloudFront]] 로 **엣지에 캐시**해
원본에서 나가는 횟수 자체를 줄이는 쪽이 성능 답이면서 동시에 비용 답이 되기도 합니다.

#### 데이터를 AWS 로 옮기는 비용도 이 과제입니다

| 옵션 | 언제 |
|---|---|
| [[aws-datasync\|AWS DataSync]] | 온프레미스와 AWS 사이를 **네트워크로** 반복 동기화할 때 |
| [[aws-snow-family\|Snow Family]] | 테라바이트~페타바이트를 **물리 디바이스로** 안전하고 빠르게 옮길 때 |
| [[aws-transfer-family\|AWS Transfer Family]] | 기존 **SFTP·FTPS** 워크플로를 그대로 두고 S3 로 받을 때 |
| [[aws-storage-gateway\|AWS Storage Gateway]] | 온프레미스에서 **계속 쓰면서** 뒤를 AWS 로 둘 때 |

`수백 TB 를 아카이브로 올려야 하는데 회선이 가늘다`는 전형적인 지문입니다.
전용 회선을 새로 깔거나 있는 회선으로 밀어 올리는 보기보다 **Snowball 여러 대**가 빠르고 쌉니다.

#### 요청자 지불 버킷

버킷 소유자가 아니라 **요청하는 쪽이 요청·다운로드 비용을 내도록** S3 버킷을 구성할 수 있습니다.
`데이터는 우리가 공개하되 전송 비용은 받아 가는 쪽이 내야 한다`는 지문의 답입니다.
공개 데이터셋처럼 **누가 얼마나 받아 갈지 모르는 데이터**를 내놓을 때 쓰는 장치라고 보시면 됩니다.

---

### L6. 어디에 돈이 나가는지 봅니다

> **이번 강의에서 다룰 내용** — 줄일 곳을 찾아 주는 도구들이 각각 어떤 화면을 보여 주는지 갈라 보겠습니다.

#### 보이지 않으면 줄일 수 없습니다

스토리지 비용은 한 번에 크게 튀지 않습니다.
**여러 계정 · 여러 버킷 · 여러 볼륨에 조금씩 나뉘어** 늘어나기 때문에, 합계만 봐서는 어디를 손대야 할지 알 수 없습니다.
그래서 아래 도구들이 하는 일은 대개 **합계를 쪼개서 보여 주는 것**입니다.
시험은 이 도구들을 이름 단위로 갈라 묻기 때문에, **어느 도구가 어떤 화면을 주는지**로 잡아 두시기 바랍니다.

#### 어디에 돈이 나가는지 보는 도구

| 도구 | 하는 일 |
|---|---|
| [[amazon-cloudwatch\|CloudWatch]] | CPU·메모리·스토리지 사용률 지표와 **경보**. 줄일 리소스와 늘릴 리소스를 찾습니다 |
| [[aws-cost-explorer\|Cost Explorer]] | **개략적인 보기**에서 시작해 필요한 만큼 드릴다운합니다. 대화용 재무 보고라면 이쪽 |
| **AWS Cost and Usage Report** | 비용을 **시간·일·월·제품·리소스·태그** 기준으로 잘게 분류한 원장입니다 |
| **AWS Budgets** | 예산 임곗값을 넘으면 알리고, 정의한 임곗값에 따라 **자동 조치**를 걸 수 있습니다 |
| **Trusted Advisor** | 안 쓰는 리소스와 배포상의 문제를 점검 항목으로 알려 줍니다 |

여기에 **비용 할당 태그**가 붙어야 도구가 쓸모 있어집니다. 태깅 전략을 정해 두고 Cost Explorer 에서 태그로 걸러 보면
어느 팀·어느 환경이 얼마를 쓰는지 갈라집니다. 계정이 여러 개라면 [[aws-organizations\|Organizations]] 의 **통합 결제**로
청구를 한곳에 모으고, [[aws-control-tower\|Control Tower]] 로 계정을 정해진 모양으로 세웁니다.

## 4. 시험에서 갈리는 지점

| 지문에 이게 있으면 | 이쪽 |
|---|---|
| `접근 패턴을 모른다` | **S3 Intelligent-Tiering** |
| `30일 후 · 90일 후` 처럼 기간이 명시 | **수명 주기 정책** |
| `1년에 한 번 볼까 말까` · `12시간 걸려도 된다` | **Glacier Deep Archive** |
| `다시 만들 수 있는 데이터` · `비용 최우선` | **One Zone-IA** |
| `규정상 7년 보관, 즉시 조회는 불필요` | Glacier + **객체 잠금** |
| `안 쓰는 EBS 볼륨이 계속 청구` | 미사용 볼륨 정리 · 스냅샷 후 삭제 |
| `gp2 를 쓰고 있는데 비용을 줄여라` | **gp3 로 전환** |
| `EFS 인데 오래된 파일이 많다` | **EFS 수명 주기 관리 (IA)** |
| `온프레미스 스토리지를 증설하는 대신` | **Storage Gateway** |
| `스냅샷이 계속 쌓인다` | **Data Lifecycle Manager** |
| `애플리케이션에 파일 시스템이 필요하다` | S3 는 후보가 아닙니다 — **EFS · FSx** 쪽 |
| `없어져도 되는 임시 데이터에 EBS 를 붙였다` | **인스턴스 스토어** (EC2 시간당 요금에 포함) |
| `프로비저닝한 IOPS 를 다 쓰지 않는다` | 볼륨 유형을 내립니다 — 성능 저하 없이 비용만 줍니다 |
| `안 붙은 볼륨이 어디 있는지 모르겠다` | **Trusted Advisor** 로 찾습니다 |
| `수백 TB 를 회선으로 올리면 몇 주가 걸린다` | **Snowball 여러 대** |
| `데이터를 받아 가는 쪽이 전송 비용을 낸다` | **요청자 지불 버킷** |
| `개략적인 비용 보기가 필요하다` | **Cost Explorer** |
| `리소스·태그 단위로 잘게 봐야 한다` | **Cost and Usage Report** |
| `한도를 넘으면 알림과 조치` | **AWS Budgets** |

> [!warning] 꺼내는 비용을 잊지 마세요
> IA 와 Glacier 는 **저장은 싸지만 꺼낼 때 돈이 붙습니다.**
> `자주 접근하는데 IA 로 옮긴다` 는 보기는 오히려 비용이 늘어 오답입니다.
> 최소 보관 기간(IA 30일 · Glacier 90일 · Deep Archive 180일)도 마찬가지로 함정이 됩니다.

## 6. 셀프 체크

- [ ] Intelligent-Tiering 과 수명 주기 정책을 가르는 조건 한 줄을 말한다
- [ ] One Zone-IA 를 써도 되는 데이터의 성격을 설명한다
- [ ] IA 로 옮기면 오히려 손해인 경우를 든다
- [ ] gp2 대신 gp3 를 고르는 이유를 두 가지 댄다
- [ ] 조용히 쌓이는 스토리지 비용 세 가지를 안다
- [ ] 인스턴스 스토어와 EBS 를 지속성과 요금 방식으로 구분한다
- [ ] Cost Explorer 와 Cost and Usage Report 를 언제 쓰는지 갈라 말한다
