> 도메인 1 · 보안 아키텍처 설계 **30%** · 과제 명세 3개 중 **세 번째**

## 1. 왜 필요한가

> 암호화 문항의 승부는 알고리즘이 아니라 **키를 누가 쥐고 누가 돌리느냐**에서 납니다.

이 과제는 "암호화를 켜라"를 묻지 않습니다. 그건 대부분 체크박스 하나입니다.
묻는 것은 **어떤 방식의 암호화인가** 입니다. AWS 가 키를 관리하는지, 내가 만든 키인지,
내가 키를 직접 들고 와야 하는지, 전용 하드웨어가 필요한지.

여기에 규정 준수 요구가 붙습니다. `키를 우리가 통제해야 한다` · `키 사용 기록이 남아야 한다` ·
`한 번 쓴 데이터는 지워지면 안 된다` 같은 조건이 붙으면 답이 하나로 좁혀집니다.

## 2. 이번에 새로 나오는 서비스

| 서비스 | 한 줄 | 이 과제에서 맡는 역할 |
|---|---|---|
| [[aws-kms\|AWS KMS]] | 암호화 키 관리 | 이 과제의 중심. 대부분의 서비스가 여기 키를 쓴다 |
| [[aws-cloudhsm\|AWS CloudHSM]] | 나만 쓰는 전용 암호화 하드웨어 | AWS 조차 키에 못 닿아야 할 때 |
| [[amazon-macie\|Amazon Macie]] | S3 안의 민감 데이터를 찾아낸다 | 개인정보가 어디 있는지 모를 때 |
| [[aws-certificate-manager\|AWS Certificate Manager]] | TLS 인증서 발급·자동 갱신 | 전송 중 암호화 |
| [[aws-secrets-manager\|AWS Secrets Manager]] | 비밀 보관 + 자동 교체 | 자격 증명 자체의 보호 |
| [[amazon-s3\|Amazon S3]] | 객체 스토리지 | 암호화·버전 관리·객체 잠금이 전부 여기서 나온다 |
| [[aws-backup\|AWS Backup]] | 백업 정책을 한 곳에서 | 보존 기간과 규정 준수 |

## 3. 이 과제가 묻는 것

---

### L1. 암호화가 실제로 하는 일

> **이번 강의에서 다룰 내용** — 암호화라는 조작이 안에서 무엇을 주고받는지, 그리고 그 조각들의 이름을 맞추고 가겠습니다.

#### 데이터를 읽을 수 없는 모양으로 바꿉니다

암호화는 데이터를 **가리는 것**이 아니라 **모양을 바꾸는 것**입니다.
원래 데이터와 **키** 를 알고리즘에 함께 넣으면, 키 없이는 되돌릴 수 없는 결과물이 나옵니다.
그 결과물을 손에 넣어도 키가 없으면 원본을 알아낼 방법이 없습니다.

AWS 는 이것을 "데이터 주위에 터널을 씌워 바깥의 누구도 읽을 수 없게 하는 일" 이라고 설명합니다.
저장 장치를 통째로 훔쳐 가도, 회선을 도청해도 소용이 없다는 것이 암호화가 주는 보호의 전부입니다.
바꿔 말하면 **키를 함께 잃으면 보호도 함께 사라집니다.** 이 과제가 키 이야기로 채워지는 이유입니다.

#### 용어부터 맞추고 가겠습니다

암호화 문항은 용어가 섞이면 그대로 무너집니다. 네 단어면 충분합니다.

| 용어 | 뜻 |
|---|---|
| 일반 텍스트 | 암호화되지 **않은** 데이터입니다. 글자만이 아니라 문서·이미지·애플리케이션도 해당합니다 |
| 알고리즘 | 일반 텍스트와 키를 받아 암호문을 만드는 코드입니다 |
| 키 | 알고리즘과 함께 쓰는 암호입니다 |
| 암호문 | 암호화를 마친 데이터입니다 |

`일반 텍스트`가 글자를 뜻하지 않는다는 점을 특히 잡아 두시기 바랍니다.
이미지든 실행 파일이든 **아직 암호화되지 않았으면** 전부 일반 텍스트입니다.

#### 대칭과 비대칭

키의 종류는 둘입니다.

| | 키 | 성격 |
|---|---|---|
| **대칭** | 잠글 때와 풀 때 **같은 키** 를 씁니다 | 빠릅니다. 대신 그 키를 상대에게 안전하게 건네주는 일이 따로 문제가 됩니다 |
| **비대칭** | **공개 키로 잠그고 개인 키로 풉니다** | 키를 건네줄 필요가 없습니다. 대신 느립니다 |

시험이 둘 중 무엇을 쓰는지를 직접 묻는 일은 드뭅니다.
다만 **왜 큰 데이터에는 대칭 키를 쓰는지**, 그리고 그 대칭 키를 어떻게 안전하게 보관하는지는
다음다음 강의의 봉투 암호화로 이어지므로 이 차이만 기억해 두시기 바랍니다.

### L2. 저장 중과 전송 중 — 어디를 지키는가

> **이번 강의에서 다룰 내용** — 암호화가 두 갈래로 나뉘는 이유와, 각각의 자리에서 무엇이 답이 되는지 살펴보겠습니다.

#### 누워 있는 데이터와 지나가는 데이터

**저장 데이터 암호화**는 무단 접근과 도난을 막는 쪽이고 보통 **한 당사자**만 관계합니다.
**전송 중 데이터 암호화**는 데이터가 두 지점 사이를 오갈 때, 즉 **둘 이상이 관계할 때** 보호하는 쪽입니다.
키에는 대칭과 비대칭이 있고, 시험은 둘 중 무엇을 쓰는지보다 **키를 누가 쥐고 어떻게 교체하는지**를 묻습니다.

| | 지키는 것 | 위협 | 손대는 곳 |
|---|---|---|---|
| **저장 중** | 디스크·버킷·테이블에 **누워 있는** 데이터 | 장비 도난, 스냅샷 유출, 권한 실수 | 스토리지 서비스의 암호화 설정과 KMS 키 |
| **전송 중** | 선 위를 **지나가는** 데이터 | 도청, 중간자 공격 | TLS · 인증서 · 프라이빗 연결 |

둘은 서로를 대신하지 못합니다. **양쪽 다 확인해야 합니다.**
지문이 `저장 중 암호화를 켰다` 고만 적어 두었다면, 전송 구간이 비어 있는 것이 답의 실마리일 수 있습니다.

#### 전송 중 암호화는 TLS 와 인증서로 합니다

브라우저와 서버 사이의 암호화는 **TLS** 가 맡습니다.
연결을 시작할 때 서버가 **인증서**를 내밀고, 클라이언트는 그것을 보고 두 가지를 확인합니다.

1. **이 서버가 정말 그 도메인의 서버가 맞는가** — 신뢰할 수 있는 인증 기관(CA)이 서명해 주었는지 봅니다
2. **이 연결에서 쓸 키를 어떻게 정할 것인가** — 인증서 안의 공개 키를 써서 대칭 키를 안전하게 합의합니다

여기서 실무의 사고가 늘 한 자리에서 납니다. **인증서에는 유효 기간이 있습니다.**
만료되면 브라우저가 경고를 띄우고 접속이 끊깁니다.
사람이 달력에 적어 두고 갱신하는 방식은 반드시 언젠가 잊힙니다.

- **ACM** 이 인증서를 발급하고 **자동으로 갱신**합니다. 갱신을 사람이 하는 보기는 대개 오답
- ACM 인증서는 **ELB · CloudFront · API Gateway** 에 붙입니다. EC2 에 직접 설치하는 용도가 아닙니다
- CloudFront 에 붙일 인증서는 **us-east-1** 에 있어야 합니다

인증서를 **ELB 같은 앞단에 붙인다**는 것은 그 지점에서 TLS 를 풀고 뒤로 넘긴다는 뜻입니다.
이것을 TLS 종료라고 하고, 뒷단 인스턴스가 암복호화 부담을 지지 않게 되는 이점이 함께 따라옵니다.

### L3. 봉투 암호화 — 데이터 키를 루트 키로 감쌉니다

> **이번 강의에서 다룰 내용** — KMS 가 큰 데이터를 어떻게 다루는지, 그리고 왜 용량이 커져도 느려지지 않는지 살펴보겠습니다.

#### KMS 는 데이터를 직접 암호화하지 않습니다

KMS 는 데이터를 직접 암호화하지 않습니다. **데이터 키**로 데이터를 암호화하고,
그 데이터 키를 다시 **루트 키**로 감싸 둡니다. 그래서 큰 파일을 KMS 로 보내지 않아도 되고,
키를 교체할 때 데이터를 전부 다시 암호화하지 않아도 됩니다.
`대용량인데 KMS 로 암호화하면 느려지지 않느냐`는 지문의 답이 여기에 있습니다.

#### 오가는 것은 키뿐입니다

절차를 한 번 따라가 보겠습니다.

```d2
kms: "AWS KMS\n루트 키는 밖으로 나오지 않습니다"
svc: "서비스 (S3 · EBS · RDS …)"
data: "데이터\n(수백 GB 여도 됩니다)"
store: "저장된 것\n암호문 + 감싼 데이터 키"

svc -> kms: "1. 데이터 키를 주십시오"
kms -> svc: "2. 평문 데이터 키 + 감싼 데이터 키"
svc -> data: "3. 평문 키로 그 자리에서 암호화"
svc -> store: "4. 평문 키는 버리고, 감싼 키를 옆에 붙여 저장"
store -> kms: "5. 읽을 때는 감싼 키만 보냅니다"
```

핵심은 **3번이 KMS 밖에서 일어난다**는 것입니다.
네트워크를 오가는 것은 몇십 바이트짜리 키뿐이고, 수백 기가바이트짜리 데이터는 제자리에 있습니다.
그래서 용량이 커져도 KMS 왕복이 늘지 않습니다.

여기서 두 가지가 더 따라 나옵니다.

- **루트 키는 KMS 밖으로 나오지 않습니다.** 감싸고 푸는 일은 언제나 KMS 안에서 일어나므로, 그 호출이 전부 [[aws-cloudtrail\|CloudTrail]] 에 남습니다
- **키를 교체해도 데이터를 다시 암호화할 필요가 없습니다.** 감싸는 키만 바꾸면 되기 때문입니다. `키를 주기적으로 교체해야 하는데 데이터가 페타바이트급이다` 라는 지문이 이 사실 하나로 풀립니다

### L4. KMS 와 CloudHSM — 키를 어디에 두는가

> **이번 강의에서 다룰 내용** — 두 서비스가 갈리는 지점이 성능이 아니라 **누가 하드웨어를 나눠 쓰느냐**라는 것을 짚어 보겠습니다.

#### 같은 일을 다른 책임 분담으로 합니다

둘 다 키를 안전한 하드웨어 안에 두고 그 밖으로 꺼내지 않는다는 점은 같습니다. 갈리는 것은 아래입니다.

| | AWS KMS | AWS CloudHSM |
|---|---|---|
| 하드웨어 | **여러 고객이 나눠 쓰는** 관리형 서비스 | **내 전용 HSM 장비**입니다 |
| 운영 | AWS 가 가용성·패치·백업까지 맡습니다 | 클러스터 구성·사용자 관리·백업이 **내 몫**입니다 |
| AWS 의 접근 | AWS 가 서비스를 운영합니다 | **AWS 직원도 내 키에 닿을 수 없습니다** |
| 다른 서비스와의 연동 | S3 · EBS · RDS … **대부분의 서비스가 그대로 씁니다** | 직접 연동이 필요합니다 |
| 인증 | | **FIPS 140-2 레벨 3** |

거의 모든 문항의 기본값은 **KMS** 입니다. AWS 서비스들이 이미 KMS 를 쓰도록 만들어져 있어
체크박스 하나로 끝나기 때문입니다.
CloudHSM 은 **규정이 전용 하드웨어를 요구할 때**만 등장합니다.
`AWS 도 접근할 수 없어야` · `FIPS 140-2 레벨 3` · `전용 하드웨어` 가 그 신호입니다.

#### KMS 키 두 종류

| | 누가 만드나 | 회전 | 정책 |
|---|---|---|---|
| **AWS 관리형 키** | 서비스가 알아서 | 자동 | 손댈 수 없다 |
| **고객 관리형 키(CMK)** | 내가 | 켤 수 있다 | **키 정책으로 누가 쓸지 통제** |

지문에 `키를 우리가 통제` · `사용 권한을 계정별로` · `교차 계정으로 키를 공유` 가 있으면 **고객 관리형 키**입니다.
`AWS 도 접근할 수 없는 전용 하드웨어` · `FIPS 140-2 레벨 3` 이면 **CloudHSM** 입니다.

**키 정책**은 [[01-secure-access\|1.1]] 에서 본 **리소스 기반 정책**입니다.
키에 붙어서 "누가 이 키를 쓸 수 있는가" 를 정합니다.
그래서 다른 계정이 내 암호화 데이터를 읽어야 한다면, IAM 정책만으로는 부족하고 **키 정책도 열어야 합니다.**

> [!warning] KMS 키는 리전을 넘지 않습니다
> KMS 키는 만들어진 **리전 안에서만** 씁니다.
> 그래서 암호화된 스냅샷이나 객체를 다른 리전으로 복제하려면 **대상 리전의 키로 다시 감싸는 단계**가 들어갑니다.
> 복제·재해 복구 문항에서 이 단계가 빠진 보기가 오답으로 나옵니다.
> 여러 리전에서 같은 키를 써야 한다면 **다중 리전 키**가 그 답입니다.

### L5. S3 암호화 네 갈래 — 키를 누가 쥐는가

> **이번 강의에서 다룰 내용** — 이름이 비슷한 네 가지 방식이 사실은 축 하나로 줄지어 있다는 것을 확인하겠습니다.

#### 먼저 어디서 암호화하느냐가 갈립니다

S3 의 암호화는 큰 갈래가 둘입니다.

- **클라이언트 측 암호화** — 데이터가 S3 로 **떠나기 전에** 내 쪽에서 암호화합니다. S3 는 이미 암호문인 덩어리를 받습니다
- **서버 측 암호화** — HTTPS 로 안전하게 보내고, **S3 에 도착한 뒤** S3 가 암호화합니다

클라이언트 측은 모든 것을 내가 통제하는 대신 모든 것이 내 부담입니다.
서버 측은 여기서 다시 **키를 어디서 가져오느냐**로 셋으로 갈립니다.
그래서 넷은 흩어진 선택지가 아니라 **통제 강도 순으로 늘어선 한 줄**입니다.

| | 키를 만드는 쪽 | 키를 보관하는 쪽 | 언제 |
|---|---|---|---|
| **SSE-S3** | AWS | AWS | 기본값. 요구가 없으면 이걸로 충분 |
| **SSE-KMS** | 내가 KMS 에서 | KMS | **키 사용 기록이 CloudTrail 에 남아야** 할 때 |
| **SSE-C** | 내가 | **내가** (요청마다 키를 보낸다) | AWS 에 키를 두면 안 될 때 |
| **클라이언트 측** | 내가 | 내가 | 올리기 **전에** 이미 암호화되어야 할 때 |

**SSE-C** 는 이름 그대로 고객이 키를 제공하는 방식입니다.
S3 는 그 키로 암호화한 뒤 **키를 버립니다.** 보관해 주지 않습니다.
그래서 객체를 읽을 때마다 같은 키를 다시 보내야 하고, 키를 잃으면 데이터도 함께 잃습니다.
`AWS 에 키를 맡길 수 없다` 는 요구를 만족시키는 대신 그 부담을 전부 지는 쪽입니다.

> [!tip] 네 갈래를 고르는 순서
> 지문에서 **키에 대한 요구를 먼저 찾으십시오.**
> 요구가 없으면 SSE-S3, `감사·정책 통제`면 SSE-KMS, `AWS 가 키를 가지면 안 됨`이면 SSE-C,
> `S3 에 닿기 전에 이미 암호화` 면 클라이언트 측입니다.

---

### L6. 지워지지 않게 · 새어 나가지 않게

> **이번 강의에서 다룰 내용** — 암호화만으로 막지 못하는 두 가지 사고, 즉 지워지는 것과 공개되는 것을 어떻게 막는지 살펴보겠습니다.

#### 암호화는 삭제를 막지 못합니다

암호화된 객체도 권한만 있으면 **지울 수 있습니다.** 암호화가 답하는 질문은 "읽을 수 있는가" 뿐입니다.
`보존 기간 동안 삭제되면 안 된다` 는 요구는 완전히 다른 장치가 맡습니다.

| | 무엇을 막나 |
|---|---|
| **버전 관리** | 덮어쓰기·삭제를 되돌릴 수 있게. 삭제 표식만 붙는다 |
| **MFA 삭제** | 버전을 영구 삭제하려면 MFA 를 요구 |
| **S3 객체 잠금** | 정해진 기간 동안 **누구도** 못 지운다. 규정 준수 모드면 루트도 못 푼다 |
| **백업 볼트 잠금** | AWS Backup 쪽의 같은 개념 |

위 두 줄과 아래 두 줄의 성격이 다릅니다.
**버전 관리는 되돌리는 장치**이고, **객체 잠금은 애초에 못 하게 하는 장치**입니다.
`실수로 지운 것을 복구` 와 `규정상 지워지면 안 됨` 은 이렇게 답이 갈립니다.

**퍼블릭 노출 막기** — `버킷이 실수로 공개되지 않도록` 이 나오면 **S3 퍼블릭 액세스 차단**입니다.
계정 수준에서 켜면 버킷 정책이 무엇이든 공개되지 않습니다.

#### 규정 준수 문항의 답이 서비스가 아닐 때

`감사 기관이 규정 준수 보고서를 요구합니다` 처럼 **서류**를 묻는 지문이 있습니다.
이때는 [[aws-artifact\|AWS Artifact]] 입니다. AWS 의 보안·규정 준수 보고서를 직접 내려받는 셀프 서비스 저장소이고,
암호화 서비스를 고르는 보기들은 전부 질문에 답하지 않은 것이 됩니다.

#### 보호는 한 겹으로 끝나지 않습니다

AWS 는 데이터 보호를 **심층 방어**로 설명합니다. 통제를 여러 겹 쌓되, 성격을 두 가지로 나눕니다.

| 성격 | 하는 일 | 예 |
|---|---|---|
| **예방** | 애초에 일어나지 않게 막습니다 | 최소 권한 정책 · 암호화 · 퍼블릭 액세스 차단 |
| **탐지** | 일어난 것을 알아냅니다 | CloudTrail · GuardDuty · Macie · Config |

그리고 **모든 데이터가 같지 않습니다.** 먼저 **분류**하고, 등급에 맞는 보존·복구·통제를 붙이는 순서입니다.
`전부 같은 수준으로 암호화한다`는 보기가 정답이 되는 경우는 드뭅니다.

분류가 먼저인 이유는 간단합니다. **무엇을 지켜야 하는지 모르면 얼마나 지켜야 하는지도 정할 수 없기 때문입니다.**
그래서 `S3 에 개인정보가 섞여 있는지 모르겠다` 는 지문의 답이 암호화가 아니라
[[amazon-macie\|Macie]] — 즉 **찾아내는 쪽**이 됩니다. 지키는 일은 찾은 다음의 일입니다.

## 4. 시험에서 갈리는 지점

| 지문에 이게 있으면 | 이쪽 |
|---|---|
| `암호화를 켜야 한다` (조건 없음) | **SSE-S3**. 가장 단순한 답 |
| `키 사용 내역을 감사` · `키 정책으로 통제` | **SSE-KMS + 고객 관리형 키** |
| `AWS 가 키에 접근할 수 없어야` | **SSE-C** 또는 클라이언트 측 암호화 |
| `전용 하드웨어` · `FIPS 140-2 레벨 3` | **CloudHSM** |
| `인증서 갱신을 잊지 않도록` | **ACM** (자동 갱신) |
| `보존 기간 동안 삭제 불가` · `규정 준수 감사` | **S3 객체 잠금** |
| `실수로 지운 파일을 복구` | **버전 관리** |
| `버킷에 개인정보가 있는지 모르겠다` | **Macie** |
| `비밀번호를 30일마다 자동 교체` | **Secrets Manager** |
| `여러 서비스의 백업 보존 정책을 한 곳에서` | **AWS Backup** |
| `규정 준수 보고서를 감사 기관에 제출` | **AWS Artifact** |
| `인스턴스가 만드는 데이터를 내구성 있게, 가장 간단히` | **암호화된 EBS 볼륨**. S3 로 옮기는 보기는 한 단계 더 듭니다 |

> [!tip] 암호화 문항이 어려워 보일 때
> 대부분은 **키를 누가 쥐느냐** 한 축으로 정리됩니다.
> AWS → SSE-S3, 나(AWS 안에) → SSE-KMS, 나(AWS 밖에) → SSE-C, 전용 장비 → CloudHSM.
> 이 순서로 통제 강도가 세지고 운영 부담도 같이 세집니다.
