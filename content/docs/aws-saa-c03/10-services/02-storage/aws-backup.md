> 여러 서비스의 백업을 한 정책으로. **무엇을 리소스로 잡느냐**가 문항이 된다

## 한 줄로 말하면

EC2·EBS·RDS·DynamoDB·EFS·FSx 같은 여러 서비스의 백업을 **한 곳에서 정책으로 묶어** 돌리고, 다른 리전·계정으로 복사까지 해 주는 관리형 서비스입니다.

## 핵심 개념

- **백업 계획(plan)** — 일정, 보존 기간, 전환 규칙을 정의합니다. 여기에 **리소스를 붙이면** 그때부터 자동으로 돕니다
- **리소스 지정이 갈림길입니다** — EC2 인스턴스를 대상으로 잡으면 **AMI 와 연결된 볼륨이 함께** 백업됩니다. EBS 볼륨만 잡으면 데이터는 남아도 **인스턴스 구성이 빠져** 그대로 복구할 수 없습니다
- **교차 리전 복사** — 계획에 넣어 두면 DR 요구(RPO)를 정책으로 만족시킬 수 있습니다. EFS 처럼 자체 교차 리전 기능이 약한 서비스에서 특히 유용합니다
- **교차 계정 복사** — 운영 계정이 털려도 백업은 다른 계정에 남게 하는 구성
- **백업 볼트와 볼트 잠금** — 볼트에 잠금을 걸면 정해진 기간 동안 **백업을 지울 수 없습니다.** S3 객체 잠금의 백업판
- **태그 기반 선택** — 특정 태그가 붙은 리소스를 자동으로 계획에 포함시킬 수 있어, 새 리소스가 늘어도 빠지지 않습니다

**직접 만드는 것과 비교**

- Lambda + EventBridge 로 스냅샷을 뜨는 구성도 동작은 합니다. 하지만 **여러 서비스에 걸치고, 보존·전환·교차 리전까지** 요구가 붙으면 만들고 유지할 것이 급격히 늘어납니다
- 그래서 `운영상 가장 효율적인` 이 조건이면 AWS Backup 쪽입니다

## 요금 모델

- **백업으로 저장된 용량**과 **복원한 용량**에 붙습니다
- 교차 리전 복사는 **전송과 대상 리전 저장**이 추가로 붙습니다
- 보존 기간을 길게 잡을수록 누적됩니다 — 규정이 요구하는 만큼만 잡는 것이 비용 설계입니다

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| RDS 자동 백업 | 자동 백업은 **최대 35일**입니다. 그보다 길게 두려면 수동 스냅샷이나 AWS Backup |
| EBS 스냅샷 + DLM | DLM 은 **EBS 전용** 자동화입니다. 여러 서비스에 걸치면 AWS Backup |
| [[aws-elastic-disaster-recovery\|Elastic Disaster Recovery]] | Backup 은 **시점 복사본**, DRS 는 **지속 복제**입니다. RPO 가 초 단위면 DRS |

## 시험 포인트

- [ ] `인스턴스 구성과 데이터를 모두` → 리소스로 **EC2 인스턴스**를 지정 (EBS 볼륨만 잡는 보기는 오답)
- [ ] `여러 서비스의 백업 정책을 한 곳에서` → AWS Backup
- [ ] `다른 리전에서도 복구` → 백업 계획의 교차 리전 복사
- [ ] RDS 를 **35일 넘게** 보관해야 하면 자동 백업이 아니라 수동 스냅샷 또는 AWS Backup
- [ ] ECS 가 쓰는 **EFS 를 다른 리전에 복제**하면서 RPO 를 맞추라면 EFS + AWS Backup 조합
