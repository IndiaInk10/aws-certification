> `Hadoop`·`Spark`·`HBase` 같은 프레임워크 이름이 지문에 있을 때. **스팟 + 임시 클러스터**가 비용 정답이다

## 한 줄로 말하면

Hadoop·Spark 클러스터를 관리형으로 띄웁니다. 대규모 분산 처리 코드를 그대로 옮길 때 씁니다.

## 핵심 개념

- **프레임워크 이름이 판단 기준**입니다. `Spark 작업을 마이그레이션` · `기존 Hadoop 파이프라인` → EMR, 그런 언급이 없으면 서버리스인 [[aws-glue\|Glue]]·[[amazon-athena\|Athena]] 가 운영 부담에서 유리합니다
- **노드 세 종류** — 마스터(조정) · 코어(HDFS 저장 + 처리) · **태스크(처리만)**
  - **태스크 노드는 데이터를 갖지 않아 스팟 인스턴스에 최적**입니다. 중단돼도 잃을 데이터가 없습니다
  - **코어 노드를 스팟으로 두는 보기는 위험**합니다 — HDFS 데이터가 함께 사라집니다. 이 대비가 그대로 문제로 나옵니다
- **EMRFS** — HDFS 대신 **S3 를 저장소로** 씁니다. 클러스터를 껐다 켜도 데이터가 남습니다
- **임시(transient) 클러스터** — 작업이 끝나면 자동 종료합니다. `야간 배치` 면 상시 클러스터보다 훨씬 쌉니다
- **EMR Serverless** — 클러스터 관리 없이 Spark 를 돌립니다

## 요금 모델

- **인스턴스 요금 + EMR 요금(인스턴스당 소액)** 입니다
- 비용 정답 조합은 거의 정해져 있습니다 — **마스터·코어는 온디맨드/예약, 태스크는 스팟**, 그리고 **작업이 끝나면 종료하는 임시 클러스터 + S3 저장**
- 24시간 띄워 두는 보기는 배치 워크로드에서 오답 쪽입니다

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| [[aws-glue\|Glue]] | 서버리스 ETL. 프레임워크 통제가 필요 없으면 Glue |
| [[amazon-athena\|Athena]] | SQL 조회만. 코드 실행이 아닙니다 |
| [[amazon-redshift\|Redshift]] | 데이터 웨어하우스 |
| [[aws-batch\|Batch]] | 일반 컨테이너 배치. 분산 데이터 프레임워크가 아닙니다 |

## 시험 포인트

- [ ] `Hadoop`·`Spark`·`HBase`·`Presto` → **EMR**
- [ ] `비용 최소화` → **태스크 노드를 스팟**으로
- [ ] **코어 노드를 스팟으로 두는 보기는 위험** (HDFS 데이터 손실)
- [ ] `배치가 끝나면 꺼야` → **임시 클러스터 + EMRFS(S3)**
- [ ] 프레임워크 언급이 없고 `운영 부담 최소` 면 Glue/Athena
