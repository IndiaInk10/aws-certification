> `누가 언제 무엇을 했는가`. **기본 90일**이라는 한 줄이 문항이 된다

## 한 줄로 말하면

계정에서 일어난 **모든 API 호출**을 기록합니다. 콘솔·CLI·SDK 어느 쪽이든 남습니다.

## 핵심 개념

- **기본으로 켜져 있고 최근 90일**은 이벤트 기록에서 바로 봅니다. **그보다 오래 보관하려면 추적(trail)을 만들어 S3 로** 내보내야 합니다 — `1년치 감사 로그` 지문의 답이 항상 이것입니다
- **이벤트 세 종류**

| | 무엇 | 기본 |
|---|---|---|
| **관리 이벤트** | 자원을 만들고 바꾸고 지우는 작업 | **켜짐** |
| **데이터 이벤트** | **S3 객체 수준**(GetObject/PutObject), Lambda 호출 | **꺼짐** — 따로 켜야 |
| 인사이트 이벤트 | 평소와 다른 호출 패턴 | 꺼짐 |

- `누가 그 S3 객체를 내려받았나` → **데이터 이벤트를 켜야** 합니다. 관리 이벤트만으로는 안 보입니다. 대신 양이 많아 요금이 붙습니다
- **CloudTrail Insights** — 비정상적인 API 호출 급증을 자동으로 감지합니다
- **조직 추적** — [[aws-organizations\|Organizations]] 전 계정의 기록을 **한 버킷에** 모읍니다. 계정마다 따로 만드는 보기와 대비됩니다
- **로그 파일 무결성 검증**으로 변조 여부를 확인합니다
- **로그 보관 버킷을 보호**하는 것이 함께 나옵니다 — 버전 관리 + **객체 잠금** + 별도 계정에 보관
- **CloudWatch Logs 로 보내면** 지표 필터로 `루트 로그인 발생 시 알림` 같은 실시간 대응을 붙일 수 있습니다
- **[[amazon-athena\|Athena]] 로 S3 의 CloudTrail 로그를 SQL 조회**하는 것이 표준 분석 방법입니다

## 요금 모델

- **관리 이벤트는 추적 하나까지 무료**, 데이터 이벤트와 인사이트는 유료입니다
- S3 저장 요금이 따로 붙으므로 **수명 주기로 Glacier 에 내리는 것**이 비용 답입니다
- 데이터 이벤트를 전부 켜면 급격히 비싸집니다 — 필요한 버킷·접두사로 범위를 좁힙니다

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| [[amazon-cloudwatch\|CloudWatch]] | **성능·상태 지표**. CloudTrail 은 **누가 무엇을 호출했는지** |
| [[aws-config\|Config]] | **구성이 어떻게 바뀌었고 규칙에 맞는지**. CloudTrail 은 **누가 바꿨는지** |
| S3 액세스 로그 | S3 자체 기능. CloudTrail 데이터 이벤트가 더 통합적입니다 |

## 시험 포인트

- [ ] `누가 이 자원을 지웠나` → **CloudTrail**
- [ ] `90일보다 오래 보관` → **추적을 만들어 S3 로**
- [ ] `누가 S3 객체를 읽었나` → **데이터 이벤트를 켜야**
- [ ] `전 계정 감사 로그를 한 곳에` → **조직 추적**
- [ ] `루트 로그인 시 즉시 알림` → CloudWatch Logs + **지표 필터 + 경보**
- [ ] `로그가 변조되면 안 된다` → 버전 관리 + **객체 잠금** + 무결성 검증
- [ ] `구성이 규칙에 맞는지` 는 CloudTrail 이 아니라 **Config**
