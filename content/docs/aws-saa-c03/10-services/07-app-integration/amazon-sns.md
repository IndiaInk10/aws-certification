> **하나를 여러 곳에** 동시에. SQS 와 짝지은 팬아웃이 시험의 단골이다

## 한 줄로 말하면

발행-구독 알림 서비스입니다. 한 번 발행하면 구독자 모두에게 **밀어 줍니다**.

## 핵심 개념

- **팬아웃 패턴** — SNS 주제 하나에 **여러 SQS 큐를 구독**시켜, 같은 이벤트를 각 시스템이 자기 속도로 처리하게 합니다. `주문 하나로 재고·결제·배송이 각각 움직여야` 의 표준 답입니다
- **구독 대상** — SQS · Lambda · HTTP/S · 이메일 · SMS · 모바일 푸시 · **Kinesis Data Firehose**
- **메시지 필터링** — 구독마다 필터 정책을 걸어 **필요한 메시지만** 받게 합니다. 큐를 여러 개 만들지 않고도 분기됩니다
- **FIFO 주제** — 순서가 필요한 팬아웃은 SNS FIFO + SQS FIFO 조합입니다
- **재시도와 DLQ** — 전달 실패를 재시도하고, 계속 실패하면 DLQ 로 보냅니다
- **보존이 없습니다.** 구독자가 없거나 못 받으면 그 메시지는 사라집니다 — 그래서 **중요한 처리는 SQS 를 사이에 끼웁니다.** SNS → Lambda 직접 연결보다 SNS → SQS → Lambda 가 복원력이 높다는 것이 판단 포인트입니다
- **암호화**와 접근 정책으로 주제를 보호합니다

## 요금 모델

- **발행 수 + 전달 수** 기준입니다. SMS 는 건당 요금이 따로 붙어 상대적으로 비쌉니다
- 서버가 없어 유휴 비용이 0 입니다

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| [[amazon-sqs\|SQS]] | 당겨 가고, 하나가 처리하면 사라집니다. 보존이 있습니다 |
| [[amazon-eventbridge\|EventBridge]] | 이벤트 **내용으로 라우팅**, SaaS·AWS 서비스 이벤트, 스케줄. 알림 전달이 목적이 아닙니다 |
| Amazon SES | 이메일 발송 전용(마케팅·트랜잭션 메일) |

## 시험 포인트

- [ ] `한 이벤트를 여러 시스템이 각각` → **SNS + SQS 팬아웃**
- [ ] `구독자마다 필요한 것만` → **메시지 필터링**
- [ ] `알림을 잃으면 안 된다` → SNS 뒤에 **SQS**
- [ ] `순서 있는 팬아웃` → SNS FIFO + SQS FIFO
- [ ] SNS 는 **저장하지 않는다** — 재처리가 필요하면 SQS/Kinesis
