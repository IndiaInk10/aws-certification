> **느슨한 결합**의 기본 부품. `요청을 잃으면 안 된다`·`처리 속도가 안 맞는다` 면 큐다

## 한 줄로 말하면

메시지 큐입니다. 보내는 쪽과 처리하는 쪽을 떼어 놓아 한쪽이 죽거나 느려도 요청이 사라지지 않게 합니다.

## 핵심 개념

**표준 큐 vs FIFO 큐**

| | 표준 | FIFO |
|---|---|---|
| 순서 | 대체로 유지, 보장 안 됨 | **엄격한 순서** |
| 중복 | **중복 전달 가능** | 정확히 한 번 |
| 처리량 | 사실상 무제한 | 제한 있음(높은 처리량 모드로 완화) |

- `순서가 반드시` · `중복 결제가 있으면 안 된다` → **FIFO**. 그 조건이 없으면 표준입니다
- 표준 큐를 쓸 때는 **소비자가 멱등**해야 한다는 것이 함께 나옵니다

**시험이 묻는 설정들**

- **가시성 제한 시간** — 소비자가 가져간 메시지가 숨겨지는 시간입니다. **처리 시간보다 짧으면 같은 메시지가 중복 처리**됩니다. `메시지가 두 번 처리된다` 의 원인
- **긴 폴링(long polling)** — 빈 응답을 줄여 **API 호출 비용과 지연을 함께 낮춥니다.** `빈 응답이 많아 비용이 든다` 의 답
- **배달 못한 편지 큐(DLQ)** — 몇 번 실패한 메시지를 따로 모읍니다. `실패한 요청을 잃지 않고 나중에 분석` 의 답
- **메시지 보존** — 기본 4일, 최대 14일
- **지연 큐 / 메시지 타이머**로 처리 시점을 미룹니다
- **메시지 크기 256KB** — 더 크면 **S3 에 두고 포인터를** 보냅니다(확장 클라이언트 라이브러리)

**전형적인 구성**

- **큐 길이(ApproximateNumberOfMessagesVisible)로 오토 스케일링** — `처리가 밀린다` 의 표준 답입니다. CPU 로 조절하는 보기보다 정확합니다
- **SNS → SQS 팬아웃** — 한 이벤트를 여러 큐가 각자 받습니다
- **API Gateway → SQS 직접 통합** — Lambda 없이 버퍼링

## 요금 모델

- **요청 수** 기준입니다. 서버가 없습니다
- **긴 폴링**이 빈 요청을 줄여 요금을 낮춥니다
- 큐로 버퍼링하면 **피크에 맞춰 인스턴스를 늘려 둘 필요가 없어져** 컴퓨팅 비용이 함께 내려갑니다

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| [[amazon-sns\|SNS]] | SNS 는 **밀어 주고**, 여러 구독자가 동시에 받습니다. SQS 는 **당겨 가고** 하나가 처리하면 사라집니다 |
| [[amazon-kinesis\|Kinesis]] | 여러 소비자가 **같은 데이터를 각자** 읽고 재처리할 수 있습니다 |
| [[amazon-eventbridge\|EventBridge]] | 규칙 기반 이벤트 라우팅·SaaS 연동·스케줄 |

## 시험 포인트

- [ ] `요청을 잃지 않고 버퍼링` → **SQS**
- [ ] `순서 보장 · 중복 불가` → **FIFO**
- [ ] `메시지가 중복 처리된다` → **가시성 제한 시간**을 늘림
- [ ] `실패한 메시지 보관` → **DLQ**
- [ ] `빈 폴링 비용` → **긴 폴링**
- [ ] `밀린 작업에 맞춰 확장` → **큐 길이 기반 오토 스케일링**
- [ ] 256KB 초과 → **S3 + 포인터**
