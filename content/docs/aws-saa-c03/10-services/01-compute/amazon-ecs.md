> AWS 방식 컨테이너 오케스트레이션. 지문에 `Kubernetes` 가 없으면 대개 이쪽

## 한 줄로 말하면

컨테이너를 어디에 얼마나 띄울지 관리하는 오케스트레이터입니다. **Kubernetes 를 쓸 이유가 지문에 없으면** ECS 가 더 단순한 답입니다.

## 핵심 개념

- **태스크 정의** — 컨테이너 이미지, vCPU·메모리, 환경 변수, 역할을 적어 둔 설계도입니다
- **서비스** — 태스크를 정해진 개수만큼 유지하고, 죽으면 다시 띄우며, 로드 밸런서에 등록합니다
- **시작 유형** — [[aws-fargate\|Fargate]](서버 없음) 또는 EC2(노드를 내가 관리). `추가 인프라를 관리할 수 없다` 면 Fargate
- **권한은 두 겹입니다**
  - **태스크 역할(taskRoleArn)** — 컨테이너 안의 애플리케이션이 AWS API 를 부를 때. S3 접근 권한은 여기
  - **태스크 실행 역할** — ECS 가 이미지를 당기고 로그를 쓸 때
  - 보안 그룹은 **네트워크 접근**이지 권한이 아닙니다. 둘을 섞는 것이 함정입니다
- **ECR** — 컨테이너 이미지를 두는 곳입니다. 프라이빗 서브넷에서 당기려면 **ECR·S3 엔드포인트**가 필요합니다
- **모놀리식을 쪼갤 때** — 코드를 최대한 살리면서 배포 단위를 나누는 답이 컨테이너입니다. 전부 Lambda 로 다시 쓰는 보기는 `코드를 유지` 조건과 부딪힙니다
- **마이크로서비스 사이 통신** — 순서가 중요하지 않으면 **SQS 표준 큐**가 처리량 면에서 유리합니다. 직접 HTTP 호출은 서비스를 다시 강하게 묶습니다

## 요금 모델

- ECS 자체는 **추가 요금이 없습니다.** 시작 유형에 따라 Fargate 태스크 자원값 또는 EC2 인스턴스값을 냅니다
- 그래서 비용 문항은 대개 **Fargate 냐 EC2 냐**로 갈립니다

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| [[amazon-eks\|Amazon EKS]] | 지문에 `Kubernetes` · 기존 k8s 매니페스트가 있으면 EKS |
| [[aws-fargate\|Fargate]] | ECS 는 오케스트레이터, Fargate 는 시작 유형. 다른 축입니다 |
| [[aws-batch\|AWS Batch]] | 큐에 넣고 끝나면 자원을 떼는 배치 작업은 Batch |

## 시험 포인트

- [ ] 컨테이너인데 `Kubernetes` 언급이 없다 → ECS
- [ ] S3 접근 권한 → **태스크 역할(taskRoleArn)** (보안 그룹 아님)
- [ ] `운영 오버헤드 최소` + 컨테이너 → ECS **on Fargate**
- [ ] 프라이빗 서브넷에서 이미지를 당기려면 **ECR·S3 엔드포인트**
- [ ] 모놀리식을 쪼개되 코드를 살린다 → 컨테이너 (전부 Lambda 재작성은 오답)
