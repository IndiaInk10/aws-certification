> 배치 작업을 큐에 넣으면 컴퓨팅을 붙였다 뗀다. **오래 도는 작업 + 스팟**의 자리

## 한 줄로 말하면

작업을 제출하면 **필요한 크기의 컴퓨팅을 알아서 띄워 돌리고 끝나면 반납**합니다. Lambda 의 15분 한도를 넘는 무거운 작업의 기본 답입니다.

## 핵심 개념

- **작업 큐와 컴퓨팅 환경** — 제출된 작업이 큐에 쌓이고, 컴퓨팅 환경이 그것을 보고 EC2 나 Fargate 를 띄워 처리합니다
- **재시도와 의존성** — 실패 시 재시도 횟수, 작업 사이 선후 관계를 정의로 선언합니다. 직접 만들면 그 로직을 다 짜야 합니다
- **스팟과 궁합이 좋습니다** — 배치는 대개 중단을 견딜 수 있어 컴퓨팅 환경을 스팟으로 잡으면 비용이 크게 떨어집니다
- **컨테이너로 정의합니다** — 작성 언어가 팀마다 달라도 컨테이너가 공통 분모가 되므로, **언어가 제각각인 작업들**을 한 곳에서 돌릴 때 잘 맞습니다
- **일정은 EventBridge** 가 맡습니다. Batch 는 "무엇을 어떻게 돌릴지", EventBridge 는 "언제 시작할지"입니다
- **Lambda 로 안 되는 경우의 답** — 15분 초과, 큰 메모리, 긴 CPU 집약 작업

## 요금 모델

- Batch 자체는 **추가 요금이 없습니다.** 띄운 EC2 나 Fargate 값만 냅니다
- 작업이 없을 때 컴퓨팅 환경을 0 으로 줄일 수 있어 **상시 인스턴스보다 쌉니다**
- 스팟을 쓰면 여기서 한 번 더 내려갑니다

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| [[aws-lambda\|AWS Lambda]] | 15분 이내 짧은 이벤트면 Lambda, 넘으면 Batch |
| [[aws-fargate\|Fargate 예약 작업]] | 짧게 반복되는 정기 작업은 Fargate 예약 작업도 됩니다. 큐·재시도·의존성이 필요하면 Batch |
| [[amazon-emr\|Amazon EMR]] | Hadoop·Spark 프레임워크가 필요하면 EMR |

## 시험 포인트

- [ ] `매시간 도는 CPU 집약 작업` + `15분 초과` → Batch
- [ ] `언어가 제각각인 작업들` → 컨테이너 + Batch, 일정은 EventBridge
- [ ] `중단돼도 되는 배치` → 컴퓨팅 환경을 **스팟**으로
- [ ] 상시 인스턴스를 띄워 두는 보기는 **노는 시간 비용** 때문에 오답
