> RDS 를 쓰되 **더 빠르고 더 잘 버텨야** 할 때. 서버리스와 글로벌 데이터베이스가 SAA 의 무기다

## 한 줄로 말하면

MySQL·PostgreSQL 호환 관계형 데이터베이스입니다. 스토리지가 **6벌 복제 · 자동 확장**이라 RDS 보다 가용성과 성능이 높습니다.

## 핵심 개념

**스토리지 구조**

- **3개 AZ 에 6벌**로 복제됩니다. **쓰기는 4벌, 읽기는 3벌**만 성공하면 되므로 AZ 하나가 통째로 죽어도 읽기·쓰기가 계속됩니다
- MySQL 대비 5배, PostgreSQL 대비 3배 성능을 표방합니다
- **10GB 에서 128TB 까지 자동 확장**됩니다. `스토리지 용량을 예측할 수 없다` 면 미리 프로비저닝하는 RDS 보다 유리합니다
- 컴퓨트와 스토리지가 분리되어 있어 복제본을 붙여도 데이터를 복사하지 않습니다

**읽기 확장**

- **읽기 전용 복제본 15개**까지(RDS 는 5개). 지연이 밀리초 수준입니다
- **엔드포인트가 세 종류**입니다 — **라이터**(쓰기, 장애 조치 시 자동으로 새 라이터를 가리킴) · **리더**(복제본에 자동 분산) · **사용자 지정**(특정 복제본 묶음으로. 예: 분석 쿼리만 큰 복제본으로)
- 애플리케이션이 **리더 엔드포인트를 쓰지 않으면** 복제본을 만들어도 읽기가 가지 않습니다
- **오토 스케일링**으로 복제본 수를 부하에 맞춰 늘립니다
- 라이터가 죽으면 **복제본이 자동 승격**됩니다(30초 안팎)

**Aurora Serverless v2**

- **용량이 자동으로 오르내립니다.** `사용량을 예측할 수 없다` · `간헐적·급증하는 워크로드` · `개발/테스트` 가 신호입니다
- 미리 큰 인스턴스를 잡아 두는 것보다 비용이 낮아 **비용 최적화 문항의 단골 정답**입니다

**Aurora 글로벌 데이터베이스**

- **여러 리전에 복제**, 지연 1초 미만
- **리전 장애 시 1분 내 승격** — `RTO 1분 · RPO 1초` 급 요구의 답입니다
- 리전 간 읽기 전용 복제본보다 빠르고 강합니다

**그 밖에**

- **백트랙**(MySQL 호환) — 백업 복원 없이 **시간을 되감습니다**. 잘못된 배포 되돌리기에 씁니다
- **복제본 자동 장애 조치 우선순위**를 티어로 정합니다
- **Babelfish** — SQL Server 애플리케이션을 코드 수정 최소로 옮깁니다
- **다중 마스터**가 아닌 한 **쓰기는 한 곳**입니다

## 요금 모델

- **인스턴스 시간 + 스토리지 사용량 + I/O** 입니다. 스토리지는 쓴 만큼만
- **Serverless v2 는 ACU 단위 초당 과금** — 유휴가 많으면 크게 절감됩니다
- **I/O-Optimized** 구성은 I/O 요금을 없애는 대신 인스턴스 단가가 높습니다. I/O 가 많으면 오히려 쌉니다
- RDS 보다 인스턴스 단가는 높지만, 복제본을 늘려도 스토리지가 복사되지 않아 규모가 커질수록 유리해집니다

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| [[amazon-rds\|RDS]] | 복제본 5개·스토리지 미리 지정. 요구가 평범하면 RDS 로 충분 |
| [[amazon-dynamodb\|DynamoDB]] | 관계형이 아님. SQL·조인이 필요하면 Aurora |
| [[amazon-redshift\|Redshift]] | 분석용 데이터 웨어하우스. Aurora 는 트랜잭션 |

## 시험 포인트

- [ ] `여러 리전 · RTO 1분 이하` → **Aurora 글로벌 데이터베이스**
- [ ] `사용량 예측 불가` · `간헐적 워크로드` → **Serverless v2**
- [ ] `읽기 복제본이 5개로 부족` → Aurora(15개)
- [ ] `스토리지 용량을 미리 못 정한다` → Aurora 자동 확장
- [ ] `잘못된 변경을 되돌려야` → **백트랙**
- [ ] 조인·트랜잭션이 필요하면 DynamoDB 는 오답
