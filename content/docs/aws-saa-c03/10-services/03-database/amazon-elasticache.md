> `DB 부하를 줄여라` + `같은 쿼리가 반복` → 캐시. **Redis 냐 Memcached 냐**를 가르는 낱말이 따로 있다

## 한 줄로 말하면

인메모리 캐시(Redis/Valkey · Memcached)를 관리형으로 제공합니다. 반복되는 읽기를 DB 앞에서 받아 냅니다.

## 핵심 개념

**Redis vs Memcached — 시험이 묻는 그 지점**

| | Redis / Valkey | Memcached |
|---|---|---|
| **지속성** | 있습니다(스냅샷·AOF) | 없습니다 — 재시작하면 사라집니다 |
| **복제·다중 AZ** | 있습니다. 자동 장애 조치 | 없습니다 |
| **데이터 구조** | 정렬 집합·목록·해시·지리 정보 | 단순 키-값 |
| **Pub/Sub** | 있습니다 | 없습니다 |
| 확장 | 샤딩(클러스터 모드) + 복제본 | 노드 추가(수평) |

- `세션 정보를 잃으면 안 된다` · `고가용성` · `리더보드`(정렬 집합) → **Redis**
- `단순 캐시 · 다중 스레드로 최대한 단순하고 저렴하게` → **Memcached**
- `리더보드`·`실시간 순위`·`지리 검색` 은 Redis 자료구조를 묻는 신호입니다

**어디에 쓰이나**

- **DB 앞 읽기 캐시** — `읽기 전용 복제본을 늘려도 여전히 느리다` 면 캐시가 근본 해법입니다
- **세션 스토어** — 여러 EC2 가 세션을 공유해 **상태 비저장**이 됩니다. 오토 스케일링이 인스턴스를 죽여도 로그인이 유지됩니다
- **속도 제한·카운터** 같은 짧은 상태

**캐시 전략** — 지연 로딩(요청 시 채움, 캐시 미스가 느림) · 쓰기 관통(항상 최신, 안 읽힐 데이터도 씀) · **TTL** 로 오래된 값을 만료시킵니다.

**주의** — ElastiCache 는 **VPC 안**에 있습니다. 인터넷에서 직접 접근하지 않습니다.

## 요금 모델

- **노드 시간 + 데이터 전송** 입니다. 예약 노드 할인이 있습니다
- 캐시로 DB 인스턴스를 줄이면 총액이 내려가는 것이 비용 논리입니다
- **서버리스 옵션**은 사용량 기준이라 유휴가 많으면 유리합니다

## 헷갈리는 것과 구분

| 비교 대상 | 차이 |
|---|---|
| **DAX** | DynamoDB 전용 캐시. 코드 수정 없이 붙습니다 |
| [[amazon-cloudfront\|CloudFront]] | 콘텐츠를 **엣지**에 캐시. ElastiCache 는 애플리케이션 안쪽 |
| [[amazon-rds\|읽기 전용 복제본]] | 복제본은 DB 자체 확장, 캐시는 DB 를 아예 안 부르게 함 |

## 시험 포인트

- [ ] `같은 쿼리 반복 · DB 부하` → ElastiCache
- [ ] `세션을 잃으면 안 됨` · `다중 AZ 장애 조치` → **Redis**
- [ ] `가장 단순한 캐시` · 지속성 불필요 → **Memcached**
- [ ] `리더보드 · 실시간 순위` → **Redis 정렬 집합**
- [ ] `상태 비저장 웹 계층` → 세션을 ElastiCache 나 DynamoDB 로
- [ ] DynamoDB 를 빠르게 → ElastiCache 가 아니라 **DAX**
