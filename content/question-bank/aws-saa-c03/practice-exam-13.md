> [!question] 한 병원이 환자 증상 수집 애플리케이션에 Amazon SQS와 SNS를 씁니다. 데이터는 **저장 시와 전송 중 모두 암호화**되어야 하고 **인가된 인원만** 접근할 수 있어야 합니다. 어떤 조합이 필요합니까? (2개 선택)
> a) **KMS 고객 관리형 키**로 SQS 서버 측 암호화를 켜고 **키 정책**으로 인가된 주체만 키를 쓰게 하며, 큐 정책에 **TLS 연결만 허용**하는 조건을 건다
> b) **KMS 고객 관리형 키**로 SNS 서버 측 암호화를 켜고 키 정책으로 인가된 주체만 키를 쓰게 한다
> c) SQS 서버 측 암호화를 켜되 기본 키 정책을 그대로 두고 사용 주체만 제한한다
> d) KMS 고객 관리형 키로 SQS 암호화를 켜고 **IAM 정책**으로 키 사용을 제한한다
>> [!success]- Answer
>> a) **KMS 고객 관리형 키**로 SQS 서버 측 암호화를 켜고 **키 정책**으로 인가된 주체만 키를 쓰게 하며, 큐 정책에 **TLS 연결만 허용**하는 조건을 건다
>> b) **KMS 고객 관리형 키**로 SNS 서버 측 암호화를 켜고 키 정책으로 인가된 주체만 키를 쓰게 한다
>> **왜 이 답인가** — 두 서비스 **모두** 암호화해야 하고, 키 접근 통제의 정석은 **키 정책**입니다. 전송 중 암호화는 큐·주제 정책의 TLS 조건으로 강제합니다.
>> **나머지가 아닌 이유** — 기본 키(AWS 관리형)는 키 정책을 세밀하게 다룰 수 없습니다. IAM 정책만으로는 키 자체에 대한 접근 경계를 완전히 통제하지 못합니다.

> [!question] 한 기업의 애플리케이션이 Auto Scaling 그룹의 EC2와 로드 밸런서, DynamoDB 테이블로 구성됩니다. **다른 리전에서 최소 다운타임으로** 서비스를 이어갈 수 있어야 합니다. 다운타임이 가장 짧은 솔루션은 무엇입니까?
> a) DR 리전에 **Auto Scaling 그룹과 로드 밸런서를 미리 만들어 두고** DynamoDB를 **글로벌 테이블**로 구성한 뒤, DNS 장애 조치가 DR 리전 로드 밸런서를 가리키게 한다
> b) 필요할 때 EC2·로드 밸런서·DynamoDB를 만드는 CloudFormation 템플릿을 준비하고 DNS 장애 조치를 구성한다
> c) 필요할 때 EC2와 로드 밸런서를 만드는 템플릿을 준비하고 DynamoDB만 글로벌 테이블로 둔다
> d) DR 리전에 ASG와 로드 밸런서를 만들고 글로벌 테이블을 구성하되, CloudWatch 경보가 Lambda를 호출해 Route 53을 갱신하게 한다
>> [!success]- Answer
>> a) DR 리전에 **Auto Scaling 그룹과 로드 밸런서를 미리 만들어 두고** DynamoDB를 **글로벌 테이블**로 구성한 뒤, DNS 장애 조치가 DR 리전 로드 밸런서를 가리키게 한다
>> **왜 이 답인가** — 인프라가 **이미 떠 있어야** 다운타임이 가장 짧습니다. 데이터는 글로벌 테이블이 계속 복제하고, 전환은 Route 53 상태 확인 기반 장애 조치가 자동으로 처리합니다.
>> **나머지가 아닌 이유** — 필요할 때 템플릿으로 만드는 방식은 배포 시간만큼 다운타임이 생깁니다. Lambda로 DNS를 직접 갱신하는 것은 이미 있는 장애 조치 기능을 다시 만드는 일입니다.

> [!question] 한 기업이 ALB 뒤 EC2 플릿에서 **동적 웹사이트**를 제공하며 여러 언어를 지원해야 합니다. 아키텍처는 us-west-1에 있고 다른 지역 사용자들의 요청 지연이 큽니다. **기존 아키텍처를 여러 리전에 다시 만들지 않으면서** 위치와 무관하게 빠르게 응답하려면 무엇을 해야 합니까?
> a) ALB를 오리진으로 CloudFront 배포를 구성하고, **`Accept-Language` 요청 헤더 기준으로 캐시**하도록 캐시 동작을 설정한다
> b) 웹사이트를 S3에서 제공하도록 바꾸고 S3를 오리진으로 CloudFront를 구성해 `Accept-Language` 기준으로 캐시한다
> c) ALB와 통합된 API Gateway API를 만들고 스테이지 캐시를 `Accept-Language` 기준으로 켠다
> d) 리전마다 EC2를 띄워 NGINX 캐시 서버로 쓰고 Route 53 지리 위치 라우팅으로 묶는다
>> [!success]- Answer
>> a) ALB를 오리진으로 CloudFront 배포를 구성하고, **`Accept-Language` 요청 헤더 기준으로 캐시**하도록 캐시 동작을 설정한다
>> **왜 이 답인가** — 아키텍처를 그대로 두고 앞에 CloudFront만 붙이면 됩니다. 언어별로 응답이 다르므로 **그 헤더를 캐시 키에 포함**시켜야 언어가 섞이지 않습니다.
>> **나머지가 아닌 이유** — 동적 사이트를 S3로 옮기는 것은 불가능합니다. 리전마다 캐시 서버를 직접 운영하는 방식은 요구한 `다시 만들지 않는다`를 어깁니다.

> [!question] 한 제조 기업의 센서가 .csv 파일을 S3에 올리면 **가능한 한 빨리 이미지로 변환**해 보고서를 만들어야 합니다. 이미지는 **1개월 뒤 필요 없어지지만** .csv는 **연 2회 ML 학습**을 위해 보관해야 하며 학습·감사는 몇 주 전에 계획됩니다. 가장 비용 효율적인 조합은 무엇입니까? (2개 선택)
> a) .csv가 올라오면 호출되어 이미지로 변환해 S3에 저장하는 **AWS Lambda 함수**를 설계한다
> b) .csv는 업로드 1일 후 **S3 One Zone-IA**로 전환하고 **이미지는 30일 후 만료**시키는 수명 주기 규칙을 만든다
> c) .csv는 1일 후 S3 Glacier로 전환하고 이미지는 30일 후 만료시킨다
> d) .csv는 1일 후 Standard-IA로 전환하고 이미지는 저중복 스토리지에 유지한다
>> [!success]- Answer
>> a) .csv가 올라오면 호출되어 이미지로 변환해 S3에 저장하는 **AWS Lambda 함수**를 설계한다
>> b) .csv는 업로드 1일 후 **S3 One Zone-IA**로 전환하고 **이미지는 30일 후 만료**시키는 수명 주기 규칙을 만든다
>> **왜 이 답인가** — `가능한 한 빨리`는 이벤트 기반 Lambda입니다. .csv는 **몇 주 전에 계획된 학습에만 쓰이고 원본 센서에서 다시 얻을 수 있는 성격**이라 One Zone-IA로 내려 비용을 아끼고, 이미지는 30일 만료로 지웁니다.
>> **나머지가 아닌 이유** — Glacier는 미리 계획된 사용이라도 복원 절차가 추가됩니다. 저중복 스토리지는 더 이상 권장되지 않으며 이미지를 남길 이유도 없습니다.

> [!question] 한 기업의 웹 애플리케이션이 API Gateway → Lambda → DynamoDB로 구성되고 사용자는 **Cognito 사용자 풀**로 식별됩니다. **구독한 사용자만 프리미엄 콘텐츠에 접근**하게 하려고 합니다. 운영 오버헤드가 가장 적은 솔루션은 무엇입니까?
> a) API 사용량 계획과 API 키를 구현해 구독하지 않은 사용자의 접근을 제한한다
> b) API Gateway에서 API 캐싱과 제한(throttling)을 켠다
> c) API Gateway에 AWS WAF를 두고 구독 여부로 사용자를 거르는 규칙을 만든다
> d) DynamoDB 테이블의 프리미엄 콘텐츠에 세분화된 IAM 권한을 적용한다
>> [!success]- Answer
>> a) API 사용량 계획과 API 키를 구현해 구독하지 않은 사용자의 접근을 제한한다
>> **왜 이 답인가** — API Gateway의 **사용량 계획 + API 키**는 호출자를 등급으로 나누고 접근·호출량을 제어하기 위해 만들어진 기능입니다. 구독 여부에 따라 다른 계획을 주면 됩니다.
>> **나머지가 아닌 이유** — 캐싱·제한은 성능·보호 장치이지 구독 구분이 아닙니다. WAF는 요청 특성으로 거르는 도구라 구독 상태를 알지 못합니다. IAM 권한을 사용자마다 관리하는 것은 오버헤드가 큽니다.

> [!question] 한 기업의 애플리케이션이 RDS DB 인스턴스 하나와 **단일 AZ에 수동으로 만든 EC2 두 대**로 되어 있습니다. 최근 직원이 **DB 인스턴스를 삭제해 24시간 동안 서비스가 중단**됐습니다. 인프라의 신뢰성을 최대로 높이려면 무엇을 해야 합니까?
> a) DB 인스턴스를 **다중 AZ로 바꾸고 삭제 방지를 켜며**, EC2는 ALB 뒤 **여러 AZ의 Auto Scaling 그룹**에서 실행한다
> b) EC2 하나를 지우고 나머지에 종료 방지를 켜며 DB를 다중 AZ로 바꾸고 삭제 방지를 켠다
> c) DB 인스턴스를 하나 더 만들고 API Gateway와 Lambda로 두 DB에 동시에 쓰게 한다
> d) EC2를 여러 AZ Auto Scaling 그룹에 넣되 스팟 인스턴스를 쓰고 DB는 다중 AZ와 삭제 방지를 켠다
>> [!success]- Answer
>> a) DB 인스턴스를 **다중 AZ로 바꾸고 삭제 방지를 켜며**, EC2는 ALB 뒤 **여러 AZ의 Auto Scaling 그룹**에서 실행한다
>> **왜 이 답인가** — 두 가지 위험을 모두 없앱니다 — **사람의 실수 삭제**는 삭제 방지가, **단일 AZ·수동 운영**은 다중 AZ ASG와 로드 밸런서가 해결합니다.
>> **나머지가 아닌 이유** — 인스턴스를 줄이는 것은 신뢰성을 낮춥니다. 프로덕션 웹 계층에 스팟만 쓰면 회수 시 중단됩니다. 애플리케이션이 두 DB에 이중 기록하는 구조는 복잡하고 위험합니다.

> [!question] 한 기업의 다계층 애플리케이션이 Auto Scaling 그룹의 EC2와 **Oracle 전용 PL/SQL을 쓰는 RDS for Oracle**로 되어 있습니다. 트래픽이 꾸준히 늘어 **EC2는 과부하가 되고 RDS는 스토리지가 부족**해졌습니다. Auto Scaling 그룹에는 조정 지표가 없고 최소 인스턴스 수만 정해져 있습니다. 트래픽이 예측하기 어렵게 계속 늘 것으로 보입니다. 자동으로 확장되게 하려면 어떤 조합이 필요합니까? (2개 선택)
> a) RDS for Oracle 인스턴스에 **스토리지 Auto Scaling**을 구성한다
> b) Auto Scaling 그룹이 **평균 CPU**를 조정 지표로 쓰도록 구성한다
> c) RDS for Oracle 인스턴스에 여유 스토리지 부족 경보를 구성한다
> d) 데이터베이스를 Aurora로 옮겨 자동 확장 스토리지를 쓴다
>> [!success]- Answer
>> a) RDS for Oracle 인스턴스에 **스토리지 Auto Scaling**을 구성한다
>> b) Auto Scaling 그룹이 **평균 CPU**를 조정 지표로 쓰도록 구성한다
>> **왜 이 답인가** — 두 병목을 각각 자동화합니다. RDS에는 **스토리지 자동 확장 기능**이 있어 켜기만 하면 되고, EC2 계층에는 조정 지표(평균 CPU)를 지정해야 실제로 늘어납니다.
>> **나머지가 아닌 이유** — 경보는 알려 줄 뿐 늘려 주지 않습니다. Aurora는 Oracle 전용 PL/SQL을 지원하지 않아 애플리케이션이 깨집니다.

> [!question] 한 기업이 온프레미스 PostgreSQL을 **RDS for PostgreSQL**로 옮긴 뒤 신제품 출시로 워크로드가 늘었습니다. **인프라를 추가하지 않고** 더 큰 워크로드를 감당하려면, 가장 비용 효율적인 솔루션은 무엇입니까?
> a) 전체 워크로드에 대해 **예약 DB 인스턴스**를 구매하고 **DB 인스턴스를 더 크게** 변경한다
> b) DB 인스턴스를 다중 AZ로 만든다
> c) 예약 DB 인스턴스를 구매하고 RDS 인스턴스를 하나 더 추가한다
> d) DB 인스턴스를 온디맨드로 바꾼다
>> [!success]- Answer
>> a) 전체 워크로드에 대해 **예약 DB 인스턴스**를 구매하고 **DB 인스턴스를 더 크게** 변경한다
>> **왜 이 답인가** — `인프라를 추가하지 않는다`는 조건이므로 **인스턴스를 늘리는 대신 키우는(수직 확장)** 것이 답이고, 상시 워크로드이므로 예약 인스턴스로 사면 비용이 가장 낮습니다.
>> **나머지가 아닌 이유** — 인스턴스를 하나 더 두는 것은 인프라 추가입니다. 다중 AZ는 가용성 수단이지 처리량을 늘리지 않습니다. 온디맨드는 더 비쌉니다.

> [!question] 솔루션스 아키텍트가 모든 신규 사용자에게 **IAM 사용자 암호의 복잡도 요건과 교체 주기**를 강제하려고 합니다. 무엇을 해야 합니까?
> a) AWS 계정 전체에 대한 **암호 정책**을 설정한다
> b) 계정의 IAM 사용자마다 암호 정책을 설정한다
> c) 서드파티 소프트웨어로 암호 요건을 설정한다
> d) 사용자 생성 이벤트에 CloudWatch 규칙을 붙여 암호를 설정한다
>> [!success]- Answer

>> **나머지가 아닌 이유** — IAM 역할이나 태그는 암호화를 수행하지 않습니다. 키 정책은 키 사용 권한을 정하는 것이지 암호화를 강제하는 장치가 아닙니다.
