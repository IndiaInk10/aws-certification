> [!question] S3에 있는 파일을 CloudFront로만 제공하고 S3 URL로 직접 접근하는 것은 막아야 합니다. 무엇을 해야 합니까?
> a) 오리진 액세스 제어(OAC)를 설정하고 버킷 정책이 그 CloudFront 배포만 허용하게 한다
> b) 버킷을 퍼블릭으로 두고 CloudFront만 안내한다
> c) 버킷 정책에서 모든 접근을 거부한다
> d) S3 정적 웹사이트 호스팅을 켠다
>> [!success]- Answer
>> a) 오리진 액세스 제어(OAC)를 설정하고 버킷 정책이 그 CloudFront 배포만 허용하게 한다
>> **왜 이 답인가** — OAC(예전의 OAI)는 **CloudFront에만 버킷을 열어 주는** 장치입니다. 버킷은 비공개로 두고 CloudFront를 통해서만 나갑니다.
>> **나머지가 아닌 이유** — 퍼블릭 버킷은 직접 접근을 그대로 허용해 요구를 어깁니다. 모든 접근을 거부하면 CloudFront도 못 읽어 사이트가 죽습니다. 정적 웹사이트 호스팅은 오히려 **퍼블릭 엔드포인트를 하나 더 만드는** 것이라 반대 방향입니다.

> [!question] ALB 뒤 EC2와 Aurora로 된 글로벌 웹 앱의 재해 복구를 설계합니다. 30분 다운타임과 약간의 데이터 손실은 견딜 수 있고, 평상시에 대기 측이 부하를 처리할 필요는 없습니다. 무엇을 해야 합니까?
> a) 두 번째 리전에 인프라를 최소로 배포하고 Aurora 복제본을 두며 Route 53 능동-수동 장애 조치를 건다
> b) 두 리전에서 동일 규모로 능동-능동 운영한다
> c) 스냅샷만 다른 리전에 복사해 둔다
> d) 단일 리전에서 다중 AZ만 구성한다
>> [!success]- Answer
>> a) 두 번째 리전에 인프라를 최소로 배포하고 Aurora 복제본을 두며 Route 53 능동-수동 장애 조치를 건다
>> **왜 이 답인가** — `30분`과 `평상시 부하를 안 받아도 된다`가 **파일럿 라이트**를 정확히 가리킵니다. DB는 복제해 두고 앞단은 최소로 두었다가 장애 때 키웁니다.
>> **나머지가 아닌 이유** — 능동-능동은 요구보다 훨씬 비싸고 `부하를 처리할 필요 없다`는 조건과 어긋납니다. 스냅샷만으로는 30분 안에 못 세웁니다. 다중 AZ는 **리전 장애를 못 막습니다.**

> [!question] MySQL 기반 온프레미스 애플리케이션을 AWS로 옮깁니다. 평소 읽기 부하가 크고, 4시간마다 운영 DB를 통째로 내보내 스테이징을 채우는데 그동안 사용자 응답이 심하게 느려집니다. 어떻게 해야 합니까?
> a) Aurora MySQL을 다중 AZ로 쓰고, 스테이징은 필요할 때 DB 복제(클론)로 만든다
> b) RDS MySQL을 쓰고 mysqldump로 계속 내보낸다
> c) 운영 DB 인스턴스 크기를 두 배로 올린다
> d) 내보내기를 새벽에만 돌린다
>> [!success]- Answer
>> a) Aurora MySQL을 다중 AZ로 쓰고, 스테이징은 필요할 때 DB 복제(클론)로 만든다
>> **왜 이 답인가** — 문제의 원인은 **전체 내보내기가 운영 DB를 붙잡는 것**입니다. Aurora는 스토리지 계층에서 복제본을 만들어 주므로 운영 DB에 부하를 주지 않고 스테이징을 세울 수 있습니다.
>> **나머지가 아닌 이유** — mysqldump는 지금 하던 그 동작이라 문제가 그대로입니다. 인스턴스를 키우는 것은 돈으로 증상만 눌렀을 뿐 내보내기 부하는 남습니다. 새벽 이전은 스테이징을 쓰는 시간대를 제약해 개발팀 요구를 포기하는 것입니다.

> [!question] 온프레미스 NAS에 700TB의 백업 데이터가 있습니다. 7년 보관해야 하고 규제 요청이 올 때만 간헐적으로 꺼내 봅니다. 회선은 500Mbps고 마이그레이션은 **1개월 안에** 끝나야 합니다. 최저 비용으로 어떻게 합니까?
> a) Snowball Edge 장치 여러 대로 옮기고 S3 Glacier Deep Archive에 보관한다
> b) 회선으로 S3 Standard에 올리고 그대로 둔다
> c) DataSync로 회선을 통해 옮기고 S3 Standard-IA에 둔다
> d) Storage Gateway를 두고 그대로 온프레미스에 남긴다
>> [!success]- Answer
>> a) Snowball Edge 장치 여러 대로 옮기고 S3 Glacier Deep Archive에 보관한다
>> **왜 이 답인가** — 500Mbps로 700TB를 밀면 이론상으로도 넉 달이 넘어 **1개월 조건이 물리적으로 불가능**합니다. 그래서 물리 장치입니다. 그리고 `간헐적 규제 요청`은 꺼내는 일이 드물다는 뜻이라 가장 싼 아카이브 계층이 맞습니다.
>> **나머지가 아닌 이유** — 회선을 쓰는 두 보기는 기한을 못 지킵니다. Standard와 Standard-IA는 7년 보관 비용이 Deep Archive보다 훨씬 큽니다. 온프레미스에 남기는 것은 마이그레이션을 안 하는 것입니다.

> a) SSE-S3로 암호화하고 교차 리전 복제를 켠 뒤 Athena로 조회한다
> b) EMR 클러스터를 세워 조회하고 스크립트로 다른 리전에 복사한다
> c) Redshift에 적재하고 스냅샷을 다른 리전에 복사한다
> d) EC2에 데이터베이스를 세워 적재한다

>> a) SSE-S3로 암호화하고 교차 리전 복제를 켠 뒤 Athena로 조회한다

> a) Aurora PostgreSQL 글로벌 데이터베이스를 쓴다
> b) RDS PostgreSQL을 다중 AZ로 둔다

> [!question] Route 53이 10여 대의 EC2로 트래픽을 보내는데, 가끔 **비정상 인스턴스의 IP가 응답으로 돌아와** 시간 초과가 납니다. 무엇을 구현해야 합니까?
> a) 레코드마다 Route 53 상태 확인을 붙이고 다중값 응답 라우팅을 쓴다
> b) TTL을 늘린다
> c) 단순 라우팅으로 바꾼다
> d) 인스턴스를 더 늘린다

> [!question] CloudWatch Logs 로그 그룹에 쌓이는 애플리케이션 로그를 OpenSearch Service로 거의 실시간 전달해야 합니다. 운영 오버헤드가 가장 적은 방법은 무엇입니까?

> a) SQS FIFO 큐를 쓴다
> b) 결제 ID를 메시지 그룹 ID로 지정한다
> c) SQS 표준 큐를 쓰고 타임스탬프로 정렬한다
> d) 가시성 제한 시간을 늘린다
>> [!success]- Answer
>> a) SQS FIFO 큐를 쓴다
>> b) 결제 ID를 메시지 그룹 ID로 지정한다
>> **왜 이 답인가** — FIFO 큐만으로는 부족합니다. **순서는 메시지 그룹 안에서 보장**되므로, 결제 ID를 그룹으로 지정해야 "같은 결제 ID끼리" 순서가 지켜지고 서로 다른 결제는 병렬로 처리됩니다.
>> **나머지가 아닌 이유** — 표준 큐 + 정렬은 애플리케이션이 순서를 떠안는 것이고 중복 전달도 처리해야 합니다. 가시성 제한 시간은 재처리 방지용이라 순서와 무관합니다.

> [!question] S3 버킷에 수백만 개 객체가 이미 들어 있는데 암호화가 꺼진 상태였습니다. 기존 객체와 앞으로 올라올 객체 **모두** 암호화되게 하려면 최소한의 노력으로 어떻게 합니까?
> a) 버킷 기본 암호화를 켜고, 기존 객체는 S3 배치 작업으로 복사해 다시 쓴다
> b) 버킷 기본 암호화만 켠다
> c) 버킷을 새로 만들고 사람이 옮긴다
> d) 버킷 정책으로 암호화되지 않은 요청을 거부한다
>> [!success]- Answer
>> a) 버킷 기본 암호화를 켜고, 기존 객체는 S3 배치 작업으로 복사해 다시 쓴다
>> **왜 이 답인가** — **기본 암호화는 앞으로 올라오는 객체에만 적용됩니다.** 이미 있는 수백만 개는 다시 쓰지 않으면 평문 그대로입니다. 배치 작업이 그 일을 대신해 줍니다.
>> **나머지가 아닌 이유** — 기본 암호화만 켜는 보기는 요구의 절반만 만족합니다. 이 지점이 문항의 전부입니다. 사람이 옮기는 것은 수백만 개에 현실적이지 않고, 버킷 정책 거부는 기존 객체를 바꾸지 않습니다.

> [!question] 퍼블릭 서브넷의 EC2 웹 서버에 기본 보안 그룹이 붙어 있고, 기본 네트워크 ACL은 모든 트래픽을 차단하도록 수정됐습니다. 어디서나 443으로 접속되게 하려면 무엇이 필요합니까? (2개 선택)
> a) 네트워크 ACL에 0.0.0.0/0에서 오는 443 인바운드를 허용하는 규칙을 넣는다
> b) 네트워크 ACL에 1024~65535 아웃바운드를 허용하는 규칙을 넣는다
> c) 보안 그룹에 443 아웃바운드 규칙을 추가한다
> d) 보안 그룹에서 모든 인바운드를 거부하는 규칙을 만든다
>> [!success]- Answer
>> a) 네트워크 ACL에 0.0.0.0/0에서 오는 443 인바운드를 허용하는 규칙을 넣는다
>> b) 네트워크 ACL에 1024~65535 아웃바운드를 허용하는 규칙을 넣는다
>> **왜 이 답인가** — **네트워크 ACL은 상태 비저장**입니다. 들어오는 것을 허용해도 **나가는 응답을 따로 허용해야** 합니다. 응답은 임시 포트 범위로 나가므로 두 규칙이 모두 필요합니다.
>> **나머지가 아닌 이유** — 보안 그룹은 **상태 저장**이라 인바운드만 열면 응답은 자동으로 나갑니다. 아웃바운드를 손댈 이유가 없습니다. 이 상태/비상태 대비가 문항의 핵심입니다. 그리고 보안 그룹에는 거부 규칙 자체가 없습니다.
