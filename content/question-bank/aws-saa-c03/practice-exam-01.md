> [!question] 한 기업이 AWS Organizations로 수십 개 계정을 운영합니다. 특정 S3 버킷을 이 조직에 속한 계정의 주체만 사용할 수 있게 하되, 계정이 추가될 때마다 정책을 고치지 않아도 되게 하려고 합니다. 어떻게 해야 합니까?
> a) 버킷 정책에 `aws:PrincipalOrgID` 조건 키로 조직 ID를 지정한다
> b) 계정이 늘어날 때마다 버킷 정책의 Principal 목록에 계정 ID를 추가한다
> c) 조직 단위(OU)마다 별도의 버킷을 만들고 각각 정책을 건다
> d) 버킷을 퍼블릭으로 열고 각 계정의 IAM 정책으로만 제어한다
>> [!success]- Answer
>> a) 버킷 정책에 `aws:PrincipalOrgID` 조건 키로 조직 ID를 지정한다
>> **왜 이 답인가** — `aws:PrincipalOrgID`는 "요청자가 이 조직 소속인가"를 한 줄로 묻습니다. 계정이 늘고 줄어도 조직 ID는 그대로라 정책을 다시 만질 일이 없습니다. 지문의 `고치지 않아도 되게`가 이 키를 정확히 가리킵니다.
>> **나머지가 아닌 이유** — 계정 ID를 나열하는 방식은 동작은 하지만 계정이 늘 때마다 사람이 손대야 해서 조건을 정면으로 위반합니다. OU마다 버킷을 나누면 데이터가 쪼개지고 관리 대상만 늘어납니다. 버킷을 퍼블릭으로 여는 보기는 요구사항이 무엇이든 거의 항상 오답입니다.

> [!question] S3에 파일이 올라오면 Lambda가 내용을 가공해 데이터베이스에 넣습니다. 파일이 한꺼번에 많이 올라오는 시간대에 Lambda가 동시 실행 한도에 걸려 일부 파일이 처리되지 않습니다. 확장성을 개선하는 방법은 무엇입니까?
> a) S3 이벤트를 SQS 큐로 보내고 Lambda가 큐에서 꺼내 처리하게 한다
> b) Lambda 함수의 메모리를 최대로 올린다
> c) Lambda 타임아웃을 15분으로 늘린다
> d) 파일을 올리는 쪽에서 업로드 속도를 늦춘다
>> [!success]- Answer
>> a) S3 이벤트를 SQS 큐로 보내고 Lambda가 큐에서 꺼내 처리하게 한다
>> **왜 이 답인가** — 큐가 완충 역할을 합니다. 급증분이 큐에 쌓이고 Lambda는 자기 속도로 꺼내 가므로 한도에 걸려도 **일이 사라지지 않습니다.** 실패한 메시지는 다시 시도되거나 DLQ로 갑니다.
>> **나머지가 아닌 이유** — 메모리와 타임아웃은 **함수 하나의 성능**을 바꿀 뿐 동시 실행 수와 무관합니다. 업로드를 늦추는 것은 요구사항을 포기하는 것이지 해결이 아닙니다.

> [!question] ALB 뒤에 EC2 인스턴스 두 대가 있는 문서 관리 웹 애플리케이션이 있습니다. 사용자가 올린 문서가 어떤 때는 보이고 어떤 때는 안 보인다는 신고가 들어옵니다. 각 인스턴스는 자체 EBS 볼륨에 파일을 저장하고 있습니다. 무엇을 해야 합니까?
> a) 파일 저장소를 Amazon EFS로 옮기고 두 인스턴스가 함께 마운트하게 한다
> b) EBS 볼륨 크기를 두 배로 늘린다
> c) ALB에 고정 세션(스티키 세션)을 켠다
> d) 각 인스턴스의 EBS 볼륨을 다른 인스턴스에도 함께 연결한다
>> [!success]- Answer
>> a) 파일 저장소를 Amazon EFS로 옮기고 두 인스턴스가 함께 마운트하게 한다
>> **왜 이 답인가** — 파일이 인스턴스마다 따로 있으니 어느 서버로 붙느냐에 따라 보이고 안 보입니다. 여러 인스턴스가 같은 파일을 동시에 봐야 하면 답은 공유 파일 시스템, 즉 EFS입니다.
>> **나머지가 아닌 이유** — 용량은 원인이 아니므로 볼륨을 키워도 그대로입니다. 스티키 세션은 증상을 가릴 뿐 파일은 여전히 한쪽에만 있고, 그 인스턴스가 죽으면 문서가 사라집니다. EBS는 원칙적으로 인스턴스 한 대에 붙는 볼륨이라 "다른 인스턴스에도 함께 연결"은 이 시나리오의 해법이 아닙니다.

> [!question] 온프레미스 SMB 파일 서버의 용량이 한계에 왔습니다. 최근 파일은 지금처럼 빠르게 열려야 하고, 7일이 지난 파일은 자동으로 저비용 아카이브로 옮겨져야 합니다. 애플리케이션은 그대로 두어야 합니다. 어떤 조합입니까?
> a) Amazon S3 File Gateway를 두고 S3 수명 주기 정책으로 7일 후 Glacier Deep Archive로 전환한다
> b) 모든 파일을 S3 Standard에 올리고 사용자가 콘솔에서 내려받게 한다
> c) EBS 볼륨을 늘리고 스냅샷을 매일 뜬다
> d) Snowball Edge로 매주 파일을 실어 보낸다
>> [!success]- Answer
>> a) Amazon S3 File Gateway를 두고 S3 수명 주기 정책으로 7일 후 Glacier Deep Archive로 전환한다
>> **왜 이 답인가** — File Gateway는 SMB로 마운트되므로 애플리케이션은 그대로 두고, 최근 파일은 로컬 캐시에서 빠르게 나옵니다. `7일이 지나면`처럼 기간이 명시되면 수명 주기 정책입니다.
>> **나머지가 아닌 이유** — 콘솔에서 내려받게 하는 방식은 기존 파일 접근 방식을 바꿔 버립니다. EBS는 SMB 공유가 아니고 아카이브 전환도 자동으로 안 됩니다. Snowball을 매주 돌리는 것은 일회성 대량 이전용 도구를 상시 운영에 쓰는 것이라 운영 부담이 오히려 큽니다.

> [!question] 프로덕션 VPC로 드나드는 트래픽을 상태 저장 규칙으로 검사하고 침입 탐지 기능을 적용해야 합니다. 관리형 서비스를 쓰려고 합니다. 무엇입니까?
> a) AWS Network Firewall
> b) AWS Firewall Manager
> c) 네트워크 ACL
> d) AWS WAF
>> [!success]- Answer
>> a) AWS Network Firewall
>> **왜 이 답인가** — VPC 경계에서 트래픽을 검사하는 관리형 방화벽은 Network Firewall입니다. 상태 저장 규칙과 침입 탐지·차단이 여기에 있습니다.
>> **나머지가 아닌 이유** — Firewall Manager는 방화벽을 **여러 계정에 걸쳐 중앙에서 관리**하는 도구지 트래픽을 검사하는 물건이 아닙니다. 이름이 비슷해 가장 많이 걸리는 함정입니다. 네트워크 ACL은 상태 비저장이고 규칙이 단순합니다. WAF는 계층 7의 HTTP 요청 내용을 봅니다.

> [!question] DynamoDB 테이블의 데이터가 애플리케이션 버그로 손상됐습니다. 손상 직전 시점으로 되돌려야 하고, 복구 지점 목표는 15분입니다. 어떻게 대비해야 합니까?
> a) 지정 시간 복구(PITR)를 켜 둔다
> b) 글로벌 테이블을 만들어 다른 리전에 복제한다
> c) 읽기 전용 복제본을 추가한다
> d) DynamoDB Accelerator(DAX)를 붙인다
>> [!success]- Answer
>> a) 지정 시간 복구(PITR)를 켜 둔다
>> **왜 이 답인가** — PITR은 최근 35일 안의 임의 시점으로 테이블을 되살립니다. `손상 직전으로 되돌린다`는 요구에 정확히 대응합니다.
>> **나머지가 아닌 이유** — 글로벌 테이블은 복제라서 **손상된 데이터가 그대로 다른 리전에도 복제됩니다.** 재해에는 강하지만 논리적 손상에는 무력합니다. 여기가 가장 자주 갈리는 지점입니다. 읽기 전용 복제본은 DynamoDB의 개념이 아니고, DAX는 캐시라 복구와 무관합니다.

> [!question] 온프레미스에 70TB의 영상 아카이브가 있습니다. 이를 S3로 옮겨야 하는데, 업무용 인터넷 회선의 대역폭을 최대한 쓰지 않으면서 되도록 빨리 끝내야 합니다. 무엇을 써야 합니까?
> a) AWS Snowball Edge 장치로 물리적으로 전송한다
> b) S3 File Gateway를 설치해 인터넷으로 동기화한다
> c) AWS DataSync로 인터넷을 통해 전송한다
> d) S3 Transfer Acceleration을 켜고 업로드한다
>> [!success]- Answer
>> a) AWS Snowball Edge 장치로 물리적으로 전송한다
>> **왜 이 답인가** — `대역폭을 쓰지 않으면서`와 70TB라는 규모가 함께 나오면 물리 장치입니다. 70TB를 회선으로 밀면 몇 주가 걸리고 그동안 업무 회선이 눌립니다.
>> **나머지가 아닌 이유** — File Gateway·DataSync·Transfer Acceleration은 셋 다 **인터넷 회선을 그대로 씁니다.** 전송을 더 빠르고 편하게 해 줄 뿐 대역폭 조건을 못 지킵니다. 특히 Transfer Acceleration은 오히려 회선을 더 강하게 쓰는 쪽입니다.

> [!question] 로그 파일을 S3에 저장합니다. 처음 30일은 자주 조회하고, 그 뒤로는 거의 안 보지만 감사 요청이 오면 몇 초 안에 꺼낼 수 있어야 하며, 4년 뒤 삭제합니다. 비용이 가장 낮은 구성은 무엇입니까?
> a) 30일 후 S3 Standard-IA로 전환하고 4년 뒤 만료시키는 수명 주기 정책
> b) 30일 후 S3 Glacier Deep Archive로 전환하고 4년 뒤 만료
> c) 계속 S3 Standard에 두고 4년 뒤 만료
> d) 30일 후 S3 One Zone-IA로 전환하고 4년 뒤 만료
>> [!success]- Answer
>> a) 30일 후 S3 Standard-IA로 전환하고 4년 뒤 만료시키는 수명 주기 정책

>> **나머지가 아닌 이유** — Deep Archive는 꺼내는 데 몇 시간이 걸려 감사 요청 조건을 못 지킵니다. Standard를 계속 쓰면 안 보는 기간의 비용이 그대로 나갑니다. One Zone-IA는 더 싸지만 **AZ 하나에만** 저장돼 그 AZ가 사라지면 로그도 사라집니다 — 감사용 기록에는 부적절합니다.

> [!question] EC2 인스턴스에서 도는 애플리케이션이 S3 버킷을 읽고 써야 합니다. 가장 안전한 방법은 무엇입니까?
> a) 필요한 권한을 가진 IAM 역할을 만들어 인스턴스에 연결한다
> b) IAM 사용자를 만들어 액세스 키를 인스턴스의 설정 파일에 넣는다
> c) 액세스 키를 환경 변수로 넣고 정기적으로 사람이 교체한다
> d) 버킷을 퍼블릭 읽기·쓰기로 연다
>> [!success]- Answer
>> a) 필요한 권한을 가진 IAM 역할을 만들어 인스턴스에 연결한다
>> **왜 이 답인가** — 역할을 쓰면 임시 자격 증명이 자동으로 발급되고 자동으로 만료됩니다. 어디에도 키가 저장되지 않습니다.
>> **나머지가 아닌 이유** — 설정 파일이든 환경 변수든 **장기 액세스 키를 인스턴스에 두는 순간** 유출 경로가 생기고 교체가 사람 몫이 됩니다. 이 두 보기는 SAA에서 거의 항상 오답 자리에 놓입니다. 버킷을 퍼블릭으로 여는 것은 문제를 권한이 아니라 노출로 바꿔 놓는 것입니다.

> [!question] 주문 처리 시스템이 하루 중 특정 시간에만 몰리고 나머지는 한가합니다. 처리 순서가 뒤바뀌면 안 되고, 메시지가 유실되어서도 안 됩니다. 무엇을 써야 합니까?
> a) SQS FIFO 큐
> b) SQS 표준 큐
> c) SNS 주제
> d) EventBridge 이벤트 버스
>> [!success]- Answer
>> a) SQS FIFO 큐
>> **왜 이 답인가** — `순서가 뒤바뀌면 안 된다`가 FIFO를 지목합니다. 큐이므로 유실 방지와 급증 완충도 함께 됩니다.
>> **나머지가 아닌 이유** — 표준 큐는 처리량이 크지만 **순서를 보장하지 않고** 중복 전달이 있을 수 있습니다. SNS는 구독자에게 밀어 주는 방식이라 소비자가 없으면 메시지가 사라져 유실 방지 조건에 맞지 않습니다. EventBridge는 이벤트 라우팅 도구로 순서 보장이 목적이 아닙니다.

> [!question] 전 세계 사용자를 대상으로 하는 웹 애플리케이션이 있습니다. 정적 자산은 S3에, 동적 API는 ALB 뒤 EC2에 있습니다. 두 종류 모두 응답이 느리다는 불만이 있습니다. 가장 적절한 것은 무엇입니까?
> a) S3와 ALB를 각각 오리진으로 등록한 CloudFront 배포를 만든다
> b) AWS Global Accelerator를 앞에 둔다
> c) 리전마다 애플리케이션을 복제하고 Route 53 지연 시간 기반 라우팅을 건다
> d) ALB를 NLB로 교체한다
>> [!success]- Answer
>> a) S3와 ALB를 각각 오리진으로 등록한 CloudFront 배포를 만든다
>> **왜 이 답인가** — CloudFront는 오리진을 여러 개 둘 수 있어 정적 자산과 동적 API를 한 배포에서 처리합니다. 정적은 엣지에 캐시되고, 동적도 엣지까지는 AWS 망을 타므로 둘 다 빨라집니다.
>> **나머지가 아닌 이유** — Global Accelerator는 경로를 좋게 할 뿐 **캐시하지 않아서** 정적 자산 쪽 이득이 CloudFront보다 작습니다. 리전 복제는 효과는 있지만 이 문제를 풀자고 하기에는 비용과 운영 부담이 몇 배입니다. NLB 교체는 HTTP 애플리케이션에서 지연을 줄여 주지 않습니다.

> a) 온프레미스 서버를 사용자 지정 오리진으로 지정한 CloudFront 배포를 만든다
> b) 유럽 리전에 인프라를 복제하고 Route 53 지리 근접 라우팅을 건다
> c) Route 53 지연 시간 기반 라우팅으로 온프레미스 서버를 가리킨다
> d) 유럽에 새 데이터 센터를 임차한다
>> [!success]- Answer
>> a) 온프레미스 서버를 사용자 지정 오리진으로 지정한 CloudFront 배포를 만든다
>> **왜 이 답인가** — CloudFront의 오리진은 S3나 ELB만이 아닙니다. **온프레미스 서버도 사용자 지정 오리진이 됩니다.** 며칠 안에 끝내야 하는 조건에서 인프라를 옮기지 않고 앞단만 붙이는 유일한 답입니다.
>> **나머지가 아닌 이유** — 유럽 복제와 데이터 센터 임차는 `며칠 안에`를 못 지키고 `백엔드는 미국에`도 어깁니다. Route 53 라우팅은 **어디로 보낼지만 고를 뿐** 목적지가 하나뿐이면 거리가 그대로라 로딩 시간이 안 줄어듭니다.

> [!question] 세 개의 가용 영역에 퍼블릭·프라이빗 서브넷을 각각 둔 VPC가 있습니다. 프라이빗 서브넷의 EC2가 소프트웨어 업데이트를 내려받아야 합니다. 무엇을 해야 합니까?
> a) 각 AZ의 퍼블릭 서브넷에 NAT 게이트웨이를 두고 해당 AZ 프라이빗 서브넷의 라우팅 테이블이 그것을 가리키게 한다
> b) 프라이빗 서브넷에 NAT 게이트웨이를 하나 만든다
> c) 프라이빗 서브넷 라우팅 테이블이 인터넷 게이트웨이를 직접 가리키게 한다
> d) 인스턴스마다 탄력적 IP를 붙인다
>> [!success]- Answer
>> a) 각 AZ의 퍼블릭 서브넷에 NAT 게이트웨이를 두고 해당 AZ 프라이빗 서브넷의 라우팅 테이블이 그것을 가리키게 한다
>> **왜 이 답인가** — NAT 게이트웨이는 **퍼블릭 서브넷에 있어야** 동작하고 **AZ 단위** 자원입니다. AZ마다 두지 않으면 한 AZ가 죽을 때 다른 AZ의 인스턴스까지 밖으로 못 나갑니다.
>> **나머지가 아닌 이유** — 프라이빗 서브넷의 NAT는 자기도 밖으로 나갈 길이 없습니다. 인터넷 게이트웨이를 직접 가리키면 그 서브넷은 정의상 퍼블릭이 되어 요구를 어깁니다. 탄력적 IP를 붙이는 것도 인스턴스를 인터넷에 노출시킵니다.

> [!question] 음식 배달 서비스의 주문 **수집**은 빠르지만 주문 **이행**은 오래 걸립니다. 피크 시간에 확장이 안 됩니다. 어떻게 해야 합니까?
> a) 수집용과 이행용 SQS 큐를 각각 두고, 각 큐의 인스턴스당 백로그를 지표로 두 Auto Scaling 그룹을 따로 조절한다
> b) 큐 하나를 두고 두 그룹이 함께 폴링하게 한다
> c) 두 그룹을 하나로 합치고 인스턴스를 늘린다
> d) 이행 작업을 수집 프로세스 안으로 옮긴다
>> [!success]- Answer
>> a) 수집용과 이행용 SQS 큐를 각각 두고, 각 큐의 인스턴스당 백로그를 지표로 두 Auto Scaling 그룹을 따로 조절한다
>> **왜 이 답인가** — **속도가 다른 두 단계는 따로 확장되어야** 합니다. 큐를 나눠야 각 단계의 밀린 양을 따로 볼 수 있고, `인스턴스당 백로그`가 바로 그 지표입니다.
>> **나머지가 아닌 이유** — 큐 하나를 공유하면 두 단계의 밀린 양이 섞여 어느 쪽을 늘려야 할지 알 수 없습니다. 그룹을 합치면 빠른 단계까지 불필요하게 늘어납니다. 이행을 수집 안으로 넣는 것은 지금 문제인 결합을 더 강하게 만드는 것입니다.

> [!question] EC2에서 도는 웹사이트가 수천 개 IP에서 오는 대규모 DDoS 공격을 받고 있고 다운타임이 허용되지 않습니다. 어떤 조치를 취해야 합니까? (2개 선택)
> a) AWS Shield Advanced를 적용한다
> b) CloudFront 배포를 앞에 두고 AWS WAF로 속도 기반 규칙을 건다
> c) GuardDuty를 켜서 공격자를 자동 차단하게 한다
> d) 보안 그룹에 공격 IP를 하나씩 거부 규칙으로 넣는다
>> [!success]- Answer
>> a) AWS Shield Advanced를 적용한다
>> b) CloudFront 배포를 앞에 두고 AWS WAF로 속도 기반 규칙을 건다
>> **왜 이 답인가** — 대규모 볼륨 공격은 Shield Advanced가 맡고, 엣지에서 흡수하며 요청 단위로 걸러 내는 것은 CloudFront + WAF입니다. 둘을 함께 쓰는 것이 표준 구성입니다.
>> **나머지가 아닌 이유** — GuardDuty는 **탐지** 서비스입니다. 알려 줄 뿐 스스로 막지 않습니다. 보안 그룹에는 애초에 **거부 규칙이 없고**, 수천 개 IP를 손으로 넣는 것은 방법도 규모도 맞지 않습니다.

> [!question] 두 리전에 걸친 여러 AWS 계정에서 API Gateway REST API를 운영합니다. SQL 인젝션과 XSS를 막는 규칙을 계정마다 따로 관리하지 않고 중앙에서 강제하려고 합니다. 무엇을 써야 합니까?
> a) AWS Firewall Manager로 WAF 규칙을 조직 전체에 배포한다
> b) 각 계정에서 WAF 웹 ACL을 따로 만들어 API 단계에 붙인다
> c) 각 계정에 Network Firewall을 세운다
> d) 각 계정에 Shield Advanced를 구독한다
>> [!success]- Answer
>> a) AWS Firewall Manager로 WAF 규칙을 조직 전체에 배포한다
>> **왜 이 답인가** — `여러 계정` + `중앙에서 강제`가 Firewall Manager의 정의입니다. 새 계정이나 새 API가 생겨도 정책이 자동으로 적용됩니다.
>> **나머지가 아닌 이유** — 계정마다 웹 ACL을 만드는 것은 동작은 하지만 관리 노력이 계정 수만큼 늘어 `최소한의 관리 노력`을 어깁니다. **바로 이 조건이 WAF 단독과 Firewall Manager를 가릅니다.** Network Firewall은 VPC 트래픽용이고, Shield는 DDoS용이라 SQL 인젝션과 무관합니다.
