> [!question] DynamoDB 테이블은 기본적으로 암호화되지만, 감사에서 **키 사용 권한을 회사가 통제하고 키 사용 기록을 확인**하라고 요구합니다. 무엇을 해야 합니까?
> a) 테이블 암호화를 **고객 관리형 KMS 키**로 지정한다
> b) 기본 AWS 소유 키를 그대로 둔다
> c) 항목 값을 애플리케이션에서 암호화한다
> d) 테이블에 대한 IAM 정책을 좁힌다
>> [!success]- Answer
>> a) 테이블 암호화를 **고객 관리형 KMS 키**로 지정한다
>> **왜 이 답인가** — 고객 관리형 키만 **키 정책으로 사용 권한을 통제하고 CloudTrail로 사용 기록을 남깁니다.**
>> **나머지가 아닌 이유** — AWS 소유 키는 고객이 보거나 통제할 수 없습니다. 애플리케이션 암호화는 요구를 과하게 넘고, IAM 정책은 테이블 접근이지 키 통제가 아닙니다.

> [!question] 두 리전의 S3 버킷에 같은 데이터를 복제해 두었습니다. 애플리케이션이 **하나의 엔드포인트로 요청하되 리전 장애 시 자동으로 다른 버킷**을 쓰게 하려면 무엇을 해야 합니까?
> a) **S3 다중 리전 액세스 포인트**를 만들고 장애 조치 구성을 적용한다
> b) 애플리케이션 코드에 버킷 두 개를 순서대로 시도하는 로직을 넣는다
> c) Route 53 장애 조치 레코드로 두 버킷 웹사이트 엔드포인트를 등록한다
> d) 두 버킷 앞에 각각 CloudFront 배포를 만든다
>> [!success]- Answer
>> a) **S3 다중 리전 액세스 포인트**를 만들고 장애 조치 구성을 적용한다

>> **나머지가 아닌 이유** — 코드에 분기를 넣는 것은 애플리케이션마다 반복해야 합니다. Route 53 방식은 정적 웹사이트 엔드포인트에만 해당하고 API 접근에는 맞지 않습니다.

> [!question] Amazon EKS로 컨테이너 애플리케이션을 운영하며 **들어오는 요청을 알맞은 마이크로서비스로 라우팅**해야 합니다. 가장 비용 효율적인 솔루션은 무엇입니까?
> a) AWS Load Balancer Controller로 **Application Load Balancer**를 프로비저닝한다
> b) AWS Load Balancer Controller로 Network Load Balancer를 프로비저닝한다
> c) Lambda 함수로 요청을 EKS에 연결한다
> d) Amazon API Gateway로 요청을 EKS에 연결한다
>> [!success]- Answer
>> a) AWS Load Balancer Controller로 **Application Load Balancer**를 프로비저닝한다
>> **왜 이 답인가** — **경로·호스트 기반 라우팅**은 계층 7 로드 밸런서인 ALB의 기능입니다. 여러 마이크로서비스를 **하나의 ALB**로 나눠 보낼 수 있어 비용도 낮습니다.
>> **나머지가 아닌 이유** — NLB는 계층 4라 경로를 보지 못해 서비스마다 리스너·주소가 필요합니다. API Gateway는 추가 요금이 붙고, Lambda는 이 역할이 아닙니다.

> [!question] 내부 마이크로서비스 간 통신에 **회사 내부 CA가 발급한 TLS 인증서**를 써야 하는데, 인증서 발급·갱신을 자동화하고 싶습니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) **AWS Private Certificate Authority**로 내부 CA를 운영하고 인증서를 발급·갱신한다
> b) ACM 퍼블릭 인증서를 발급받는다
> c) 자체 서명 인증서를 만들어 배포한다
> d) Secrets Manager에 인증서를 저장한다

> d) `alias/aws/ebs` 별칭의 KMS 키를 만들고 계정의 기본 EBS 볼륨 암호화를 켠다
>> [!success]- Answer
>> a) 새 KMS 키를 만들고 EKS 클러스터에서 **KMS 시크릿 암호화(envelope encryption)**를 활성화한다
>> **왜 이 답인가** — EKS에는 **etcd에 저장되는 Kubernetes 시크릿을 KMS 키로 봉투 암호화**하는 기능이 있습니다. 요구가 그 기능을 정확히 가리킵니다.
>> **나머지가 아닌 이유** — Secrets Manager는 별도 저장소라 **etcd 안의 시크릿을 암호화하지 않습니다.** EBS 암호화는 볼륨 수준이라 요구와 다릅니다.

> [!question] Aurora 글로벌 데이터베이스를 운영하는 팀이 **정기 점검을 위해 계획적으로 기본 리전을 바꾸려** 합니다. 데이터 손실 없이 전환해야 합니다. 어떤 방법을 써야 합니까?
> a) **관리형 계획 장애 조치(switchover)**를 실행해 복제가 따라잡은 뒤 역할을 바꾸게 한다
> b) 보조 클러스터를 글로벌 데이터베이스에서 분리해 승격한다
> c) 기본 클러스터를 삭제해 보조가 승격되게 한다
> d) 애플리케이션 연결만 보조 클러스터로 바꾼다
>> [!success]- Answer
>> a) **관리형 계획 장애 조치(switchover)**를 실행해 복제가 따라잡은 뒤 역할을 바꾸게 한다
>> **왜 이 답인가** — 계획된 전환은 **복제 지연이 0이 될 때까지 기다렸다가 역할을 교체**하므로 데이터 손실이 없고 글로벌 데이터베이스 구성도 유지됩니다.
>> **나머지가 아닌 이유** — 분리 후 승격은 **재해 상황용**이라 데이터 손실 위험이 있고 글로벌 구성이 깨집니다. 기본을 삭제하는 것은 위험하고, 연결만 바꾸면 보조는 여전히 읽기 전용입니다.

> [!question] 한 글로벌 스트리밍 기업이 CloudFront로 콘텐츠를 **국가별로 단계적으로 공개**하려 합니다. **공개 대상이 아닌 국가의 시청자는 볼 수 없어야** 합니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) CloudFront에서 **허용 목록 방식의 지리적 제한**을 추가하고 사용자 지정 오류 메시지를 설정한다
> b) 제한 콘텐츠용 새 URL을 만들고 서명된 URL·쿠키로 접근을 인가한다
> c) 콘텐츠 데이터를 암호화하고 사용자 지정 오류 메시지를 설정한다
> d) 새 URL을 만들고 서명된 URL에 시간 제한 접근 정책을 설정한다
>> [!success]- Answer
>> a) CloudFront에서 **허용 목록 방식의 지리적 제한**을 추가하고 사용자 지정 오류 메시지를 설정한다
>> **왜 이 답인가** — 국가 기준 차단은 CloudFront의 **지리적 제한(geo restriction)** 기능입니다. 허용 목록에 공개한 국가만 넣으면 나머지는 자동으로 막힙니다.
>> **나머지가 아닌 이유** — 서명된 URL·쿠키는 **사용자별 접근 제어**이지 국가 기준이 아닙니다. 암호화는 시청 자체를 막지 않습니다.

> [!question] 한 미디어 기업이 CloudFront로 콘텐츠를 전달하며 **프리미엄 고객만** 미디어 스트림과 파일에 접근하게 하려 합니다. 또한 **영화 대여나 음원 다운로드처럼 개별 콘텐츠를 온디맨드로** 제공합니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) 프리미엄 고객에게 **CloudFront 서명된 URL**을 생성해 제공한다
> b) 프리미엄 고객에게 S3 서명된 쿠키를 생성해 제공한다
> c) 오리진 액세스 제어(OAC)로 비프리미엄 고객의 접근을 제한한다
> d) 필드 수준 암호화를 켜서 비프리미엄 고객을 차단한다
>> [!success]- Answer
>> a) 프리미엄 고객에게 **CloudFront 서명된 URL**을 생성해 제공한다
>> **왜 이 답인가** — **개별 파일 하나에 대한 접근**을 제한할 때는 서명된 URL입니다(여러 파일에 걸친 접근이면 서명된 쿠키). 대여·다운로드처럼 콘텐츠 단위 제공이 그 조건입니다.
>> **나머지가 아닌 이유** — OAC는 **CloudFront가 S3에 접근하는 방법**이지 최종 사용자 구분이 아닙니다. 필드 수준 암호화는 폼 데이터 보호 기능입니다.
