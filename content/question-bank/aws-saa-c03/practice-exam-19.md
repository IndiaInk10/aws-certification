> [!question] ECS 서비스가 **ALB 뒤에서 웹 요청을 처리**하는데, CPU 기준으로 조정했더니 **요청이 몰려도 CPU가 늦게 오르는 워크로드**라 응답이 느려진 뒤에야 확장됩니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) **대상당 요청 수(`ALBRequestCountPerTarget`)**를 지표로 하는 대상 추적 조정 정책을 구성한다
> b) CPU 목표값을 더 낮춘다
> c) 예약 조정으로 근무 시간에 용량을 고정한다
> d) 작업 하나의 CPU 할당을 늘린다
>> [!success]- Answer
>> a) **대상당 요청 수(`ALBRequestCountPerTarget`)**를 지표로 하는 대상 추적 조정 정책을 구성한다
>> **왜 이 답인가** — 이 워크로드에서 부하를 **가장 먼저 정확히 나타내는 값은 요청 수**입니다. 작업 하나가 감당할 요청 수를 목표로 두면 CPU가 오르기 전에 확장이 시작됩니다.
>> **나머지가 아닌 이유** — CPU 목표를 낮추는 것은 여전히 늦게 반응하며 평소 낭비가 늘어납니다. 예약 조정은 변동에 대응하지 못하고, 작업 크기를 키우는 것은 확장이 아닙니다.

> c) Amazon S3를 파일 시스템으로 온프레미스 서버에 마운트한다
> d) Amazon EFS 볼륨을 온프레미스 서버에 마운트한다
>> [!success]- Answer
>> a) **AWS Storage Gateway 파일 게이트웨이**를 배포해 NFS 스토리지를 대체한다
>> b) **AWS Storage Gateway 볼륨 게이트웨이**를 배포해 블록 스토리지를 대체한다
>> **왜 이 답인가** — 프로토콜별로 게이트웨이가 나뉩니다 — **NFS·SMB는 파일 게이트웨이**, **iSCSI 블록은 볼륨 게이트웨이**. 둘 다 로컬 캐시를 제공해 애플리케이션을 바꾸지 않아도 됩니다.
>> **나머지가 아닌 이유** — S3는 파일 시스템으로 마운트하는 물건이 아닙니다. EFS를 직접 마운트하면 로컬 캐시가 없어 지연이 커집니다.

> [!question] 사내에서 만든 서비스를 **다른 계정의 VPC에 노출**해야 하는데, **인터넷을 거치지 않고 상대가 IP 대역을 알 필요도 없어야** 합니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) NLB 뒤에 서비스를 두고 **AWS PrivateLink 엔드포인트 서비스**로 게시해 소비자가 인터페이스 엔드포인트로 접속하게 한다
> b) VPC 피어링을 맺는다
> c) 전송 게이트웨이로 연결한다
> d) 서비스를 퍼블릭 ALB로 노출하고 보안 그룹으로 제한한다
>> [!success]- Answer
>> a) NLB 뒤에 서비스를 두고 **AWS PrivateLink 엔드포인트 서비스**로 게시해 소비자가 인터페이스 엔드포인트로 접속하게 한다

> [!question] Auto Scaling 그룹이 띄우는 인스턴스는 **애플리케이션이 준비되기까지 5분**이 걸립니다. 그런데 새 인스턴스가 뜨자마자 **ELB 상태 확인에 실패해 종료되고 다시 뜨는 일이 반복**됩니다. 무엇을 해야 합니까?
> a) Auto Scaling 그룹의 **상태 확인 유예 기간(health check grace period)**을 준비 시간보다 길게 설정한다

> c) 조정 정책의 쿨다운을 늘린다
> d) 상태 확인 유형을 ELB에서 EC2로 되돌린다

>> a) Auto Scaling 그룹의 **상태 확인 유예 기간(health check grace period)**을 준비 시간보다 길게 설정한다

> a) S3와 DynamoDB용 **게이트웨이 VPC 엔드포인트**를 만들고 라우팅 테이블에 연결한다

> d) 인스턴스를 퍼블릭 서브넷으로 옮긴다
>> [!success]- Answer
