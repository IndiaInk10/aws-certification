> [!question] 개발자들이 **자기 애플리케이션용 IAM 역할을 직접 만들 수 있어야** 하지만, 그렇게 만든 역할이 **관리자 권한을 갖는 일은 없어야** 합니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) 개발자에게 역할 생성 권한을 주되, **생성하는 역할에 권한 경계(permissions boundary)를 반드시 붙이도록** 조건을 건 정책을 부여한다
> b) 개발자에게 역할 생성 권한을 주지 않고 요청할 때마다 관리자가 만들어 준다
> c) 개발자 계정에 관리자 권한을 거부하는 SCP를 붙인다
> d) 개발자가 만든 역할을 매일 검사해 과도한 권한을 회수한다
>> [!success]- Answer
>> a) 개발자에게 역할 생성 권한을 주되, **생성하는 역할에 권한 경계(permissions boundary)를 반드시 붙이도록** 조건을 건 정책을 부여한다
>> **왜 이 답인가** — 권한 경계는 **그 주체가 가질 수 있는 권한의 상한선**입니다. 경계 부착을 강제하면 개발자가 어떤 정책을 붙여도 상한을 넘지 못하므로, 위임과 통제를 함께 얻습니다.
>> **나머지가 아닌 이유** — 관리자가 매번 만들어 주면 위임이 사라집니다. SCP는 계정 단위 상한이라 **개발자가 만든 역할에만** 적용하기 어렵고, 사후 검사는 그 사이의 위험을 막지 못합니다.

> [!question] 주문 애플리케이션이 결제 승인 요청을 SQS 큐에 넣으면 소비자가 처리합니다. 결제사 규정상 **요청을 보낸 뒤 최소 5분이 지나야** 승인 조회를 할 수 있는데, 지금은 소비자가 메시지를 곧바로 꺼내 조회했다가 실패하고 재시도를 반복합니다. 코드 변경을 최소로 하면서 이 문제를 해결하려면 무엇을 해야 합니까?
> a) 큐의 **지연(delay) 설정을 5분으로** 두어 메시지가 큐에 들어간 뒤 5분 동안 보이지 않게 한다
> b) 큐의 가시성 제한 시간을 5분으로 늘린다
> c) 큐의 메시지 보존 기간을 5분으로 줄인다
> d) 소비자 코드에 5분 `sleep`을 넣는다
>> [!success]- Answer
>> a) 큐의 **지연(delay) 설정을 5분으로** 두어 메시지가 큐에 들어간 뒤 5분 동안 보이지 않게 한다
>> **왜 이 답인가** — 지연 큐(또는 메시지 단위 `DelaySeconds`)는 **처음부터 일정 시간 동안 메시지를 숨깁니다.** `보낸 뒤 최소 5분`이라는 조건을 큐 설정 한 줄로 표현합니다.
>> **나머지가 아닌 이유** — 가시성 제한 시간은 **이미 꺼내 간 메시지**를 다른 소비자에게 숨기는 값이라 첫 수신 시점을 늦추지 못합니다. 보존 기간은 메시지가 버려지는 시각이고, 소비자에서 기다리는 방식은 그동안 처리 자원을 잡아먹습니다.

> [!question] 인스턴스에 **임시 스크래치 공간이 필요하며 초당 수십만 IOPS**를 요구합니다. 인스턴스가 종료되면 데이터는 사라져도 됩니다. 어떤 스토리지를 써야 합니까?
> a) **인스턴스 스토어(NVMe)** 볼륨을 사용한다
> b) 프로비저닝된 IOPS(io2) EBS 볼륨을 사용한다
> c) 범용(gp3) EBS 볼륨을 사용한다
> d) EFS를 마운트한다
>> [!success]- Answer
>> a) **인스턴스 스토어(NVMe)** 볼륨을 사용한다
>> **왜 이 답인가** — 인스턴스 스토어는 **호스트에 직접 붙은 디스크**라 가장 낮은 지연과 높은 IOPS를 제공합니다. "사라져도 된다"는 조건이 휘발성 저장소를 쓰라는 신호입니다.
>> **나머지가 아닌 이유** — io2는 네트워크 연결 스토리지라 지연이 더 크고 비쌉니다. gp3는 성능이 부족하고, EFS는 공유 파일 시스템으로 이 목적에 맞지 않습니다.

> d) AWS Config 규칙으로 퍼블릭 S3 버킷을 탐지한다
>> [!success]- Answer
>> a) **IAM Access Analyzer**를 켜서 외부 주체와 공유되는 리소스를 자동으로 찾아내고 결과를 검토한다

> b) 폴링 주기를 늘려 호출 횟수를 줄인다
> c) 큐를 FIFO 큐로 바꾼다

> a) 큐의 **메시지 보존 기간을 기본 4일에서 최대 14일로** 늘린다

> c) 큐에 배달 못한 편지 큐를 붙이고 최대 수신 횟수를 1로 둔다
> d) 큐를 FIFO 큐로 바꾼다

>> [!success]- Answer
>> a) 상태 머신 유형을 **익스프레스 워크플로(Express Workflows)**로 만든다
>> **왜 이 답인가** — 익스프레스는 **초당 수십만 건의 단기 실행**을 위해 만들어졌고 요금 체계가 실행 시간·메모리 기준이라 이런 패턴에서 표준보다 훨씬 쌉니다. 대신 실행 이력은 남지 않는데, 지문이 필요 없다고 했습니다.
>> **나머지가 아닌 이유** — 표준 워크플로는 **상태 전환 수로 과금**되어 고빈도에 불리하고 이력 보존을 끄는 설정도 없습니다. 워크플로를 함수 하나로 합치면 분기·재시도를 코드로 떠안습니다.

> d) 데이터를 복호화해 별도 버킷에 두고 접근을 준다
