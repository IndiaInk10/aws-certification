> [!question] 중요한 데이터가 든 S3 버킷을 **실수로 지우는 것**으로부터 보호해야 합니다. 어떤 조합입니까? (2개 선택)
> a) 버킷에 버전 관리를 켠다
> b) 버킷에 MFA 삭제를 켠다
> c) 버킷에 기본 암호화를 켠다
> d) 객체에 수명 주기 정책을 만든다
>> [!success]- Answer
>> a) 버킷에 버전 관리를 켠다
>> b) 버킷에 MFA 삭제를 켠다
>> **왜 이 답인가** — 버전 관리가 있으면 삭제해도 **이전 버전이 남아** 되돌릴 수 있고, MFA 삭제는 **버전을 영구 삭제하려 할 때 추가 인증을 요구**해 실수를 한 단계 더 막습니다. MFA 삭제는 버전 관리가 켜져 있어야 쓸 수 있어 둘이 짝입니다.
>> **나머지가 아닌 이유** — 암호화는 **훔쳐보는 것**을 막지 지우는 것을 막지 않습니다. 수명 주기 정책은 오히려 **정해진 때에 지우는** 기능이라 방향이 반대입니다.

> [!question] 공개 웹 앱을 ALB 뒤에 두는데, **외부 인증 기관이 발급한** TLS 인증서를 써야 하고 매년 갱신해야 합니다. 어떻게 해야 합니까?
> a) 외부 인증서를 ACM 으로 **가져오기(import)** 해 ALB 에 붙이고, 만료 전에 새 인증서를 다시 가져온다
> b) ACM 에서 인증서를 발급받아 ALB 에 붙이고 관리형 자동 갱신을 쓴다
> c) ACM 사설 인증 기관으로 인증서를 발급한다
> d) 인증서를 EC2 인스턴스에 직접 설치한다
>> [!success]- Answer
>> a) 외부 인증서를 ACM 으로 **가져오기(import)** 해 ALB 에 붙이고, 만료 전에 새 인증서를 다시 가져온다
>> **왜 이 답인가** — `외부 인증 기관이 발급한` 인증서라고 못 박았습니다. ACM 은 남이 발급한 인증서도 가져와 ELB·CloudFront 에 붙일 수 있게 해 줍니다. 다만 **가져온 인증서는 자동 갱신 대상이 아니라** 매년 다시 가져와야 합니다.
>> **나머지가 아닌 이유** — ACM 이 직접 발급하면 자동 갱신이 되지만 그건 **외부 CA 라는 조건을 어깁니다.** 사설 CA 는 내부용이라 공개 웹 앱에 맞지 않고, EC2 직접 설치는 ALB 에서 TLS 를 끝내는 구성이 아닙니다.

> [!question] 기밀 데이터를 S3 에 저장합니다. 저장 중 암호화가 필요하고, **키 사용 내역이 감사 기록으로 남아야** 하며, **키는 매년 교체**되어야 합니다. 운영 효율이 가장 높은 것은 무엇입니까?
> a) SSE-KMS 를 쓰고 KMS 키의 자동 교체를 켠다
> b) SSE-KMS 를 쓰고 키를 사람이 매년 교체한다
> c) SSE-S3 를 쓴다
> d) SSE-C 를 쓴다
>> [!success]- Answer
>> a) SSE-KMS 를 쓰고 KMS 키의 자동 교체를 켠다
>> **왜 이 답인가** — 요구가 셋입니다. 암호화(SSE-KMS), **사용 내역 감사**(KMS 호출이 CloudTrail 에 남음), **매년 교체**(KMS 자동 교체가 연 단위). 세 번째를 자동으로 처리하는 것이 운영 효율의 차이입니다.
>> **나머지가 아닌 이유** — 수동 교체는 사람이 매년 챙겨야 합니다. **SSE-S3 는 AWS 가 키를 관리해 사용 내역을 따로 감사할 수 없고**, SSE-C 는 요청마다 키를 넘겨야 해 부담이 가장 큽니다.

> [!question] S3 객체를 **바꾸지 못하게** 해야 하는데 **언제까지인지는 정해지지 않았고** 회사가 결정할 때까지입니다. 특정 사용자만 그 보호를 해제할 수 있어야 합니다. 무엇을 써야 합니까?
> a) 객체 잠금을 켜고 **법적 보존(legal hold)** 을 건다
> b) 객체 잠금을 켜고 보존 기간을 100년으로 잡는다
> c) Glacier 볼트 잠금 정책을 적용한다
> d) CloudTrail 로 변경을 감시하다 알림이 오면 되돌린다
>> [!success]- Answer
>> a) 객체 잠금을 켜고 **법적 보존(legal hold)** 을 건다
>> **왜 이 답인가** — 법적 보존은 **기간이 없습니다.** 명시적으로 해제할 때까지 유지되고, 해제 권한을 특정 사용자에게만 줄 수 있습니다. `기간이 정해지지 않았다`가 보존 기간이 아니라 법적 보존을 가리킵니다.
>> **나머지가 아닌 이유** — 100년 보존 기간은 **기간을 정해 버리는 것**이고 규정 준수 모드면 줄일 수도 없습니다. 볼트 잠금은 Glacier 볼트용이라 대상이 다릅니다. 사후 감시는 이미 바뀐 뒤라 `바꾸지 못하게`가 아닙니다.

> [!question] EventBridge 규칙이 Lambda 함수를 호출합니다. **최소 권한**으로 이 호출을 허용하려면 무엇을 해야 합니까?
> a) 함수에 리소스 기반 정책을 붙여 호출 동작 하나만 EventBridge 서비스에 허용한다
> b) 함수에 리소스 기반 정책을 붙여 모든 Lambda 동작을 EventBridge 서비스에 허용한다
> c) 함수의 실행 역할에 호출 권한을 추가한다
> d) 함수에 리소스 기반 정책을 붙여 모든 주체에게 허용한다
>> [!success]- Answer
>> a) 함수에 리소스 기반 정책을 붙여 호출 동작 하나만 EventBridge 서비스에 허용한다
>> **왜 이 답인가** — **누가 이 함수를 부를 수 있는가는 리소스 기반 정책**이 정합니다. 주체를 EventBridge 로, 동작을 호출 하나로 좁히면 최소 권한입니다.
>> **나머지가 아닌 이유** — 모든 Lambda 동작을 열면 삭제·수정까지 가능해져 최소 권한이 아닙니다. **실행 역할은 함수가 다른 서비스를 부를 때 쓰는 것**이라 방향이 반대입니다. 모든 주체 허용은 논외입니다.

> [!question] EC2 인스턴스 1,000대에 설치된 서드파티 소프트웨어의 **심각한 취약점을 최대한 빨리 패치**해야 합니다. 무엇을 써야 합니까?
> a) Systems Manager Patch Manager 로 패치를 적용한다
> b) Lambda 함수를 만들어 각 인스턴스에 적용한다
> c) 인스턴스에 접속해 순서대로 적용한다
> d) 인스턴스를 전부 새 AMI 로 교체한다
>> [!success]- Answer
>> a) Systems Manager Patch Manager 로 패치를 적용한다
>> **왜 이 답인가** — Patch Manager 는 **패치 적용을 대규모로 자동화**하도록 만들어진 도구입니다. 1,000대에 한 번에 걸고 적용 결과까지 확인할 수 있습니다.
>> **나머지가 아닌 이유** — Lambda 로 직접 만들면 접속·재시도·결과 수집을 전부 짜야 합니다. 수동 접속은 1,000대에 현실성이 없고, AMI 교체는 패치 하나를 위해 전체를 다시 만드는 과한 조치입니다.

> [!question] 협력사가 올린 파일 중 **개인정보가 들어 있는 것**을 찾아 격리해야 합니다. 개발 노력을 최소화하려면 무엇을 써야 합니까?
> a) 파일을 S3 에 받고 Amazon Macie 로 검사해 발견되면 알리고 격리한다
> b) 파일을 S3 에 받고 Amazon Inspector 로 검사한다
> c) Lambda 에 직접 만든 검사 알고리즘을 넣어 처리한다
> d) GuardDuty 를 켜 둔다

>> a) 파일을 S3 에 받고 Amazon Macie 로 검사해 발견되면 알리고 격리한다
>> **왜 이 답인가** — Macie 는 **S3 안의 민감 데이터를 찾아내는** 관리형 서비스입니다. 개인정보 패턴이 이미 들어 있어 만들 것이 없습니다.
>> **나머지가 아닌 이유** — Inspector 는 **취약점 스캔**, GuardDuty 는 **위협 탐지**로 대상이 다릅니다. 직접 만든 알고리즘은 `개발 노력 최소화`와 정반대이고 정확도까지 떠안습니다.

> [!question] 퍼블릭 서브넷의 EC2 가 S3 의 파일만 처리하고 **다른 네트워크 접근은 전혀 필요 없습니다.** 보안을 가장 크게 높이려면 무엇을 해야 합니까?
> a) 인스턴스를 프라이빗 서브넷으로 옮기고 S3 게이트웨이 엔드포인트를 만들어 라우팅에 연결한다
> b) NAT 게이트웨이를 만들어 그쪽으로 S3 트래픽을 보낸다
> c) 보안 그룹 아웃바운드를 S3 로만 제한한다
> d) 인터넷 게이트웨이를 지우고 Direct Connect 를 깐다
>> [!success]- Answer
>> a) 인스턴스를 프라이빗 서브넷으로 옮기고 S3 게이트웨이 엔드포인트를 만들어 라우팅에 연결한다

>> **나머지가 아닌 이유** — Flexible Retrieval 과 Deep Archive 는 **꺼내는 데 분에서 시간**이 걸려 `즉시`를 못 지킵니다. Standard-IA 는 즉시 나오지만 분기 1회짜리에는 저장 단가가 비쌉니다. **아카이브 3종은 꺼내는 속도로 갈립니다.**

<sub>관련: [[amazon-s3-glacier]] [[amazon-s3]] | 모듈 [[11-cost-storage]]</sub>

> [!question] 매달 약 300MB 의 JSON 데이터를 재해 복구용으로 백업합니다. 꺼낼 일은 거의 없지만 필요하면 가져올 수 있어야 하고, 비용은 최소여야 합니다. 무엇을 써야 합니까?
> a) S3 Glacier
> b) S3 Standard
> c) Amazon RDS for PostgreSQL
> d) Amazon OpenSearch Service
>> [!success]- Answer
>> a) S3 Glacier
>> **왜 이 답인가** — 백업이라 **평소에 읽지 않고** 필요할 때만 꺼냅니다. 그 접근 형태에 가장 싼 것이 아카이브 계층입니다.
>> **나머지가 아닌 이유** — Standard 는 안 읽는 데이터에 값을 그대로 냅니다. RDS 와 OpenSearch 는 **조회하려고 띄워 두는 서비스**라 백업 보관용으로는 인스턴스 비용이 계속 나갑니다. 백업의 목적은 조회가 아니라 보관입니다.

> [!question] 규정상 애플리케이션 로그를 **7년** 보관해야 하고, 보고 도구가 **모든 파일에 접근**할 수 있어야 합니다. 가장 비용 효율적인 저장소는 무엇입니까?
> a) Amazon S3
> b) Amazon EFS
> c) Amazon EBS
> d) EC2 인스턴스 스토어
>> [!success]- Answer
>> a) Amazon S3
>> **왜 이 답인가** — 7년치가 계속 쌓이므로 **용량을 미리 잡지 않아도 늘어나는** 곳이어야 하고, 저장 단가도 가장 낮습니다. 수명 주기로 오래된 것을 더 싼 계층에 내릴 수도 있습니다.
>> **나머지가 아닌 이유** — EFS 는 되지만 저장 단가가 훨씬 높습니다. EBS 는 인스턴스에 묶여 있고 용량을 미리 정해야 합니다. **인스턴스 스토어는 휘발성이라 7년 보관에 쓸 수 없습니다.**

> [!question] API 로 들어오는 요청량이 매우 들쭉날쭉해서 **몇 시간씩 요청이 하나도 없을 때**도 있습니다. 처리는 비동기로 하면 됩니다. 가장 비용 효율적인 처리 방식은 무엇입니까?
> a) AWS Lambda 함수
> b) EKS 에 올린 컨테이너 서비스
> c) ECS on EC2 에 올린 컨테이너 서비스
> d) AWS Glue 작업
>> [!success]- Answer
>> a) AWS Lambda 함수
>> **왜 이 답인가** — 요청이 없는 시간이 길다는 것이 핵심입니다. Lambda 는 **실행한 만큼만** 내므로 그 시간에 비용이 0 입니다.
>> **나머지가 아닌 이유** — EKS 와 ECS on EC2 는 **아무 요청이 없어도 노드가 떠 있어** 요금이 계속 나갑니다. Glue 는 ETL 용 서비스라 API 요청 처리에 맞는 도구가 아닙니다.

> [!question] S3 버킷의 데이터를 외부 연구자들이 내려받아 쓰게 공개하려는데, **내려받는 쪽이 데이터 전송 비용을 부담**하게 하고 싶습니다. 무엇을 켜야 합니까?
> a) 버킷에 요청자 지불(Requester Pays)을 켠다
> b) 버킷 정책으로 다운로드를 제한한다
> c) CloudFront 를 앞에 둔다
> d) 사전 서명된 URL 을 발급한다
>> [!success]- Answer
>> a) 버킷에 요청자 지불(Requester Pays)을 켠다
>> **왜 이 답인가** — 요청자 지불은 **요청과 데이터 전송 요금을 내려받는 쪽에 넘기는** 버킷 설정입니다. 저장 요금은 여전히 버킷 소유자가 냅니다. 공개 데이터셋을 배포할 때 쓰는 자리입니다.
>> **나머지가 아닌 이유** — 버킷 정책과 사전 서명 URL 은 **누가 접근하느냐**를 다루지 요금을 누가 내는지는 바꾸지 않습니다. CloudFront 는 오히려 소유자 쪽 비용을 늘립니다.
