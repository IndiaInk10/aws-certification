## 도메인 2 · 복원력 (2문항)

> [!question] 한 회사가 여러 마이크로서비스로 구성된 애플리케이션을 구축하고 있습니다. 회사는 AWS에 소프트웨어를 배포하기 위해 컨테이너 기술을 사용하기로 결정했습니다. 회사에는 **유지 관리와 조정에 드는 지속적인 노력을 최소화**하는 솔루션이 필요합니다. **회사는 추가 인프라를 관리할 수 없습니다.** 솔루션스 아키텍트는 이러한 요구 사항을 충족하기 위해 어떤 작업 조합을 수행해야 합니까? (2개 선택)
> a) Amazon Elastic Container Service(Amazon ECS) 클러스터를 배포한다
> b) Fargate 시작 유형으로 Amazon ECS 서비스를 배포한다. 원하는 태스크 수를 2 이상으로 지정한다
> c) Amazon EC2 시작 유형으로 Amazon ECS 서비스를 배포한다. 원하는 태스크 수를 2 이상으로 지정한다
> d) 여러 가용 영역에 걸친 Amazon EC2 인스턴스에 Kubernetes 컨트롤 플레인을 배포한다
>> [!success]- Answer
>> a) Amazon Elastic Container Service(Amazon ECS) 클러스터를 배포한다
>> b) Fargate 시작 유형으로 Amazon ECS 서비스를 배포한다. 원하는 태스크 수를 2 이상으로 지정한다
>> **왜 이 답인가** — "**추가 인프라를 관리할 수 없다**"가 시작 유형을 정합니다. Fargate는 컨테이너 인스턴스를 두지 않습니다. 태스크를 2개 이상 두는 것은 가용성 요구를 함께 만족시킵니다.
>> **나머지가 아닌 이유** — EC2 시작 유형은 **컨테이너 인스턴스를 회사가 관리**해야 합니다. Kubernetes 컨트롤 플레인을 직접 배포하는 것은 관리 부담이 가장 큰 선택입니다.

<sub>관련: [[amazon-ecs]] [[aws-fargate]] | 모듈 [[04-scalable-decoupled]]</sub>

> [!question] 한 회사에 Amazon Route 53으로 트래픽이 전달되는 10개의 Amazon EC2 인스턴스에서 호스팅되는 웹 애플리케이션이 있습니다. 회사는 애플리케이션에 접속하려고 할 때 간헐적으로 시간 초과 오류를 겪습니다. 네트워킹 팀은 **일부 DNS 쿼리가 비정상 인스턴스의 IP 주소를 반환하여** 시간 초과 오류가 발생한다는 것을 확인했습니다. 솔루션스 아키텍트는 이러한 시간 초과 오류를 해결하기 위해 무엇을 구현해야 합니까?
> a) EC2 인스턴스 앞에 상태 확인이 구성된 Application Load Balancer(ALB)를 생성한다. Route 53에서 ALB로 라우팅한다
> b) 각 EC2 인스턴스에 대해 Route 53 단순 라우팅 정책 레코드를 생성한다. 각 레코드에 상태 확인을 연결한다
> c) 각 EC2 인스턴스에 대해 Route 53 장애 조치 라우팅 정책 레코드를 생성한다. 각 레코드에 상태 확인을 연결한다
> d) EC2 인스턴스를 오리진으로 하는 Amazon CloudFront 배포를 생성한다. EC2 인스턴스에 상태 확인을 연결한다
>> [!success]- Answer
>> a) EC2 인스턴스 앞에 상태 확인이 구성된 Application Load Balancer(ALB)를 생성한다. Route 53에서 ALB로 라우팅한다
>> **왜 이 답인가** — 로드 밸런서는 **상태 확인에 실패한 대상으로 요청을 보내지 않습니다.** DNS가 인스턴스 IP를 직접 나눠 주는 구조 자체를 없애는 것이 근본 해결입니다.
>> **나머지가 아닌 이유** — **단순 라우팅 정책은 상태 확인을 지원하지 않습니다.** 장애 조치 정책은 기본/보조 두 곳을 위한 것이라 10개 인스턴스를 고르게 나누는 데 맞지 않습니다. CloudFront는 오리진 상태로 트래픽을 나누는 장치가 아닙니다.
