> [!question] 한 이미지 호스팅 기업이 **S3 객체가 실수로 퍼블릭 노출되는 것**을 막으려 합니다. **계정 전체의 모든 S3 객체가 비공개로 유지**되어야 합니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) **계정 수준에서 S3 퍼블릭 액세스 차단**을 켜고, IAM 사용자가 이 설정을 바꾸지 못하도록 Organizations SCP를 적용한다
> b) GuardDuty로 버킷 정책을 감시하고 Lambda로 자동 복구한다
> c) Trusted Advisor로 퍼블릭 버킷을 찾아 이메일 알림을 받고 수동으로 고친다
> d) Resource Access Manager로 퍼블릭 버킷을 찾아 Lambda로 자동 복구한다
>> [!success]- Answer
>> a) **계정 수준에서 S3 퍼블릭 액세스 차단**을 켜고, IAM 사용자가 이 설정을 바꾸지 못하도록 Organizations SCP를 적용한다
>> **왜 이 답인가** — 퍼블릭 액세스 차단은 **버킷 정책·ACL이 무엇이든 공개를 막는 스위치**입니다. 계정 수준에 켜고 SCP로 잠그면 사후 대응이 아니라 **애초에 공개될 수 없게** 됩니다.
>> **나머지가 아닌 이유** — 감지 후 되돌리는 방식들은 그 사이에 이미 노출됩니다. Resource Access Manager는 리소스 공유 서비스라 이 용도가 아닙니다.

> [!question] 한 기업의 마이크로서비스 기반 서버리스 웹 애플리케이션이 **여러 DynamoDB 테이블에서 데이터를 조회**해야 하며, **기본 성능에 영향을 주지 않아야** 합니다. 운영 효율이 가장 높은 솔루션은 무엇입니까?
> a) **AWS AppSync 파이프라인 리졸버**를 사용한다
> b) CloudFront와 Lambda@Edge 함수를 사용한다
> c) 엣지 최적화 API Gateway와 Lambda 함수를 사용한다
> d) DynamoDB 커넥터를 쓰는 Athena 연합 쿼리를 사용한다
>> [!success]- Answer
>> a) **AWS AppSync 파이프라인 리졸버**를 사용한다
>> **왜 이 답인가** — AppSync는 **여러 데이터 원본을 하나의 GraphQL 요청으로 묶어** 가져오며, 파이프라인 리졸버가 그 순서를 정의합니다. 별도 컴퓨팅 계층 없이 조회를 합칠 수 있어 운영 효율이 가장 높습니다.
>> **나머지가 아닌 이유** — Lambda로 여러 테이블을 순회하면 코드와 지연이 늘어납니다. Athena 연합 쿼리는 분석용이라 애플리케이션 실시간 조회에 맞지 않습니다.

> [!question] 한 기업의 모바일 앱이 영상 클립을 **원본(raw) 형식 그대로** S3에 올리고 사용자가 S3에서 바로 내려받습니다. 파일이 커서 **버퍼링과 재생 문제**가 생깁니다. 성능과 확장성을 최대로 하면서 운영 오버헤드를 최소화하려면 어떤 조합이 필요합니까? (2개 선택)
> a) 콘텐츠 전달과 캐싱을 위해 Amazon CloudFront를 배포한다
> b) Amazon Elastic Transcoder로 영상 파일을 적절한 형식으로 변환한다
> c) AWS DataSync로 영상 파일을 다른 리전의 S3 버킷에 복제한다
> d) 변환을 위해 EC2 Auto Scaling 그룹을 배포한다
>> [!success]- Answer
>> a) 콘텐츠 전달과 캐싱을 위해 Amazon CloudFront를 배포한다
>> b) Amazon Elastic Transcoder로 영상 파일을 적절한 형식으로 변환한다
>> **왜 이 답인가** — 원인은 두 가지입니다 — **파일이 크다**(변환으로 해결)와 **멀리서 받는다**(엣지 캐싱으로 해결). 둘 다 관리형 서비스로 처리하면 운영 오버헤드가 적습니다.
>> **나머지가 아닌 이유** — EC2로 변환기를 직접 운영하면 관리 부담이 생깁니다. 리전마다 복제하는 것은 저장 비용만 늘고 근본 원인(파일 크기)을 그대로 둡니다.

> [!question] VPC 안 컨테이너 애플리케이션이 **하루 1TB의 데이터를 S3에 저장·조회**합니다. **비용을 최소화**하고 **트래픽이 인터넷을 타지 않게** 하려면 어떤 솔루션이 적합합니까?
> a) Amazon S3용 **게이트웨이 VPC 엔드포인트**를 만들어 VPC의 모든 라우팅 테이블에 연결한다
> b) S3용 인터페이스 엔드포인트를 만들어 모든 라우팅 테이블에 연결한다
> c) 버킷에 S3 Intelligent-Tiering을 켠다
> d) 버킷에 S3 Transfer Acceleration을 켠다
>> [!success]- Answer
>> a) Amazon S3용 **게이트웨이 VPC 엔드포인트**를 만들어 VPC의 모든 라우팅 테이블에 연결한다
>> **왜 이 답인가** — 게이트웨이 엔드포인트는 **요금이 전혀 없고** 트래픽을 AWS 네트워크 안에 가둡니다. 하루 1TB를 NAT로 보내면 처리 요금이 크게 붙습니다.
>> **나머지가 아닌 이유** — 인터페이스 엔드포인트는 시간·처리 요금이 붙고 라우팅 테이블이 아니라 서브넷에 연결됩니다. 스토리지 계층과 전송 가속은 이 요구와 무관합니다.

> c) 프로덕션 계정 버킷의 퍼블릭 액세스 차단을 끈다

> c) WAF 웹 ACL을 만들어 ALB에 연결하고 정적 파일 캐시 규칙을 추가한다

> [!question] 한 기업이 AWS Organizations를 쓰며 ap-southeast-2 외 리전에서는 리소스를 만들지 못하게 SCP를 걸어 두었습니다. 감사 결과 직원들이 **암호화하지 않은 EBS 볼륨**을 만든 것이 드러났습니다. 앞으로 이 리전에서 시작되는 모든 EC2가 **암호화된 EBS 볼륨을 쓰게** 하되 **직원 작업에 미치는 영향은 최소**여야 합니다. 어떤 조합이 필요합니까? (2개 선택)
> a) EC2 콘솔에서 **EBS 암호화 계정 속성**을 선택하고 기본 암호화 키를 지정한다
> b) SCP를 만들어 루트 OU에 붙이고 `ec2:Encrypted`가 false이면 `ec2:CreateVolume`을 거부한다
> c) IAM 권한 경계를 만들어 루트 OU에 붙이고 암호화되지 않은 볼륨 생성을 거부한다
> d) 계정마다 IAM 정책을 수정해 암호화되지 않은 볼륨 생성을 거부한다
>> [!success]- Answer
>> a) EC2 콘솔에서 **EBS 암호화 계정 속성**을 선택하고 기본 암호화 키를 지정한다
>> b) SCP를 만들어 루트 OU에 붙이고 `ec2:Encrypted`가 false이면 `ec2:CreateVolume`을 거부한다
>> **왜 이 답인가** — 기본 암호화를 켜면 **직원이 아무것도 하지 않아도 새 볼륨이 암호화**되어 영향이 최소입니다. SCP는 루트 사용자까지 포함해 예외를 원천 차단하는 안전장치입니다.
>> **나머지가 아닌 이유** — **권한 경계는 OU에 붙일 수 없고** IAM 주체에 붙입니다. 계정마다 IAM 정책을 고치는 방식은 누락되기 쉽고 루트 사용자를 막지 못합니다.

> [!question] 한 기업이 **FTP로 하루 종일 들어오는 수천 개의 작은 파일**을 야간 배치로 처리하는데 시간이 오래 걸립니다. **파일이 도착하는 즉시 처리**하되 FTP 클라이언트는 거의 바꾸지 않아야 하고, 처리 성공 후 파일을 삭제해야 하며 **파일당 처리에 3~8분**이 걸립니다. 운영 효율이 가장 높은 솔루션은 무엇입니까?
> a) **AWS Transfer Family**로 FTP 서버를 만들어 파일을 **S3 Standard**에 저장하고, **S3 이벤트 알림으로 Lambda 함수**를 호출해 처리·삭제한다
> b) Transfer Family로 FTP 서버를 만들어 EBS에 저장하고 S3 이벤트로 AWS Batch 작업을 호출한다
> c) EC2에 FTP 서버를 올려 S3 Glacier에 저장하고 EventBridge로 야간에 Batch 작업을 돌린다
> d) EC2에 FTP 서버를 올려 EBS에 저장하고 야간에 Batch 작업을 돌린다
>> [!success]- Answer
