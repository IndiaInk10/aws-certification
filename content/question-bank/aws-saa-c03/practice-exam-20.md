> c) 수명 주기 후크로 인스턴스를 두 번째 대상 그룹에 등록하는 스크립트를 실행한다
> d) NLB를 ALB의 대상으로 등록한다

> b) 리전마다 별도 KMS 키를 만들고 데이터를 재암호화한다
> c) KMS 키를 복사한다
> d) 데이터를 평문으로 전송한 뒤 대상 리전에서 암호화한다
>> [!success]- Answer
>> a) **KMS 다중 리전 키**를 만들어 두 리전에서 같은 키 재료로 복호화되게 한다
>> **왜 이 답인가** — 다중 리전 키는 **동일한 키 재료를 가진 복제본**을 다른 리전에 두어, 한 리전에서 암호화한 데이터를 다른 리전에서 바로 복호화할 수 있게 합니다.
>> **나머지가 아닌 이유** — 리전별 단독 키는 재암호화가 필요합니다. 일반 KMS 키는 복사할 수 없고, 평문 전송은 보안 요건에 어긋납니다.

> [!question] 마케팅 캠페인 때 **수십만 통의 이메일을 발송**하는데, 지금은 웹 요청 처리 중에 발송을 시도해 **요청이 지연되고 발송 한도에 걸리면 실패**합니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) 발송 요청을 **SQS 큐에 넣고 소비자가 Amazon SES로 천천히 발송**하게 하며 웹 요청은 즉시 응답한다
> b) 웹 서버 인스턴스를 늘려 동시에 더 많이 발송한다
> c) 발송 코드에 재시도 로직을 넣는다
> d) SNS 주제로 이메일을 발송한다
>> [!success]- Answer
>> a) 발송 요청을 **SQS 큐에 넣고 소비자가 Amazon SES로 천천히 발송**하게 하며 웹 요청은 즉시 응답한다
>> **왜 이 답인가** — 큐가 **발송 속도와 요청 처리 속도를 분리**합니다. 사용자는 기다리지 않고, 소비자는 SES 발송 한도에 맞춰 꺼내 보내므로 실패도 사라집니다.
>> **나머지가 아닌 이유** — 서버를 늘리면 한도에 더 빨리 걸립니다. 재시도만 넣으면 요청은 여전히 느립니다. SNS 이메일은 **서식 없는 알림용**이라 마케팅 발송에 맞지 않습니다.

> [!question] 개발자가 **수 기가바이트 파일을 KMS API로 직접 암호화하려다 요청이 거부**되었습니다. 올바른 방법은 무엇입니까?
> a) KMS로 **데이터 키를 생성해 그 키로 파일을 암호화**하고, 암호화된 데이터 키를 파일과 함께 저장한다(봉투 암호화)
> b) 파일을 4KB 단위로 나눠 KMS로 각각 암호화한다
> c) KMS 키 사양을 비대칭으로 바꾼다
> d) KMS 요청 할당량 증가를 신청한다
>> [!success]- Answer
>> a) KMS로 **데이터 키를 생성해 그 키로 파일을 암호화**하고, 암호화된 데이터 키를 파일과 함께 저장한다(봉투 암호화)
>> **왜 이 답인가** — KMS는 **작은 크기의 데이터만 직접 암호화**합니다. 대용량은 데이터 키로 로컬에서 암호화하고 그 데이터 키만 KMS로 보호하는 봉투 암호화가 정답입니다.
>> **나머지가 아닌 이유** — 조각내기는 호출 폭증과 관리 지옥을 만듭니다. 키 사양 변경과 할당량 증가는 크기 제한을 없애지 못합니다.

> d) 볼륨 생성 권한을 제한한다
