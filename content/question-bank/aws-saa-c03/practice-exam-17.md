> [!question] Auto Scaling 그룹이 축소되거나 배포로 인스턴스를 교체할 때마다 **처리 중이던 요청이 끊겨 5xx 오류**가 발생합니다. 무엇을 해야 합니까?
> a) 대상 그룹의 **등록 취소 지연(연결 드레이닝)** 값을 요청 처리 시간보다 길게 설정한다
> b) Auto Scaling 그룹의 쿨다운을 늘린다
> c) ALB의 유휴 제한 시간을 늘린다
> d) 대상 그룹 상태 확인 간격을 줄인다
>> [!success]- Answer
>> a) 대상 그룹의 **등록 취소 지연(연결 드레이닝)** 값을 요청 처리 시간보다 길게 설정한다
>> **왜 이 답인가** — 등록 취소 지연은 **대상을 빼기 전에 진행 중인 요청이 끝날 때까지 기다립니다.** 처리 시간보다 길게 잡으면 배포·축소 중에도 요청이 잘리지 않습니다.

> a) Kinesis 데이터 보존 기간을 늘리도록 기본 설정을 변경한다
> b) 처리량에 맞게 Kinesis 샤드 수를 늘린다
> c) 애플리케이션이 Kinesis Producer Library(KPL)를 쓰도록 변경한다
> d) S3 버킷에서 버전 관리를 켠다

> d) 스냅샷을 표준 계층에 그대로 둔다
>> [!success]- Answer
>> a) 스냅샷을 **EBS 스냅샷 아카이브 계층으로 이동**한다

> a) API에 **리소스 정책**을 붙여 허용할 VPC 엔드포인트와 IP 범위만 명시한다

> c) Lambda 권한 부여자에서 요청 IP를 검사한다
> d) 사용량 계획과 API 키로 제한한다

> a) 작업을 시작할 때 해당 인스턴스에 **축소 보호(scale-in protection)**를 켜고 끝나면 해제한다
> b) Auto Scaling 그룹의 최소 용량을 늘린다
> c) 종료 정책을 `OldestInstance`로 바꾼다
> d) 인스턴스에 종료 방지를 켠다
>> [!success]- Answer
>> a) 작업을 시작할 때 해당 인스턴스에 **축소 보호(scale-in protection)**를 켜고 끝나면 해제한다
>> **왜 이 답인가** — 축소 보호는 **그 인스턴스를 축소 후보에서 제외**합니다. 작업 중일 때만 켜고 끝나면 풀면 되므로 확장·축소는 그대로 두면서 유실만 막습니다.
>> **나머지가 아닌 이유** — 최소 용량이나 종료 정책은 **어느 인스턴스가 바쁜지 알지 못합니다.** EC2 종료 방지는 API 종료를 막을 뿐 Auto Scaling의 축소에는 적용되지 않습니다.

> a) **Amazon SageMaker**로 모델을 만들고 학습하며 **Amazon QuickSight**로 시각화한다
> b) AWS Glue의 ML 변환으로 모델을 만들고 OpenSearch로 시각화한다
> c) 마켓플레이스의 ML AMI로 모델을 만들고 OpenSearch로 시각화한다
> d) QuickSight의 계산 필드로 모델을 만들고 학습한 뒤 QuickSight로 시각화한다
>> [!success]- Answer
>> a) **Amazon SageMaker**로 모델을 만들고 학습하며 **Amazon QuickSight**로 시각화한다
>> **왜 이 답인가** — 모델 구축·학습의 관리형 서비스는 SageMaker이고, BI 대시보드는 QuickSight입니다. 두 서비스가 통합되어 있어 오버헤드가 적습니다.
>> **나머지가 아닌 이유** — Glue의 ML 변환은 중복 레코드 식별 등 한정된 용도입니다. AMI를 직접 운영하면 관리 부담이 큽니다. QuickSight 계산 필드는 모델 학습 기능이 아닙니다.

>> [!success]- Answer
>> a) 보안 암호에 **리소스 정책으로 애플리케이션 계정 역할을 허용**하고, 암호화에 쓰인 **KMS 고객 관리형 키도 그 역할에 사용 허용**한다

> [!question] Step Functions 워크플로의 여러 단계가 **DynamoDB에 항목을 넣고 SNS로 알리는 단순 호출**뿐인데, 단계마다 그 일만 하는 Lambda 함수를 만들어 유지하고 있습니다. 운영 오버헤드를 줄이려면 무엇을 해야 합니까?
> a) 상태 머신에서 **AWS SDK 서비스 통합으로 DynamoDB·SNS를 직접 호출**하게 하고 중간 Lambda를 없앤다
> b) 여러 Lambda 함수를 하나로 합친다
> c) 각 Lambda를 컨테이너 이미지로 배포한다
> d) 상태 머신을 익스프레스 워크플로로 바꾼다
>> [!success]- Answer
>> a) 상태 머신에서 **AWS SDK 서비스 통합으로 DynamoDB·SNS를 직접 호출**하게 하고 중간 Lambda를 없앤다

> [!question] CloudFront 서명 URL로 유료 콘텐츠를 제공하는데, **서명에 쓰는 키를 여러 배포에서 공유하고 주기적으로 교체**해야 합니다. 어떤 방식으로 관리해야 합니까?
> a) 퍼블릭 키를 CloudFront에 등록해 **키 그룹**으로 묶고, 배포의 동작에 그 키 그룹을 지정한다
> b) 계정 루트 사용자의 CloudFront 키 페어를 만들어 쓴다
> c) 배포마다 별도의 퍼블릭 키를 등록하고 코드에 하드코딩한다
> d) ACM 인증서로 URL을 서명한다
>> [!success]- Answer
>> a) 퍼블릭 키를 CloudFront에 등록해 **키 그룹**으로 묶고, 배포의 동작에 그 키 그룹을 지정한다
>> **왜 이 답인가** — 키 그룹은 **퍼블릭 키를 묶어 배포에 연결**하는 현행 방식이며, 새 키를 그룹에 추가하고 옛 키를 빼는 식으로 **무중단 교체**가 됩니다.
>> **나머지가 아닌 이유** — 루트 계정 키 페어 방식은 권장되지 않는 옛 방식입니다. 키를 하드코딩하면 교체가 어렵고, ACM 인증서는 TLS용이지 URL 서명용이 아닙니다.

> [!question] 애플리케이션이 사용자에게 **S3 사전 서명 URL**을 발급해 파일을 내려받게 합니다. 보안 검토에서 **URL이 공유되면 누구나 쓸 수 있다**는 지적이 나왔습니다. 위험을 줄이려면 무엇을 해야 합니까?
> a) **URL 만료 시간을 짧게 두고, 발급에 쓰는 역할의 권한을 필요한 객체로 좁힌다**
> b) URL을 HTTPS 대신 HTTP로 발급한다
> c) 버킷을 퍼블릭으로 열고 URL 발급을 없앤다
> d) 발급에 계정 루트 자격 증명을 쓴다
>> [!success]- Answer
>> a) **URL 만료 시간을 짧게 두고, 발급에 쓰는 역할의 권한을 필요한 객체로 좁힌다**
>> **왜 이 답인가** — 사전 서명 URL은 **발급자의 권한을 만료 시각까지 위임**합니다. 그래서 만료를 짧게 하고 발급 주체의 권한 자체를 좁히는 것이 유일한 통제 수단입니다.
>> **나머지가 아닌 이유** — HTTP는 전송을 노출시켜 더 위험합니다. 버킷 공개는 통제를 완전히 잃고, 루트 자격 증명 사용은 최악의 선택입니다.
