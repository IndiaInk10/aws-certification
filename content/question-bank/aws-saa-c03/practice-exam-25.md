> [!question] `example.com`과 `country1.example.com` 같은 **여러 하위 도메인**을 ALB 뒤에서 운영하며 **전송 중 데이터를 암호화**하려고 합니다. 어떤 조합이 필요합니까? (2개 선택)
> a) ACM 콘솔에서 **정점 도메인 `example.com`과 와일드카드 `*.example.com`의 퍼블릭 인증서**를 요청한다
> b) **DNS 공급자에 필요한 DNS 레코드를 추가해** 도메인 소유권을 검증한다
> c) ACM에서 정점 도메인과 와일드카드의 **프라이빗** 인증서를 요청한다
> d) 이메일 주소로 소유권을 검증한 뒤 DNS 검증으로 전환한다
>> [!success]- Answer
>> a) ACM 콘솔에서 **정점 도메인 `example.com`과 와일드카드 `*.example.com`의 퍼블릭 인증서**를 요청한다
>> b) **DNS 공급자에 필요한 DNS 레코드를 추가해** 도메인 소유권을 검증한다
>> **왜 이 답인가** — 인터넷 사용자가 접속하므로 **퍼블릭 인증서**여야 하고, 하위 도메인을 모두 덮으려면 **와일드카드 + 정점 도메인**을 함께 넣습니다. 검증은 자동 갱신에 유리한 **DNS 검증**을 씁니다.
>> **나머지가 아닌 이유** — 프라이빗 인증서는 외부 브라우저가 신뢰하지 않습니다. 이메일 검증은 갱신 때마다 사람이 확인해야 합니다.

> [!question] Aurora 클러스터에서 장애 조치가 일어난 뒤 애플리케이션이 **여전히 옛 라이터 인스턴스 엔드포인트로 접속**해 쓰기에 실패합니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) 애플리케이션이 인스턴스 엔드포인트 대신 **클러스터 엔드포인트(쓰기)와 리더 엔드포인트(읽기)**를 쓰게 한다
> b) 장애 조치 후 엔드포인트를 수동으로 바꾼다
> c) 복제본을 모두 삭제한다
> d) 애플리케이션의 연결 제한 시간을 늘린다
>> [!success]- Answer
>> a) 애플리케이션이 인스턴스 엔드포인트 대신 **클러스터 엔드포인트(쓰기)와 리더 엔드포인트(읽기)**를 쓰게 한다
>> **왜 이 답인가** — 클러스터 엔드포인트는 **항상 현재 라이터를 가리키도록 Aurora가 갱신**합니다. 인스턴스 엔드포인트를 직접 쓰면 승격 후에도 옛 인스턴스를 향하게 됩니다.
>> **나머지가 아닌 이유** — 수동 변경은 자동 장애 조치의 의미를 없앱니다. 복제본 삭제는 가용성을 버리는 선택이고, 제한 시간은 대상 선택 문제와 무관합니다.

> a) **AWS Local Zones**에 애플리케이션을 배포하고 eu-central-1의 VPC를 그 Local Zone까지 확장한다
> b) AWS Wavelength Zones에 배포하고 VPC를 확장한다
> c) eu-central-1에 배포하고 VPC를 CloudFront 엣지 로케이션까지 확장한다
> d) eu-central-1에 배포하고 VPC를 CloudFront 리전 엣지 캐시까지 확장한다
>> [!success]- Answer
>> a) **AWS Local Zones**에 애플리케이션을 배포하고 eu-central-1의 VPC를 그 Local Zone까지 확장한다

> [!question] 온프레미스 **MySQL 호환 데이터베이스**가 최소 2GiB 메모리를 꾸준히 쓰고 있으며, 사용량이 들쭉날쭉한 애플리케이션이 이를 씁니다. 관리형 서비스로 옮기면서 **예기치 않은 증가를 오토 스케일링으로** 감당하려고 합니다. 관리 오버헤드가 가장 적은 솔루션은 무엇입니까?
> a) 최소 용량 1 ACU의 **Amazon Aurora Serverless v2** 데이터베이스를 프로비저닝한다
> b) 최소 용량 1 ACU의 Amazon Aurora 데이터베이스를 프로비저닝한다
> c) 2GiB 메모리의 RDS for MySQL을 프로비저닝한다
> d) 기본 설정의 DynamoDB 데이터베이스를 프로비저닝한다
>> [!success]- Answer
>> a) 최소 용량 1 ACU의 **Amazon Aurora Serverless v2** 데이터베이스를 프로비저닝한다

> a) **내구성과 가용성은 다른 문제**이므로, 손실이 허용되지 않으면 여러 AZ에 저장하는 클래스를 쓰고 One Zone은 재생성 가능한 데이터에만 쓴다
> b) 접근 중단을 감수할 수 있으므로 One Zone-IA를 쓴다
> c) One Zone-IA에 두고 버전 관리를 켜면 손실 위험이 사라진다
> d) One Zone-IA에 두고 수명 주기로 Glacier에 전환하면 안전하다
>> [!success]- Answer
>> a) **내구성과 가용성은 다른 문제**이므로, 손실이 허용되지 않으면 여러 AZ에 저장하는 클래스를 쓰고 One Zone은 재생성 가능한 데이터에만 쓴다

> b) 콘솔에서 같은 작업을 환경마다 반복한다
