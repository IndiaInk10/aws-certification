> [!question] 한 기업의 여러 웹 서버가 공통 RDS MySQL 다중 AZ DB 인스턴스에 자주 접근해야 합니다. 웹 서버가 데이터베이스에 **안전하게 연결**하면서 사용자 자격 증명을 자주 교체해야 한다는 보안 요건도 만족해야 합니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) 자격 증명을 AWS Secrets Manager에 저장하고 웹 서버가 접근할 수 있도록 필요한 IAM 권한을 부여한다
> b) 자격 증명을 Systems Manager OpsCenter에 저장하고 웹 서버에 IAM 권한을 부여한다
> c) 자격 증명을 안전한 S3 버킷에 저장하고 웹 서버가 가져와 쓰도록 IAM 권한을 부여한다
> d) 자격 증명을 KMS로 암호화한 파일로 웹 서버 파일 시스템에 두고 웹 서버가 복호화해 쓰게 한다
>> [!success]- Answer
>> a) 자격 증명을 AWS Secrets Manager에 저장하고 웹 서버가 접근할 수 있도록 필요한 IAM 권한을 부여한다
>> **왜 이 답인가** — `자주 교체`가 Secrets Manager를 가리킵니다. RDS와 통합된 **자동 교체**가 기능으로 있고 접근은 IAM으로 통제됩니다.
>> **나머지가 아닌 이유** — OpsCenter는 운영 이슈를 관리하는 도구지 비밀 저장소가 아닙니다. S3나 서버 파일 시스템에 두는 방식은 교체를 사람이 해야 하고 서버가 늘수록 관리가 커집니다.

> [!question] 한 기업이 사용자가 사진을 올리고 사진 프레임을 추가하는 이미지 분석 애플리케이션을 만들었습니다. 지금은 **EC2 인스턴스 한 대**와 메타데이터 저장용 DynamoDB를 씁니다. 사용자가 늘고 시간대·요일에 따라 동시 사용자 수가 크게 달라질 것으로 예상되어 확장 가능한 구성이 필요합니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) 사진 처리는 AWS Lambda가 맡고, 사진은 Amazon S3에 저장하며 메타데이터는 DynamoDB에 그대로 둔다
> b) 사진 처리를 Lambda가 맡고 사진과 메타데이터를 모두 DynamoDB에 저장한다
> c) Kinesis Data Firehose로 사진을 처리하고 사진과 메타데이터를 저장한다
> d) EC2 인스턴스를 세 대로 늘리고 프로비저닝된 IOPS SSD(io2) EBS 볼륨에 사진과 메타데이터를 저장한다
>> [!success]- Answer
>> a) 사진 처리는 AWS Lambda가 맡고, 사진은 Amazon S3에 저장하며 메타데이터는 DynamoDB에 그대로 둔다
>> **왜 이 답인가** — 각 데이터가 제자리로 갑니다 — **이미지 파일은 S3**, **메타데이터는 DynamoDB**, **간헐적 처리는 Lambda**. 셋 다 사용량에 따라 알아서 늘고 줄어듭니다.
>> **나머지가 아닌 이유** — DynamoDB에 사진을 담는 것은 항목 크기 한도(400KB) 때문에 맞지 않습니다. Firehose는 스트림 적재 서비스입니다. EC2를 세 대로 고정하는 것은 변동 폭이 큰 수요를 감당하지 못합니다.

> [!question] 한 기업이 공개된 영화 데이터를 단일 AZ Amazon RDS DB 인스턴스의 SQL 데이터베이스에 저장합니다. 매일 임의 간격으로 스크립트가 쿼리를 실행해 새로 추가된 영화 수를 기록하고 업무 시간에 최종 합계를 보고합니다. 개발 팀은 **스크립트가 돌 때 개발 작업용 데이터베이스 성능이 나빠진다**고 합니다. 운영 오버헤드가 가장 적은 해결책은 무엇입니까?
> a) 데이터베이스의 읽기 전용 복제본을 만들고 스크립트가 복제본에만 쿼리하도록 구성한다
> b) DB 인스턴스를 다중 AZ 배포로 변경한다
> c) 개발 팀이 매일 종료 시 항목을 수동으로 내보내게 한다
> d) 스크립트가 자주 실행하는 쿼리를 Amazon ElastiCache로 캐싱한다
>> [!success]- Answer
>> a) 데이터베이스의 읽기 전용 복제본을 만들고 스크립트가 복제본에만 쿼리하도록 구성한다
>> **왜 이 답인가** — 무거운 **읽기**가 원본을 방해하는 상황이므로 읽기를 복제본으로 떼어 내면 끝납니다. 만들고 연결 문자열만 바꾸면 되므로 오버헤드가 가장 적습니다.
>> **나머지가 아닌 이유** — 다중 AZ의 대기 인스턴스는 **읽기를 받지 않습니다**(가용성 목적). 수동 내보내기는 자동화를 사람 일로 되돌립니다. 임의 간격의 집계 쿼리는 캐시 적중률이 낮습니다.

> [!question] 한 애플리케이션이 EC2, AWS Fargate, AWS Lambda를 함께 씁니다. **EC2는 데이터 수집 계층**을 돌리는데 사용이 산발적이고 예측 불가이며 **언제 중단돼도 괜찮습니다.** 프런트엔드는 Fargate, API 계층은 Lambda에서 돌고 **두 계층의 사용량은 향후 1년간 예측 가능합니다.** 가장 비용 효율적인 구매 옵션 조합은 무엇입니까? (2개 선택)
> a) 데이터 수집 계층에는 스팟 인스턴스를 사용한다
> b) 프런트엔드와 API 계층에는 1년 **Compute Savings Plans**를 구매한다
> c) 프런트엔드와 API 계층에는 1년 EC2 Instance Savings Plans를 구매한다
> d) 데이터 수집 계층에는 1년 전체 선결제 예약 인스턴스를 구매한다
>> [!success]- Answer
>> a) 데이터 수집 계층에는 스팟 인스턴스를 사용한다
>> b) 프런트엔드와 API 계층에는 1년 **Compute Savings Plans**를 구매한다
>> **왜 이 답인가** — 중단을 견디는 산발적 워크로드는 스팟이 가장 쌉니다. 그리고 **Fargate와 Lambda까지 적용되는 약정은 Compute Savings Plans뿐**입니다.
>> **나머지가 아닌 이유** — EC2 Instance Savings Plans와 예약 인스턴스는 **EC2에만** 적용되어 Fargate·Lambda를 덮지 못합니다. 예측 불가한 워크로드에 1년 약정을 거는 것도 어긋납니다.

> [!question] 한 기업이 기밀 감사 문서를 S3에 저장하고 버킷 정책으로 감사 팀 IAM 사용자만 접근하도록 최소 권한을 적용했습니다. 관리자들은 **문서가 실수로 삭제되는 것**을 우려해 더 안전한 방법을 원합니다. 무엇을 해야 합니까?
> a) S3 버킷에서 버전 관리와 MFA 삭제 기능을 켠다
> b) 감사 팀 각 IAM 사용자 자격 증명에 다중 인증(MFA)을 켠다
> c) 감사 기간 동안 `s3:DeleteObject`를 거부하는 S3 수명 주기 정책을 감사 팀 계정에 추가한다
> d) KMS로 버킷을 암호화하고 감사 팀이 KMS 키에 접근하지 못하게 한다
>> [!success]- Answer
>> a) S3 버킷에서 버전 관리와 MFA 삭제 기능을 켠다
>> **왜 이 답인가** — 버전 관리가 삭제를 되돌릴 수 있게 하고, MFA 삭제가 **버전 영구 삭제에 추가 인증을 요구**합니다. 실수 삭제 방지의 표준 조합입니다.
>> **나머지가 아닌 이유** — 로그인 MFA는 접속을 보호할 뿐 삭제 동작을 막지 않습니다. 수명 주기 정책은 권한을 거부하는 도구가 아닙니다. 키 접근을 막으면 삭제가 아니라 **읽기**가 막혀 업무가 멈춥니다.

> [!question] 한 기업이 AWS에서 2계층 전자상거래 사이트를 운영합니다. 웹 계층은 EC2로 트래픽을 보내는 로드 밸런서로, 데이터베이스 계층은 RDS DB 인스턴스로 되어 있습니다. **EC2와 RDS는 퍼블릭 인터넷에 노출되면 안 되지만**, EC2는 서드파티 웹 서비스로 결제를 처리하기 위해 인터넷 접근이 필요합니다. 전체는 고가용성이어야 합니다. 어떤 조합이 요구 사항을 충족합니까? (2개 선택)
> a) Auto Scaling 그룹으로 EC2를 프라이빗 서브넷에 띄우고 RDS 다중 AZ DB 인스턴스를 프라이빗 서브넷에 배포한다
> b) 두 가용 영역에 걸쳐 퍼블릭 서브넷 두 개, 프라이빗 서브넷 두 개, NAT 게이트웨이 두 개로 VPC를 구성하고 **퍼블릭 서브넷에 ALB를 배포**한다
> c) 프라이빗 서브넷 두 개와 NAT 게이트웨이 두 개로 VPC를 구성하고 프라이빗 서브넷에 ALB를 배포한다
> d) Auto Scaling 그룹으로 EC2를 두 AZ의 퍼블릭 서브넷에 띄우고 RDS 다중 AZ를 프라이빗 서브넷에 배포한다
>> [!success]- Answer
>> a) Auto Scaling 그룹으로 EC2를 프라이빗 서브넷에 띄우고 RDS 다중 AZ DB 인스턴스를 프라이빗 서브넷에 배포한다
>> b) 두 가용 영역에 걸쳐 퍼블릭 서브넷 두 개, 프라이빗 서브넷 두 개, NAT 게이트웨이 두 개로 VPC를 구성하고 **퍼블릭 서브넷에 ALB를 배포**한다
>> **왜 이 답인가** — 노출되면 안 되는 것은 프라이빗으로, 사용자를 받아야 하는 ALB는 퍼블릭으로 갑니다. 결제 호출은 NAT가 대신 나가 주고, 고가용성 조건 때문에 **ALB도 NAT도 AZ마다** 있어야 합니다.
>> **나머지가 아닌 이유** — ALB를 프라이빗에 두면 인터넷 사용자가 들어오지 못합니다. EC2를 퍼블릭 서브넷에 두는 것은 노출 금지 조건을 어깁니다.

> [!question] 한 기업이 MySQL 데이터베이스로 구동되는 온프레미스 애플리케이션을 AWS로 옮기고 있습니다. 평상시에도 읽기 부하가 큰데, **4시간마다 개발 팀이 프로덕션 데이터베이스를 전부 내보내 스테이징 환경을 채웁니다.** 그동안 사용자는 지연을 겪고 개발 팀은 작업이 끝날 때까지 스테이징을 쓰지 못합니다. 지연 문제를 해소하고 개발 팀이 지체 없이 스테이징을 쓰게 하려면 어떤 아키텍처를 권장해야 합니까?
> a) 프로덕션에 다중 AZ Aurora 복제본과 함께 Aurora MySQL을 쓰고, **데이터베이스 복제(cloning)**로 필요할 때 스테이징 데이터베이스를 만든다
> b) 다중 AZ Aurora 복제본과 함께 Aurora MySQL을 쓰고 mysqldump 백업·복원으로 스테이징을 채운다
> c) 다중 AZ와 읽기 전용 복제본이 있는 RDS for MySQL을 쓰고 대기 인스턴스를 스테이징 데이터베이스로 쓴다
> d) 다중 AZ와 읽기 전용 복제본이 있는 RDS for MySQL을 쓰고 mysqldump 백업·복원으로 스테이징을 채운다
>> [!success]- Answer
>> a) 프로덕션에 다중 AZ Aurora 복제본과 함께 Aurora MySQL을 쓰고, **데이터베이스 복제(cloning)**로 필요할 때 스테이징 데이터베이스를 만든다
>> **왜 이 답인가** — Aurora 복제(클론)는 **쓰기 시 복사** 방식이라 데이터를 실제로 퍼 나르지 않습니다. 몇 분 안에 스테이징이 만들어지고 프로덕션에 부하를 주지 않습니다.
>> **나머지가 아닌 이유** — mysqldump는 지금 문제를 일으키고 있는 바로 그 방식입니다. 다중 AZ 대기 인스턴스는 접속해서 쓸 수 있는 대상이 아닙니다.

> [!question] 한 기업이 글로벌 전자상거래 애플리케이션의 데이터 저장소로 Amazon Aurora를 씁니다. **큰 보고서를 돌릴 때** 애플리케이션 성능이 나빠지고, CloudWatch를 보니 월간 보고서 실행 시 `ReadIOPS`와 `CPUUtilization`이 치솟습니다. 가장 비용 효율적인 해결책은 무엇입니까?
> a) 월간 보고 작업을 Aurora 복제본으로 옮긴다
> b) 월간 보고 작업을 Amazon Redshift로 옮긴다
> c) Aurora 데이터베이스를 더 큰 인스턴스 클래스로 바꾼다
> d) Aurora 인스턴스의 프로비저닝된 IOPS를 늘린다
>> [!success]- Answer
>> a) 월간 보고 작업을 Aurora 복제본으로 옮긴다
>> **왜 이 답인가** — 보고서는 **읽기**이고 원본 인스턴스를 방해합니다. Aurora 복제본으로 읽기를 떼어 내면 기본 인스턴스는 트랜잭션에 집중합니다. 데이터를 옮기지 않아 비용도 가장 적습니다.
>> **나머지가 아닌 이유** — Redshift로 옮기면 별도의 웨어하우스와 적재 파이프라인이 필요합니다. 인스턴스를 키우는 것은 한 달에 한 번 쓰는 여유를 상시로 사는 셈입니다. Aurora 스토리지는 IOPS를 따로 프로비저닝하지 않습니다.

> [!question] 한 기업의 애플리케이션이 VPC의 EC2 인스턴스에서 실행되며 그중 하나가 객체를 저장·조회하기 위해 Amazon S3 API를 호출해야 합니다. 보안 규정상 **애플리케이션의 어떤 트래픽도 인터넷을 통과할 수 없습니다.** 어떤 솔루션이 요구 사항을 충족합니까?

> c) EC2 인스턴스와 같은 AWS 리전에 S3 버킷을 만든다

>> **왜 이 답인가** — 세 요구가 각각 다른 서비스에 대응합니다. **높은 IOPS 블록 스토리지는 EBS(프로비저닝된 IOPS)**, 대용량 내구성 저장은 S3, 장기 아카이브는 Glacier입니다.
>> **나머지가 아닌 이유** — 인스턴스 스토어는 빠르지만 인스턴스가 멈추면 사라져 영상 처리 데이터를 맡기기 어렵습니다. EFS는 300TB 보관에 S3보다 훨씬 비쌉니다.

> [!question] 한 기업이 AWS에서 OLTP 워크로드를 운영하며 다중 AZ 배포의 **암호화되지 않은** RDS DB 인스턴스를 사용합니다. 이 인스턴스에서 매일 스냅샷을 뜹니다. 앞으로 **데이터베이스와 스냅샷이 항상 암호화되게** 하려면 무엇을 해야 합니까?
> a) 최신 DB 스냅샷의 복사본을 암호화하고, 그 암호화된 스냅샷을 복원해 기존 DB 인스턴스를 대체한다
> b) 새 암호화 EBS 볼륨을 만들어 스냅샷을 복사하고 DB 인스턴스에서 암호화를 켠다
> c) 스냅샷을 복사하며 KMS로 암호화를 켠 뒤 기존 DB 인스턴스에 그 스냅샷을 복원한다
> d) 스냅샷을 SSE-KMS로 암호화된 S3 버킷에 복사한다
>> [!success]- Answer
>> a) 최신 DB 스냅샷의 복사본을 암호화하고, 그 암호화된 스냅샷을 복원해 기존 DB 인스턴스를 대체한다
>> **왜 이 답인가** — **이미 만들어진 RDS 인스턴스는 나중에 암호화를 켤 수 없습니다.** 유일한 경로는 스냅샷을 복사하면서 암호화하고, 그 스냅샷으로 **새 인스턴스를 만들어 교체**하는 것입니다.
>> **나머지가 아닌 이유** — 기존 인스턴스에 암호화를 켜는 보기들은 애초에 불가능한 동작입니다. 스냅샷을 암호화된 버킷에 두어도 데이터베이스 자체는 여전히 평문입니다.

> [!question] 한 기업의 다계층 애플리케이션이 **단일 가용 영역**의 Auto Scaling 그룹에서 프런트엔드 웹 서버 여섯 대를 Application Load Balancer 뒤에서 돌립니다. **애플리케이션을 수정하지 않고** 고가용성을 갖추도록 인프라를 바꿔야 합니다. 어떤 아키텍처를 선택해야 합니까?
> a) Auto Scaling 그룹이 **두 가용 영역에 각각 세 인스턴스씩** 쓰도록 수정한다
> b) 두 리전에 각각 세 인스턴스를 두는 Auto Scaling 그룹을 만든다
> c) 다른 리전에 인스턴스를 빠르게 만들 수 있는 템플릿을 만든다
> d) ALB를 라운드 로빈 구성으로 바꿔 웹 계층 트래픽을 분산한다
>> [!success]- Answer
>> a) Auto Scaling 그룹이 **두 가용 영역에 각각 세 인스턴스씩** 쓰도록 수정한다
>> **왜 이 답인가** — 지금의 단일 장애 지점은 **가용 영역 하나**입니다. 인스턴스 수를 유지한 채 두 AZ에 나눠 배치하면 한 AZ가 죽어도 서비스가 이어집니다. 애플리케이션은 손대지 않습니다.
>> **나머지가 아닌 이유** — 리전을 늘리는 것은 요구 이상으로 복잡하고 비쌉니다. 템플릿만 만들어 두는 것은 장애 시 사람이 개입해야 합니다. 라운드 로빈은 분산 방식일 뿐 가용성과 무관합니다.

> [!question] 한 기업이 애플리케이션에서 데이터를 암호화해야 하는 개발자들을 지원하기 위해 **확장 가능한 키 관리 인프라**를 구축하려고 합니다. 운영 부담을 줄이려면 무엇을 해야 합니까?
> a) AWS Key Management Service(AWS KMS)로 암호화 키를 보호한다
> b) 다중 인증(MFA)으로 암호화 키를 보호한다
> c) AWS Certificate Manager(ACM)로 암호화 키를 만들고 저장·할당한다
> d) IAM 정책으로 키에 접근할 수 있는 사용자 범위를 제한한다
>> [!success]- Answer
>> a) AWS Key Management Service(AWS KMS)로 암호화 키를 보호한다
>> **왜 이 답인가** — KMS가 바로 **관리형 키 관리 인프라**입니다. 키 생성·보관·교체·감사 기록을 대신 해 주므로 직접 구축할 필요가 없습니다.
>> **나머지가 아닌 이유** — MFA와 IAM 정책은 접근을 제한하는 수단이지 키 관리 인프라가 아닙니다. ACM은 TLS 인증서를 다루는 서비스입니다.

> [!question] 한 기업이 S3 버킷을 저장소로 쓰는 파일 공유 애플리케이션을 개발하며 모든 파일을 **CloudFront 배포를 통해서만** 제공하려고 합니다. **S3 URL로 직접 접근하는 것은 막아야** 합니다. 무엇을 해야 합니까?
> a) 오리진 액세스 아이덴티티(OAI)를 만들어 CloudFront 배포에 할당하고, S3 버킷 권한을 OAI만 읽을 수 있게 구성한다
> b) 버킷마다 CloudFront 접근에만 읽기를 허용하는 정책을 각각 작성한다
> c) IAM 사용자를 만들어 객체 읽기 권한을 주고 그 사용자를 CloudFront에 할당한다
> d) CloudFront 배포 ID를 Principal로, 대상 버킷을 ARN으로 지정하는 버킷 정책을 작성한다
>> [!success]- Answer
>> a) 오리진 액세스 아이덴티티(OAI)를 만들어 CloudFront 배포에 할당하고, S3 버킷 권한을 OAI만 읽을 수 있게 구성한다
>> **왜 이 답인가** — OAI는 **CloudFront가 S3에 접근할 때 쓰는 전용 신원**입니다. 버킷이 OAI에게만 읽기를 허용하면 직접 URL 접근은 자동으로 막힙니다.
>> **나머지가 아닌 이유** — CloudFront에 IAM 사용자를 할당하는 개념은 없습니다. 배포 ID를 Principal로 쓰는 것은 IAM 정책 문법이 아닙니다.
