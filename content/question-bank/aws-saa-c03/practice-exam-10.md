> [!question] 한 기업이 계약 문서를 보관해야 합니다. 계약 기간은 5년이며 그동안 문서를 **덮어쓰거나 삭제할 수 없어야** 합니다. 또한 문서를 저장 시 암호화하고 **암호화 키를 매년 자동 교체**해야 합니다. 운영 오버헤드가 가장 적은 조합은 무엇입니까? (2개 선택)
> a) 문서를 S3에 저장하고 **규정 준수 모드**의 S3 객체 잠금을 사용한다
> b) **AWS KMS 고객 관리형 키**로 서버 측 암호화를 하고 키 교체를 구성한다
> c) 문서를 S3에 저장하고 거버넌스 모드의 객체 잠금을 사용한다
> d) SSE-S3를 사용하고 키 교체를 구성한다
>> [!success]- Answer
>> a) 문서를 S3에 저장하고 **규정 준수 모드**의 S3 객체 잠금을 사용한다
>> b) **AWS KMS 고객 관리형 키**로 서버 측 암호화를 하고 키 교체를 구성한다
>> **왜 이 답인가** — `아무도 삭제할 수 없다`는 규정 준수 모드이고, `키를 매년 자동 교체`는 **KMS 고객 관리형 키의 자동 교체**입니다. 두 기능 모두 켜기만 하면 됩니다.
>> **나머지가 아닌 이유** — 거버넌스 모드는 권한이 있는 사용자가 해제할 수 있습니다. SSE-S3는 키 교체 주기를 사용자가 구성할 수 없습니다. 가져온(imported) 키는 자동 교체를 지원하지 않습니다.

> [!question] 한 기업의 API가 모니터링 디바이스에서 실시간 데이터를 받아 RDS DB 인스턴스에 저장합니다. 데이터 양이 변동하며 **트래픽이 몰릴 때 API가 시간 초과 오류**를 냅니다. 원인은 데이터베이스가 쓰기 트래픽을 감당하지 못하는 것입니다. **데이터베이스 연결 수를 최소화**하면서 **데이터가 유실되지 않게** 하려면 어떤 솔루션이 적합합니까?
> a) API가 들어오는 데이터를 Amazon SQS 큐에 쓰게 하고, SQS가 호출하는 Lambda 함수가 큐에서 데이터베이스로 쓰게 한다
> b) DB 인스턴스를 메모리가 더 많은 유형으로 키운다
> c) DB 인스턴스를 다중 AZ로 바꾸고 애플리케이션이 모든 활성 인스턴스에 쓰게 한다
> d) API가 SNS 주제에 쓰게 하고 SNS가 호출하는 Lambda가 데이터베이스에 쓰게 한다
>> [!success]- Answer
>> a) API가 들어오는 데이터를 Amazon SQS 큐에 쓰게 하고, SQS가 호출하는 Lambda 함수가 큐에서 데이터베이스로 쓰게 한다
>> **왜 이 답인가** — 큐가 **급증을 흡수**하고 Lambda가 **일정한 속도로** 데이터베이스에 씁니다. 연결 수가 통제되고 밀린 데이터는 큐에 남아 유실되지 않습니다.
>> **나머지가 아닌 이유** — 인스턴스를 키우는 것은 다음 급증에서 같은 문제를 반복합니다. 다중 AZ 대기 인스턴스에는 쓸 수 없습니다. SNS는 저장하지 않아 유실을 막지 못합니다.

> [!question] 한 전자상거래 기업의 주문 처리 애플리케이션이 API Gateway와 Lambda를 쓰고 데이터는 Aurora PostgreSQL에 저장합니다. 판매 행사 중 주문이 급증하자 일부 고객이 시간 초과를 겪고 주문이 처리되지 않았습니다. 원인은 **열린 연결이 너무 많아** 데이터베이스의 CPU·메모리 사용률이 높았던 것입니다. **애플리케이션 변경을 최소로** 하면서 시간 초과를 막으려면 어떤 솔루션이 적합합니까?
> a) Amazon RDS Proxy로 데이터베이스 프록시를 만들고 Lambda가 데이터베이스 엔드포인트 대신 프록시 엔드포인트를 쓰게 한다
> b) Lambda에 프로비저닝된 동시성을 구성하고 데이터베이스를 여러 리전의 글로벌 데이터베이스로 바꾼다
> c) 다른 리전에 읽기 전용 복제본을 만들고 API Gateway의 쿼리 문자열로 트래픽을 복제본으로 보낸다
> d) DMS로 데이터를 DynamoDB로 옮기고 Lambda가 DynamoDB를 쓰게 한다
>> [!success]- Answer
>> a) Amazon RDS Proxy로 데이터베이스 프록시를 만들고 Lambda가 데이터베이스 엔드포인트 대신 프록시 엔드포인트를 쓰게 한다
>> **왜 이 답인가** — Lambda가 동시에 많이 뜨면 **연결도 그만큼 열려** 데이터베이스가 무너집니다. RDS Proxy는 연결을 모아 재사용하므로 이 문제를 정면으로 해결하고, 바꿀 것은 **연결 문자열 하나**입니다.
>> **나머지가 아닌 이유** — 프로비저닝된 동시성은 연결 수 문제를 줄여 주지 않습니다. 읽기 복제본은 쓰기 부하를 덜지 못합니다. DynamoDB 이전은 애플리케이션을 다시 쓰는 큰 변경입니다.

> [!question] 한 기업의 보안 팀이 네트워크 트래픽을 **VPC 플로 로그**로 캡처하기를 요청했습니다. 이 로그는 **90일 동안 자주 조회**되고 그 뒤에는 간헐적으로 조회됩니다. 로그를 구성할 때 무엇을 해야 합니까?
> a) 대상을 Amazon S3로 지정하고, **수명 주기 정책으로 90일 후 S3 Standard-IA로 전환**한다
> b) 대상을 CloudWatch로 지정하고 로그 그룹 만료를 90일로 설정한다
> c) 대상을 Kinesis로 지정하고 스트림이 90일 동안 로그를 보관하게 한다
> d) 대상을 CloudTrail로 지정하고 S3에 저장하며 Intelligent-Tiering을 켠다
>> [!success]- Answer
>> a) 대상을 Amazon S3로 지정하고, **수명 주기 정책으로 90일 후 S3 Standard-IA로 전환**한다
>> **왜 이 답인가** — 플로 로그는 CloudWatch Logs나 **S3**로 보낼 수 있고, `90일 후 간헐 조회`라는 알려진 패턴에는 수명 주기 정책으로 Standard-IA로 내리는 것이 맞습니다.
>> **나머지가 아닌 이유** — 로그 그룹 만료는 90일 뒤 로그를 **지워 버립니다.** Kinesis는 장기 보관소가 아니고, CloudTrail은 플로 로그의 대상이 될 수 없습니다.

> [!question] 한 기업이 사용자 관리를 **Amazon Cognito**로 합니다. 사용자가 로그인하면 애플리케이션이 API Gateway의 REST API로 DynamoDB에서 데이터를 가져옵니다. **REST API 접근을 통제**할 AWS 관리형 솔루션으로 개발 노력을 줄이려고 합니다. 운영 오버헤드가 가장 적은 솔루션은 무엇입니까?
> a) API Gateway에 **Amazon Cognito 사용자 풀 권한 부여자**를 구성해 Cognito가 각 요청을 검증하게 한다
> b) API Gateway에 Lambda 권한 부여자를 구성해 요청한 사용자를 검증한다
> c) 사용자마다 API 키를 만들어 요청에 넣게 하고 Lambda로 검증한다
> d) 요청 헤더에 사용자 이메일을 담아 보내고 Lambda로 권한을 검증한다
>> [!success]- Answer
>> a) API Gateway에 **Amazon Cognito 사용자 풀 권한 부여자**를 구성해 Cognito가 각 요청을 검증하게 한다
>> **왜 이 답인가** — 이미 Cognito를 쓰고 있으므로, API Gateway에 **사용자 풀 권한 부여자**를 지정하면 토큰 검증을 AWS가 대신 합니다. 작성할 코드가 없습니다.
>> **나머지가 아닌 이유** — Lambda 권한 부여자는 검증 코드를 직접 짜고 유지해야 합니다. API 키는 사용자 인증 수단이 아니고, 헤더의 이메일을 믿는 방식은 위조가 가능합니다.

> [!question] 한 기업의 인프라가 단일 리전의 EC2 인스턴스와 RDS DB 인스턴스로 구성되어 있습니다. **다른 리전에 데이터를 백업**하려고 합니다. 운영 오버헤드가 가장 적은 솔루션은 무엇입니까?
> a) AWS Backup으로 EC2 백업과 RDS 백업을 다른 리전으로 복사한다
> b) Amazon Data Lifecycle Manager로 EC2 백업과 RDS 백업을 다른 리전으로 복사한다
> c) EC2의 AMI를 만들어 다른 리전으로 복사하고 RDS는 다른 리전에 읽기 전용 복제본을 만든다
> d) EBS 스냅샷을 만들어 복사하고 RDS 스냅샷을 S3로 내보낸 뒤 교차 리전 복제를 구성한다
>> [!success]- Answer
>> a) AWS Backup으로 EC2 백업과 RDS 백업을 다른 리전으로 복사한다
>> **왜 이 답인가** — AWS Backup은 **여러 서비스의 백업을 한 정책으로 묶고 교차 리전 복사까지 지원**합니다. 백업 계획 하나로 끝나므로 운영 오버헤드가 가장 적습니다.
>> **나머지가 아닌 이유** — Data Lifecycle Manager는 EBS 스냅샷·AMI 중심이라 RDS를 다루지 않습니다. 나머지 보기들은 리소스 종류마다 절차를 따로 만들어 관리해야 합니다.

> [!question] 한 엔터테인먼트 기업이 미디어 메타데이터를 DynamoDB에 저장합니다. 애플리케이션은 **읽기 위주**이고 지연이 발생합니다. 추가 운영 부담을 감당할 인력이 없고 **애플리케이션을 다시 구성하지 않고** DynamoDB 성능을 개선해야 합니다. 무엇을 권장해야 합니까?
> a) Amazon DynamoDB Accelerator(DAX)를 사용한다
> b) Amazon ElastiCache for Redis를 사용한다
> c) DynamoDB 글로벌 테이블로 데이터를 복제한다
> d) 자동 검색을 켠 ElastiCache for Memcached를 사용한다
>> [!success]- Answer
>> a) Amazon DynamoDB Accelerator(DAX)를 사용한다
>> **왜 이 답인가** — DAX는 **DynamoDB 전용 인메모리 캐시**로, API 호출 방식이 같아 애플리케이션 코드를 거의 바꾸지 않고 붙일 수 있습니다. 읽기 지연이 마이크로초 수준으로 떨어집니다.
>> **나머지가 아닌 이유** — ElastiCache를 쓰면 캐시 조회·저장 로직을 애플리케이션에 직접 넣어야 합니다. 글로벌 테이블은 리전 간 복제라 읽기 지연 개선 수단이 아닙니다.

> [!question] 한 기업이 다계층 웹 애플리케이션에 Amazon ElastiCache를 쓰려고 합니다. 솔루션스 아키텍트가 ElastiCache 클러스터용 **Cache VPC**와 애플리케이션 EC2용 **App VPC**를 만들었고 둘 다 us-east-1에 있습니다. EC2 인스턴스가 캐시 클러스터에 접근하게 하려면, 가장 비용 효율적인 솔루션은 무엇입니까?
> a) 두 VPC 사이에 피어링 연결을 만들고 양쪽 라우팅 테이블에 경로를 추가한 뒤, **ElastiCache 보안 그룹**이 애플리케이션 보안 그룹에서 오는 인바운드를 허용하게 한다
> b) 두 VPC 사이에 피어링을 만들고 경로를 추가한 뒤 **피어링 연결의 보안 그룹**에 인바운드 규칙을 구성한다
> c) Transit VPC를 만들어 양쪽 라우팅 테이블이 그쪽을 거치게 하고 ElastiCache 보안 그룹에 인바운드 규칙을 구성한다
> d) Transit VPC를 만들고 Transit VPC의 보안 그룹에 인바운드 규칙을 구성한다
>> [!success]- Answer
>> a) 두 VPC 사이에 피어링 연결을 만들고 양쪽 라우팅 테이블에 경로를 추가한 뒤, **ElastiCache 보안 그룹**이 애플리케이션 보안 그룹에서 오는 인바운드를 허용하게 한다
>> **왜 이 답인가** — 같은 리전의 두 VPC를 잇는 가장 싼 방법이 **피어링**입니다(추가 인프라 요금이 없습니다). 그리고 보안 그룹은 **리소스에 붙는 것**이므로 캐시 쪽 보안 그룹에서 허용해야 합니다.
>> **나머지가 아닌 이유** — 피어링 연결에는 보안 그룹이 없습니다. Transit VPC(또는 전송 게이트웨이)는 연결이 많을 때 쓰는 구조로, VPC 두 개에는 과하고 비쌉니다.

> [!question] 한 기업이 데이터를 S3 버킷으로 옮기려 합니다. 저장 시 암호화되어야 하고 **암호화 키는 매년 자동으로 교체**되어야 합니다. 운영 오버헤드가 가장 적은 솔루션은 무엇입니까?
> a) KMS 고객 관리형 키를 만들어 **자동 키 교체를 켜고**, 버킷 기본 암호화가 그 키를 쓰도록 설정한 뒤 데이터를 옮긴다
> b) 데이터를 옮기고 SSE-S3를 쓰며 SSE-S3 키의 내장 교체 동작에 맡긴다
> c) KMS 고객 관리형 키를 만들어 기본 암호화로 설정하고 매년 수동으로 교체한다
> d) 고객 키 자료로 미리 암호화해 옮기고, 키 자료를 가져온 KMS 키에서 자동 교체를 켠다
>> [!success]- Answer
>> a) KMS 고객 관리형 키를 만들어 **자동 키 교체를 켜고**, 버킷 기본 암호화가 그 키를 쓰도록 설정한 뒤 데이터를 옮긴다
>> **왜 이 답인가** — `매년 자동 교체`를 **사용자가 켜고 확인할 수 있는** 것은 KMS 고객 관리형 키입니다. 버킷 기본 암호화로 지정하면 이후 올라오는 객체가 자동으로 그 키로 암호화됩니다.
>> **나머지가 아닌 이유** — SSE-S3의 키 교체는 AWS 내부 동작이라 요구를 명시적으로 만족한다고 보기 어렵습니다. 수동 교체는 매년 사람 손이 갑니다. **가져온 키 자료는 자동 교체를 지원하지 않습니다.**

> [!question] 한 기업이 RDS for PostgreSQL DB 인스턴스로 웹 서버 플릿을 운영합니다. 규정 점검 후 모든 프로덕션 데이터베이스에 **복구 지점 목표(RPO) 1초 미만**을 요구하기로 했습니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) DB 인스턴스에 다중 AZ 배포를 켠다
> b) 한 가용 영역의 DB 인스턴스에 오토 스케일링을 켠다
> c) DB 인스턴스를 한 AZ에 두고 다른 AZ에 읽기 전용 복제본을 여러 개 만든다
> d) DB 인스턴스를 한 AZ에 두고 AWS DMS의 변경 데이터 캡처(CDC) 작업을 구성한다
>> [!success]- Answer
>> a) DB 인스턴스에 다중 AZ 배포를 켠다
>> **왜 이 답인가** — 다중 AZ는 **동기 복제**라 커밋이 두 AZ에 함께 기록됩니다. 데이터 손실이 사실상 없어 RPO 1초 미만을 만족합니다.
>> **나머지가 아닌 이유** — 읽기 전용 복제본과 DMS CDC는 **비동기**라 복제 지연만큼 손실이 생길 수 있습니다. 오토 스케일링은 복구 지점과 무관합니다.

<sub>관련: [[amazon-rds]] | 모듈 [[05-high-availability]]</sub>

> [!question] 솔루션스 아키텍트가 새 AWS 계정을 만들고 **루트 사용자 접근을 보호**해야 합니다. 어떤 조합이 필요합니까? (2개 선택)
> a) 루트 사용자에게 강력한 암호를 설정한다
> b) 루트 사용자에 다중 인증(MFA)을 켠다
> c) 루트 사용자 액세스 키를 암호화된 S3 버킷에 보관한다
> d) 루트 사용자를 관리 권한이 있는 그룹에 추가한다
>> [!success]- Answer
>> a) 루트 사용자에게 강력한 암호를 설정한다
>> b) 루트 사용자에 다중 인증(MFA)을 켠다
>> **왜 이 답인가** — 루트 계정 보호의 기본이 **강력한 암호와 MFA**입니다. 이후 일상 작업은 IAM 사용자·역할로 하고 루트는 거의 쓰지 않는 것이 원칙입니다.
>> **나머지가 아닌 이유** — 루트 액세스 키는 아예 **만들지 않고 삭제하는 것**이 권장이라 어디에 보관하든 틀린 방향입니다. 루트는 이미 모든 권한을 가지므로 그룹에 넣거나 정책을 붙일 수 없습니다.

<sub>관련: [[aws-iam]] | 모듈 [[01-secure-access]]</sub>

> [!question] 한 기업이 EBS 볼륨 기반 EC2 인스턴스와 Application Load Balancer, Aurora 데이터베이스로 새 CRM 애플리케이션을 만듭니다. 모든 데이터는 **저장 시와 전송 중 모두 암호화**되어야 합니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) AWS KMS로 EBS 볼륨과 Aurora 스토리지를 저장 시 암호화하고, **ACM 인증서를 ALB에 연결**해 전송 중 데이터를 암호화한다
> b) ALB에 KMS 인증서를 써서 전송 중 암호화하고 ACM으로 EBS와 Aurora를 저장 시 암호화한다
> c) 루트 계정으로 로그인해 인증서를 올리고 계정 전체에 대한 암호화 옵션을 켠다
> d) BitLocker로 저장 데이터를 암호화하고 TLS 키를 KMS에 가져와 ALB에 연결한다
>> [!success]- Answer
>> a) AWS KMS로 EBS 볼륨과 Aurora 스토리지를 저장 시 암호화하고, **ACM 인증서를 ALB에 연결**해 전송 중 데이터를 암호화한다
>> **왜 이 답인가** — 역할이 명확히 나뉩니다. **저장 시 암호화는 KMS**, **전송 중 암호화(TLS 인증서)는 ACM**입니다.
>> **나머지가 아닌 이유** — 둘을 뒤집은 보기는 이름만 바꾼 함정입니다. KMS는 TLS 인증서를 발급하지 않고, 계정 전체 암호화를 켜는 스위치는 존재하지 않습니다.
