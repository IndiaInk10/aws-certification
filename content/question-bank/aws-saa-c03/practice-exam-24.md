> [!question] 두 가용 영역에 인스턴스를 **각각 4대씩 총 8대**로 운영하며 피크 때 8대가 모두 필요합니다. **AZ 하나가 사라져도 서비스 품질을 유지**하려면 어떻게 용량을 계획해야 합니까?
> a) AZ마다 **8대씩 총 16대**를 두어 한 AZ가 사라져도 남은 AZ가 피크 부하를 감당하게 한다
> b) AZ마다 4대를 유지하고 장애 시 Auto Scaling이 부족분을 채우게 한다
> c) 세 번째 AZ를 추가하고 AZ마다 4대를 유지한다
> d) 인스턴스 유형을 두 배 크기로 바꾸고 AZ마다 2대를 둔다
>> [!success]- Answer
>> a) AZ마다 **8대씩 총 16대**를 두어 한 AZ가 사라져도 남은 AZ가 피크 부하를 감당하게 한다
>> **왜 이 답인가** — AZ 하나를 잃어도 **남은 쪽만으로 피크를 감당해야** 품질이 유지됩니다. 두 AZ 구성에서는 각 AZ가 전체 부하를 처리할 수 있어야 합니다.
>> **나머지가 아닌 이유** — 장애 시 Auto Scaling이 채우는 방식은 **인스턴스가 뜨는 동안 성능이 떨어지고**, 그 순간 해당 AZ의 용량 확보가 실패할 수도 있습니다. 세 번째 AZ를 쓰는 보기는 AZ당 4대라 한 AZ 손실 후 8대가 되어 아슬아슬하고, 큰 인스턴스 2대 구성은 한 대만 잃어도 절반이 사라집니다.

> [!question] **VoIP 기능**이 있는 애플리케이션을 전 세계에 제공하며 **리전 간 자동 장애 조치**가 필요하고, **사용자 기기의 IP 캐싱에 의존하지 않고** 지연을 최소화해야 합니다. 무엇을 해야 합니까?
> a) 상태 확인과 함께 **AWS Global Accelerator**를 사용한다
> b) Route 53의 지리 위치 라우팅 정책을 사용한다
> c) 여러 오리진을 가진 CloudFront 배포를 만든다
> d) 경로 기반 라우팅을 쓰는 Application Load Balancer를 만든다
>> [!success]- Answer
>> a) 상태 확인과 함께 **AWS Global Accelerator**를 사용한다
>> **왜 이 답인가** — Global Accelerator는 **고정 애니캐스트 IP**를 주므로 클라이언트가 IP를 캐싱해도 문제가 없고(뒤에서 대상만 바뀝니다), UDP를 지원하며 상태 확인으로 리전 장애 조치를 자동 처리합니다.
>> **나머지가 아닌 이유** — Route 53 기반 전환은 **DNS 캐시**에 좌우됩니다. CloudFront·ALB는 HTTP 계열이라 VoIP 트래픽에 맞지 않습니다.

> b) 대상 위치와 작업을 만들되 모든 데이터를 전송하는 모드로 설정한다
> c) Lambda 함수에 파일 시스템을 마운트하고 S3 이벤트로 호출해 복사하게 한다
> d) 같은 VPC에 EC2를 띄워 파일 시스템을 마운트하고 동기화 스크립트를 만든다
>> [!success]- Answer
>> a) 대상 S3 버킷과 EFS에 대한 **AWS DataSync 위치와 작업**을 만들고, **변경된 데이터만 전송하는 모드**로 설정한다
>> **왜 이 답인가** — DataSync는 **S3·EFS 사이의 전송을 관리형으로 처리**하고, 전송 모드를 `변경된 데이터만`으로 두면 요구가 그대로 표현됩니다.
>> **나머지가 아닌 이유** — 모든 데이터를 매번 전송하면 비용과 시간이 낭비됩니다. Lambda·EC2 스크립트는 코드를 만들어 유지해야 합니다.

> a) 업체들이 소유한 계정에 대해 **S3 버킷 교차 계정 액세스**를 구성한다

> d) 업체마다 데이터를 복제하도록 S3 글로벌 테이블을 구성한다

> a) 함수를 **여러 AZ의 충분히 큰 프라이빗 서브넷**에 연결하고 서브넷 IP 여유를 확보한다

> c) 함수를 퍼블릭 서브넷으로 옮긴다
> d) 함수의 제한 시간을 늘린다
>> [!success]- Answer

>> [!success]- Answer
