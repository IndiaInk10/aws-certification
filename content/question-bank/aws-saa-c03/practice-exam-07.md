> [!question] 한 기업의 S3 버킷에 중요한 데이터가 있습니다. **실수로 인한 삭제**로부터 데이터를 보호해야 합니다. 어떤 조합이 필요합니까? (2개 선택)
> a) S3 버킷에서 버전 관리를 켠다
> b) S3 버킷에서 MFA 삭제를 켠다
> c) S3 버킷에 버킷 정책을 만든다
> d) S3 버킷에서 기본 암호화를 켠다
>> [!success]- Answer
>> a) S3 버킷에서 버전 관리를 켠다
>> b) S3 버킷에서 MFA 삭제를 켠다
>> **왜 이 답인가** — 버전 관리를 켜면 삭제해도 이전 버전이 남아 되돌릴 수 있습니다. MFA 삭제는 **버전을 영구 삭제할 때 추가 인증을 요구**해 되돌릴 수 없는 삭제를 막습니다. 둘은 함께 쓰도록 설계된 짝입니다.
>> **나머지가 아닌 이유** — 암호화는 **유출**을 막는 것이지 삭제를 막지 않습니다. 버킷 정책도 도움이 되지만 이 문항이 요구하는 `실수 삭제 방지`의 표준 조합은 버전 관리 + MFA 삭제입니다.

> [!question] 한 기업의 HTTP 애플리케이션이 Network Load Balancer 뒤에 있고, 대상 그룹은 웹 서비스를 실행하는 여러 EC2 인스턴스의 Auto Scaling 그룹입니다. NLB가 **애플리케이션의 HTTP 오류를 감지하지 못해** 문제가 생기면 인스턴스를 수동으로 재시작해야 합니다. 사용자 지정 스크립트나 코드를 작성하지 않고 가용성을 개선하려면 무엇을 해야 합니까?
> a) NLB를 Application Load Balancer로 교체하고 애플리케이션 URL로 HTTP 상태 확인을 켜며, 비정상 인스턴스를 교체하도록 Auto Scaling을 구성한다
> b) NLB에서 애플리케이션 URL을 지정해 HTTP 상태 확인을 켠다
> c) EC2에 크론 작업을 추가해 매분 로컬 로그를 확인하고 HTTP 오류가 있으면 애플리케이션을 재시작한다
> d) NLB의 `UnhealthyHostCount` 지표를 감시하는 CloudWatch 경보를 만들고 경보 시 인스턴스를 교체하게 한다
>> [!success]- Answer
>> a) NLB를 Application Load Balancer로 교체하고 애플리케이션 URL로 HTTP 상태 확인을 켜며, 비정상 인스턴스를 교체하도록 Auto Scaling을 구성한다
>> **왜 이 답인가** — **HTTP 응답 코드를 이해하는 것은 계층 7 로드 밸런서인 ALB**입니다. ALB 상태 확인을 ASG가 쓰게 하면 비정상 인스턴스가 자동으로 교체되고 스크립트를 짤 필요가 없습니다.
>> **나머지가 아닌 이유** — 크론 스크립트는 `코드를 작성하지 않는다`는 조건을 어깁니다. NLB의 상태 확인은 기본적으로 TCP 수준이라 애플리케이션이 500을 뱉어도 정상으로 봅니다. 지표 경보만으로는 원인인 HTTP 오류를 잡아내지 못합니다.

> [!question] 한 기업의 수천 대 엣지 디바이스가 하루에 총 1TB의 상태 알림을 생성하며 알림 하나는 약 2KB입니다. 이 알림을 수집·저장해 나중에 분석해야 합니다. 고가용성을 원하지만 비용을 최소화해야 하고 **추가 인프라를 관리하고 싶지 않으며**, 최근 14일 데이터는 즉시 분석할 수 있어야 하고 그보다 오래된 데이터는 아카이브해야 합니다. 운영 효율이 가장 높은 솔루션은 무엇입니까?
> a) Kinesis Data Firehose 전송 스트림으로 알림을 수집해 S3 버킷에 전달하고, S3 수명 주기 구성으로 14일 후 Glacier로 전환한다
> b) 두 가용 영역에 EC2 인스턴스를 띄우고 로드 밸런서 뒤에서 알림을 받아 스크립트로 S3에 저장한 뒤 14일 후 Glacier로 전환한다
> c) Firehose로 수집해 Amazon OpenSearch Service 클러스터에 전달하고, 매일 수동 스냅샷을 뜬 뒤 14일이 지난 데이터를 클러스터에서 삭제한다
> d) SQS 표준 큐로 수집하고 메시지 보존 기간을 14일로 설정한 뒤, 소비자가 메시지 나이를 확인해 14일이 되면 S3로 복사하고 큐에서 삭제한다
>> [!success]- Answer
>> a) Kinesis Data Firehose 전송 스트림으로 알림을 수집해 S3 버킷에 전달하고, S3 수명 주기 구성으로 14일 후 Glacier로 전환한다
>> **왜 이 답인가** — Firehose는 **관리할 인프라가 없는 수집 파이프라인**이고 S3로 자동 적재합니다. 14일 경계는 수명 주기 정책이 알아서 처리합니다.
>> **나머지가 아닌 이유** — EC2 기반 수집은 관리할 인프라가 늘어납니다. OpenSearch 클러스터는 노드를 운영해야 하고 수동 스냅샷은 운영 부담입니다. SQS는 메시지 큐이지 장기 데이터 저장소가 아니며 소비자가 나이를 계산하게 만드는 설계는 복잡합니다.

> [!question] 한 기업의 애플리케이션이 각 5MB 정도의 파일을 대량으로 만들어 Amazon S3에 저장합니다. 사내 정책상 파일은 **4년 보관 후 삭제**해야 하며, 재생성이 어려운 중요 데이터라 **항상 즉시 액세스**할 수 있어야 합니다. 파일은 생성 후 30일 동안 자주 액세스되지만 그 뒤에는 거의 액세스되지 않습니다. 가장 비용 효율적인 스토리지 솔루션은 무엇입니까?
> a) 수명 주기 정책으로 30일 후 S3 Standard에서 S3 Standard-IA로 옮기고 4년 후 파일을 삭제한다
> b) 수명 주기 정책으로 30일 후 S3 Glacier로 옮기고 4년 후 삭제한다
> c) 수명 주기 정책으로 30일 후 S3 One Zone-IA로 옮기고 4년 후 삭제한다
> d) 수명 주기 정책으로 30일 후 Standard-IA로 옮기고 4년 후 S3 Glacier로 옮긴다
>> [!success]- Answer
>> a) 수명 주기 정책으로 30일 후 S3 Standard에서 S3 Standard-IA로 옮기고 4년 후 파일을 삭제한다
>> **왜 이 답인가** — `항상 즉시 액세스`가 Glacier 계열을 전부 지웁니다(조회에 시간이 걸립니다). 자주 안 보지만 즉시 꺼내야 하는 자리는 Standard-IA이고, 4년 뒤 삭제도 수명 주기가 처리합니다.
>> **나머지가 아닌 이유** — One Zone-IA는 AZ 하나에만 두므로 재생성이 어려운 중요 데이터에 위험합니다. 4년 뒤에 Glacier로 옮기는 보기는 삭제하라는 정책을 어깁니다.

> [!question] 한 기업이 매장 고객의 구매 이력을 바탕으로 마케팅 서비스를 제공합니다. 매장은 SFTP로 거래 데이터를 업로드하며 일부 파일은 200GB를 넘습니다. 최근 일부 매장이 포함하면 안 되는 **개인 식별 정보(PII)**가 든 파일을 올린 것이 발견되었습니다. PII가 다시 공유되면 관리자에게 알리고 후속 조치도 자동화하려고 합니다. 개발 노력이 가장 적은 방법은 무엇입니까?
> a) S3 버킷을 안전한 전송 지점으로 쓰고 Amazon Macie로 객체를 검사한 뒤, PII가 발견되면 Amazon SNS로 관리자에게 알린다
> b) S3 버킷을 전송 지점으로 쓰고 Amazon Inspector로 객체를 검사한 뒤, PII가 있으면 수명 주기 정책으로 객체를 제거한다
> c) Lambda 함수에 사용자 지정 검사 알고리즘을 구현해 객체 업로드 시 실행하고, PII가 있으면 SNS로 알린다
> d) Lambda 함수에 사용자 지정 검사 알고리즘을 구현하고 PII가 있으면 SES로 알린 뒤 수명 주기 정책으로 제거한다
>> [!success]- Answer
>> a) S3 버킷을 안전한 전송 지점으로 쓰고 Amazon Macie로 객체를 검사한 뒤, PII가 발견되면 Amazon SNS로 관리자에게 알린다
>> **왜 이 답인가** — Macie는 **S3의 민감 데이터를 자동으로 찾아내는** 서비스입니다. PII 탐지 로직을 직접 만들 필요가 없어 개발 노력이 가장 적습니다.
>> **나머지가 아닌 이유** — Inspector는 워크로드 취약점을 보는 서비스라 파일 내용을 검사하지 않습니다. 검사 알고리즘을 직접 짜는 두 보기는 요구와 정반대로 개발 노력이 가장 큽니다.

> [!question] 한 기업이 고객 정보를 Amazon DynamoDB에 저장하는 쇼핑 애플리케이션을 운영합니다. **데이터 손상에 대비**해 복구 지점 목표(RPO) 15분, 복구 시간 목표(RTO) 1시간을 만족하는 솔루션을 설계해야 합니다. 무엇을 권장해야 합니까?
> a) DynamoDB 지정 시간 복구(PITR)를 구성하고 필요 시 원하는 시점으로 복원한다
> b) DynamoDB 글로벌 테이블을 구성하고 복구 시 애플리케이션을 다른 리전으로 향하게 한다
> c) 매일 DynamoDB 데이터를 S3 Glacier로 내보내고 복구 시 다시 가져온다
> d) 15분마다 DynamoDB 테이블의 EBS 스냅샷을 예약해 복구 시 스냅샷으로 복원한다
>> [!success]- Answer
>> a) DynamoDB 지정 시간 복구(PITR)를 구성하고 필요 시 원하는 시점으로 복원한다
>> **왜 이 답인가** — PITR은 최근 35일 안의 **어느 시점으로든 되돌립니다.** 손상 직전으로 복원하면 되므로 RPO 15분을 여유 있게 만족합니다.
>> **나머지가 아닌 이유** — 글로벌 테이블은 손상된 데이터까지 그대로 복제하므로 데이터 손상 대비책이 아닙니다. 하루 한 번 내보내기는 RPO 15분을 못 지킵니다. DynamoDB에는 EBS 스냅샷이라는 개념이 없습니다.

> [!question] 한 기업의 애플리케이션이 여러 SaaS 소스와 통합해 데이터를 수집합니다. EC2 인스턴스가 데이터를 받아 S3 버킷에 업로드하고, 같은 인스턴스가 업로드 완료 시 사용자에게 알림도 보냅니다. 애플리케이션 성능이 느려 최대한 개선하려고 합니다. 운영 오버헤드가 가장 적은 솔루션은 무엇입니까?
> a) SaaS 소스마다 Amazon AppFlow 플로를 만들어 S3 버킷으로 데이터를 전송하고, 업로드가 끝나면 S3 이벤트 알림이 SNS 주제로 이벤트를 보내게 한다
> b) Auto Scaling 그룹을 만들어 EC2를 확장하고, 업로드 완료 시 S3 이벤트 알림이 SNS 주제로 이벤트를 보내게 한다
> c) SaaS 소스마다 EventBridge 규칙을 만들어 S3 버킷을 대상으로 지정하고, 업로드 완료용 두 번째 규칙의 대상으로 SNS 주제를 지정한다
> d) EC2 대신 Docker 컨테이너를 만들어 Amazon ECS에 올리고, CloudWatch Container Insights가 업로드 완료 시 SNS로 이벤트를 보내게 한다
>> [!success]- Answer
>> a) SaaS 소스마다 Amazon AppFlow 플로를 만들어 S3 버킷으로 데이터를 전송하고, 업로드가 끝나면 S3 이벤트 알림이 SNS 주제로 이벤트를 보내게 한다
>> **왜 이 답인가** — AppFlow는 **SaaS 애플리케이션과 AWS 사이의 데이터 전송을 위한 관리형 서비스**입니다. 데이터를 받아 옮기던 EC2가 통째로 사라지고, 알림은 S3 이벤트가 대신합니다.
>> **나머지가 아닌 이유** — EC2를 늘리거나 컨테이너로 바꾸는 보기는 관리할 인프라가 그대로 남습니다. EventBridge는 SaaS 소스에서 데이터를 끌어오는 커넥터가 아닙니다.

> [!question] 한 기업이 같은 AWS 리전의 S3 버킷에서 사진을 자주 업로드·다운로드하는 사진 처리 애플리케이션을 운영합니다. **데이터 전송 요금이 늘어난 것**을 확인하고 비용을 줄이려고 합니다. 무엇을 해야 합니까?
> a) VPC에 S3 게이트웨이 VPC 엔드포인트를 배포하고 해당 버킷 접근을 허용하는 엔드포인트 정책을 붙인다
> b) 퍼블릭 서브넷에 NAT 게이트웨이를 배포하고 버킷 접근을 허용하는 엔드포인트 정책을 붙인다
> c) 퍼블릭 서브넷에 API Gateway를 배포하고 라우팅 테이블에서 S3 호출을 그쪽으로 보낸다
> d) 애플리케이션을 퍼블릭 서브넷에 배포해 인터넷 게이트웨이를 통해 버킷에 접근하게 한다
>> [!success]- Answer
>> a) VPC에 S3 게이트웨이 VPC 엔드포인트를 배포하고 해당 버킷 접근을 허용하는 엔드포인트 정책을 붙인다
>> **왜 이 답인가** — 게이트웨이 엔드포인트는 **엔드포인트 요금도 데이터 처리 요금도 없습니다.** 같은 리전 S3 트래픽이 NAT를 거치지 않게 되므로 전송 요금이 사라집니다.
