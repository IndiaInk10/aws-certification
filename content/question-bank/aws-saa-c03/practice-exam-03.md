> [!question] 외부 업체가 자기 AWS 계정의 자동화 도구로 우리 계정에서 작업해야 합니다. 업체에는 우리 계정의 IAM 자격 증명이 없습니다. 어떻게 권한을 줍니까?
> a) 업체 계정을 신뢰하는 IAM 역할을 만들고 외부 ID 조건을 걸어 수임하게 한다
> b) 업체용 IAM 사용자를 만들어 액세스 키를 전달한다
> c) 우리 계정의 루트 자격 증명을 알려 준다
> d) 필요한 리소스를 퍼블릭으로 연다
>> [!success]- Answer
>> a) 업체 계정을 신뢰하는 IAM 역할을 만들고 외부 ID 조건을 걸어 수임하게 한다
>> **왜 이 답인가** — 교차 계정 접근의 표준 답입니다. 자격 증명이 오가지 않고, 필요 없어지면 신뢰 관계만 끊으면 됩니다. **외부 ID**는 제3자가 다른 고객의 역할을 대신 수임하는 사고를 막는 장치라 업체 시나리오에서 특히 요구됩니다.
>> **나머지가 아닌 이유** — 액세스 키 전달은 장기 자격 증명을 남의 손에 넘기는 것입니다. 루트 공유와 퍼블릭 공개는 어떤 상황에서도 정답이 아닙니다.

> [!question] 게임 시스템에서 하나의 이벤트를 리더보드·매치메이킹·인증 서비스에 **동시에** 보내되 **순서도 보장**되어야 합니다. 무엇을 써야 합니까?
> a) SNS FIFO 주제에 발행하고 각 서비스의 SQS FIFO 큐가 구독하게 한다
> b) SQS FIFO 큐 하나를 세 서비스가 함께 폴링한다
> c) SNS 표준 주제에 발행한다
> d) 서비스마다 직접 호출한다
>> [!success]- Answer
>> a) SNS FIFO 주제에 발행하고 각 서비스의 SQS FIFO 큐가 구독하게 한다
>> **왜 이 답인가** — 요구가 **동시 전달(팬아웃)과 순서** 둘입니다. 팬아웃은 SNS, 순서는 FIFO. 둘을 함께 갖춘 것이 SNS FIFO 주제입니다.
>> **나머지가 아닌 이유** — 큐 하나를 여러 서비스가 폴링하면 **한 메시지를 한 소비자만 가져가** 세 서비스가 모두 받지 못합니다. 여기가 큐와 주제를 가릅니다. 표준 주제는 순서를 보장하지 않고, 직접 호출은 서비스를 강하게 묶습니다.

> [!question] RDS for MySQL에 읽기 전용 복제본을 추가하려 합니다. 그 전에 무엇을 확인해야 합니까? (2개 선택)
> a) 원본 DB 인스턴스의 자동 백업이 켜져 있는지 확인한다
> b) 원본 DB 인스턴스의 백업 보존 기간이 0보다 큰지 확인한다
> c) 원본을 다중 AZ로 먼저 바꾼다
> d) 원본을 중지한다
>> [!success]- Answer
>> a) 원본 DB 인스턴스의 자동 백업이 켜져 있는지 확인한다
>> b) 원본 DB 인스턴스의 백업 보존 기간이 0보다 큰지 확인한다
>> **왜 이 답인가** — 읽기 전용 복제본은 원본의 백업을 기반으로 만들어집니다. **자동 백업이 꺼져 있으면(보존 0) 복제본을 만들 수 없습니다.** 두 보기는 같은 전제를 두 각도에서 말합니다.
>> **나머지가 아닌 이유** — 다중 AZ는 복제본 생성의 **전제 조건이 아닙니다.** 둘은 목적이 다른 별개 기능입니다. 원본을 중지하면 복제본을 만들 수 없습니다.

> [!question] 웨어러블 기기 데이터를 DynamoDB에 저장합니다. 워크로드가 **일정하고 예측 가능**하며 예산을 넘기지 않아야 합니다. 가장 비용 효율적인 방법은 무엇입니까?
> a) 프로비저닝 모드로 읽기·쓰기 용량 단위를 지정한다
> b) 온디맨드 모드를 쓴다
> c) 프로비저닝 모드에 Auto Scaling만 켠다
> d) 테이블을 여러 개로 나눈다
>> [!success]- Answer
>> a) 프로비저닝 모드로 읽기·쓰기 용량 단위를 지정한다
>> **왜 이 답인가** — 예측 가능한 워크로드에서는 프로비저닝 모드의 **단가가 온디맨드보다 낮습니다.** 용량을 고정하면 지출 상한도 예측됩니다.
>> **나머지가 아닌 이유** — 온디맨드는 요청 단가가 높아 일정한 워크로드에서 손해입니다. 이 `일정·예측 가능` 한 문장이 두 모드를 가릅니다. Auto Scaling은 변동이 있을 때 쓸모가 있고, 테이블 분할은 비용과 무관합니다.

> d) 노드에 퍼블릭 IP를 붙인다
>> [!success]- Answer
>> a) DynamoDB용 게이트웨이 VPC 엔드포인트를 만들고 프라이빗 서브넷 라우팅 테이블에 추가한다

> [!question] 관리자가 실수로 데이터를 고쳐 손실이 났습니다. 지난 30일 안의 **임의 시점(변경 5분 전)** 으로 RDS를 되돌릴 수 있어야 합니다. 무엇을 설계에 넣어야 합니까?
> a) 자동 백업을 켜고 보존 기간을 30일 이상으로 두어 지정 시간 복구를 쓴다
> b) 수동 스냅샷을 매일 뜬다
> c) 읽기 전용 복제본을 둔다
> d) 다중 AZ를 켠다
>> [!success]- Answer
>> a) 자동 백업을 켜고 보존 기간을 30일 이상으로 두어 지정 시간 복구를 쓴다
>> **왜 이 답인가** — 자동 백업은 트랜잭션 로그를 함께 보관해 **보존 기간 안의 임의 시점**으로 복구할 수 있게 합니다. `5분 전`처럼 정확한 시점을 요구하면 이것입니다.

> [!question] EC2에 직접 설치한 MySQL이 1TB io2 볼륨을 쓰고 있고, 피크에 읽기·쓰기 합쳐 약 1,000 IOPS가 필요합니다. 관리 부담을 줄이면서 가용성도 확보하려면 무엇을 씁니까?
> a) 범용 SSD(gp3) 볼륨을 쓰는 RDS for MySQL 다중 AZ 배포
> b) io2 Block Express를 쓰는 RDS for MySQL 다중 AZ 배포
> c) EC2에 그대로 두고 볼륨만 키운다
> d) DynamoDB로 옮긴다
>> [!success]- Answer
>> a) 범용 SSD(gp3) 볼륨을 쓰는 RDS for MySQL 다중 AZ 배포
>> **왜 이 답인가** — 필요한 것은 **1,000 IOPS뿐**이고 그 정도는 범용 SSD가 충분히 냅니다. 프로비저닝 IOPS는 수만 IOPS가 필요할 때 쓰는 것이라 여기서는 **돈만 더 드는 과한 선택**입니다. RDS 다중 AZ가 관리와 가용성을 함께 해결합니다.
>> **나머지가 아닌 이유** — io2는 요구를 넘어서는 비용입니다. EC2 유지는 관리 부담이 그대로이고, DynamoDB는 MySQL 애플리케이션을 다시 쓰는 일입니다.

> a) 흐름 로그와 CloudTrail을 근거로 EventBridge 규칙을 만들어 SNS로 보낸다

> c) 보안 그룹에서 22번과 3389번을 막는다

> [!question] Auto Scaling 그룹으로 뜨고 지는 인스턴스가 **시작·종료 직후에** 감사 시스템으로 보고서를 보내야 합니다. 가장 효율적인 방법은 무엇입니까?
> a) Auto Scaling 수명 주기 후크를 걸고 EventBridge로 받아 처리한다
> b) 인스턴스에서 5분마다 보고하는 크론을 돌린다
> c) 사용자 데이터 스크립트에서만 시작 시 보고한다
> d) 매일 인스턴스 목록을 조회해 비교한다
>> [!success]- Answer
>> a) Auto Scaling 수명 주기 후크를 걸고 EventBridge로 받아 처리한다

>> **나머지가 아닌 이유** — 주기적 크론은 즉시가 아니고 종료 시점을 놓칩니다. 사용자 데이터는 시작만 다뤄 종료 보고가 빠집니다. 매일 비교는 실시간이 아닙니다.

> a) 온프레미스 AD와 신뢰 관계를 맺은 AWS Managed Microsoft AD에 파일 시스템을 조인한다
> b) 파일 시스템을 AD에 조인하지 않고 IAM 정책으로 통제한다
> c) 접근 통제를 S3 버킷 정책으로 옮긴다
> d) 사용자마다 IAM 사용자를 만든다
>> [!success]- Answer
>> a) 온프레미스 AD와 신뢰 관계를 맺은 AWS Managed Microsoft AD에 파일 시스템을 조인한다

> [!question] 고객 관리형 KMS 키로 암호화된 Aurora 데이터베이스의 **백업을 인수한 회사의 다른 계정과** 같은 리전에서 공유해야 합니다. 무엇을 해야 합니까?
> a) 스냅샷을 만들고, 그 스냅샷과 암호화에 쓴 KMS 키를 모두 대상 계정과 공유한다
> b) 스냅샷만 공유한다
> c) 스냅샷을 기본 KMS 키로 다시 암호화해 공유한다
> d) 데이터베이스를 퍼블릭으로 연다
>> [!success]- Answer
>> a) 스냅샷을 만들고, 그 스냅샷과 암호화에 쓴 KMS 키를 모두 대상 계정과 공유한다
>> **왜 이 답인가** — 암호화된 스냅샷은 **키가 없으면 복원할 수 없습니다.** 스냅샷 공유와 키 권한 부여가 짝으로 필요합니다.
>> **나머지가 아닌 이유** — 스냅샷만 공유하면 상대는 아무것도 못 합니다. **AWS 관리형 기본 키로 암호화된 스냅샷은 애초에 공유할 수 없어서** 세 번째 보기는 불가능합니다. 데이터베이스 공개는 보안 요구를 정면으로 어깁니다.

> [!question] 병원이 환자 기록을 S3에 저장합니다. **전송 중과 저장 중 모두 암호화**되어야 하고, 저장 데이터의 **암호화 키는 규정 준수 팀이 직접 관리**해야 합니다. 어떤 조합입니까?
> a) 버킷 정책에 `aws:SecureTransport` 조건을 걸고, 기본 암호화를 고객 관리형 KMS 키(SSE-KMS)로 설정한다
> b) 버킷 정책에 `aws:SecureTransport` 조건을 걸고, 기본 암호화를 SSE-S3로 설정한다
> c) 기본 암호화를 SSE-KMS로만 설정한다
> d) 클라이언트에서만 암호화한다
>> [!success]- Answer
>> a) 버킷 정책에 `aws:SecureTransport` 조건을 걸고, 기본 암호화를 고객 관리형 KMS 키(SSE-KMS)로 설정한다
>> **왜 이 답인가** — `aws:SecureTransport`가 **HTTPS가 아닌 요청을 거부**해 전송 중 요구를 만족하고, 고객 관리형 KMS 키가 **키를 직접 관리한다**는 요구를 만족합니다.
>> **나머지가 아닌 이유** — SSE-S3는 AWS가 키를 관리해 `팀이 관리` 조건을 못 지킵니다. 세 번째 보기는 전송 중 요구가 빠졌습니다. **요구를 두 개로 쪼개 각각 확인하면** 갈립니다.
