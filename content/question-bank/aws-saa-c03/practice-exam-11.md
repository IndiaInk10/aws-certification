> [!question] 새 VPC의 **프라이빗 서브넷**에 있는 EC2 인스턴스에는 아웃바운드 인터넷 접근이 없지만, **외부 공급업체에서 매달 보안 업데이트를 내려받아야** 합니다. 무엇을 해야 합니까?
> a) NAT 게이트웨이를 만들어 **퍼블릭 서브넷에 두고** 프라이빗 서브넷 라우팅 테이블의 기본 경로로 지정한다
> b) 인터넷 게이트웨이를 만들어 VPC에 붙이고 프라이빗 서브넷 라우팅 테이블의 기본 경로로 지정한다
> c) NAT 인스턴스를 만들어 EC2와 **같은 프라이빗 서브넷**에 두고 기본 경로로 지정한다
> d) 인터넷 게이트웨이를 붙이고 NAT 인스턴스를 같은 프라이빗 서브넷에 둔 뒤 인터넷 게이트웨이를 기본 경로로 지정한다
>> [!success]- Answer
>> a) NAT 게이트웨이를 만들어 **퍼블릭 서브넷에 두고** 프라이빗 서브넷 라우팅 테이블의 기본 경로로 지정한다
>> **왜 이 답인가** — 프라이빗 서브넷이 **나가기만 하고 들어오지는 못하게** 하려면 NAT입니다. NAT는 반드시 **퍼블릭 서브넷**에 있어야 자기 트래픽을 인터넷 게이트웨이로 내보낼 수 있습니다.
>> **나머지가 아닌 이유** — 프라이빗 서브넷에 인터넷 게이트웨이 경로를 달면 그 순간 퍼블릭 서브넷이 되어 버립니다. NAT를 프라이빗 서브넷에 두면 NAT 자신이 밖으로 못 나갑니다.

> [!question] 한 기업이 EC2 인스턴스 다섯 대에 애플리케이션을 배포하고 ALB가 대상 그룹으로 트래픽을 분산합니다. 평소 CPU는 10% 미만이지만 **가끔 65%까지 치솟습니다.** 확장을 자동화하면서 **비용을 최적화하고 급증 시 충분한 CPU**를 보장하려면 어떤 솔루션이 적합합니까?
> a) EC2 Auto Scaling 그룹을 만들어 기존 ALB·대상 그룹을 연결하고, `ASGAverageCPUUtilization` 기반 **대상 추적 정책**을 목표 50%로 설정하며 최소 2·희망 3·최대 6으로 둔다
> b) Auto Scaling 그룹을 만들어 최소 2·희망 3·최대 6으로만 설정한다
> c) CPU가 20% 미만이면 Lambda가 인스턴스 하나를 종료하도록 CloudWatch 경보를 건다
> d) CPU 20% 미만과 50% 초과에 각각 경보를 걸어 SNS로 메일을 받고 사람이 인스턴스 수를 조절한다
>> [!success]- Answer
>> a) EC2 Auto Scaling 그룹을 만들어 기존 ALB·대상 그룹을 연결하고, `ASGAverageCPUUtilization` 기반 **대상 추적 정책**을 목표 50%로 설정하며 최소 2·희망 3·최대 6으로 둔다
>> **왜 이 답인가** — 대상 추적은 **평상시에는 인스턴스를 줄여 비용을 아끼고 급증하면 자동으로 늘립니다.** 조정 정책이 있어야 실제로 확장·축소가 일어납니다.
>> **나머지가 아닌 이유** — 조정 정책 없는 Auto Scaling 그룹은 개수만 유지합니다. 사람이 개입하거나 Lambda로 인스턴스를 종료하는 방식은 자동화가 아니며 위험합니다.

> [!question] 한 기업이 모바일 앱 사용자를 대상으로 하는 마케팅 커뮤니케이션 서비스를 개발합니다. 사용자에게 **SMS로 확인 메시지를 보내고 사용자가 답장**할 수 있어야 하며, 답장은 분석을 위해 **1년 동안 저장**해야 합니다. 무엇을 해야 합니까?
> a) Amazon Pinpoint 여정(journey)을 만들고, Pinpoint가 이벤트를 Kinesis 데이터 스트림으로 보내 분석·보관하도록 구성한다
> b) Amazon Connect 컨택 플로로 SMS를 보내고 Lambda로 응답을 처리한다
> c) Amazon SQS로 SMS를 배포하고 Lambda로 응답을 처리한다
> d) SNS FIFO 주제를 만들고 Kinesis 데이터 스트림을 구독시켜 분석·보관한다
>> [!success]- Answer
>> a) Amazon Pinpoint 여정(journey)을 만들고, Pinpoint가 이벤트를 Kinesis 데이터 스트림으로 보내 분석·보관하도록 구성한다
>> **왜 이 답인가** — **양방향 SMS(사용자가 답장할 수 있는)**를 지원하는 서비스가 Pinpoint입니다. 응답 이벤트를 Kinesis로 흘려 보관·분석하는 통합도 준비되어 있습니다.
>> **나머지가 아닌 이유** — SNS의 SMS는 **단방향 발송**이라 답장을 받지 못합니다. SQS는 메시지 큐이지 SMS 발송 채널이 아니고, Connect는 콜센터 서비스입니다.

> [!question] 한 기업이 AI/ML 연구용 대용량 데이터셋을 us-east-1의 S3 버킷에 두고 판매합니다. 고객은 구매 후 **S3 서명된 URL**로 파일을 받으며, 고객은 **북미와 유럽에 분산**되어 있습니다. **데이터 전송 비용을 줄이면서** 성능은 유지하거나 개선하려면 무엇을 해야 합니까?
> a) 기존 S3 버킷을 오리진으로 하는 **CloudFront 배포**를 만들고 고객 요청을 CloudFront URL로 보내며, 접근 제어는 **CloudFront 서명된 URL**로 바꾼다
> b) 기존 버킷에 S3 Transfer Acceleration을 켜고 고객을 그 엔드포인트로 보낸다
> c) eu-central-1에 두 번째 버킷을 만들어 교차 리전 복제하고 고객을 가까운 리전으로 보낸다
> d) 웹 애플리케이션이 데이터를 스트리밍하도록 고치고 접근 제어를 애플리케이션에 직접 구현한다
>> [!success]- Answer
>> a) 기존 S3 버킷을 오리진으로 하는 **CloudFront 배포**를 만들고 고객 요청을 CloudFront URL로 보내며, 접근 제어는 **CloudFront 서명된 URL**로 바꾼다
>> **왜 이 답인가** — CloudFront의 데이터 송신 단가가 S3 직접 전송보다 싸고, **오리진(S3)에서 CloudFront로 가는 전송은 무료**입니다. 캐시된 파일은 오리진 요청도 줄여 성능까지 좋아집니다. 접근 제어는 CloudFront 서명된 URL로 그대로 유지됩니다.
>> **나머지가 아닌 이유** — Transfer Acceleration은 업로드 가속이며 요금이 추가됩니다. 리전 복제는 저장·복제 비용이 늘고, 애플리케이션 스트리밍은 서버 부하와 비용을 키웁니다.

> [!question] 솔루션스 아키텍트가 IAM 그룹에 정책 두 개를 붙였습니다 — **Policy1은 EC2·Directory Service·CloudWatch Logs에 대한 모든 작업을 허용**하고, **Policy2는 `ds:Delete*`, `iam:Delete*`, `logs:Delete*`를 명시적으로 거부**합니다. 이 그룹에 추가된 클라우드 엔지니어는 어떤 작업을 할 수 있습니까?
> a) Amazon EC2 인스턴스 삭제
> b) IAM 사용자 삭제
> c) 디렉터리 삭제
> d) CloudWatch Logs의 로그 삭제
>> [!success]- Answer
>> a) Amazon EC2 인스턴스 삭제
>> **왜 이 답인가** — **명시적 거부는 항상 허용을 이깁니다.** 디렉터리·IAM·로그 삭제는 Policy2가 막았고, EC2 삭제(종료)만 거부 목록에 없어 남습니다.
>> **나머지가 아닌 이유** — 세 보기는 모두 Policy2의 거부에 걸립니다. IAM 사용자 삭제는 애초에 허용도 없고 거부까지 걸려 이중으로 막힙니다.

> a) **가용 영역마다 서브넷을 하나씩** 두고 Auto Scaling 그룹이 두 AZ에 인스턴스를 분산하게 하며, DB 인스턴스를 **다중 AZ 배포**로 구성한다
> b) 두 AZ에 걸치는 서브넷 두 개를 두고 인스턴스를 분산하며 DB가 각 네트워크에 연결되게 한다
> c) AZ마다 서브넷을 두고 인스턴스를 분산하며 DB가 각 네트워크에 연결되게 한다
> d) 두 AZ에 걸치는 서브넷 하나를 두고 인스턴스를 분산하며 DB를 다중 AZ로 구성한다
>> [!success]- Answer
>> a) **가용 영역마다 서브넷을 하나씩** 두고 Auto Scaling 그룹이 두 AZ에 인스턴스를 분산하게 하며, DB 인스턴스를 **다중 AZ 배포**로 구성한다
>> **왜 이 답인가** — **서브넷은 가용 영역 하나에만 존재합니다.** 그래서 AZ마다 서브넷을 따로 만들어야 하고, 데이터베이스는 다중 AZ 배포로 자동 장애 조치를 얻습니다.
>> **나머지가 아닌 이유** — "두 AZ에 걸친 서브넷"은 존재할 수 없는 구성입니다. DB를 여러 네트워크에 연결한다는 표현도 RDS의 고가용성 방식이 아닙니다.

> a) AWS Lake Formation으로 데이터 레이크를 만들고 RDS에 대한 Glue JDBC 연결을 만든 뒤 S3 버킷을 Lake Formation에 등록하고 **Lake Formation 액세스 제어**로 권한을 관리한다
> b) 구매 데이터를 RDS에 직접 쓰도록 바꾸고 RDS 액세스 제어로 제한한다

> d) Redshift 클러스터를 만들고 Lambda로 주기적으로 데이터를 옮긴 뒤 Redshift 액세스 제어로 제한한다
>> [!success]- Answer
>> a) AWS Lake Formation으로 데이터 레이크를 만들고 RDS에 대한 Glue JDBC 연결을 만든 뒤 S3 버킷을 Lake Formation에 등록하고 **Lake Formation 액세스 제어**로 권한을 관리한다

> [!question] 한 기업의 온프레미스 MySQL 데이터베이스를 글로벌 영업 팀이 **드문드문** 사용합니다. 다운타임은 최소여야 하며, 데이터베이스 관리자는 향후 사용자 증가를 대비해 **특정 인스턴스 유형을 고르지 않고** AWS로 옮기려고 합니다. 어떤 서비스를 권장해야 합니까?
> a) Amazon Aurora Serverless for MySQL
> b) Amazon Aurora MySQL
> c) Amazon RDS for MySQL
> d) Amazon Redshift Spectrum
>> [!success]- Answer
>> a) Amazon Aurora Serverless for MySQL
>> **왜 이 답인가** — `인스턴스 유형을 고르지 않는다` + `사용이 드문드문하다`가 Aurora Serverless를 정확히 가리킵니다. 용량이 자동으로 오르내리고 쓰지 않을 때 비용도 줄어듭니다.
>> **나머지가 아닌 이유** — Aurora와 RDS의 프로비저닝 방식은 인스턴스 클래스를 골라야 합니다. Redshift Spectrum은 분석 쿼리 기능이라 MySQL 대체가 아닙니다.

> [!question] 한 기업이 3계층 애플리케이션을 VPC로 옮긴 뒤 검토하다가, 보안 팀이 **계층 사이의 보안 그룹 규칙에 최소 권한 원칙이 적용되지 않은 것**을 발견했습니다. 이를 바로잡으려면 무엇을 해야 합니까?
> a) **보안 그룹 ID**를 소스나 대상으로 지정해 보안 그룹 규칙을 만든다
> b) 인스턴스 ID를 소스나 대상으로 지정해 규칙을 만든다
> c) VPC CIDR 블록을 소스나 대상으로 지정해 규칙을 만든다
> d) 서브넷 CIDR 블록을 소스나 대상으로 지정해 규칙을 만든다
>> [!success]- Answer
>> a) **보안 그룹 ID**를 소스나 대상으로 지정해 보안 그룹 규칙을 만든다
>> **왜 이 답인가** — 보안 그룹을 소스로 지정하면 **정확히 그 계층에 속한 인스턴스만** 허용됩니다. 인스턴스가 바뀌거나 IP가 바뀌어도 규칙을 고칠 일이 없습니다.

> [!question] 한 기업이 온프레미스에서 **사용자 지정 애플리케이션의 취약점**을 통한 침해를 겪었습니다. 이제 애플리케이션을 EC2로 옮기면서 **EC2 인스턴스의 취약점을 능동적으로 스캔하고 상세 보고서를 보내는** 솔루션을 구현하려고 합니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) Amazon Inspector를 켜고 에이전트를 EC2에 배포한 뒤, Lambda로 보고서 생성·배포를 자동화한다
> b) AWS Shield를 배포해 EC2를 스캔하고 Lambda로 결과를 CloudTrail에 기록한다
> c) Amazon Macie와 Lambda로 EC2 취약점을 스캔해 CloudTrail에 기록한다
> d) Amazon GuardDuty를 켜고 에이전트를 EC2에 배포해 Lambda로 보고서를 자동화한다
>> [!success]- Answer
>> a) Amazon Inspector를 켜고 에이전트를 EC2에 배포한 뒤, Lambda로 보고서 생성·배포를 자동화한다
>> **왜 이 답인가** — **EC2·컨테이너의 소프트웨어 취약점과 네트워크 노출을 스캔**하는 서비스가 Inspector입니다. `취약점 스캔`이라는 단어가 이 서비스를 가리킵니다.
>> **나머지가 아닌 이유** — Shield는 DDoS 완화, Macie는 S3의 민감 데이터 탐지, GuardDuty는 로그 기반 위협 탐지입니다. 셋 다 취약점 스캐너가 아닙니다.
