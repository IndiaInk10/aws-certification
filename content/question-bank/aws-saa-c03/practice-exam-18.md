> d) 파라미터 값을 팀별로 암호화해 저장한다
>> [!success]- Answer

> a) Step Functions에서 **작업 토큰 콜백(`waitForTaskToken`)** 패턴을 써서 외부 시스템이 토큰과 함께 성공·실패를 회신하게 한다
> b) Wait 상태를 두고 정해진 시간마다 상태를 다시 조회한다
> c) Lambda 함수의 제한 시간을 15분으로 늘려 회신을 기다린다
> d) EC2 인스턴스를 띄워 회신이 올 때까지 폴링한다
>> [!success]- Answer
>> a) Step Functions에서 **작업 토큰 콜백(`waitForTaskToken`)** 패턴을 써서 외부 시스템이 토큰과 함께 성공·실패를 회신하게 한다

> [!question] 한 기업이 EC2 Linux 인스턴스 두 대와 탄력적 IP로 **고가용성 SFTP 서비스**를 운영하며, 신뢰하는 IP만 접속을 허용하고 사용자 계정은 Linux 사용자로 관리합니다. 이제 **서버리스**이면서 높은 성능과 **세밀한 보안 구성**을 제공하고 사용자 권한도 계속 통제할 수 있는 방식을 원합니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) 기본 암호화를 켠 S3 버킷을 만들고, **신뢰 IP만 허용하는 퍼블릭 엔드포인트의 AWS Transfer Family SFTP 서비스**를 만들어 버킷을 연결하고 사용자에게 접근 권한을 부여한다
> b) 암호화된 EFS 볼륨을 만들고 탄력적 IP와 VPC 엔드포인트를 가진 Transfer Family SFTP를 만들어 EFS를 연결한다
> c) 암호화된 EBS 볼륨을 만들고 퍼블릭 엔드포인트의 Transfer Family SFTP에 EBS를 연결한다
> d) 기본 암호화를 켠 S3 버킷을 만들고 **프라이빗 서브넷 내부 접근만 되는** VPC 엔드포인트의 Transfer Family SFTP에 연결한다
>> [!success]- Answer
>> a) 기본 암호화를 켠 S3 버킷을 만들고, **신뢰 IP만 허용하는 퍼블릭 엔드포인트의 AWS Transfer Family SFTP 서비스**를 만들어 버킷을 연결하고 사용자에게 접근 권한을 부여한다
>> **왜 이 답인가** — Transfer Family는 **서버리스 SFTP**이고 저장소로 S3를 붙입니다. 인터넷의 신뢰 IP에서 접속해야 하므로 퍼블릭 엔드포인트를 쓰고, 사용자 권한은 IAM 역할·정책으로 계속 통제합니다.
>> **나머지가 아닌 이유** — Transfer Family에 **EBS를 붙일 수는 없습니다.** 프라이빗 전용 엔드포인트로 만들면 인터넷 사용자가 접속하지 못합니다.

> a) 역할 신뢰 정책에 **외부 ID(`sts:ExternalId`) 조건**을 넣어 우리에게만 발급된 값이 있을 때만 수임되게 한다
> b) 공급자에게 IAM 사용자와 액세스 키를 발급한다
> c) 신뢰 정책의 주체를 `*`로 두고 권한을 좁힌다
> d) 역할의 최대 세션 기간을 줄인다
>> [!success]- Answer
>> a) 역할 신뢰 정책에 **외부 ID(`sts:ExternalId`) 조건**을 넣어 우리에게만 발급된 값이 있을 때만 수임되게 한다

> a) **HTTP API**로 다시 만들어 Lambda 프록시 통합을 구성한다
> b) REST API에 캐싱을 켠다
> c) REST API를 엣지 최적화 엔드포인트로 바꾼다
> d) Lambda 함수 URL로 바꾸고 API Gateway를 없앤다

> a) gp3 볼륨
> b) gp2 볼륨
> c) io1 볼륨
> d) io2 볼륨
>> [!success]- Answer
>> a) gp3 볼륨
>> **왜 이 답인가** — gp3는 **용량과 별개로 IOPS·처리량을 지정**할 수 있고 최대 16,000 IOPS까지 지원합니다. 15,000이면 gp3로 충분하고 io 계열보다 훨씬 쌉니다.
>> **나머지가 아닌 이유** — gp2는 **용량에 비례해 IOPS가 정해져** 성능을 따로 프로비저닝할 수 없습니다. io1·io2는 더 높은 성능을 주지만 이 요구에는 과하고 비쌉니다.

> d) Lambda에 예약된 동시성을 설정한다
>> [!success]- Answer
>> a) API Gateway 메서드에 **요청 검증(request validation)**과 모델을 설정해 형식이 맞지 않으면 백엔드 호출 전에 거부하게 한다

> a) **Amazon Detective**로 결과와 연결된 활동 그래프를 따라 조사한다
> b) Athena로 CloudTrail 로그를 질의한다
> c) CloudWatch Logs Insights로 애플리케이션 로그를 본다
> d) Security Hub 대시보드를 확인한다
>> [!success]- Answer
>> a) **Amazon Detective**로 결과와 연결된 활동 그래프를 따라 조사한다
>> **왜 이 답인가** — Detective는 **CloudTrail·VPC 흐름 로그·GuardDuty 결과를 자동으로 연결한 그래프**를 만들어 조사 시간을 줄이는 서비스입니다.
>> **나머지가 아닌 이유** — Athena·Logs Insights는 **질의를 직접 짜야** 하는 지금의 문제 그대로입니다. Security Hub는 결과를 모아 보여 줄 뿐 원인 추적 도구가 아닙니다.

> [!question] Auto Scaling 그룹의 트래픽이 **매일 같은 모양으로 오르내리는 것이 몇 주째 반복**되고 있습니다. 지금은 지표 기반으로만 조정해 아침마다 잠시 느립니다. 사람이 시간을 지정하지 않고도 미리 확보하게 하려면 무엇을 해야 합니까?
> a) Auto Scaling 그룹에 **예측 조정(predictive scaling)**을 켜 과거 패턴으로 필요한 용량을 미리 띄우게 한다
> b) 예약 조정으로 매일 아침 시각과 용량을 직접 지정한다
> c) 대상 추적의 목표값을 낮춘다
> d) 인스턴스 예열 시간을 줄인다
>> [!success]- Answer
>> a) Auto Scaling 그룹에 **예측 조정(predictive scaling)**을 켜 과거 패턴으로 필요한 용량을 미리 띄우게 한다
>> **왜 이 답인가** — 예측 조정은 **과거 지표를 학습해 앞으로의 수요를 예측하고 미리 확장**합니다. `매일 같은 모양으로 반복`은 예측이 잘 맞는 조건이고, 시각을 사람이 지정하지 않아도 됩니다.
>> **나머지가 아닌 이유** — 예약 조정은 사람이 시각과 용량을 정해야 합니다. 목표값을 낮추면 하루 종일 인스턴스가 더 많아져 비용이 늘고, 예열 시간을 줄이면 준비 안 된 인스턴스로 트래픽이 갑니다.

> [!question] 감사에서 **운영자가 인스턴스에서 무슨 명령을 실행했는지 기록**을 요구합니다. 현재 Session Manager로 접속하지만 기록은 남기지 않습니다. 어떻게 해야 합니까?
> a) Session Manager **세션 기본 설정에서 로그 전송을 켜서** 세션 출력을 S3와 CloudWatch Logs로 남긴다
> b) 인스턴스에 접속할 때마다 화면을 캡처하게 한다
> c) CloudTrail을 켜서 명령을 기록한다
> d) VPC 흐름 로그를 켠다
>> [!success]- Answer
>> a) Session Manager **세션 기본 설정에서 로그 전송을 켜서** 세션 출력을 S3와 CloudWatch Logs로 남긴다
>> **왜 이 답인가** — Session Manager는 **세션 로깅 옵션**으로 입력·출력 전체를 저장할 수 있습니다. 설정만으로 감사 요건이 충족됩니다.
>> **나머지가 아닌 이유** — 화면 캡처는 절차적 통제로 신뢰할 수 없습니다. CloudTrail은 **세션 시작 API**는 남기지만 세션 안의 명령은 남기지 않고, 흐름 로그는 네트워크 메타데이터입니다.

> [!question] 수백 대의 EC2 인스턴스에 **정해진 승인 패치만, 정해진 시간대에** 적용해야 합니다. 어떤 솔루션이 요구 사항을 충족합니까?
> a) **Systems Manager Patch Manager**에 패치 기준선을 정의하고 **유지 관리 기간**에 적용하게 한다
> b) 인스턴스마다 자동 업데이트를 켠다
> c) 사용자 데이터 스크립트에 패치 명령을 넣는다
> d) 매번 새 AMI로 인스턴스를 교체한다
>> [!success]- Answer
>> a) **Systems Manager Patch Manager**에 패치 기준선을 정의하고 **유지 관리 기간**에 적용하게 한다
>> **왜 이 답인가** — 패치 기준선은 **어떤 패치를 승인할지**, 유지 관리 기간은 **언제 적용할지**를 정합니다. 두 요구가 정확히 대응됩니다.
>> **나머지가 아닌 이유** — 자동 업데이트는 승인·시간 통제가 없습니다. 사용자 데이터는 **최초 부팅 때만** 실행되고, AMI 교체는 이 요구에 비해 과한 변경입니다.
