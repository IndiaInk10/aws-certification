> [!question] 선택한 EC2 인스턴스 몇 대에 **지금 한 번** 진단 스크립트를 돌려 결과를 모아야 합니다. 정기 패치가 아니라 일회성 작업입니다. 무엇을 써야 합니까?
> a) Systems Manager Run Command 로 명령을 실행하고 결과를 받는다
> b) Systems Manager Patch Manager 로 실행한다
> c) 유지 관리 기간을 만들어 예약한다
> d) 인스턴스마다 SSH 로 접속해 실행한다
>> [!success]- Answer
>> a) Systems Manager Run Command 로 명령을 실행하고 결과를 받는다
>> **왜 이 답인가** — Run Command 는 **지금 한 번, 고른 대상에** 명령을 돌리고 출력까지 모아 옵니다. `일회성`과 `선택한 대상`이 이 도구를 지목합니다.
>> **나머지가 아닌 이유** — **Patch Manager 는 패치 전용**이라 임의 스크립트를 돌리는 도구가 아닙니다. 유지 관리 기간은 **정해진 시각에 반복**하려고 쓰는 것이라 일회성과 어긋납니다. SSH 직접 접속은 키와 접근 경로를 열어야 하고 결과 취합도 손으로 해야 합니다.

> [!question] Auto Scaling 그룹의 인스턴스에서 **애플리케이션 프로세스만 죽었는데** 인스턴스 자체는 살아 있어서, ASG 가 교체하지 않고 ELB 는 계속 그쪽으로 트래픽을 보냅니다. 무엇을 해야 합니까?
> a) Auto Scaling 그룹의 상태 확인 유형을 EC2 에서 **ELB** 로 바꾼다
> b) Auto Scaling 그룹의 최소 용량을 늘린다
> c) 인스턴스에 CloudWatch 경보를 걸어 CPU 를 감시한다
> d) ELB 의 유휴 제한 시간을 줄인다
>> [!success]- Answer
>> a) Auto Scaling 그룹의 상태 확인 유형을 EC2 에서 **ELB** 로 바꾼다
>> **왜 이 답인가** — 기본값인 EC2 상태 확인은 **하이퍼바이저가 보는 인스턴스 상태**만 봅니다. 인스턴스가 켜져 있으면 정상입니다. ELB 상태 확인으로 바꿔야 로드 밸런서가 애플리케이션을 비정상으로 판정했을 때 ASG 가 그 인스턴스를 교체합니다.
>> **나머지가 아닌 이유** — 대수를 늘려도 죽은 인스턴스는 그대로 남아 트래픽을 받습니다. CPU 경보는 프로세스가 죽으면 오히려 CPU 가 내려가 안 울립니다. 유휴 제한 시간은 연결 유지 시간이라 무관합니다.

> a) Amazon FSx for Lustre 파일 시스템
> b) Storage Gateway 파일 게이트웨이
> c) EFS 를 Lustre 지원으로 구성
> d) EC2 에 Windows 파일 공유 역할을 설치

> [!question] 프라이빗 서브넷의 인스턴스 몇 대가 **아주 가끔** 소프트웨어 업데이트를 받으러 나갑니다. 트래픽이 매우 적은데 NAT 게이트웨이 시간당 요금이 부담입니다. 비용만 놓고 보면 무엇을 검토해야 합니까?
> a) NAT 인스턴스로 바꾸되 패치·확장·장애 조치를 직접 떠안는다는 것을 감수한다
> b) NAT 게이트웨이를 AZ 마다 하나씩 더 만든다
> c) 인스턴스에 탄력적 IP 를 붙인다
> d) 인터넷 게이트웨이를 하나 더 만든다
>> [!success]- Answer
>> a) NAT 인스턴스로 바꾸되 패치·확장·장애 조치를 직접 떠안는다는 것을 감수한다
>> **왜 이 답인가** — 트래픽이 아주 적으면 작은 EC2 한 대가 NAT 게이트웨이보다 쌀 수 있습니다. 대신 **관리형이 아니어서** 패치·대역폭 확장·장애 대응이 전부 내 일이 됩니다. 문항이 `비용만 놓고 보면`이라고 범위를 좁혀 준 것이 단서입니다.
>> **나머지가 아닌 이유** — 게이트웨이를 더 만들면 비용이 늘어납니다. 탄력적 IP 부착은 인스턴스를 인터넷에 노출시켜 프라이빗에 둔 이유를 없앱니다. 인터넷 게이트웨이는 VPC 당 하나면 충분하고 개수와 비용이 무관합니다.
>> **실무 판단** — 대부분의 경우 정답은 여전히 NAT 게이트웨이입니다. 이 문항은 **트레이드오프를 아는지**를 묻는 것이지 NAT 인스턴스를 권하는 것이 아닙니다.

> [!question] 중요한 데이터가 든 S3 버킷을 **실수로 지우는 것**으로부터 보호해야 합니다. 어떤 조합입니까? (2개 선택)
> a) 버킷에 버전 관리를 켠다
> b) 버킷에 MFA 삭제를 켠다
> c) 버킷에 기본 암호화를 켠다
> d) 객체에 수명 주기 정책을 만든다
>> [!success]- Answer
>> a) 버킷에 버전 관리를 켠다
>> b) 버킷에 MFA 삭제를 켠다
>> **왜 이 답인가** — 버전 관리가 있으면 삭제해도 **이전 버전이 남아** 되돌릴 수 있고, MFA 삭제는 **버전을 영구 삭제하려 할 때 추가 인증을 요구**해 실수를 한 단계 더 막습니다. MFA 삭제는 버전 관리가 켜져 있어야 쓸 수 있어 둘이 짝입니다.
>> **나머지가 아닌 이유** — 암호화는 **훔쳐보는 것**을 막지 지우는 것을 막지 않습니다. 수명 주기 정책은 오히려 **정해진 때에 지우는** 기능이라 방향이 반대입니다.

> [!question] SQS 큐를 소비하는 애플리케이션이 **처리할 수 없는 메시지 하나 때문에** 계속 실패하고 재시도하면서 뒤의 메시지까지 밀리고 있습니다. 무엇을 해야 합니까?
> a) 큐에 데드 레터 큐를 붙이고 최대 수신 횟수를 정해 그 횟수를 넘긴 메시지가 옮겨지게 한다
> b) 가시성 제한 시간을 늘린다
> c) 큐를 FIFO 로 바꾼다
> d) 소비자 인스턴스를 늘린다
>> [!success]- Answer
>> a) 큐에 데드 레터 큐를 붙이고 최대 수신 횟수를 정해 그 횟수를 넘긴 메시지가 옮겨지게 한다
>> **왜 이 답인가** — 몇 번을 시도해도 안 되는 메시지는 **큐에서 빼내야** 뒤가 흐릅니다. 최대 수신 횟수가 그 판단 기준이고, 빼낸 것은 DLQ 에 남아 나중에 조사할 수 있습니다.
>> **나머지가 아닌 이유** — 가시성 제한 시간을 늘리면 **그 메시지가 큐를 더 오래 막습니다.** FIFO 전환은 순서 보장 기능이라 관계가 없고, 소비자를 늘리면 실패하는 소비자가 늘어날 뿐입니다.

> [!question] 청구서를 보니 쓰지 않는 **탄력적 IP 주소** 요금이 매달 붙고 있습니다. 원인은 무엇이고 어떻게 없앱니까?
> a) 실행 중인 인스턴스에 연결되지 않은 탄력적 IP 에 요금이 붙는다 — 쓰지 않는 것을 해제한다
> b) 탄력적 IP 는 개수와 무관하게 정액이라 줄일 수 없다
> c) 인스턴스를 중지하면 요금이 멈춘다
> d) 보안 그룹에서 인바운드를 막으면 요금이 멈춘다
>> [!success]- Answer
>> a) 실행 중인 인스턴스에 연결되지 않은 탄력적 IP 에 요금이 붙는다 — 쓰지 않는 것을 해제한다
>> **왜 이 답인가** — 탄력적 IP 는 **붙어서 쓰이고 있을 때는 대체로 무료**이고, **놀고 있을 때 요금이 붙습니다.** 주소가 희소 자원이라 붙잡아만 두는 것을 막는 구조입니다. 조용히 새는 비용의 전형입니다.
>> **나머지가 아닌 이유** — 정액이라 줄일 수 없다는 것은 사실이 아닙니다. **인스턴스를 중지하면 오히려 연결이 끊긴 상태가 되어 요금이 붙습니다** — 직관과 반대라 자주 틀립니다. 보안 그룹은 요금과 무관합니다.

> [!question] 공개 웹 앱을 ALB 뒤에 두는데, **외부 인증 기관이 발급한** TLS 인증서를 써야 하고 매년 갱신해야 합니다. 어떻게 해야 합니까?
> a) 외부 인증서를 ACM 으로 **가져오기(import)** 해 ALB 에 붙이고, 만료 전에 새 인증서를 다시 가져온다
> b) ACM 에서 인증서를 발급받아 ALB 에 붙이고 관리형 자동 갱신을 쓴다
> c) ACM 사설 인증 기관으로 인증서를 발급한다
> d) 인증서를 EC2 인스턴스에 직접 설치한다
>> [!success]- Answer
>> a) 외부 인증서를 ACM 으로 **가져오기(import)** 해 ALB 에 붙이고, 만료 전에 새 인증서를 다시 가져온다
>> **왜 이 답인가** — `외부 인증 기관이 발급한` 인증서라고 못 박았습니다. ACM 은 남이 발급한 인증서도 가져와 ELB·CloudFront 에 붙일 수 있게 해 줍니다. 다만 **가져온 인증서는 자동 갱신 대상이 아니라** 매년 다시 가져와야 합니다.

> [!question] 병원 API 가 PDF·JPEG 보고서를 받습니다. 그 안에서 **보호 대상 건강 정보(PHI)를 식별**해야 하고 개발 노력은 최소여야 합니다. 어떤 조합입니까?
> a) Amazon Textract 로 글자를 뽑고 Amazon Comprehend Medical 로 PHI 를 식별한다
> b) Amazon Textract 로 글자를 뽑고 SageMaker 로 모델을 만들어 식별한다
> c) Amazon Rekognition 으로 글자를 뽑고 Comprehend Medical 로 식별한다
> d) 파이썬 라이브러리로 직접 글자를 뽑고 직접 규칙을 만들어 식별한다
>> [!success]- Answer

>> **나머지가 아닌 이유** — 웹 서버를 0.0.0.0/0으로 열면 **ALB를 우회한 직접 접근이 가능**해져 최소 권한이 깨집니다. VPC CIDR 전체 허용은 그 VPC의 모든 자원을 들이는 것이고, DB를 인터넷에 여는 것은 최악입니다.

> [!question] EC2 에 직접 올린 MySQL 을 쓰는데 **복제와 확장을 사람이 손으로** 관리하고 있습니다. 수요에 따라 용량을 넣고 빼는 일을 단순화하려면 무엇으로 옮겨야 합니까?
> a) Aurora MySQL 호환 서버리스
> b) Aurora PostgreSQL 호환 서버리스
> c) 더 큰 EC2 인스턴스에 MySQL 을 다시 설치
> d) DynamoDB
>> [!success]- Answer
>> a) Aurora MySQL 호환 서버리스
>> **왜 이 답인가** — 복제와 용량 조절을 **서비스가 대신** 하고, 기존이 MySQL 이므로 **엔진 호환이 유지되어** 애플리케이션을 고치지 않아도 됩니다.
>> **나머지가 아닌 이유** — PostgreSQL 호환으로 가면 엔진이 바뀌어 쿼리와 드라이버를 손봐야 합니다. **여기서 갈립니다.** 더 큰 EC2 는 손으로 관리하는 상황이 그대로이고, DynamoDB 는 관계형이 아니라 재작성이 필요합니다.

> [!question] 새 배포 엔지니어가 CloudFormation 템플릿으로만 리소스를 만듭니다. **최소 권한**을 지키려면 어떤 조합입니까? (2개 선택)
> a) 엔지니어용 IAM 사용자를 만들고 CloudFormation 작업만 허용하는 정책이 붙은 그룹에 넣는다
> b) CloudFormation이 수임할 서비스 역할을 만들어 실제 리소스 생성 권한은 그 역할에 준다
> c) 엔지니어에게 AdministratorAccess를 준다
> d) 엔지니어가 루트 자격 증명을 쓰게 한다
>> [!success]- Answer
>> a) 엔지니어용 IAM 사용자를 만들고 CloudFormation 작업만 허용하는 정책이 붙은 그룹에 넣는다
>> b) CloudFormation이 수임할 서비스 역할을 만들어 실제 리소스 생성 권한은 그 역할에 준다
>> **왜 이 답인가** — 사람에게는 **스택을 다룰 권한만** 주고, 리소스를 만드는 권한은 **CloudFormation 서비스 역할**에 둡니다. 사람이 콘솔에서 직접 리소스를 만들 수는 없게 되어 최소 권한이 실제로 지켜집니다.
>> **나머지가 아닌 이유** — 관리자 권한과 루트 사용은 최소 권한의 정반대이고, 루트는 어떤 일상 작업에도 쓰면 안 됩니다.

> [!question] 퍼블릭 서브넷의 웹 계층 Auto Scaling 그룹이 프라이빗 서브넷의 RDS MySQL에 **연결되지 않는다**는 보고가 있습니다. 무엇을 확인해야 합니까?
> a) DB 보안 그룹이 웹 계층 보안 그룹에서 오는 3306을 허용하는지 확인한다
> b) DB에 퍼블릭 IP를 붙인다
> c) DB를 퍼블릭 서브넷으로 옮긴다
> d) 인터넷 게이트웨이를 하나 더 만든다
>> [!success]- Answer
>> a) DB 보안 그룹이 웹 계층 보안 그룹에서 오는 3306을 허용하는지 확인한다
>> **왜 이 답인가** — 같은 VPC 안이므로 **라우팅은 이미 됩니다.** 막히는 곳은 거의 항상 보안 그룹 인바운드 규칙입니다.
>> **나머지가 아닌 이유** — 퍼블릭 IP 부여와 서브넷 이동은 **DB를 인터넷에 노출**시키는 것이라 문제 해결이 아니라 보안 사고입니다. 인터넷 게이트웨이는 VPC 내부 통신과 무관합니다.
