> [!question] 모든 IAM 사용자 암호에 복잡성 요건과 교체 주기를 강제하려고 합니다. 무엇을 해야 합니까?
> a) 계정 전체에 적용되는 암호 정책을 설정한다
> b) IAM 사용자마다 암호 정책을 설정한다
> c) 사용자마다 인라인 정책으로 규칙을 적는다
> d) 그룹마다 암호 정책을 설정한다
>> [!success]- Answer
>> a) 계정 전체에 적용되는 암호 정책을 설정한다
>> **왜 이 답인가** — **IAM 암호 정책은 계정 수준에서 하나만 존재합니다.** 설정하면 그 계정의 모든 IAM 사용자에게 적용됩니다.
>> **나머지가 아닌 이유** — 사용자별·그룹별 암호 정책은 **존재하지 않는 기능**입니다. 나머지 세 보기는 전부 같은 이유로 탈락합니다. 이런 문항은 "그 설정이 어느 단위에 있는가"를 아는지 묻습니다.

> [!question] 여러 리전에 웹 계층을 따로 배포하되, 예약 데이터는 **전 세계가 하나의 기본 데이터베이스**를 보고 업데이트 지연은 1초 미만이어야 합니다. 무엇을 써야 합니까?
> a) Aurora 글로벌 데이터베이스 — 한 리전에 기본 클러스터, 나머지에 읽기 전용 보조 클러스터
> b) 리전마다 독립된 RDS를 두고 애플리케이션이 동기화한다
> c) DynamoDB 글로벌 테이블
> d) 리전마다 읽기 전용 복제본을 둔 단일 RDS
>> [!success]- Answer
>> a) Aurora 글로벌 데이터베이스 — 한 리전에 기본 클러스터, 나머지에 읽기 전용 보조 클러스터
>> **왜 이 답인가** — 요구가 **단일 기본 DB**와 **1초 미만 복제**입니다. Aurora 글로벌 데이터베이스가 정확히 그 구조이고 보통 1초 안쪽으로 복제됩니다.
>> **나머지가 아닌 이유** — DynamoDB 글로벌 테이블은 **여러 리전에서 쓰기가 가능한 다중 마스터**라 `단일 기본 데이터베이스` 요구와 다릅니다. 애플리케이션 동기화는 일관성을 직접 떠안는 일이고, 일반 RDS 교차 리전 복제본은 지연이 더 큽니다.

> [!question] 온프레미스 MySQL을 AWS로 옮깁니다. 접근이 드물고 불규칙하며, 앞으로 사용자가 늘 것 같은데 **인스턴스 유형을 고르고 싶지 않습니다.** 다운타임은 최소여야 합니다. 무엇을 권해야 합니까?
> a) Aurora Serverless for MySQL
> b) RDS for MySQL 단일 AZ
> c) EC2에 MySQL 직접 설치
> d) DynamoDB
>> [!success]- Answer
>> a) Aurora Serverless for MySQL
>> **왜 이 답인가** — `인스턴스 유형을 고르지 않는다`가 서버리스를 그대로 지목합니다. 접근이 드물고 불규칙한 워크로드에서 용량이 자동으로 오르내려 비용도 맞습니다.
>> **나머지가 아닌 이유** — RDS와 EC2 설치는 인스턴스 유형을 정해야 합니다. DynamoDB는 관계형이 아니라 MySQL 애플리케이션을 다시 써야 합니다.

> [!question] 개발자용 PostgreSQL 개발 환경이 여럿인데, 각 환경은 **하루 8시간 중 절반 정도만** 쓰입니다. 가장 비용 효율적인 방법은 무엇입니까?
> a) Aurora Serverless를 쓰거나, EventBridge 일정으로 인스턴스를 켜고 끈다
> b) 환경마다 RDS를 24시간 켜 둔다
> c) 개발용에도 다중 AZ를 켠다
> d) 예약 인스턴스를 산다
>> [!success]- Answer
>> a) Aurora Serverless를 쓰거나, EventBridge 일정으로 인스턴스를 켜고 끈다
>> **왜 이 답인가** — 쓰지 않는 시간이 절반이므로 **안 쓸 때 비용이 0에 가까워지는 쪽**이 답입니다. 서버리스는 자동으로, 일정 기반 시작·중지는 명시적으로 그렇게 만듭니다.
>> **나머지가 아닌 이유** — 24시간 유지와 예약 인스턴스는 노는 시간에도 돈을 냅니다. 개발 환경에 다중 AZ를 켜는 것은 비용을 두 배로 만드는 방향입니다.

> [!question] 프라이빗 서브넷의 EC2가 인터넷의 라이선스 서버와 통신해야 합니다. 운영 유지 보수를 최소화하는 **관리형** 해법은 무엇입니까?
> a) 퍼블릭 서브넷에 NAT 게이트웨이를 두고 프라이빗 라우팅 테이블이 그것을 가리키게 한다
> b) EC2로 NAT 인스턴스를 직접 세운다
> c) 인스턴스마다 탄력적 IP를 붙인다
> d) 인스턴스를 퍼블릭 서브넷으로 옮긴다
>> [!success]- Answer
>> a) 퍼블릭 서브넷에 NAT 게이트웨이를 두고 프라이빗 라우팅 테이블이 그것을 가리키게 한다
>> **왜 이 답인가** — NAT 게이트웨이는 **관리형**이라 패치·확장·가용성을 AWS가 맡습니다. `관리형`과 `유지 보수 최소`가 NAT 인스턴스가 아니라 게이트웨이를 지목합니다.
>> **나머지가 아닌 이유** — NAT 인스턴스는 내가 패치하고 확장해야 하는 EC2입니다. 탄력적 IP와 퍼블릭 서브넷 이전은 인스턴스를 인터넷에 노출시켜 프라이빗에 둔 이유를 없앱니다.

> [!question] 파트너가 하루 종일 **FTP로 작은 파일 수천 개**를 보냅니다. 파일마다 처리에 30초쯤 걸리고, 처리에 성공한 파일은 지워야 합니다. FTP 클라이언트 변경은 최소여야 합니다. 어떤 구성입니까?
> a) Transfer Family로 FTP 엔드포인트를 만들어 S3에 받고, S3 이벤트로 Lambda를 호출해 처리 후 원본을 삭제한다
> b) EC2에 FTP 서버를 세우고 야간 배치로 한꺼번에 처리한다
> c) 파일을 모아 두었다가 EMR로 밤에 처리한다
> d) 파트너에게 S3 API를 쓰도록 요청한다
>> [!success]- Answer
>> a) Transfer Family로 FTP 엔드포인트를 만들어 S3에 받고, S3 이벤트로 Lambda를 호출해 처리 후 원본을 삭제한다

> a) AWS Glue 작업으로 CSV를 Parquet 같은 지원 형식으로 변환한다
> b) 레거시 애플리케이션을 다시 작성한다
> c) EC2에 변환 스크립트를 상시 돌린다
> d) 분석 도구를 바꾼다

> a) Cost Explorer API를 호출해 비용과 예측을 가져온다
> b) 결제 콘솔에서 매달 CSV를 내려받아 넣는다
> c) 비용 및 사용 보고서를 S3에 받아 직접 집계·예측 로직을 만든다

> a) 고객 관리형 키로 EBS 암호화를 지정한 시작 템플릿을 만들어 노드 그룹이 쓰게 한다

> c) 애플리케이션에서 데이터를 암호화해 쓴다
> d) 기본 EBS 암호화만 켠다

> [!question] 단일 AZ RDS for PostgreSQL을 쓰는데, 데이터 과학자들에게 **운영에 영향 없는 거의 실시간 읽기**를 주면서 **고가용성**도 확보해야 합니다. 가장 비용 효율적인 방법은 무엇입니까?

> [!question] 사용자가 이미지를 올리면 **웹 서버가 그 자리에서 크기를 조정해** S3에 저장합니다. 업로드가 느리다는 불만이 많습니다. 어떤 조합으로 고쳐야 합니까? (2개 선택)
> a) 브라우저가 사전 서명된 URL로 S3에 원본을 직접 올리게 한다
> b) S3 이벤트 알림으로 Lambda를 불러 올라온 원본의 크기를 조정하게 한다
> c) 웹 서버 인스턴스를 더 큰 것으로 바꾼다
> d) 일정에 따라 Lambda를 돌려 그동안 쌓인 이미지를 처리한다
>> [!success]- Answer
>> a) 브라우저가 사전 서명된 URL로 S3에 원본을 직접 올리게 한다
>> b) S3 이벤트 알림으로 Lambda를 불러 올라온 원본의 크기를 조정하게 한다
>> **왜 이 답인가** — 느린 원인이 **업로드 경로에 서버와 이미지 처리가 함께 끼어 있는 것**입니다. 업로드는 서버를 아예 거치지 않게 하고, 크기 조정은 올라온 뒤에 비동기로 돌리면 사용자는 기다리지 않습니다.
>> **나머지가 아닌 이유** — 서버를 키워도 여전히 모든 바이트가 서버를 지나갑니다. 일정 기반 처리는 이미지가 한참 뒤에야 준비되어 사용자 경험이 오히려 나빠집니다.

> [!question] REST API로 프런트엔드를 제공하되, 백엔드는 **프라이빗 VPC 서브넷의 컨테이너**에 있습니다. 어떻게 잇습니까?
> a) API Gateway REST API를 만들고 VPC 링크로 프라이빗 서브넷의 ECS 서비스에 연결한다
> b) ECS 서비스에 퍼블릭 IP를 붙여 API Gateway가 직접 호출하게 한다
> c) 컨테이너를 퍼블릭 서브넷으로 옮긴다
> d) API Gateway 없이 ALB만 인터넷에 노출한다
>> [!success]- Answer
>> a) API Gateway REST API를 만들고 VPC 링크로 프라이빗 서브넷의 ECS 서비스에 연결한다
>> **왜 이 답인가** — VPC 링크는 API Gateway가 **VPC 안의 프라이빗 자원에 닿게** 해 주는 통로입니다. 백엔드를 프라이빗에 둔 채로 API만 공개할 수 있습니다.
>> **나머지가 아닌 이유** — 퍼블릭 IP를 붙이거나 서브넷을 옮기는 것은 **프라이빗에 둔 이유를 없앱니다.** ALB만 노출하면 API Gateway가 주는 인증·스로틀링·사용 계획이 사라집니다.

> [!question] 부서별로 IAM 그룹을 만들어 새 사용자를 넣었습니다. 권한을 주는 **가장 안전한** 추가 작업은 무엇입니까?
> a) 최소 권한 원칙에 맞는 IAM 정책을 만들어 그룹에 연결한다
> b) 사용자마다 관리자 정책을 붙인다
> c) 그룹에 AdministratorAccess를 붙인다
> d) 필요할 때마다 사용자에게 인라인 정책을 하나씩 붙인다
>> [!success]- Answer
>> a) 최소 권한 원칙에 맞는 IAM 정책을 만들어 그룹에 연결한다
>> **왜 이 답인가** — 그룹에 붙이면 **소속만 바꿔도 권한이 따라가** 사람이 늘어도 관리가 안 늘어납니다. 그리고 필요한 만큼만 주는 것이 안전의 기준입니다.
>> **나머지가 아닌 이유** — 관리자 권한 부여는 최소 권한의 정반대입니다. 사용자별 인라인 정책은 그룹을 만든 의미를 없애고 누가 무엇을 할 수 있는지 파악하기 어려워집니다.
